# ADR-0029: Per-viewer композиция в MCU — базовый композит + персональная дельта

- **Статус:** proposed
- **Дата:** 2026-10-23
- **Решение принято:** владелец проекта (S21 трекера)
- **Связанные ADR:** 0002 (прозрачность MCU/SFU), 0004 (композитор), 0012 (layout), 0026 (режим MCU/SFU), 0030 (контракт раскладки в сигналинге)
- **Связанные требования:** §2 «Video Layout Features» спецификации Codian MCU 4200 (8 пунктов); S21, S12, S20 трекера

## Контекст (Context)

`McuEngine` композитит **один** кадр 1920×1080 на комнату и отдаёт его всем
зрителям: `RoomState.composite` (`crates/vks-media-mcu/src/engine.rs`),
пересборка на каждом видео-тике, раздача клонами, egress тянет композит на
каждый терминал (`crates/vks-server/src/gateway_video.rs`) и ресемплит его под
профиль.

Из-за этого невыполнимы пункты §2 спецификации Codian 4200:

* **self-view** (окно собственного вида) — по определению персонально;
* **приоритет заполнения** + «self-view низшего приоритета» ⇒ состав общей
  сетки различается у разных зрителей (зритель не должен видеть себя в общей
  сетке — правило C6 в `docs/implementation/MASTER_PLAN_CLEANUP_LAYOUTS_2026-10-23.md`);
* **«Important»** и **voice activation** требуют, чтобы состав окон задавался
  движком, а не приходил готовым от админки.

Фактическая поддержка §2 сейчас ≈ 0 из 8: `assign_by_role`
(`crates/vks-layout/src/roles.rs`) не вызывается нигде; `is_speaking` не
покидает движок (сервер пишет `false`); порядка прихода нет
(`publisher_tracks: BTreeMap` — сортировка по UUID); персональных раскладок нет
(`LayoutDescriptor` — один на комнату).

Дополнительно: `destroy_room` не вызывается при завершении сессии ⇒ 2–3 МиБ
утечки на комнату; per-viewer буфера умножат её на число зрителей.

Измеренная база (release-soak, 4 участника, `crates/vks-media-mcu/tests/mcu_tick_soak.rs`):
compose mean 9.83 мс, p99 19.7 мс, `le_2ms_ratio = 0.0`, `le_33ms_ratio = 1.0`.

## Варианты (Options)

### Вариант A: «слой» — общий базовый композит + per-viewer оверлей self-view
- Описание: композитор один на комнату; зрителю дорисовывается маленькое окно
  с его камерой.
- Плюсы: минимальная дифф; базовый кадр шэрится по `Arc`; зрители без
  отклонений платят ноль.
- Минусы: не покрывает §2 полностью — правило C6 требует, чтобы зрителя **не
  было** в общей сетке, а значит нужна per-viewer замена окна; «Important» и
  персональные раскладки не выражаются.
- Риски: «заплатка», которую придётся переделывать.

### Вариант B: полностью per-viewer композиция
- Описание: у каждого зрителя своя раскладка, геометрия и композит; N композиций
  на тик.
- Плюсы: покрывает все 8 пунктов §2, включая персональные раскладки.
- Минусы: наивно не укладывается в бюджет кадра: масштабирование тиражируется
  по числу зрителей (~10 мс на композит ⇒ ~100 мс при 10 зрителях против
  бюджета 33 мс); N аллокаций холста по 3 МиБ на тик.
- Риски: без тайл-кейша — тупик по производительности.

### Вариант C: per-viewer выбор источников при общей геометрии
- Описание: окна (геометрия) общие и вычисляются один раз; персонально —
  **заселение** окон (кто в каком) и, опционально, персональная геометрия.
- Плюсы: попадание в семантику §2 (окна общие ⇒ «важно»/«голос» меняют
  заселение, а не набор окон); дешёвая сборка (memcpy из кэша); персональная
  геометрия добавляется без переделки конвейера.
- Минусы: требует явного pin-решения по §2 (вычитается ли окно self-view из
  общего набора).
- Риски: при неверной трактовке self-view как «ячейки, а не оверлея» общее
  окно надо пересчитывать.

## Решение (Decision)

Выбираем **Вариант C как семантическую модель + Вариант A как физическую
реализацию**, с обязательной инфраструктурой — **тайл-кейшем**, без которого
Вариант B нереализуем, а Вариант C дорог. Решающий вопрос — не «A/B/C», а
«строим ли тайл-кейш».

1. **План зрителя.** В `vks-layout` появляется модуль `viewer` с чистыми типами
   `ViewerPlan { version, cells: Vec<PlanCell>, self_view: Option<PlanCell>, viewer }`
   и **чистой** функцией `plan_viewer(&ViewerContext, viewer) -> ViewerPlan`
   (без состояния и без пикселей; сериализуема; сравнима ⇒ пригодна как ключ
   кэша). Планировщик владеет геометрией и ролями (`roles.rs`, `codian.rs`);
   движок владеет состоянием (`join_order`, `active_speaker`, `important`,
   `self_view_policy`).
2. **Заселение персонально, геометрия общая.** Зритель исключается из общей
   сетки (self-view — низший приоритет) и получает окно self-view. Семейство
   раскладки выбирается по числу **остальных** участников ⇒ у всех участников
   комнаты план совпадает; отдельный план — у наблюдателя/рекордера.
3. **Тайл-кейш.** Масштабирование выполняется один раз на ключ
   `(участник, ширина окна, высота окна, z)` за тик; сборка кадра — memcpy из
   готовых тайлов. Число вызовов масштабирования **не зависит** от числа
   зрителей (критерий проверяется тестом-счётчиком).
4. **Доставка до egress без копирования общего кадра.** Движок отдаёт
   `frame_for_viewer(room, viewer) -> Option<Arc<Frame>>`:
   * зритель без отклонений ⇒ **тот же** `Arc<Frame>`, что и базовый (0 копий);
   * зритель с отклонением ⇒ персональная сборка из тайлов (1 холст на зрителя,
     из них перерисовываются ≤ 2 прямоугольника дельты);
   * egress (`gateway_video.rs`) вызывает `frame_for_viewer(room, participant_id)`.
5. **Персональная геометрия — точка расширения, а не отдельный проект.**
   `PlanCell.rect` становится per-viewer; переход с общей геометрии на
   персональную — изменение данных плана, а не конвейера.
6. **Единственный путь геометрии сохраняется:** вся геометрия (в т.ч. окно
   self-view) считается через `vks_layout::preset::cell_rect` /
   `codian::geometry`; допуск — ±2 px, измерение — оракул теста.
7. **Совместимость:** `frame_for_viewer` без включённых флагов отдаёт побайтово
   тот же кадр, что и сегодняшний `composite_frame` ⇒ нулевой риск регрессии.

Затронутые крейты: `vks-layout` (новый модуль `viewer`), `vks-media-mcu`
(`compositor`: тайл-кейш; `engine`: планы, `frame_for_viewer`), `vks-core`
(новое `ViewerPreferences`, без поломки `LayoutDescriptor`), `vks-server`
(egress), `vks-client-sdk` — только в необязательной фазе 6.

## Последствия (Consequences)

### Положительные
- Открываются §2: self-view, приоритет заполнения, «Important», voice
  activation; персональные раскладки — точка расширения.
- Композиция перестаёт тиражироваться по числу зрителей: масштабирование
  O(участники × размеры), сборка O(зрители × memcpy).
- `is_speaking`/`active_speaker` выходят из движка ⇒ voice activation получает
  источник данных.
- Инфраструктура (тайл-кейш, `Arc`-кадры) прямо работает на S20 (≤2 мс).

### Отрицательные / компромиссы
- Один персональный кадр на зрителя с отклонением (3.0 МиБ при 1920×1080) —
  физический потолок контракта «один сжатый трек на зрителя»; снижается до
  1.32 МиБ, если композить сразу на размере egress (фаза 5).
- Код конвейера усложняется: план, кэш планов, тайл-кейш, дельта-сборка
  (оценка ≈ 1300–1400 LOC вместе с тестами).
- `LayoutDescriptor` не `#[non_exhaustive]` ⇒ поля персональных настроек
  выносятся в отдельную структуру, чтобы не ломать 23 литерала.
- Утечка комнат (2–3 МиБ) усиливается ⇒ teardown комнаты (`destroy_room`)
  обязателен в фазе 2.

### Что нужно сделать для реализации
- [ ] Фаза 0: ADR-0029 (этот документ) + `vks-layout/src/viewer.rs` +
      `McuEngine::frame_for_viewer` + egress на `Arc<Frame>`; критерий:
      побайтовое равенство с текущим композитом, `Arc::ptr_eq` для двух
      зрителей.
- [ ] Фаза 1: тайл-кейш; критерий: побайтовое равенство с эталонным
      `Compositor::compose`, число масштабирований == число `TileKey`,
      soak: V=10 ≤ 1.5 × V=1.
- [ ] Фаза 2: серверный self-view (план + дельта ≤ 2 прямоугольника);
      критерий: окно self-view = своя камера, в общей сетке зрителя нет,
      вне дельты кадр равен базе, геометрия ±2 px.
- [ ] Фаза 3: voice activation / «Important» / приоритет заполнения; критерий:
      крупное окно следует за активным спикером, план пересчитывается по
      событию, а не на тик.
- [ ] Фаза 4: персональные раскладки; критерий: разные планы ⇒ разные кадры,
      одинаковые ⇒ один `Arc`.
- [ ] Фаза 5 (опционально): композиция на размере egress, удаление
      `resize_i420`; критерий: ±2 px к текущей геометрии.
- [ ] Фаза 6 (опционально, дополнение): клиентский self-view для браузеров по
      capability; критерий: для такого клиента персональный кадр не собирается.
- [ ] Teardown: вызывать `destroy_room` при завершении сессии комнаты.
