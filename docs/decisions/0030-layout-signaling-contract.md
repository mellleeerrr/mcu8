# ADR-0030: Контракт раскладки в сигналинге (нормализованные rect, 0-based slot_id, снимок в JoinRoomResult)

- **Статус:** accepted
- **Дата:** 2026-10-23
- **Решение принято:** владелец проекта (S9/S10 трекера)
- **Связанные ADR:** 0012 (layout engine), 0026 (режим MCU/SFU)
- **Связанные требования:** S9, S10 трекера; `docs/architecture/LAYOUT_ENGINE.md`, `docs/architecture/SIGNALING_PROTOCOL.md` §9

## Контекст (Context)

Прототип `SignalingMessage.layout_changed` (поле 80) был объявлен, но **никогда
не отправлялся**: сервер применял раскладку в MCU, а клиент продолжал рисовать
собственную авто-сетку. Поле `Layout layout = 5` в `JoinRoomResult` (снимок для
позднего участника) было объявлено, но не заполнялось.

Три неопределённости делали любую реализацию расхождением с композитом:

1. **Единица координат.** `Rect` в протоколе — `float` (proto3 ⇒ f32). Пиксели
   холста MCU (1920×1080) или доли единицы?
2. **Нумерация слотов.** `LayoutDescriptor.assignments`/`geometry[].slot` —
   0-based, а `position` в админском API — 1-based (`calculate`/`attach_abonent`
   вендора). Какой индекс уедет по проводу?
3. **Кто присылает раскладку.** Сервер отправляет **дескриптор** (заявку) или
   **эффективную раскладку** (то, что реально рисует композитор)?

Третий вопрос оказался главным: в режиме `auto` дескриптор приходит **без
геометрии** (её строит движок по числу участников), а прямоугольники из
админки не клампятся в холст. Значит «провод» и «композит» разошлись бы:
клиент нарисовал бы пустой экран, а композит — другую картинку.

## Варианты (Options)

### Вариант A: сервер шлёт дескриптор
- Описание: `proto_layout(&LayoutDescriptor)` — геометрия из `descriptor.geometry`.
- Плюсы: минимум кода; сервер не знает про композит.
- Минусы: в режиме `auto` клиент получает **0 слотов** ⇒ пустой экран;
  прямоугольники не клампятся ⇒ «провод» ≠ «композит»; участники не
  разложены по слотам (нужен разбор `assignments` на сервере).
- Риски: расхождение с картинкой у клиента и в композите.

### Вариант B: клиент строит раскладку сам (как сейчас)
- Описание: сервер молчит, клиент рисует авто-сетку.
- Плюсы: ноль кода на сервере.
- Минусы: схемы Codian (`codian_01…codian_52`) невозможны — геометрия
  известна только серверу; это прямое расхождение со спецификацией 4200.
- Риски: несовместимость с вендором.

### Вариант C: сервер шлёт **эффективную** раскладку композитора
- Описание: `McuEngine::current_layout(room) -> Option<vks_layout::Layout>` —
  ровно то, что рисует композитор (авто-сетка, кламп, распределение
  участников); прото-конвертер переводит её в нормализованные координаты.
- Плюсы: один источник истины; клиент не знает, как строится сетка; вся
  геометрия Codian доезжает без специальных случаев.
- Минусы: сервер зависит от результата композитора (нужен публичный accessor
  в `vks-media-mcu`); для комнаты, которой ещё нет, раскладка лежит в
  `pending_layouts` ⇒ accessor должен это учитывать.
- Риски: при изменении правил композиции меняется и «провод» — но это и
  правильно: провод обязан отражать картинку.

## Решение (Decision)

Выбран **Вариант C**. Контракт зафиксирован так:

1. **Единица координат — доли холста `[0.0, 1.0]`.** `Rect` в протоколе
   нормализован относительно холста MCU; пересчёт пикселей в доли делает
   **сервер**, один раз, через `vks_layout::Layout::to_normalized` (тот же
   код, что и в композиторе). Клиент масштабирует под свой холст
   (`NormalizedLayout::scale_to_canvas`).
2. **Нумерация слотов — 0-based везде на проводу.** `Slot.id` = индекс слота в
   `vks_layout::Layout` (0-based) = `geometry[].slot` = `assignments[value]`.
   1-based `position` из админского API конвертируется в одном месте
   (`gateways.rs`, `position_base`).
3. **Снимок раскладки — в существующем поле `JoinRoomResult.layout` (5).**
   Отдельный push-кадр после ответа не используется: он создавал гонку
   (push мог прийти позже ответа) и лишние кадры в потоке клиента.
4. **Живая смена раскладки — `LayoutChanged` (поле 80)** после успешного
   `apply_layout`; источник — та же эффективная раскладка.
5. **Нормализация и разбор вида раскладки — в `vks-layout`**
   (`LayoutKind::as_str`/`LayoutKind::parse`), а не в сервере и клиенте
   отдельно: раньше в проекте было три копии маппинга, и одна теряла
   информацию (`focus`/`speaker` ⇒ `grid` по проводу ⇒ клиент рисовал не то,
   что композитор).
6. **Клиентский владелец состояния — `Conference`.** Push-хендлер транспорта
   складывает событие в очередь конференции; приложение забирает очередь
   (`Conference::drain_events`) и рисует через `Conference::media()`. Второй
   копии раскладки в SDK нет.

Затронутые крейты: `vks-layout` (единственный маппинг вида раскладки),
`vks-media-mcu` (`current_layout`), `vks-server` (`layout_signal`,
`gateways.rs`, `lib.rs`), `vks-client-sdk` (`layout.rs`, `conference.rs`,
`signaling_client.rs`).

## Последствия (Consequences)

### Положительные
- Клиент и композит рисуют одно и то же: раскладка на проводе = картинка.
- Режим `auto` больше не даёт пустого экрана (регрессия закрыта тестом
  `auto_layout_broadcast_contains_real_cells`).
- Снимок позднего участника приезжает в ответе на join ⇒ гонки нет; отдельный
  push-кадр и его чтение в интеграционном тесте убраны.
- Один маппинг вида раскладки вместо трёх.
- Схемы Codian доезжают до клиента без специальных случаев.

### Отрицательные / компромиссы
- `Rect` в протоколе теперь нормализованные: клиенты, читавшие `LayoutChanged`
  как пиксели, сломаются. В репозитории таких клиентов нет; протокол
  зафиксирован здесь и в `SIGNALING_PROTOCOL.md` §9.
- `vks-server` теперь зависит от результата композитора (`current_layout`):
  композит и протокол связаны сильнее — это плата за единый источник истины.
- `JoinRoomResult.layout` в SDK — `Option<Layout>` без `Eq` ⇒ `JoinRoomResult`
  больше не `Eq` (в репозитории это ни на что не влияет).

### Что нужно сделать для реализации
- [x] `McuEngine::current_layout` (включая pending-раскладку для ещё не
      созданной комнаты).
- [x] `layout_signal::proto_layout` по эффективной раскладке; `Pinned` для
      закреплённых слотов, `Fixed` — занятых, `Auto` — свободных.
- [x] Снимок в `JoinRoomResult.layout`; отдельный late-joiner push удалён.
- [x] Клиент: `Conference` — владелец раскладки; `drain_events`; `media()`.
- [x] Тесты: auto-режим, снимок позднего участника, round-trip uuid, живой
      push до отрисовки.
