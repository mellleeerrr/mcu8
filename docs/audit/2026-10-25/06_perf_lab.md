## 0. Позиция и уверенность

**Позиция (защищаю до консенсуса или до поражения по правилам §2 PLAN_ORCHESTRATION_v0):**

Без собственных генераторов нагрузки и без жёсткой привязки CPU любые цифры ёмкости MCU фиктивны.
Причины конкретные, не риторические:

1. **Ботов нет.** `sipp`, `callgen323`, `baresip`, `pjsua`, `sshpass` — отсутствуют (проверено `command -v`). Единственный существовавший генератор — `/tmp/h323_uas_parallel.py` из T07d, в репозитории его нет (`docs/progress/evidence/t07d-h323-inbound/SUMMARY.md:118`). Значит нагрузку нужно **написать**, и это первый артефакт, а не последний.
2. **`pidstat -p $MCU_PID` в одиночку даёт неверную цифру для видео.** Кодирование и декодирование видео у шлюза живёт в дочерних процессах FFmpeg — и это **два** процесса на каждую видеосессию, энкодер и декодер (`crates/vks-server/src/gateway_video.rs:480-500`: `spawn_codec(true)` + `spawn_codec(false)`), а не в потоке `vks-server`. При N=20 видео-сессий это ~40 процессов, которых `pidstat -p $MCU_PID` не видит. Замер «только по PID» систематически занижает стоимость видеосессии, т. е. **завышает ёмкость M3/M4 — в разы**. Правильная первичная метрика — `cpu.stat` cgroup-а MCU-контура (в него входят дети), а `pidstat` — вторичная атрибуция по потокам. Детали и точный путь cgroup — §3.2 (там же приняты 4 требования Lead'а и указано, где его формулировка расходится с фактами ВМ).
3. **Порт-пул шлюза — жёсткий потолок 100 пар.** `RtpPortPool::default() = new(41000, 41200)` (`crates/vks-gateway-sip/src/rtp_bridge.rs:20-22`) — чётные 41000…41198 = **100 пар RTP/RTCP (200 портов)**. Видеовызов берёт 2 пары (аудио+видео, `gateways.rs:1336/1350`) → **50 видео-** или **100 аудио-вызовов** на процесс; при исчерпании — отказ «No RTP/RTCP port pair is available» (`gateways.rs:1339`). Матрица «N=40 видео» физически невозможна без правки кода.
4. **Изоляция ядер в текущем состоянии НЕ включена и без root не включается.** `cpuset` не делегирован (см. §1.4), `mcu.slice`/`bots.slice` — пустые runtime-слайсы без unit-файлов и без `cpuset.cpus`. Пока это так, боты и MCU делят 36 ядер, и «ёмкость одного ядра» измеряет шум планировщика.
5. **ВМ сейчас шумит.** `mpstat 1 3`: среднее `%usr 47.28 / %sys 7.71 / %idle 44.23`, `load average 8.27` (17:05:25). Прогон в таком состоянии невалиден независимо от методики.

**Уверенность:**
- в фактах §1 (среда, код, лимиты) — **высокая** (проверено командами/чтением файлов);
- в архитектуре стенда §2 — **высокая** для no-root варианта, **средняя** для root-варианта (нужен пароль sudo, у меня его нет);
- в дизайне SIP-бота §6 — **средняя**: код-скелет не компилировался (правило раунда: без `cargo build`); API-поверхность, которую он использует, прочитана и стабильна;
- в H.323-боте §7 — **высокая** (путь уже проверен живым прогоном T07d на 20 вызовах, надо лишь переиспользовать);
- в априорных оценках ёмкости §9 — **низкая** (это гипотезы, которые и должен проверить harness).

## 2. Архитектура стенда

### 2.1. Два исполнения: `root` и `no-root`

Стенд обязан запускаться в обоих режимах, потому что в этой сессии root недоступен (§1.4), а «сначала harness» означает «harness должен работать сегодня».

| Возможность | `root` | `no-root` (сегодня) |
|---|---|---|
| Разделение ядер | `cgroup cpuset` через `AllowedCPUs=` на user-юнит (runtime, без рестарта) | `taskset -ac 0-15 $MCU_PID` + `taskset -c 16-35` для ботов |
| Вес CPU | `CPUWeight=1000` (mcu) / `100` (bots) | то же — cpu контроллер делегирован, `systemd-run --user --slice=bots.slice -p CPUWeight=100` |
| Память | `MemoryMax` | `systemd-run --user -p MemoryMax=` работает |
| Сеть | `veth` 10.200.0.1↔10.200.0.2 + `netns` для ботов | loopback: боты на `127.0.0.1:5080+N` (SIP) и `127.0.0.1:2720+N` (H.323) |
| `tc netem` | да, на veth bot-стороны | **нет** (нужен `CAP_NET_ADMIN`) |
| Проверка изоляции | `cpuset.cpus.effective` + `/proc/<pid>/status` | `taskset -p` / `Cpus_allowed_list` |

Ключевой момент: `taskset -ac 0-15` на живом процессе меняет affinity **всех потоков** (`-a` = all tasks) без рестарта и без root. Новые потоки наследуют affinity создателя, поэтому «утечки» на ботовые ядра не будет для тредов, созданных после. Треды, созданные до, нужно перечислить отдельно (`setup_isolation.sh` это делает и печатает diff до/после).

### 2.2. Разделение ядер

```
MCU  : 0-15   (16 ядер, 44 % машины)
боты : 16-35  (20 ядер, 56 % машины)
```
Пропорция 16/20 выбрана из PLAN §5.1 и оставлена: MCU — измеряемая сторона, ему нужно меньше ядер, чем генератору, потому что каждый бот тратит CPU на кодирование/таймеры, а MCU — на микс/композит.

Файл: `scripts/bench/setup_isolation.sh` (режимы `--root` / `--no-root`, идемпотентен, всё проверяет и печатает).

Проверка изоляции (обязательна, входит в каждый прогон, пишется в `meta.json`):

```bash
# 1. affinity живого MCU (все треды)
for t in /proc/$MCU_PID/task/*; do taskset -pc "$t" 2>/dev/null; done | sed 's/.*: //' | sort -u
# ожидаем: "0-15"
# 2. cgroup-принадлежность
cat /proc/$MCU_PID/cgroup                       # .../vks-mcu.service
cat /sys/fs/cgroup/<cg>/cgroup.procs            # pid сервера + pid h323_listener
# 3. фактическое ядро каждого треда в момент замера
ps -L -o pid,tid,psr,comm -p $MCU_PID | awk 'NR>1 && ($3<0 || $3>15)'
# ожидаем: пусто
# 4. боты не на ядрах MCU
ps -o pid,psr,comm -C vks-sipbot | awk '$2<=15'   # ожидаем: пусто
# 5. cpuset-файл (только root-режим)
cat /sys/fs/cgroup/mcu.slice/cpuset.cpus.effective    # 0-15
```

### 2.3. Почему cgroup, а не только `taskset`

`taskset` — это affinity, но не accounting. Мне нужны обе вещи:
- affinity, чтобы боты не отбирали кэш/ядра у MCU (измеряемая сторона);
- **учёт**, потому что `cpu.stat` cgroup-а MCU включает `vks-server` + python-сайдкар + **все** FFmpeg-дети. Именно это и есть «стоимость MCU».
`taskset`-режим учёт даёт только через `pidstat` по дереву (медленно, теряет короткоживущие процессы) — поэтому в no-root режиме `collect.sh` дополнительно суммирует `pidstat -C ffmpeg` и процесс-дерево, а в отчёт пишется флаг `accounting=cgroup|pidstat`.

### 2.4. Сеть

**root-режим (когда появится sudo):**
```
ip link add veth-mcu type veth peer name veth-bots
ip addr add 10.200.0.1/24 dev veth-mcu
ip link set veth-mcu up
ip netns add bots
ip link set veth-bots netns bots
ip -n bots addr add 10.200.0.2/24 dev veth-bots
ip -n bots link set veth-bots up
ip -n bots link set lo up
ip -n bots route add default via 10.200.0.1
```
SIP UAS слушает `0.0.0.0:5060`, allowlist у SIP UAS нет (только token bucket, `gateways.rs:2121-2123`) → боты из `10.200.0.2` принимаются.
**H.323 UAS имеет allowlist** `VKS_H323_UAS_ALLOW=127.0.0.1/32,192.168.1.0/24` и читает его при старте процесса (`h323_listener.py:724` `peer_allowed`; env фиксирован в `/proc/1177265/environ`). Бот из `10.200.0.2` будет **отвергнут**. Варианты: (а) добавить `10.200.0.0/24` в allowlist = правка юнита + рестарт (решает Lead); (б) оставить H.323-ботов на loopback — так и делаем, см. ниже.

**no-root режим (сегодня, без рестарта и без правок):**
- SIP-боты: bind `127.0.0.1:5080..5100`, target `127.0.0.1:5060`. Вся 127/8 — локальная, настраивать нечего.
- H.323-боты: bind `127.0.0.1:2720..2740`, target `127.0.0.1:1720`. Источник = `127.0.0.1` → попадает в `127.0.0.1/32` allowlist **без изменений в живом процессе**.
- Медиа: MCU в SDP-answer объявляет `c=IN IP4 <candidate_addr>` = `192.168.1.93` (`gateways.rs:2096` → `build_answer(local_ip=advertised_ip, ...)`, `uas.rs:240-248`). Бот обязан отправлять RTP на `192.168.1.93:<порт из answer>` (это локальный адрес → маршрут через `lo`). Источник пакетов будет `192.168.1.93`, поэтому `c=` в оффере бота можно ставить `192.168.1.93` (иначе `remote_ip` в UAS не совпадёт с реальным источником — латч есть, но он помечен как NAT-latch и лишний шум в метриках).
- `%soft`-стоимость: на loopback/veth RX обрабатывается в контексте отправителя (veth/lo отдают пакет в softirq отправителя), поэтому часть сетевого стека уедет в cgroup ботов. Это не ошибка методики, а её граница — учитывается мостом (см. §3.3).

**netem (только root):** `scripts/bench/netem.sh` ставит `tc qdisc replace dev veth-bots root netem loss X% delay Yms` внутри netns ботов. Без root скрипт падает с внятной ошибкой, а не молча ничего не делает.

## 3. Методика замера (ядро отчёта)

### 3.1. Что измеряем

Для каждого прогона (scenario × N × profile × duration) фиксируем:

**MCU-контур (первичное) — `P_mcu_contour`:**
- `Δusage_usec` cgroup-а живого юнита (`…/app.slice/vks-mcu.service`, путь берётся из `/proc/<pid>/cgroup`) за окно → `P_mcu_contour` в «% одного ядра» = `Δusage_usec / Δt_usec × 100`. Включает `vks-server` + python-сайдкар `h323_listener` + **все** FFmpeg-дети (энкодер и декодер на каждую видеосессию, `gateway_video.rs:480-500`).
- `user_usec` / `system_usec` раздельно → `%usr` / `%sys` без `top`.
- `cpu.pressure` (`some avg10`, `total`) — признак того, что планировщик уже не успевает (не путать с нехваткой CPU: pressure растёт раньше, чем `c_device`).
- `pidstat -u -t -p $MCU_PID 1 120` → атрибуция по потокам: кто именно жжёт (аудио-бридж, видео-бридж, композитор, tokio-роутер).
- Дети: `ffmpeg_count`, `ffmpeg_ticks` (utime+stime из `/proc/<pid>/stat`), `ffmpeg_share_of_contour` = Δtики(ffmpeg)/Δтики(дерево); `mcu_process_tree.tsv` — инвентарь на конец окна (pid/ppid/comm/Cpus_allowed).
- `mpstat -P 0-15 1 120` → `%soft`/`%irq` по ядрам MCU; `mpstat -P 16-35` → контроль, что боты не протекли.
- `perf stat -p $MCU_PID` (paranoid=1 разрешает) → IPC, `cache-misses`, `branch-misses` как объяснение формы кривой; для FFmpeg-детей — отдельный `perf stat -p <child>` при необходимости.

**Сторона ботов (для SLA, не для ёмкости):**
- RTP: `seq` gap/loss, RFC 3550 A.8 interarrival jitter, RTT из RTCP SR/RR (LSR/DLSR), one-way delay `[не проверено]` (нужна синхронизация часов — см. открытый вопрос №3).
- MOS-LQ по E-model (§5).
- Видео: принятый FPS, битрейт, число запрошенных IDR/PLI (у нас PLI в шлюзе не реализован — `grep` PLI в `crates/vks-gateway-sip/src/` пусто → в отчёт пишется `pli_supported=false`).

**Хост-сторона (замыкание баланса):**
- `Δusage_usec` всего root-cgroup минус MCU минус боты = «прочее» (`sshd`, DSH-агенты, шум). Если `прочее > 2 %`, прогон помечается `noisy=true` и в агрегат не идёт.

### 3.2. Замерять контур MCU, а не PID (поправка Lead'а от 17:1x, принята с уточнениями)

ТЗ требует «замер только по PID MCU». Цель верная (не мерить ботов), реализация `pidstat -p <pid>` — неполная. Поправка Lead'а: наш MCU на **каждую** SIP/H.323-видеосессию порождает **два** дочерних процесса FFmpeg — энкодер и декодер. Проверено по коду:

- `crates/vks-server/src/gateway_video.rs:480-500` — `spawn_video_media_bridge`: `let mut encoder = spawn_codec(true, ...)` и `let mut decoder = match spawn_codec(false, ...)`;
- `crates/vks-server/src/gateway_video.rs:304-360` — `Command::new("ffmpeg")`, `-threads 1 -filter_threads 1`, `-preset ultrafast -tune zerolatency`;
- `crates/vks-server/src/gateway_video.rs:545-548` — декодер читает кадр в свежий `vec![0; frame_bytes]`; для 1280×720 I420 `frame_bytes = 1280·720·3/2 = 1 382 400` B (`gateway_video.rs:139-141`, default-профиль 1280×720@30 — `gateway_video.rs:61-73`). Это **1.32 МиБ** (а не 1.38 МиБ; 1.3824 МБ — десятичные), 30 аллокаций такой величины в секунду на сессию, при 20 видеосессиях — ~830 МБ/с churn аллокатора.

Значит при N=20 видео-сессий в контуре MCU живёт **~40 ffmpeg-процессов**, и `pidstat -p $MCU_PID` их не видит. **Замер только по PID vks-server занижает стоимость видео-сессии, т. е. завышает ёмкость — на M3/M4 в разы.** Требования 1-4 Lead'а приняты, с одной фактической поправкой:

| # | Требование Lead'а | Факт на этой ВМ | Как реализовано |
|---|---|---|---|
| 1 | мерить `cat /sys/fs/cgroup/mcu.slice/cpu.stat` до/после + `cpu.pressure`, либо pidstat по дереву | `mcu.slice` как cgroup **не существует** (runtime-слайс без unit-файла, `cpuset.*` нет). Реальный cgroup MCU — `/sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/app.slice/vks-mcu.service` (`/proc/1177177/cgroup`); `cpu.stat` и `cpu.pressure` в нём **есть и доступны без root уже сейчас** | `collect.sh` берёт путь из `/proc/<pid>/cgroup` (а не хардкод `mcu.slice`), снимает `usage_usec/user_usec/system_usec`, `cpu.pressure{some,total}`, `pids.current`, `memory.current` каждую секунду; fallback — `pidtree` |
| 2 | число живых ffmpeg, их CPU, доля энкодеров/декодеров в контуре | реализовано: `ffmpeg_count` / `ffmpeg_encoder_count` / `ffmpeg_decoder_count` (max+mean), `ffmpeg_ticks` (utime+stime по `/proc/<pid>/stat`), `encoder_ticks`/`decoder_ticks` (роль по `cmdline`: `rawvideo` на входе = энкодер), доли `ffmpeg_share_of_contour`/`encoder_share_of_contour`/`decoder_share_of_contour` | `collect.sh` + `samples.json` + `mcu_process_tree.tsv` (pid/ppid/comm/Cpus_allowed/ticks на конец окна); `parse.py`/`formula.py` выводят `ffmpeg_share` отдельной колонкой |
| 3 | боты в `bots.slice`, MCU+дети в `mcu.slice`; `c_device=(P_active−P_idle)/N` по cgroup | `mcu.slice`/`bots.slice` без юнитов → в root-режиме создаются (§2.1), в no-root — `taskset` + user-slice `CPUWeight` | формула: `P` = сумма по контуру (cgroup или дерево PID), §4.1 |
| 4 | два режима: (a) до изоляции — дерево PID + `taskset` на будущих ядрах MCU; (b) после — cgroup v2; валидировать, что ffmpeg-дети унаследовали cpuset | ffmpeg спавнится из процесса MCU (`tokio::process::Command`) → наследует и cgroup, и `cpuset.cpus`/affinity **автоматически** | режимы `--mode auto\|cgroup\|pidtree`; валидация: `Cpus_allowed_list` для `pid` и для первого ffmpeg из `mcu_process_tree.tsv` (колонки `mcu_allowed` / `ffmpeg_allowed` в каждом сэмпле) |

Фактические дополнения к поправке:

1. **`pidstat -p` vs дерево.** `pidstat` нужен не как источник цифры, а как атрибуция по потокам (`-t`) — «кто именно жжёт: аудио-бридж, видео-бридж, композитор, tokio». Первичная цифра — монотонный счётчик (`usage_usec`/тики), потому что 120-секундное окно с 1-секундными сэмплами `pidstat` теряет короткоживущие ffmpeg.
2. **Дети FFmpeg определяются по cgroup, а не по имени** (как и просил Lead): в `pidtree`-режиме мы всё равно фильтруем по `comm == "ffmpeg"` — это допустимо только потому, что боты туда не попадают (они в другом cgroup/на других ядрах); в `cgroup`-режиме фильтра по имени нет вообще, весь контур = cgroup.
3. **H.323-сигналинг** — тоже ребёнок (`python3 h323_listener.py`, pid 1177265 в том же cgroup): cgroup-метрика его учитывает, `pidstat -p $MCU_PID` — нет.
4. **`cpu.pressure`** пишется как `avg10` + `total`: при `avg10 > 5 %` на MCU-ядре прогон помечается `contended=true` (планировщик уже не успевает), даже если `c_device` выглядит нормально.
5. **Энкодер и декодер разделяются по `cmdline`** (`/proc/<pid>/cmdline`): у энкодера на входе `-f rawvideo`, у декодера `-f h264/hevc`. Это эвристика, и она помечена как таковая: если FFmpeg поменяет порядок аргументов, роли перепутаются (доля суммарная `ffmpeg_share` останется верной, разделение — нет). В отчёт пишутся обе цифры: суммарная доля и раздельная; выводы по «что оптимизировать» делаются по суммарной.
6. **Функциональная проверка расчёта сделана на синтетике, не на MCU.** `formula.py`/`parse.py` прогнаны на искусственных `samples.json` (idle 10 % ядра, active 201 % ядра, N=20, 40 ffmpeg-детей): получено `c_device = 9.55 %`, `N_per_core @70/85/95 = 7/8/9`, `ffmpeg_share = 66.7 %`, `encoder_count_max = decoder_count_max = 20` — совпало с ручным расчётом. Это проверяет только арифметику и формат, но не методику; методика проверяется первым живым прогоном.

Итог по §3.2: **первичная метрика — `cpu.stat` контура MCU (`P_mcu_contour`)**, вторичные — `pidstat -t` по потокам, `pidstat`/`/proc/<pid>/stat` по детям, `mpstat` по ядрам. Формула §4 использует `P_mcu_contour`, а не один PID.


### 3.3. Атрибуция сетевого стека (граница методики, проговаривается в каждом отчёте)

На одной ВМ (и особенно на `lo`/`veth`) обработка RX идёт в контексте отправителя: softirq NET_RX заряжается на задачу, которая отправила пакет. Следствия:
- `P_mcu` **не включает** ту часть приёма, что случилась «в боте»;
- настоящий MCU с NIC имел бы IRQ/ksoftirqd на своих ядрах (это видно в `%soft` = 0.08 % сейчас, когда трафика нет).

Поэтому в отчёт всегда пишется **три числа**:
```
P_mcu_cg    — cgroup MCU (первичное, идёт в формулу)
P_bots_cg   — cgroup/набор PID ботов (контроль, не идёт в формулу)
P_host      — весь root cgroup; K_net = P_host − P_mcu_cg − P_bots_cg − P_idle_host
```
и `K_net` интерпретируется как «сетевой стек, который на реальной машине лёг бы на ядра MCU». Для класса A/B/C формула считается по `P_mcu_cg`, а `K_net` публикуется отдельной строкой как систематическая поправка (`capacity_correction`). Если `K_net / P_mcu_cg > 0.2`, цифра помечается `derated` и вывод о ёмкости делается по `P_mcu_cg + K_net` (консервативно).

### 3.4. Схема прогона (таймлайн)

```
t=0      старт сбора: cpu.stat baseline (idle), mpstat, pidstat
t=0..10  IDLE-окно (10 с)                     → P_idle (усреднение 10 с)
t=10     ramp: боты поднимаются по 2/с (или burst, флаг RAMP)
t=10..30  прогрев (исключается из расчёта)     → фиксируется T_ready (все connected)
t=30..150 ОКНО ИЗМЕРЕНИЯ (120 с)               → P_active, SLA-метрики
t=150..180 опционально: смена спикера/презентации (M5-сценарии)
t=180    teardown: BYE всем, ожидание 10 с, проверка cgroup.procs == пусто
```
Первые 20 с (ramp+прогрев) отбрасываются — как в ТЗ (`от_создания_ботов...txt:79`).
3 итерации на ячейку, в агрегат идёт median, в отчёт — `min/median/max` и `cv = stdev/mean` (если `cv > 0.05`, ячейка помечается нестабильной).

4. **`target-cpu=native` невоспроизводим.** Либо он зафиксирован как часть определения сборки серии (и записан в паспорт, и используется во **всех** прогонах серии), либо не используется вообще. Смешивать «native» и «не native» внутри одной серии запрещено: это разные бинари с разным кодом (AVX2 против baseline), и разница в `c_device` будет объясняться флагом, а не архитектурой.

Отдельно: требование `regress-hygiene` «`pidstat -p MCU` не видит видео» — независимое подтверждение §3.2 (мы пришли к этому из кода `gateway_video.rs:480-500`, они — из состава крейтов). Расхождений нет.

## 4. Формула ёмкости (исправленная, с разбором ошибки в `doc/`)

### 4.1. Две допустимые конвенции (и одна запрещённая)

**Конвенция A — по контуру MCU (cgroup / дерево PID; рекомендуемая, её и требует ТЗ в смысле «не мерить ботов»).**
`cpu.stat`/`pidtree` дают `P` в процентах **одного ядра** (100 % = 1 ядро, 400 % = 4 ядра) и включают **весь контур**: `vks-server` + python `h323_listener` + все FFmpeg-дети (в режиме `pidtree` — сумма `utime+stime` по дереву, §3.2). Тогда:

```
P_mcu_contour = Σ по контуру (cgroup usage_usec  |  дерево PID utime+stime)
c_device [% одного физ. ядра] = (P_mcu_contour_active − P_mcu_contour_idle) / N
N_per_core = floor(U_limit / c_device)
U_limit ∈ {70, 85, 95} % одного ядра
```
`C_total` в формуле **отсутствует**: единицы уже «проценты ядра». Дополнительно из того же окна выводится разложение:

```
c_device = c_server + c_python + Σ c_ffmpeg
c_ffmpeg / c_device = ffmpeg_share        (пишется в отчёт отдельной колонкой)
```
Если `ffmpeg_share` близок к 1 на видео-профилях — оптимизировать надо кодек-воркеры, а не композитор; если близок к 0 — наоборот. Это и есть «декомпозиция», которой требует §11.1.

**Конвенция B — по системе (если снимаем `mpstat`/`top` по всей машине).**
`U` — проценты **всей машины** (максимум 100 %, а не 36×100 %). Тогда занятых ядер `= (U_active − U_idle)/100 × C_total`, и

```
c_device [% одного ядра] = (U_active − U_idle) × C_total / N
N_per_core = floor(U_limit / c_device)      # тот же U_limit в % одного ядра
```

**Запрещённая конвенция C (та, что была в черновике):**
```
c_device = (U_active − U_idle) / (N × C_total)      ← НЕВЕРНО (C_total в знаменателе)
```
Разбор на числах (U_idle=2 %, U_active=40 %, C_total=8, N=20):
- реально занято ядер: `(40−2)/100 × 8 = 3.04`; на устройство: `3.04/20 = 0.152` ядра = **15.2 % одного ядра**;
- конвенция C даёт `38/(20×8) = 0.2375` — если трактовать это как «доли ядра», получается **0.2375 ядра** = 23.75 % вместо 15.2 %, т. е. стоимость завышена в 1.56 раза, а ёмкость **занижена** в 1.56 раза (не в `C_total²`).

**Точная формулировка ошибки:** в черновике перепутаны единицы измерения — делитель `C_total` превращает «проценты всей машины» в «проценты одной машины, поделённые на число ядер», что не является ни долей ядра, ни процентом. Множитель ошибки ровно `C_total` (деление вместо умножения), а не `C_total²`: заявление про квадрат (`от_создания_ботов...txt:2`, `ещё_раз_все_тесты...txt:3`) неверно, потому что в исходной записи `C_i = U_i·N_i/C_total` деление одно. Утверждение «ёмкость завышается в C_total² раз» было бы верно только если бы `C_total` попадал в знаменатель дважды (например, в цене устройства и в `N_per_core`). Наша формула избавлена от этого класса ошибок тем, что **все величины приведены к «процентам одного ядра» до деления на N** и `C_total` не участвует вообще.

Замечание к формулировке ТЗ «ошибка — `Ctotal` в знаменателе»: в актуальном тексте `от_создания_ботов...txt:87` формула уже исправлена на умножение (`(U_active−U_idle)·C_total/N`) — то есть ошибку исправили в тексте, но не в объяснении её величины. В отчёт это идёт как «исправлено, но объяснение ошибочно».

### 4.2. Нелинейность α

Стоимость устройства не константа: миксер O(N) на участника, композитор O(1) на комнату + O(N) на ресайз источников, энкодер — O(1) на получателя (сейчас per-call, `gateway_video.rs:305`).

```
α = c_device(N₂) / c_device(N₁)          # N₁=10, N₂=20 — как в ТЗ
γ = 1 + log₂(α)                          # показатель степенного закона
c_device(N) = c_device(N₀) · (N/N₀)^(γ−1)
```
- `α > 1` (γ>1) — «дорожает»: рост числа одновременных говорящих, per-viewer композиция (ADR-0029, статус `proposed`).
- `α < 1` (γ<1) — «дешевеет»: общий композит на комнату амортизируется на N зрителей — ровно текущая архитектура (`docs/decisions/0029-per-viewer-composition-mcu.md:11-14`: `RoomState.composite` — **один** кадр на комнату).
- `α ≈ 1` — линейный режим, `N_per_core` считается напрямую.

Практика: снимаем в 4 точках `N ∈ {5, 10, 20, 40}` (40 — только audio-only, из-за пула), фитим γ МНК в логарифмах, в отчёт даём и α(20/10), и γ, и доверительный интервал. Для видео 40 невозможно → фитим по {5,10,20}.

### 4.3. Контракт на «устройство» и топологию комнаты (без него цифра бессмысленна)

`N_per_core` без указания топологии — не число. Фиксируем два контракта, оба меряем:

| Контракт | Описание | Зачем |
|---|---|---|
| `T1` | N устройств в **одной** комнате, все send audio (+video), каждый получает 1 микс + 1 композит | Худший случай для композитора и «20 устройств» из ТЗ |
| `T2` | N устройств по **4 в комнате** (N/4 комнат) | Проверка амортизации композита и per-room-стоимости |

«Устройство» = 1 SIP- или H.323-вызов с 1 аудиопотоком (20 мс, G.711/G.722/Opus/G.726) и, в видео-профилях, 1 видеопотоком на вход и 1 композитом на выход.

### 4.4. Границы применимости формулы (пишутся в отчёт всегда)

1. `N_per_core` верен только для того профиля/топологии, на котором измерен; экстраполяция на другой микс — только через `γ` и с оговоркой.
2. Пул портов 100 пар ограничивает N сверху (§2.5): N≤50 для видео (2 пары/вызов) → для `N/ядро > 50` при видео нужна правка кода, иначе отказ (`gateways.rs:1339`).
3. `U_limit` — это потолок **одного ядра**, а `N_per_core × C_total` — потолок машины; последний дополнительно ограничен памятью (`MemoryMax`) и пулом портов, что проверяется как `min(...)`.
4. Один прогон даёт `c_device` с доверительным интервалом; в отчёт идёт медиана 3 итераций и худший класс SLA, а не лучший.
5. **Граница видео-профилей:** на каждую видеосессию приходится 2 процесса FFmpeg (`gateway_video.rs:480-500`), т.е. 40 процессов при N=20. `c_device` включает их (это и есть стоимость MCU), но `N_per_machine` дополнительно ограничен `pids.max` и памятью: 1.32 МиБ на кадр (`frame_bytes()`, `gateway_video.rs:139-141`) × 30 fps × 20 сессий ≈ **0.83 ГБ/с** только на вход декодера, плюс кадры композита и выхода энкодера — суммарно порядка 1.6 ГБ/с аллокаций (§3.2, §9 п.4), поэтому на высоких N возможен упор в аллокатор/GC, а не в CPU. Признак: `%sys` растёт быстрее `%usr`, `ffmpeg_share` падает, `cpu.pressure` растёт.

### 5.2. E-model (G.107) — явные уравнения

```
R = R₀ − I_s − I_d − I_e,eff + A
R₀ = 93.2                       (дефолт G.107 для узкополосного соединения, SLR=+8, RLR=+2 дБ)
I_s = 1.4                       (одновременные impairments; дефолт, если не измеряются отдельно)
I_d = 0.024·d + 0.11·(d − 177.3)·H(d − 177.3)
      где d = OWD_мс + jitter_buffer_мс + 2·(codec_delay_мс), H(x)=0 при x<0, иначе 1
I_e,eff = I_e + (95 − I_e)·(P_pl / (P_pl + B_pl))
      P_pl — процент потерь, B_pl — «burstiness» кодек-специфичный (G.113 App. I)
A = 0                           (advantage factor; для мобильных сетей 5-10, у нас 0)
MOS = 1 + 0.035·R + 7·10⁻⁶·R·(R−60)·(100−R),  R ∈ [0,100]; clamp [1.0, 4.5]
```
Опорные `I_e` (G.113 App. I, узкополосные): G.711 ≈ 0 (определяется через `I_e`=0 и `B_pl`=25.1 при loss), G.722 ≈ 0.6-1.0, G.726-32 ≈ 7, G.729A ≈ 11, Opus ≈ 0-2 (широкополосно; для сравнения с G.711 использовать `R` только как относительную метрику и помечать `mos_supported=false` для Opus — G.107 не калиброван для 48 кГц).
Джиттер в `d` входит через измеренную глубину jitter-буфера бота, а не через «jitter/2» — иначе методика неповторяема.

**Ограничение, которое надо произнести вслух:** MOS 4.3+ достижим только при `I_d` малом, т. е. OWD < 150 мс **и** jitter < 15 мс. На одной ВМ через loopback OWD ≈ 0.1-0.5 мс, поэтому класс A будет достигаться «даром», и SLA-матрица на этом стенде проверяет **только деградацию от нагрузки**, а не транспорт. Для честной проверки классов B/C нужен netem (root) — без него классы B/C недостижимы и в отчёт пишется `transport_impairment=none`.

### 6.3. Медиа: откуда звук и картинка

- **Аудио:** без ffmpeg. 20 мс кадр генерируется в самом боте: 1 кГц синус + амплитудная манипуляция (чтобы VAD/MOS не видели «тишину»), кодируется обёртками крейта (`rtp_bridge::encode_ulaw`, `g722::G722Codec::encode`, `g726`, `opus::OpusCodec::encode`). Битовая идентичность с реальным терминалом не нужна — нужен стабильный поток 50 пакетов/с.
- **Видео:** предкодированный Annex-B из `scripts/bench/prepare_media.sh` (`ffmpeg -f lavfi -i testsrc2 … -c:v libx264 -profile:v baseline -tune zerolatency -bsf:v h264_mp4toannexb -f h264`), один файл на профиль, генерируется один раз.
  Бот читает файл в память, режет на NAL (`rtp_bridge`/`h265.rs` дают `split_annexb`; для H.264 — свой сплиттер, ~20 строк), и **пакетизирует по RFC 6184**: `STAP-A` для мелких NAL, `FU-A` для NAL > MTU (порог 1200 байт полезной нагрузки), `marker=1` на последнем пакете кадра, `timestamp += 3000` на кадр (90 кГц / 30 fps), `seq` строго +1.
  H.265 по RFC 7798 (`h265.rs:76-130` уже содержит сплиттер и `packetize_h265` — переиспользовать).
- **Пейсинг:** один `tokio::time::interval(Duration::from_millis(20))` на вызов; видео-кадры выдаются по 30/с из того же тика (каждый 2-й тик — кадр + возможные FU-A). Джиттер отправки пишется в статистику (`send_lag_us` p50/p99) — если бот сам не укладывается в 20 мс, замер невалиден.

### 6.4. Что бот считает

- `rx_packets`, `rx_bytes`, `expected` (по max seq и по времени), `lost = expected − rx`, `loss_pct`, `dup`, `out_of_order`, `reordered_pct`;
- RFC 3550 A.8 jitter (`J += (|D| − J)/16`, D в RTP-единицах с поправкой на clock rate);
- RTT по RTCP: бот шлёт RR c `LSR`/`DLSR` (RFC 3550 §6.4.1), MCU отвечает SR — из `LSR`/`DLSR` получаем RTT. Если MCU не шлёт SR — RTT = `None`, и в отчёте честно `rtt_source=none` (**не проверено**: шлёт ли наш `rtcp_socket` SR — см. открытый вопрос №2);
- видео: `frames_rx` (marker-биты), фактический `fps`, `bitrate`, `idr_seen`, `loss_pct` по NAL;
- MOS по §5.2;
- `sdp_answer` (полный текст) и `disposition` (connected / 488 / 404 / 503 / timeout) — чтобы отрицательные результаты были данными, а не «не получилось».

## 11. Контраргументы (спор с `media-core` и `proto-chain`)

### 11.1. Против `media-core`: «главный блокер — compositor/mixer, дайте shared composite canvas + SIMD + zero-copy, и ёмкость вырастет на ≥30 %»

**Ответ 1 (согласие по существу, но цифра «30 %» уже устарела).** Композитор был горячим путём: `resize_i420` 1920×1080→720p = 8.0–8.6 мс/кадр на **каждую** egress-сессию (`03_media_engine.md` §4.2; вызывается из `gateway_video.rs:645`). После O3 в итерации 2 вся не-FFmpeg часть (resize+композит+копии) — **18.8 % ядра/устройство**, а главная статья сместилась в FFmpeg-детей: **43.6 % → 76.8 % контура** (N=1→20). «≥30 %» — правда для resize-статьи, которой после O3 уже нет; выиграть следующие 30 % можно только на enc/dec.

**Ответ 2 (самокоррекция: не ×20 и не ×1.3–1.45, а ×1.16 — см. §9.2).** Per-viewer композиция (ADR-0029) уронит ёмкость не в N раз: композит после S20-2 — 15.4 % ядра на комнату, переход на per-viewer добавит 0.154 ядра/зритель к измеренным 0.954 ядра/устройство (рост в **1.16** раза). Приоритет уточняется: **сначала per-call enc/dec (45–77 % контура), потом раскладка** — resize уже не доминирует.

**Ответ 3 (что даёт быстрый выигрыш).** Не SIMD и не клоны, а: (а) O3-строчные срезы — уже сделано, замерено 3.9× на не-FFmpeg части; (б) главный остаток — enc/dec в детях: `-threads 1` × 20 = 20 однопоточных x264; ферма энкодеров O7 (пул `/metrics vks_codec_worker_pool_size 8`) — туда же, это следующий по величине выигрыш; (в) `alloc` в `resize_i420` (`gateway_video.rs:738`: `vec![...]` на каждый кадр каждой сессии ≈ 1.7 ГБ/с при N=20) — arena/O5, снимает `%sys`. Что из этого больше — покажет декомпозиция `c_device` из harness.

### 11.2. Против `proto-chain`: «главный блокер — неполная протокольная цепочка (SRTP/TLS, H.245, H.239, BFCP, ASN.1 PER), а не скорость медиа»

**Ответ 1 (согласие по факту, несогласие по приоритету).** Да, цепочка неполная — я это подтверждаю своими замерами кода: SRTP → 488 (`uas.rs:7,992-994`), H.239 — нет, BFCP — только JSON-заглушка (`settings_admin.rs:40,43`), FastStart/Tunneling — нет (`t07d SUMMARY:112-115`). Но из этого не следует, что первым делом надо доделывать цепочку: **пока нет ботов, любая доделанная цепочка не проверяется ни одним живым тестом**, кроме 1-2 ручных сценариев из T07c/T07d. Каждый следующий протокольный узел будет проверяться вручную и «на глаз».

**Ответ 2 (что даёт harness цепочке).** Написав бота один раз, `proto-chain` получает измеримый вход для каждого узла: SRTP-бот (когда SRTP появится) сразу даёт loss/jitter/MOS; H.239-бот — время установления второго канала и FPS контента. Без бота каждый новый протокол тестируется `tcpdump`'ом и надеждой. **Harness — ускоритель для proto-chain, а не конкурент.**

**Ответ 3 (прямой контрпример к «медиа не блокер»).** Даже если закрыть всю цепочку, 20 SIP-вызовов с видео упрутся в 50-парный пул портов (`rtp_bridge.rs:20-22`) и в per-call ffmpeg — это не протокольные, а медийно-ресурсные ограничения, и они сработают раньше, чем H.239.

### 11.3. Самокритика (что скажут против меня)

- «3-6 часов на harness, а на выходе только цифры»: harness — код, переиспользован `net-resilience` (netem), `media-core` (A/B), `proto-chain` (SRTP/H.239), Lead'ом — инфраструктурный вклад.
- «Априорные оценки t14b — soak без RTP»: согласен, помечены §9 как гипотезы; их роль — порядок величины (18.4 нс/пиксель = 16.95 мс / 921600).
- «no-root — не изоляция»: `taskset -ac` = affinity без accounting; поэтому в no-root отчёте `isolation=affinity-only`, `accounting=pidstat`, видео `±`.
