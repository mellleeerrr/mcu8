## 0. Позиция и уверенность

**Позиция (защищаю):**

1. **Главный блокер ёмкости — медиаядро, а не протоколы и не сеть.** Узкое место —
   egress видео. [ИЗМЕРЕНО] на этом CPU (микробенч, §4.2, Appendix C): `resize_i420`
   1920×1080→1280×720 = **8.0–8.6 мс/кадр на каждую сессию**, identity-1080p =
   18.8–20.9 мс. Плюс композит 1920×1080 с аллокацией 3.11 МиБ на тик, **один
   FFmpeg-энкодер на каждую шлюзовую сессию** и **глобальный `rooms`-мьютекс,
   удерживаемый на всё время композита**. Итого **0.34–0.51 физ. ядра на
   720p30-устройство**, **0.77–0.99 на 1080p30** — против требования «20 устройств
   на ядро» разрыв 7–17× (§4.4).
   Механизм дороговизны `resize` — **не деление** (≤8 %, в пределах шума), а
   bounds-checked `get().unwrap_or(16)` на каждый пиксель и скалярная адресация:
   строчные срезы дают 3–4× (2.0–2.8 мс). Это уточнение раунда 1, §4.2.
2. **Целевая архитектура:** shared composite canvas **на выходной профиль**
   (а не 1920×1080 всегда) + один encode на группу зрителей с одинаковым профилем
   и планом + RTP-заголовки на зрителя; tile cache + dirty-rect; SIMD-микшер и
   top-K VAD; пул кадров и zero-copy; per-room actor вместо глобального мьютекса;
   worker-per-core.
3. **Монолитный `engine.rs` (120 785 B, 2540 строк) — структурная причина:**
   одна `Mutex<BTreeMap<RoomId, RoomState>>` на весь сервер, тик приходит из чужого
   egress-цикла, своего медиа-планировщика нет. Без per-room actor любая оптимизация
   остаётся однопоточной.

**Уверенность:** 0.85 — что видео-egress доминирует по CPU и что O1/O3/O7 дают
≥30 % CPU/сессию (resize уже измерен: 8.0–8.6 → 2.0–2.8 мс); 0.75 — в оценке
текущей ёмкости (±40 %, decode/encode не измерены); 0.8 — что «20 устройств/ядро»
достижимо при **выключенном** self-view и только вместе с O8 (decode-gating);
0.9 — что при **включённом** self-view оно НЕ достижимо (потолок 3–5, §4.6, это
структурный предел энкодера, а не дефект нашего кода).

**Где я уточняю исходную формулировку (честно):**

* «per-viewer encode» сегодня относится **только к шлюзовым** SIP/H.323-сессиям;
  браузерные зрители идут через str0m-fanout **без транскода**
  (`crates/vks-media-sfu/src/webrtc_room.rs:416-446`).
* аудиомикшер — **не** главный блокер по CPU: [ЗАМЕР] 0.162 мс на 20 мс тик при
  4 участниках (≈0.8 % ядра) и это **худший случай** — soak гонял звук «около полной
  шкалы», т.е. ветку `tanh` почти на каждом сэмпле
  (`docs/progress/evidence/t14b-mcu-tick-soak/SUMMARY.md:26-28`,
  `docs/progress/evidence/t14b-mcu-tick-soak/soak-60s-4p.json` → `audio.mean_seconds=0.000162`). Аудио надо чинить из-за
  аллокаций и локов, но 10× на нём не получить.
**Что изменил раунд 1 (трассируемость):**
* `resize_i420` — **измерен**: 8.0–8.6 мс (720p), не оценка; но механизм другой:
  деление ≤8 %, главное — bounds-check/адресация (§4.2);
* ёмкость **сейчас** пересчитана: A 1.4–2.1 (было «2–3»), B 1.7–2.5, C 1.9–2.8;
* «после плана» — с учётом **декода**, который я сначала потерял: без decode-gating
  A≈6–16, а не 20+; цель 20/ядро достигается только с новой **O8** (§4.4);
* self-view ON: потолок **3–5** устройств/ядро (было 8–9) — encode на каждого
  зрителя + декод; плюс найден H13 (клон 3.11 МиБ на каждый проигравший guard);
* аудио: O(N²) **микширования нет** (guard идемпотентен, `engine.rs:264-268`), но
  есть O(N²) **копий до guard** (~150 МиБ/с, 40 тыс. аллокаций/с) — §5.4(4).

**Где я уточняю исходную формулировку (честно):**
  UDP-цикле и двух глобальных мьютексах (`crates/vks-media-sfu/src/udp_loop.rs:143-230`,
  `crates/vks-media-sfu/src/engine.rs:79-84`).

## 1. Карта пайплайна кадр → кадр

### 1.0 Два разных пайплайна (не путать)

| Путь | Кто | Композит | Транскод | Код |
|---|---|---|---|---|
| SIP/H.323 gateway | аппаратный терминал | да | decode + encode, **по процессу на сессию** | `crates/vks-server/src/gateway_video.rs` |
| WebRTC/браузер | str0m-peer | нет | нет (только PT-rewrite) | `crates/vks-media-sfu/src/webrtc_room.rs:416-446` |

MCU-композит **не имеет собственного планировщика**: он выполняется внутри
egress-цикла шлюзовой сессии, которая первой прошла guard
`crates/vks-media-mcu/src/engine.rs:279-295`. Следствие: комната без шлюзовых
видео-сессий (только браузеры) не композитится вообще, а стоимость композита
оплачивает случайная сессия.

### 1.5 Захваты блокировок и копии — сводка

Глобальные мьютексы движка: `rooms`, `frames`, `audio`, `pending_layouts`
(`engine.rs:528-545`). Всё состояние комнаты — под одним `rooms`; порядок захвата
`rooms → frames|audio` (`:668-671`, `:704-709`, `:776-778`, `:1062-1069`).

Копии на один 33 мс тик одной 20-партийной комнаты 720p30 **[АРИФМЕТИКА]**:

* композит: 3.11 МиБ аллокация + ~8.3 МиБ записи (`vec![128; …]` 3.11 + `fill(16)` 2.07 + блит 3.11);
* egress: 20 × (1.38 МиБ чтение холста + 1.38 МиБ запись выхода `resize_i420`) = 55 МиБ;
* decode-выход: 20 × 1.38 МиБ аллокация+заливка = 27.6 МиБ;
* audio: 20 × (2 клона × 3.84 КиБ + N выходов) ≈ 1.5 МиБ на 20 мс тик → 2.5 МиБ на 33 мс;
* итого ≈ 95–100 МиБ памяти в секунду на комнату — это не bandwidth-предел.
  Аллокации: ~1.2 тыс./с на видео-путь (canvas + N resize + N decode-буферов) и
  **~40 тыс./с на аудио-путь** из-за копий до guard (H6: 20 вызывающих × 20
  участников × 2 клона × 50 Гц), каждая через malloc/`mmap`/page-fault.

### O1. Shared composite canvas на выходной профиль

**Что менять.** `Compositor` получает целевой размер (`Canvas` уже существует в
`vks-layout/src/rect.rs`), `engine.rs:297-306` — кэш холстов по ключу
`(w, h)` в `RoomState`; `slot_rects` пересчитываются в координатах профиля
(геометрия уже нормализована — `vks-layout` возвращает `Rect` в пикселях канваса
1920×1080, `layout_bridge.rs:115-130`, значит достаточно линейного масштаба).
`gateway_video.rs:644-645` перестаёт вызывать `resize_i420`: кадр уже нужного
размера. Группировка зрителей — в `vks-server`: `EgressGroup { key: (codec,w,h,fps,bitrate,plan_hash) }`.

**Выигрыш.** Для 720p-группы площадь композита падает с 1920×1080 = 2.07 Мпикс до
1280×720 = 0.92 Мпикс (2.25× меньше блита и заливки), и **исчезает `resize_i420`**
целиком. [ОЦЕНКА] композит 5.23 → ~2.3 мс; resize 20 × 8 мс → 0. Суммарно по
комнате −160 мс на 33 мс тик (главный вклад в разрыв 10×).

**Как замерить.** `criterion` на `Compositor::compose` для 4/9/16 слотов при
выходном размере 1920×1080 vs 1280×720 (бенчмарк создать — его нет); плюс
`vks_mcu_tick_duration_seconds` в soak при `VKS_MCU_TICK_METRICS=1`.

**Риск.** (а) пиксельная неэквивалентность: downscale «композит → профиль» двумя
разными путями даёт разные картинки (сейчас nearest-neighbour по
`floor(x·fw/dw)`, `compositor.rs:155-192`); (б) letterbox-поля считаются в
координатах профиля — golden-тесты из `compositor.rs:235-490` обязаны быть
переписаны на оба размера; (в) 1080p-профиль ничего не выигрывает (остаётся 1:1) —
не пытаться «оптимизировать» identity-путь.

### O2. Tile cache + dirty-rect + persistent double buffer

**Что менять.** В `RoomState` добавить `TileCache: BTreeMap<SlotKey, CachedTile>`,
где `CachedTile { src: Arc<Frame> (сравнение по `Arc::ptr_eq`), rect: PixelRect,
scaled: Frame }`; `Compositor::blit` заменяется на «масштабировать в тайл один раз,
затем `copy_from_slice` в холст». Холст — два persistent буфера в `RoomState`
(swap по тику), заливка фона только по dirty-областям. Dirty = (новый `Arc` кадра)
ИЛИ (изменился `PixelRect`) ИЛИ (прошёл кроссфейд-тик: `layout_bridge.rs:70-77`,
`lerp` меняет rect каждый тик 300 мс).

**Выигрыш.** В 20-партийной комнате меняются 1–3 кадра за тик, остальные 17 — те же
`Arc`. [ОЦЕНКА] mean 5.23 → 1.0–1.5 мс (3–5×), и почти нулевая работа на тик в
«тишине». Плюс снимает 3.11 МиБ alloc+fill на тик (часть O5).

**Как замерить.** Тот же criterion-бенч: `compose` при 1/3/20 «грязных» слотах;
счётчик «сколько тайлов пересобрано» в soak.

**Риск.** Главный — **корректность инвалидации**: кадр может измениться по
содержимому без смены `Arc` (сейчас `set_participant_frame` всегда создаёт новый
`Arc` — `engine.rs:1069`, это спасает). Любая оптимизация, переиспользующая буфер
кадра (O5!), ломает `ptr_eq` — инвалидация должна идти по version-токену, а не по
указателю. Это надо зафиксировать инвариантом до начала работ.

### O3. `resize_i420`: строчные срезы, Bresenham, exact-ratio, AVX2

**Что менять** (`gateway_video.rs:735-764`), в порядке отдачи (см. §4.2 —
измеренный разбор):
1. **Строчная структура (главное, −60 %).** Вместо `output[oo + y*pw + x] = src.get(so + sy*ss + sx)…`
   — один `let src_row = &src[so + sy*ss ..][..ss];` и
   `let out_row = &mut output[oo + y*pw ..][..pw];`, затем
   `for (x, item) in out_row.iter_mut().enumerate()` (bounds-check и адресная
   арифметика выносятся из пиксельного цикла). Это же место — точка для AVX2.
2. **Bresenham вместо деления (−0–8 %).** Заменить `x * source_stride / plane_width`
   на шаг+остаток (точное `floor(x*sw/dw)`, как в `compositor.rs:181-191`).
   Сам по себе даёт мало, но нужен для векторизации (в пиксельном цикле не остаётся
   ни `div`, ни проверки деления на ноль, которую Rust вставляет для
   runtime-знаменателя).
3. **Exact-ratio кернелы** (identity / 2:1 / 4:3 / 3:2) по образцу `compositor.rs:157-180`
   и эталона Cisco (отдельные `scale_half.cpp`, `scale_two_thirds.cpp`:
   `/home/pro/Документы/MCU/cisco CMS/analysis/meta/A2_media_pipeline/README.md:18`).
   **identity-случай (1080p-профиль) — просто `copy_from_slice`: 20.9 → 0.26 мс (×70).**
4. **AVX2** под `#[target_feature(enable = "avx2")]` + `is_x86_feature_detected!`
   (в репозитории нет ни одной `std::arch` строки; сборка без `-C target-cpu`,
   `Cargo.toml:82-92`). E5-2699 v3 = Haswell: AVX2 есть, AVX-512 нет. Замечание:
   ad-hoc `-C target-cpu=native` (Приложение D) включает авто-векторизацию
   компилятора, но внутренний цикл resize из-за деления и bounds-check не
   векторизуется — поэтому микробенч на дефолтном `x86-64` остаётся консервативной
   оценкой; при этом `native` делает замеры невоспроизводимыми на другой машине
   (R-26).
5. **Интерим на 1 строку**, если O1/O7 не готовы: отдать 1920×1080 холст энкодеру
   и добавить `-vf scale=W:H` (`gateway_video.rs:317-360`, как уже сделано для
   декодера `:356`) — масштабирует libswscale (SIMD), наш цикл удаляется.

**Выигрыш [ИЗМЕРЕНО].** 720p: 8.02–8.58 → **2.02–2.78 мс** (−65–75 %), 360p:
1.99–2.10 → 0.66–0.71, identity: 18.84–20.94 → **0.26** (memcpy). В пересчёте на
ядро: 0.24–0.26 → 0.06–0.08 ядра на устройство; это −0.18 ядра с каждого 720p30
устройства и −0.6 ядра с 1080p30. Цель Lead P3 (≥30 % CPU/сессию) перекрывается
только этой правкой.

**Как замерить.** criterion-бенч 1920×1080→{720p,360p,1080p} + golden-тест
байт-в-байт против текущей реализации на всех раскладках. Микробенч-протокол
воспроизведён в Appendix C.

**Риск.** (а) хрома может «bleed» на 1 сэмпл при нечётных origin (уже
задокументировано для композита, `compositor.rs:108-113`) — golden-тест обязан
включать Focus 8+, 7×7 и промежуточные rect кроссфейда; (б) Bresenham-аккумулятор
должен быть точным (`u64`/шаг+остаток), иначе расхождение с `floor(x*sw/dw)` на
последних столбцах (проверить на 1920→1280, 1920→640, 1920→1080); (в) identity
нельзя включать «на глаз» — только при точном равенстве `w,h` и `is_yuv420p()`.

### O4. Аудио: SIMD-микшер (AVX2), один проход, top-K, N-1 на месте

**Что менять.** `audio_mixer.rs:70-130`:
* один проход: `sum[L]` (8-wide AVX2 FMA) + одновременно `energy[N]` для VAD и
  top-K;
* `mix_and_mix_minus` не возвращает `Vec<Vec<f32>>`: писать N-1 в переданный
  вызывающим буфер (или по требованию, N-1 = `sum − own`, как уже сделано
  алгоритмически — `audio_mixer.rs:100-105`);
* soft-clip: вместо `tanh` на каждом сэмпле — только при `|x| > 1.0` (уже так,
  `:35-41`), но вынести проверку на блок: `max|block| <= 1.0` → `copy_from_slice`
  без ветвей;
* `engine.rs:399-476`: убрать `participant_audio.clear()`+N insert (`:406-409`) и
  `mixed_audio.clone()` на каждого (`:414`, `:417`) — хранить `sum` и набор
  активных, N-1 отдавать в `copy_participant_audio` (`:928-947`) на месте;
* VAD: переиспользовать `sum_sq` из одного прохода, убрать копию
  `let mut frame = [0.0f32; 960]` (`:427-435`), ZCR считать по срезу;
* top-K (K=4) по энергии: остальным участникам отдавать одинаковый микс
  «top-K», а не N разных N-1 — это и есть «top-K по VAD» из ТЗ.

**Выигрыш.** [ОЦЕНКА] аудио-тик 0.162 → 0.03–0.05 мс (worst case tanh) и
~0 аллокаций/тик; на 20 участниках ~0.35 → 0.1 мс, т.е. 1.7 % → 0.5 % ядра
на комнату. **Влияние на ёмкость устройств — 1–3 %**, не более: аудио не блокер
(фиксирую честно, см. §0).

**Как замерить.** criterion на `mix_and_mix_minus` (N=4/20, L=960, с tanh-ветвью и
без); `perf stat -e instructions,cycles` до/после; требование — численно
эквивалентно в пределах 1e-6 (порядок суммирования f32 меняется!).

**Риск.** Порядок суммирования f32 → биты не совпадут; тесты `audio_mixer.rs:137-227`
используют `1e-6` — сохранить допуск. Изменение семантики top-K меняет поведение
«слышу всех» → это продуктовое решение, нужно в ADR/тестах (сейчас N-1 честный для
всех — `engine.rs:405-418`).

### O5. Пул кадров / frame arena + zero-copy

**Что менять.**
* `Frame { data: Vec<u8> }` (`crates/vks-media-mcu/src/frame.rs:22-30`) →
  вариант с `bytes::Bytes`/`Arc<[u8]>` **или** `FramePool` на комнату: 3 буфера
  под холст + буферы под decode/resize, выдаваемые под гарантию единственного
  владельца (generation-хендл, без `unsafe`);
* `gateway_video.rs:544` → `read_exact_into(&mut pooled)` (в `codec_worker`
  такой метод уже есть — `ffmpeg.rs:721-750`, но путь шлюза его не использует);
* `gateway_video.rs:738` → переиспользуемый буфер из пула;
* `compositor.rs:44-50` → persistent холст из пула (см. O2);
* `Bytes` уже есть в SFU-пути и хорошо работает: `forwarder.rs:21-32`,
  `udp_loop.rs:204` — образец для переиспользования.

**Выигрыш.** Убирает 3.11 МиБ alloc+fill на тик/комнату и 20 × 1.38 МиБ/тик
на сессии; [ОЦЕНКА] 5–8 % CPU и, важнее, убирает page-fault-джиттер (сейчас
3.11 МиБ = 760 page-fault на тик при холодном mmap — при `malloc`-арене часть
переиспользуется, поэтому [НЕ ПРОВЕРЕНО] без `dhat`).

**Как замерить.** `dhat`/`heaptrack` на soak (число alloc и байт/тик), плюс
`perf stat -e page-faults` на процесс (сейчас idle-база: 0 faults/3 с, `perf stat`
ниже).

**Риск.** Публичный тип `Frame` используется в `vks-server`
(`gateways.rs`, `gateway_video.rs:552`) — смена типа ломает API и требует ADR;
пул с алиасингом — потенциальный UB, если отданный буфер живёт дольше; правило
проекта «no `unsafe` в движке» (`crates/vks-media-mcu/src/lib.rs:33-35`).

### O6. per-room actor + worker-per-core

**Что менять.** `engine.rs:533-545`: убрать `rooms/frames/audio` как глобальные
мьютексы; `RoomActor` — владелец `RoomState`, вход через `mpsc<Command>` +
`oneshot` для запросов; комнаты шардируются по N медиа-воркерам
(`room_hash % N`), N = 4–8 зарезервированных физических ядер, каждый воркер —
отдельный поток с `sched_setaffinity`; аудио-тик (20 мс) и видео-тик (33 мс) —
таймеры внутри actor'а, а не в egress-задаче шлюза; egress-задачи получают
готовый кадр через `watch`/`Arc`.

**Выигрыш.** Снимает H4 (16 % duty глобального мьютекса), делает композит
параллельным по комнатам (сейчас фактически 1 ядро на весь сервер), убирает H6 и
H8 (глобальные копии уходят в actor). Это единственный способ дойти до целей
`MEDIA_PIPELINE.md:189-198` (20 комнат / 4 ядра на комнату) и до требования ТЗ
«20 устройств на ядро» на многокомнатной нагрузке.

**Как замерить.** мультикомнатный soak (сейчас 1 комната — признано в
`SUMMARY.md:63-64`): 1/4/8 комнат × 20 мс/33 мс, мерить p99 аудио-тика и
суммарный CPU; `perf stat -e context-switches` до/после.

**Риск.** Самый большой рефакторинг в скоупе (engine.rs 120 785 B; impl — до
`:1333`, дальше 1200 строк тестов); async/sync граница (actor синхронный,
вызывающие — из tokio); порядок событий `RoomEvent::{Speaking,LayoutChanged}`
(`engine.rs:735-745`, `:399-476`) должен сохраниться; инверсии блокировок
`rooms → pending_layouts` (`:996-998`, комментарий про ABBA) исчезают — это плюс.
Отдельная зависимость от `net-resilience` (принята в раунде 1, §5.2): хэш
`SO_REUSEPORT` по 4-tuple не знает комнату, поэтому per-core UDP-читатели требуют
`SO_ATTACH_REUSEPORT_EBPF` с парсингом SSRC (`bpf_skb_load_bytes`, offset 8..12) и
таблицей SSRC→core — иначе RTCP/NACK уезжают на чужой воркер.

### O7. Отказ от per-viewer полного кадра: egress-группы

**Что менять.** В `vks-server` рядом с `spawn_video_media_bridge`
(`gateway_video.rs:477-732`) ввести `EgressGroup`:
* один FFmpeg-энкодер (`WorkerPool` уже существует и умеет это —
  `transcoder_runtime.rs:24-74`, `ffmpeg.rs:897-1000` (`WorkerPool`) —
  но видео-путь шлюза его **не использует**, спавнит `Command::new("ffmpeg")` сам,
  `gateway_video.rs:304-306`);
* один цикл чтения выхода энкодера → N RTP-потоков: переписывать только
  заголовок (SSRC/seq/PT/timestamp), payload — общий `Bytes`;
* PLI от любого зрителя → keyframe у группового энкодера;
* NACK/RTX-кэш **на группу**, ключ `(room, ssrc, seq)`, а не `(viewer, seq)`:
  при одном энкодере пакеты идентичны, кэш шарится и становится **дешевле**, чем
  при 20 независимых энкодерах (учтено с `net-resilience`, §5.2).

**Выигрыш.** [ОЦЕНКА] encode 20 × (2–5 мс) → 1 × (2–5 мс): −95 % стоимости энкодера
для группы; packetize на зрителя — единицы микросекунд (5–10 пакетов/кадр × 12 B).
Это то, что делают оба эталона: Vinteo — «**один физический энкодер — x264 или
NVENC — на many клиентов с одинаковыми параметрами**»
(см. `/home/pro/Документы/MCU/vinteo/08_отчёты_анализа/12_Архитектура_микшера_MCU.md:539`, механизм
`MultiVideoEncoder::attachClient` — `:569`), Cisco — `mf_video_compose_get_output()`
с индексируемыми выходами
(см. `/home/pro/Документы/MCU/cisco CMS/analysis/meta/15_MIXER_ELEMENTS_API.md:13-14`).

**Как замерить.** На стенде: 20 сессий с одинаковым профилем, `perf stat` по дереву
процессов; ожидание — число энкодеров 20 → 1 и падение CPU в детях в ~10–20×;
интеграционный тест — 20 зрителей получают байт-идентичный payload с разными
SSRC/seq.

**Риск.** (а) **SRTP**: при шифровании per-viewer ключами шарить готовые пакеты
нельзя — шифровать надо на зрителя (AES-NI, ~1–2 % ядра на 1.5 Мбит/с [НЕ ПРОВЕРЕНО]);
(б) ADR-0029: если планы зрителей различаются (self-view), группа распадается на
подгруппы по `plan_hash`, и в худшем случае это снова N энкодеров — см. §4.6;
(в) новый зритель обязан дождаться keyframe группы (стандартно, но меняет
поведение «мгновенного подключения»); (г) два пути управления FFmpeg-процессами
(пул с process-group kill по ADR-0028 — `ffmpeg.rs:227`, `:238-258` — и «сырой»
`Command` в `gateway_video.rs:304`, kill только прямого ребёнка `:722-725`)
надо свести к одному; (д) SRTP: шифрование остаётся per-viewer, поэтому кэш
ретрансмитов обязан хранить **открытый** payload и шифровать при отправке — иначе
ключи разных зрителей несовместимы с общим пакетом.

### O8. Decode-gating: не декодировать то, что не видно

**Что менять.** `gateway_video.rs:522-532` (запись в stdin декодера) и очередь
`access_tx` (`:503`): если участник не присутствует ни в одной видимой ячейке
раскладки (`RoomState::current_layout.slots` + `is_focus`,
`engine.rs:207-215`, `:331-333`; focus уже вычисляется по `important/active_speaker`),
не кормить декодер и не обновлять `set_participant_frame`; при входе в фокус —
PLI/fast-update и ожидание keyframe.

**Выигрыш.** Декод — единственная стоимость, которая линейна по N и **не шарится**
(1–3 мс/кадр/устройство, в детях FFmpeg). 20-партийная комната, focus 1+5:
decode 20×(1..3) = 20–60 мс/тик → 5–15 мс/тик. Это ровно разница между
A≈6–16 и A≈18–30 устройств/ядро (§4.4).

**Как замерить.** `pidstat -t`/`cgroup cpu.stat` по детям FFmpeg до/после;
интеграционный тест: 20 сессий + focus-раскладка, CPU 15 невидимых декодеров ≈ 0,
переключение фокуса даёт картинку ≤ одного keyframe-интервала.

**Риск.** (а) переключение фокуса = keyframe-задержка 100–300 мс (смягчается
предсказанием по VAD, `engine.rs:331`); (б) H.264/H.323 не даёт «частичного»
декодирования — только полный дроп; (в) ломает «все видят всех» в равномерной
сетке → продуктовое решение; (г) счётчики `video_rx_packets`/`dropped_video_frames`
обязаны считать drop по причине «not visible», иначе QoE-метрики врут; (д) при
дропе нужно сбрасывать декодер/keyframe-state, иначе первый кадр после возврата
в фокус будет битым (проверять `depacketizer` state).

### 4.2 Механизм `resize_i420`: что реально дорого (микробенч)

[ИЗМЕРЕНО] standalone-бенчмарк (Appendix C): точная копия `gateway_video.rs:735-764`,
E5-2699 v3, 200 итераций, два прогона сборки (`-C opt-level=2` и `=3`), мс/кадр:

| Вариант | 1920×1080→720p | →360p | identity 1080p |
|---|---|---|---|
| как в коде (`u32 div` + `get().unwrap_or(16)`) | **8.02–8.58** | 1.99–2.10 | 18.84–20.94 |
| Bresenham вместо деления, bounds-check сохранён | 7.88–8.56 | 2.45–2.70 | 5.54–6.14 |
| Bresenham + строчные срезы | **2.02–2.78** | 0.66–0.71 | 4.34–5.28 |
| чистый `copy_from_slice` 3.11 МиБ | — | — | **0.26** |

`perf stat` по тому же бинарю: cycles 30.46e9, instructions 62.21e9 → **IPC 2.04**,
branch-misses 200.1e6. 720p: 8.0–8.6 мс × 2.42 ГГц / 1.3824e6 = **14–15 тактов/сэмпл**
— оценка «12–17» первой версии подтверждена.

**Где ошибался мой разбор (и разбор Lead).** Деление — не главный компонент:
его удаление даёт 0–8 % (в пределах шума между opt-level=2 и 3). ~60 % стоимости —
bounds-checked `get(...).unwrap_or(16)` плюс пересчёт адреса на каждый пиксель;
строчные срезы дают 3–4×. Причина: Rust для деления на **runtime**-знаменатель
вставляет проверку на ноль (`div` + ветка в панику), `get()` — вторую ветку,
`unwrap_or` — третью; итого 21 инструкция/сэмпл при IPC 2.04. **Вывод для O3:
порядок работ «строчная структура → Bresenham → exact-ratio → AVX2», а не «сначала
убрать деление».** Итоговые 2.02–2.78 мс подтверждают, что цель «≥30 % CPU/сессию»
достигается одной этой функцией.

### 4.6 Структурный предел: self-view ON

Если у каждого зрителя свой план (self-view / персональная раскладка, ADR-0029
вариант C), общий encode невозможен: нужно N энкодеров. Это физика, а не наш код:
эталон TrueConf считает энкодеры дефицитным ресурсом — `vsm.limits.encoders = 106`
при `decoders = 1696`, модель «картинка одна, кодировщик — на каждого получателя»
(`/home/pro/Документы/MCU/mcu trueconf/reconstruction/00_DOCUMENTATION/MASTER_ARCHITECTURE.md:355-357`,
`:394-401`, `:1161-1162`). Цена на устройство = decode 1–3 + **encode 3.5** +
copies 0.15–0.3 + per-viewer дельта (клон холста + 2 блита; после tile cache —
~0.35 мс) ≈ 5.0–7.2 мс/кадр → **0.152–0.217 ядра** → **A 3.2–4.6, B 3.9–5.6,
C 4.4–6.3 устройств/ядро**.
Дополнительно H13: сейчас при self-view ON каждый проигравший guard зритель делает
`base.data.clone()` 3.11 МиБ (`engine.rs:790-795`, `:842`) — до 19 клонов за 30 мс
(≈1.9 ГБ/с); лечится кэшем дельты по generation-токенам
(composite generation, поколение своей камеры, layout version), а не клоном на вызов.

То есть **20 устройств/ядро при включённом self-view не достижимо ни при каком
плане** (потолок 3–5); это продуктовое ограничение, которое должно быть зафиксировано
в ADR-0029 вместе с ценой. При выключенном (дефолт, `engine.rs:854-859`) — достижимо
только вместе с O8.

## 5. Контраргументы: `proto-chain` и `net-resilience`

### 5.1 Против позиции `proto-chain` («главный блокер — протокольная цепочка»)

**Что верно.** Без SRTP/TLS, H.245/H.239, BFCP↔H.239, `PLI↔videoFastUpdatePicture`
и ASN.1 PER аппаратные терминалы не дозвонятся — и тогда **нечего мерить**.
Это гейт по оси «0 → 1 устройство», и я его не оспариваю.

**Где позиция не выдерживает.**

1. **Разные оси, не конкурирующие задачи.** Протоколы решают «подключится ли
   устройство», медиаядро — «сколько их влезет в ядро». Критерий ТЗ — «ёмкость
   1 физического ядра», т.е. вторая ось. После закрытия протокольных дыр 20
   устройств **подключатся**, но такая комната съест **~8 ядер из 36** (§4.3) —
   при требовании 20 устройств на ядро. Протоколы эту цифру не сдвинут ни на процент.
2. **Асимметрия рисков.** Протокольные дыры — конечный список механизмов с
   RFC/H.241-номерами, закрывается инкрементально и проверяется по одному вызову.
   Медиа-разрыв 10× — архитектурный: пока не убраны (а) скалярный `resize_i420`
   с bounds-check на каждый пиксель (`gateway_video.rs:757-759`; [ИЗМЕРЕНО]
   8.0–8.6 мс/кадр), (б) холст 1920×1080 + отдельный `resize_i420` на
   каждую сессию (`compositor.rs:44-50`, `gateway_video.rs:644-645`),
   (в) энкодер на сессию (`gateway_video.rs:488-500`), (г) глобальный мьютекс на
   композит (`engine.rs:776-783`) — ёмкость не растёт вообще. Это «либо
   рефакторинг, либо ничего», а не список правок.
3. **Медиа-работа не требует ботов.** Оптимизации §3 проверяются in-process:
   criterion + существующий soak-харнесс `crates/vks-media-mcu/tests/mcu_tick_soak.rs`
   + `vks_mcu_tick_duration_seconds`. Протокольные дыры **нельзя** проверить без
   реальных терминалов (боты отсутствуют — это блокер `perf-lab`). Значит медиа
   можно двигать **параллельно** с протоколами, а не после них.
4. **Измеренная доля.** Даже в режиме M0 (signaling-only) медиа-стоимость видна
   сразу; при переходе M1→M2→M3 (ТЗ) рост CPU будет монотонно медийным. Если
   после закрытия протоколов M3 (20×720p30) съест 7–9 ядер из 36 — «блокер»
   определён неверно.

**Ответ на их критерий победы.** Я не предлагаю откладывать P2; предлагаю не
считать P2 достаточным и вести P3 параллельно, потому что P3 — единственный путь
к цифре «20 устройств/ядро», а его объём — 4 конкретных патча с уже существующими
тестами.

### 5.2 Против позиции `net-resilience` («2 % loss / 30 мс jitter без NACK/RTX/FEC/PLC»)

**Что верно.** При 2 % loss без NACK/RTX/FEC картинка рассыпается, MOS-цели
класса B/C недостижимы. Jitter buffer в MCU нет, `recv_from` по одному пакету
(`udp_loop.rs:143-230`), sysctl дефолтные — всё так.

**Где позиция не выдерживает.**

1. **Порядок зависимостей по CPU.** Механизмы устойчивости **добавляют** CPU
   (NACK-кэш и ретрансмиты, FEC encode/decode, PLC, pacing), а не убирают. Сегодня
   запас — 2 устройства/ядро; включение FEC/NACK на нынешнем медиаядре сделает
   хуже, а не лучше. Сначала ёмкость (O1–O7), потом resilience — иначе resilience
   некуда класть.
2. **Измеряемая матрица ТЗ начинается с loss < 0.1 %.** SLA-класс A (MOS≥4.3,
   loss <0.1 %, U_limit 70 %) — это базовая ёмкость; resilience нужен для B/C.
   Смешивать «сколько влезает» и «как переживаем 2 % loss» нельзя: это разные
   прогоны и разные слагаемые CPU.
3. **Часть их механизмов — в моём дизайне, а не рядом.** Per-viewer NACK/RTX-кэш
   должен строиться **вместе** с egress-группами (O7): если сначала сделать
   per-viewer кэш пакетов для 20 независимых энкодеров, а потом объединить
   энкодеры в группы (O7), кэш придётся переделывать. Аналогично
   **worker-per-core**: per-core UDP-читатели (`recvmmsg` + `SO_REUSEPORT`) имеют
   смысл только если комнаты пришпилены к ядрам (O6). Предлагаю joint-design:
   O6 задаёт affinity, их L3-механизмы читают/пишут внутри того же воркера.
4. **Сеть не объясняет 10×.** Даже идеальный jitter buffer с `recvmmsg` не уберёт
   144 мс/тик на `resize_i420` и 70 мс/тик на 20 энкодеров.

**Честная уступка (принята после раунда 1 с `net-resilience`).**
1. Их P0 — **JB + reorder-буфер + SO_RCVBUF + метрики** — я принимаю как
   *предусловие измерения ёмкости*, а не как add-on для класса B: `RtpSource::accept`
   выбрасывает любой пакет с `seq < last` (`gateway_audio.rs:585-595`: `distance == 0
   || distance >= 0x8000` → `None`), т.е. при джиттере baseline сам теряет пакеты, и
   «loss <0.1 %» на нём измерить нельзя. Это независимо от моей позиции и
   проверяемо по коду.
2. Их уточнение по NACK-кэшу принимаю и встроил в O7: ключ `(room, ssrc, seq)`,
   кэш шарится на группу — при одном энкодере он **дешевле**, чем при 20.
3. Их уточнение по `SO_REUSEPORT`+eBPF принимаю и встроил в O6: без
   `SO_ATTACH_REUSEPORT_EBPF` (SSRC→core) 4-tuple-хэш уводит RTCP/NACK на чужой
   воркер; это часть дизайна O6, а не «просто affinity».

Итоговая точка консенсуса (подтверждена `net-resilience` в ответном сообщении,
записана у них в §7.1): P0 (JB/reorder/SO_RCVBUF/метрики) — предусловие валидности
замера; мой O1–O7 — параллельно; NACK-кэш проектируется сразу под egress-группы
(O7), ключ `(room, ssrc, seq)`, хранит открытый payload; worker-per-core (O6) +
SO_REUSEPORT/eBPF (SSRC offset 8..12) — один дизайн. За «FPS ≥ 27 при 2 % loss» и
валидность цифры потерь отвечают они, за «сколько влезает на ядро» — я.
Их уточнение, принятое мной: `MissedTickBehavior::Skip` даёт потерю playout **одной
сессии** (её очередь растёт → drop-oldest на 120 мс, `gateway_audio.rs:232-233,307,327`),
а не потерю микса комнаты — комната тикается через guard (`engine.rs:264-268`).

| M-4 | O6 (per-room actor/worker-per-core) + O5 (пул/zero-copy) | M-3; согласование с net-resilience | мультикомнатный soak 8 комнат, аудио p99 ≤2 мс |
| M-5 | O4 (аудио SIMD/top-K) | M-4 | 0 аллокаций/тик, −60 % CPU аудио |

### 5.4 Раунд 1 Lead: ответы на 4 контрдовода

**1) «7–10 мс на resize = 12–17 тактов/сэмпл — слишком много; докажи или дай
честный диапазон; допустимо ли 1.5–4 мс и как изменится вывод?»**

[ИЗМЕРЕНО] микробенч на этом CPU (Appendix C): **8.02–8.58 мс/кадр** (720p),
18.84–20.94 (identity-1080p), 14–15 тактов/сэмпл, IPC 2.04. Magnitude моей оценки
подтверждён; **механизм — нет**: удаление деления даёт 0–8 % (в пределах шума),
~60 % — bounds-checked `get` и адресная арифметика (см. §4.2). Допустимо ли
«1.5–4 мс»? Как **цель после правки** — да (2.02–2.78 мс); как **текущее
состояние** — нет, это занижение в 2–4×. Если бы было 1.5–4, `c_device` 720p был
бы 0.20–0.35 и A ≈ 2–3.5; измеренные 8.0–8.6 дают **A 1.4–2.1**. То есть моя
первая формулировка «2–3 сессии/ядро» была верхней границей — исправлено на
**1.4–2.1 (A), 1.7–2.5 (B), 1.9–2.8 (C)** (§4.4).

**2) «Найди код, который делает композит РАЗНЫМ для зрителей; сколько различных
композитов за тик при self-view OFF/ON; почему egress-группы вместо простого
«один композит на комнату»?»**

`tick_video_for_viewer` (`engine.rs:790-795`) сначала зовёт `tick_video_at`, а при
throttle уходит в `frame_for_viewer` (`:807-848`). В `frame_for_viewer`:
`if !state.self_view { return Some(base) }` (`:811-812`) — **тот же `Arc` всем**.
Различные композиты появляются только при self_view ON: для зрителя-издателя
клонируется холст (`:842`), очищается его ячейка (`:843`) и его камера блитится в
ячейку низшего приоритета (`:844-846`), т.е. до `1 + P` различных кадров
(P = число зрителей с собственной ячейкой, которых не устраивает «низший» слот).
Итог: **OFF → ровно 1 композит/тик (0 копий); ON → 1 общий + до P клонов, причём
клон делается на КАЖДЫЙ вызов, включая 19 проигравших guard** (H13, ~1.9 ГБ/с
memcpy при 20 зрителях). То есть «один композит на комнату» **уже есть** —
дублируются не композиты, а **resize (8.0 мс) и encode (2–5 мс) на сессию**;
O1+O3 убирают resize, O7 — encode. Что сломается при группировке: RTP seq/SSRC/
timestamp (каждому свой поток), PLI→keyframe группы, SRTP per-viewer, счётчики
`*_rx_*` на сессию, «мгновенный» join (нужен keyframe). Что **не** сломается:
раскладка room-wide (`RoomState.current_layout`; `plan_viewer`/`ViewerPlan` в
проде не используются — grep по `vks-server`/`vks-media-mcu` пуст), focus/pinned —
свойства раскладки комнаты (`engine.rs:207-215`, `:331-333`), version/`LayoutChanged`
тоже room-wide (`:735-745`, `:883-907`). Если ADR-0029 фаза 1 введёт per-viewer
планы — ключ группы обязан включать их хэш (в O7 это `plan_hash`).

**3) «Сведи к одному числу: сколько 720p30 SIP-устройств на одно физ. ядро для
A/B/C; отдельно потолок при self-view ON».**

Одна таблица — §4.4. Кратко:

| Сценарий | A (70 %) | B (85 %) | C (95 %) |
|---|---|---|---|
| Сейчас | **1.4–2.1** | 1.7–2.5 | 1.9–2.8 |
| После O1+O3+O7 (без O8) | **6–16 (центр 9)** | 8–19 | 9–22 |
| +O8 decode-gating (focus 1+5) | **18–30 (центр 23)** | 22–37 | 25–41 |
| self-view ON | **3.2–4.6** | 3.9–5.6 | 4.4–6.3 |

Для пользователя формулировка: «сейчас — 1–2 устройства на ядро; после плана без
decode-gating — 9 (A) / 11 (B) / 13 (C); с decode-gating — 23 (A) / 28 (B) / 31 (C);
с включённым самопросмотром — 3–5». «0.20 ядра на комнату» больше не использую как
ответ на этот вопрос: это сумма без декода и без класса SLA, то есть некорректная.

**4) «Проверь скрытую O(N²): `gateway_audio.rs:360` зовут все сессии; идемпотентно
ли по `now_ms`? Если нет — 20× микширование. Плюс стоимость mix_minus на 20
участников».**

`tick_audio_at` (`engine.rs:702-720`) берёт `rooms`, затем **копирует всю audio-map
и каждый `Vec<f32>`** (`:709`, `:711-714`), и только потом вызывает
`RoomState::tick_audio_at`, где guard `if now_ms < last + 18 { return (false, …) }`
(`:264-268`). **Идемпотентно: микширование выполняется 1 раз за ≥18 мс на комнату**,
не 20× — вызовы идут с общим монотонным `media_clock_ms()` (`gateway_audio.rs:6-9`),
разница микросекунды, первый победил. Вызывающие: `gateway_audio.rs:360` (каждая
SIP-сессия), `gateway_aac.rs:294`, тест `room_events.rs:144`.
**Но скрытая O(N²) есть — в копиях до guard:** 20 вызовов × (клон карты из N `Vec`
+ N клонов) ≈ **800 аллокаций и ~3 МиБ memcpy за 20 мс** на комнату (≈150 МиБ/с,
40 тыс. аллокаций/с), всё под глобальным `rooms` — это H6, а не микширование.
Стоимость самого `mix_and_mix_minus` при N=20: O(N·L) = 19 200 сложений на `sum` +
19 200 на минус-миксы + N выходных `Vec` по 3.84 КиБ; [ОЦЕНКА] 0.6–0.8 мс/тик
(линейно от измеренных 0.162 мс при N=4) → **3–4 % ядра на 20-партийную комнату**,
т.е. **~2 % от видео-стоимости**. Вердикт: **не блокер**, но pre-guard копии
обязательны к удалению (дешёвая часть O4: проверить `last_audio_ms` до клонирования,
например вынести guard в wrapper через `AtomicU64` на комнату).

## 8. Реализация O7: ферма энкодеров (итерация 3)

Новый модуль `crates/vks-media-mcu/src/farm.rs` (1069 строк, 10 тестов) + проводка
`engine.rs`/`lib.rs` (+462) и `gateway_video.rs` (+682/−107; в числе — O3/O1 раунда 2).

### 8.1 Что изменилось
* **Один энкодер на группу** `EncoderKey = (room, canvas_version, EncoderSpec)`, где
  `EncoderSpec` — всё, от чего зависит битстрим: `codec, width, height, fps,
  bitrate_kbps, maxrate_kbps, bufsize_kbps, profile, level, keyint, encoder_params`
  (params — строка шлюза, единый источник истины; спека §B.2).
* `EncoderFarm`: `acquire`/`publish`/`release`/`invalidate_room`/`snapshot`,
  refcount = зрители + энкодер; при нуле child убивается **группой процессов**
  (`kill(-pgid, SIGKILL)`, ADR-0028). Актор группы пишет кадры в stdin, режет
  Annex-B на access units по AUD (H.264 type 9 / H.265 type 35), кэширует SPS/PPS
  и рассылает `Arc<AccessUnit>` через `broadcast` (нулевые копии NAL).
* **Per-viewer осталась только RTP-обвязка**: свой SSRC/seq/ts, свой буфер
  packetize (F10). IDR-гейт: новый зритель не получает дельта-кадры до первого
  IDR (≤ keyint = 1 с).
* `RoomState`-уровень не менялся: ферма — поле `McuEngine`, публикация кадра идёт
  из существующего render-таска (`tick_video_for_viewer` → `publish_video_frame`),
  дедуп одинаковых кадров от N сессий — внутри фермы (окно 0.75·1/fps).
* **Egress-resize уехал в энкодер**: группа получает холст комнаты, `-vf scale`
  включается только при несовпадении холста и профиля. С O1 (холст = профиль
  первой сессии) в parent масштабирования нет вовсе.
* **Групповой keyframe**: `keyframe_requests` теперь per-EncoderKey;
  PLI/FIR любого зрителя инкрементит счётчик группы, актор его потребляет.
  Форс-IDR не делается (нет runtime-хука у raw-pipe FFmpeg; рестарт рвёт поток
  всем зрителям) — `keyint=fps` даёт ≤ 1 с, это осознанное ограничение v1,
  форс-IDR = P4b (спека §B.6).

### 8.2 Побочный, но важный эффект: `ensure_composite_size` вызывается ДО `acquire`
Смена холста (`set_composite_size`/`ensure_composite_size`) инвалидирует группы
(`farm.invalidate_room`: версия + cancel). Группа, взятая на старом размере,
осталась бы без кадров, поэтому O1-вызов перенесён выше `acquire`. Это же
защищает от «тихого» зависания видео при смене холста в тестах/админке.

### 8.3 Ожидаемый эффект
FFmpeg-энкодеров в комнате: было **N зрителей**, стало **1 на (room, профиль)**.
Для 20-партийной комнаты одного профиля: 20 → 1 энкодер (19 × 0.28–0.31 ядра
`[ЗАМЕР]` Lead ≈ **5.4–5.9 ядра** на комнату, т.е. **0.27–0.30 ядра/устройство**).
Процессов FFmpeg: 2N → N + 1 (декодеры остаются per-participant — это вход, не выход).
Ожидание по контуру: снимает основную часть оставшейся ffmpeg-доли (70–77 % на
итерации 2), приёмка Lead — **≥2.4 устройства/ядро на testsrc2, ≥3.0 на реальном
720p30**. Реальные числа — на harness perf-lab (итерация 3).

### 8.4 Тесты
`vks-media-mcu` lib: 10 новых в `farm.rs` — Annex-B/AUD-нарезка (H.264 и H.265),
классификация NAL (IDR/parameter sets обоих кодеков), стабильность ключа,
refcount-цикл acquire/release → убийство группы, разные профили → разные группы,
`Overloaded` при лимите, `invalidate_room` (версия + `Closed` для старого ключа +
новые кадры только новой группе), групповой keyframe-счётчик, дедуп публикаций,
кэш SPS/PPS для позднего зрителя.
`vks-server` lib: `two_subscribers_share_one_encoder_group` (реальный H.264:
1 группа на комнату, refcount 3+энкодер, оба зрителя получают битстрим, у каждого
свои RTP-пакеты, после ухода всех группа и FFmpeg остановлены) и
`self_view_room_falls_back_to_per_session_encoder` (self-view ⇒ ферма не
создаётся, старый путь работает). Существующий `h265_loopback…` теперь идёт
через ферму (H.264-loopback — `#[ignore]`-тест, кодирование проверено
`two_subscribers…` с реальным FFmpeg).

Итог приёмки: `cargo test -p vks-media-mcu -p vks-server` = **120 + 120 + 31
passed, 0 failed** (4 ignored), exit 0. `cargo clippy -p vks-media-mcu -p

### 8.4a Критичный баг живого прогона и фикс (итерация 3, ревизия 2)
Первый живой прогон итерации 3: зритель получал ~11 пакетов / 3.5 КБ (один AU
SPS+PPS+IDR), энкодер 6.5 % CPU, в логах только `encoder group started`.
Причина: **актор группы делал write в stdin и read из stdout в одном цикле**.
Границей AU служит AUD *следующего* кадра, а следующий кадр нельзя закодировать,
пока писатель не вышел из read → клинч; AU выдавался только после 2-секундного
таймаута чтения. Фикс: актор разделён на **писатель** (mpsc → stdin) и
**читатель** (stdout → Annex-B → AU → broadcast, отдельный таск, непрерывный
дренаж; хвост флашится на остановке). Диагностика: `warn "encoder group is
starving: AU output lags input"` (раз в 30 кадров, виден на INFO) и `debug
"encoder group progress"` (frames_written/encoded). Тест
`two_subscribers_share_one_encoder_group` усилен: требует **≥10 AU за 1.2 с**
после первого кадра — со старым актором падал, с новым проходит, т.е. регрессия
закрыта тестом, а не глазами.
Аварийный выключатель без пересборки: **`VKS_VIDEO_FARM=0` (или `off`) ⇒
per-session путь итерации 2**; по умолчанию ферма включена.

## 9. P4a: метрики фермы (`encoder_group_*` / `viewer_rtp_*`)

Новый модуль `crates/vks-server/src/farm_metrics.rs`; проводка в `lib.rs`
(`install` при сборке приложения, `update()` в `/metrics`, роут
`/api/v3/mcu/farm`); в `farm.rs` — агрегат [`ViewerRtp`] и 4 новых поля
`GroupStat`; в `gateway_video.rs` — per-viewer RTP учитывается через
`GroupViewer::note_rtp/note_dropped`.

### 9.1 Что отдаётся
`/metrics` (гейджи текущего состояния, метки `room,codec,width,height`):
`encoder_group_active`, `encoder_group_refcount`, `encoder_group_viewers`,
`encoder_group_frames`, `encoder_group_keyframes`,
`encoder_group_dropped_frames`, `encoder_group_restarts`,
`encoder_group_keyframe_requests`, `viewer_rtp_packets`, `viewer_rtp_bytes`,
`viewer_rtp_dropped_frames`.

Семантика: это **состояние группы**, а не кумулятивные счётчики процесса —
`frames/keyframes/dropped/restarts/keyframe_requests` считаются с момента
создания группы, при ретире серии исчезают (`reset()` на каждом сборе), при
пересоздании начинаются с нуля. Так сделано осознанно: группа = жизнь
энкодера, а `active/refcount/viewers` показывают, склеила ли ферма зрителей.
Для proto-chain: `encoder_group_keyframe_requests` = PLI/FIR, дошедшие до
потребителя группы (production-видимость для приёмки PLI без debug-логов).

`/api/v3/mcu/farm` — JSON: `{groups:[{room,canvas_version,codec,width,height,
fps,bitrate_kbps,profile,level,refcount,viewers,frames,keyframes,
dropped_frames,restarts,keyframe_requests,viewer_rtp:{packets,bytes,
dropped_frames}}], totals:{groups,viewers,frames,viewer_rtp_packets,
viewer_rtp_bytes,keyframe_requests}}`.

### 9.2 Ограничения
1. Гейджи, не counters: `rate()` по ним не строится; для PLI/дропов смотреть
   абсолютные значения и производные по времени в панели.
2. Кардинальность: одна серия на группу (≤ профилей на комнату, лимит
   `VKS_VIDEO_FARM_MAX_GROUPS`); комнаты без фермы (self-view, `VKS_VIDEO_FARM=0`)
   серий не дают.
3. `viewer_rtp_*` — агрегат по зрителям группы (один `GroupViewer` на сессию);
   per-viewer разрез — следующий шаг, если понадобится (нужны метки зрителя,
   это +1 кардинальность на сессию).
4. `/api/v3/mcu/farm` смонтирован в `m5_api` рядом с `/api/v3/gateways/status`
   (вне auth-обёртки legacy-адаптера) — как и остальные M5-эндпоинты мониторинга.
5. `install` идемпотентен по адресу движка; в тестах собирается несколько
   приложений, метрики агрегируют живые движки (в продакшене движок один).

### 9.3 Тесты

## 10. P1: битрейт группы по числу видимых окон

Основание: BENCHMARK §10 — общий энкодер на 20 окон даёт +8.6 % битрейта;
решение Lead'а — коэффициент с жёстким клампом.

### 10.1 Правило и реализация
`bitrate_group = clamp(base × (1 + 0.02 × (visible_windows − 1)), base, 1.25 × base)`;
`visible = 0` → `base`. `maxrate` и `bufsize` масштабируются тем же
коэффициентом (`bufsize = 2 × bitrate`).

* `engine.rs`: `McuEngine::visible_windows(room)` — число **занятых** ячеек
  композита: берётся *эффективная* раскладка (`current_layout`, то, что
  реально рисует композитор) и считаются слоты с назначенным участником;
  чистая `group_bitrate_kbps(base, visible)` + `GROUP_BITRATE_CEILING_PCT = 125`.
  **Почему не «кадр в слоте»** (первая версия, не прошла живую приёмку): в
  production кадры пишет `set_participant_frame` из декодера моста, и в момент
  подсчёта кадр может быть ещё не декодирован/пропущен, а `slot_rects()`
  (`bridge.current(elapsed)`) в переходе отдаёт неполную геометрию — окно
  композита при этом уже существует. Считать надо окна раскладки, а не
  «пришли ли байты»; пустые ячейки (участник без видео) и аудио-только
  участники не считаются.
* `gateway_video.rs`: `farm_spec_for(profile, visible_windows)` считает
  битрейт группы; в прологе моста видимые окна берутся один раз, а render-таск
  на каждом тике сравнивает число окон и через `watch`-канал сообщает
  output-таску **только при изменении**; тот при смене битрейта берёт
  **новый `EncoderKey`** (`acquire` новой группы, старая ретируется по
  refcount), а не пересоздаёт энкодер на каждом кадре. IDR-гейт после
  пере-ключёвки взводится заново (новая группа стартует с IDR).

### 10.2 Наблюдаемость
`encoder_group_visible_windows{room,codec,width,height}` в `/metrics` и поле
`visible_windows` в `/api/v3/mcu/farm` (на группу) — чтобы живая приёмка
показывала, из какого числа окон посчитан битрейт: 1 бот → `visible_windows 1`
и `bitrate_kbps 2048`; N ботов → `visible_windows N` и `bitrate_kbps` по
формуле (напр. 3 окна → 2088 при base 2048).

### 10.3 Ограничения
1. На переходе (старая+новая группа одного профиля живут одновременно, пока
   не ретируется старая) у семей `encoder_group_*`/`viewer_rtp_*` метки
   `room,codec,width,height` совпадают → в `/metrics` видна одна серия
   (последняя запись), а не две. Это переходное состояние длиной в один
   ретир (доли секунды); `active/refcount` после него корректны. Полный
   разрез — метка `bitrate_kbps` (меняет формат серий P4a; не добавлял, чтобы
   не ломать приёмку PLI у proto-chain — решает Lead).
2. `visible_windows` считается по кадрам, реально лежащим в слотах, поэтому
   «окно с чёрным кадром» (кадр есть, контента нет) считается видимым — для
   битрейта это безопасный переучёт вверх, кламп ограничивает 25 %.

### 10.4 P0-фиксы после живой приёмки «Итерации 4» (найдены Lead/perf-lab)

**Баг 1 — утечка энкодеров (корень — гонка `acquire`).** На живом прогоне
после churn оставались ffmpeg-энкодеры с `PPid` MCU, 0 % CPU и живыми
stdin-пайпами, при `groups=[]`. Воспроизведено на замороженном бинаре
`2d0aec43…` в изолированном инстансе: 3 SIP-бота × 1 цикл → **4 живых
энкодера-сироты**, `groups=[]`, в логе `encoder group started`=9 против
`retired`=5. Причина: `EncoderFarm::acquire` — check-then-spawn-then-insert
без блокировки. 2–4 render-таска сессий одновременно берут новый ключ при
re-key, каждый проходит проверку «группы нет», каждый спавнит FFmpeg; второй
`insert` затирает первый в мапе. Осиротевший `Arc<Group>` держит actor +
reader, actor ждёт `input.recv()` (sender жив внутри самой группы) и никогда
не доходит до `kill_child` → child живёт вечно; `retire()` его не видит (нет
в мапе), поэтому и `wait()` не вызывается — при ручном `kill -9` остаются `Z`
(ровно то, что видел Lead). Фикс: (а) `creation: tokio::sync::Mutex` —
медленный путь (повторная проверка → spawn → вставка) сериализован, вставка в
мапу идёт **до** спавна актора; (б) watchdog в акторе: каждые 20 мс сверяет
по `Weak<FarmInner>` + `Arc::ptr_eq`, что группа всё ещё в мапе; нет — выходит
и убивает child (страховка от любых будущих потерь группы); (в) `retire()` и
`invalidate_room()` сразу бьют `kill(-pgid, SIGKILL)` по pid child'а
(pid == pgid: спавн с `process_group(0)`), затем ждут актора и добивают
повторно; (г) `kill_child` делает `wait()` (нет зомби); (д) `kill_on_drop(true)`
у child'а — паника актора не оставляет процесс; (е) `Drop for FarmInner` —
backstop-kill всех групп; (ж) `acquire` со старой версией холста возвращает
`Closed`, а не плодит child без кадров.
Живая проверка фикса (`f5ab9394…`, изолированный инстанс, тот же
`/tmp/video_probe.py`, 720p25): **5 циклов × 3 бота** — после каждого цикла
`children=0`, `zombies=0`, `groups=0`; в логе `started`=10 / `retired`=10,
`orphaned`=0. Тесты: `concurrent_acquires_share_one_encoder_process`
(multi-thread, 8 одновременных `acquire` → 1 группа и 1 ffmpeg; без
creation-мьютекса падает — проверено), `orphaned_actor_self_terminates_and_kills_child`,
`retire_kills_encoder_process_group` (+0 зомби), `invalidate_room_kills_encoder_processes`,
gateway-e2e «3 зрителя × 3 цикла → ровно одна группа, после цикла групп нет».

**Баг 2 — re-key churn.** На 10 ботах десятки групп: каждый render-таск
сессии писал своё значение visible в общий `watch`, значения перетирались
(thrash), каждая смена → новый `EncoderKey` → новая группа. Фикс: канал
видимых окон принадлежит **движку** — один `watch::Sender` на комнату,
значение считается только из состояния движка (`visible_windows`), сессии
лишь читают; публикация с гистерезисом 500 мс (`VISIBLE_WINDOWS_STABLE`):
новое число уходит в канал, только если продержалось стабильно дольше —
флаппинг вверх-вниз не пере-ключывает группы. Тесты: 2 engine-теста на
дебаунс/флаппинг, gateway-тест «три зрителя по одному → ровно одна группа,
после ухода всех групп нет», 2 real-ffmpeg теста фермы (retire/invalidate →
ноль дочерних процессов).

### 10.7 P0-ingest: джиттер на входе (bot→MCU) ронял видео ×100

**Симптом (Lead/perf-lab, T2 «Итерации 6»).** 5 мс джиттера на входе:
видео 42.7 pps вместо 317.6, битрейт 2.55 → 0.02 Mbit/s, `c_device`
38.5 → 7.0 %, `viewer_rtp_packets` −85 %, при **нулевых потерях**
(`loss=0`, `reorder=0`, `jb_late=0`, `keyframe_requests=0`,
`restarts=0`). Джиттер только MCU→bot — норма; ломает только bot→MCU.

**Корень (три слоя, все на приёме RTP).**
1. `RtpSource::accept` (`gateway_audio.rs`) отбрасывал пакет с `seq`
   «старше последнего» (`distance >= 0x8000`) как реплей — это верно для
   аудио (у микшера нет reorder-буфера), но для видео джиттер = легальный
   reorder. Пакеты терялись **до** депакетизатора и даже не считались во
   `video_rx_packets` (только `rejected_packets`).
2. `H264Depacketizer` (FU-A) требовал `seq == last+1`; первый же
   переставленный фрагмент давал `Err(())`, `self.fragment.clear()` — NAL
   (часто SPS/PPS/IDR) терялся целиком. В логе живой: `[h264] non-existing
   PPS 0 referenced`, `Error submitting packet to decoder: Invalid data`.
3. Приёмный цикл (`gateway_video.rs`) очищал `pending_access` при любой
   смене `timestamp` у пакета — при перемешанных кадрах AU уничтожался
   посреди сборки, маркер уже нечего было отдавать в декодер.

Итог: декодер получал рвань, кадров почти нет → композит чёрный →
энкодер группы отдаёт ~20 кбит/с «пустых» P-кадров. Потери и jitter-буфер
бота при этом нулевые — потому симптом и выглядел как «видео сломалось само».

**Фикс (только приём видео, аудио-путь не тронут по семантике).**
- `VideoReorderBuffer` в `gateway_video.rs`: окно `REORDER_WINDOW_PACKETS=32`
  пакета / `REORDER_MAX_DELAY=30 мс`. Пакеты копятся, выдаются строго по
  `seq` (`wrapping`-арифметика, дубликаты отбрасываются, опоздавшие за окно
  считаются `late`); реальная дыра (потеря) пропускается при переполнении
  окна или по таймауту 30 мс на 20-мс тике — один потерянный пакет не
  стопорит вход.
- `RtpSource::accept_reordered()` — включает приём «старых» seq только для
  видео-сессии (`spawn_video_media_bridge`); аудио остаётся строгим
  (дубль/реплей по-прежнему `None`).
- Депакетизатор получает уже упорядоченный поток, поэтому FU-A-склейка и

### 10.9 Замер декодеров 720p30: пул отклонён

**Протокол.** Каждое N — свежий изолированный инстанс (свои DB/порты/лог),
N×`scripts/bench/sipbot.py` 720p30 (тот же клиент, что в T2), прогрев 12 с,
замер дерева процессов MCU (parent + все потомки, включая `ffmpeg`) 12 с;
скрипт `/tmp/dec_measure3.py`, точки `/tmp/dm3/point-*.json`. Замер на
production **не** велся: `target-impl` бинарь, PID 1907913 не трогался.

| N | farm=on, ядра | ядро/сессия | farm=off, ядра | ядро/сессия |
|---|---|---|---|---|
| 1 | 0.697 | 0.697 | 0.688 | 0.688 |
| 5 | 2.079 | 0.416 | 3.954 | 0.791 |
| 10 | 3.708 | 0.371 | 8.074 | 0.807 |
| 20 | 7.129 | 0.356 | — | — |

**Арифметика.** Линейная подгонка farm=on (N=1..20):
`cores ≈ 0.40 + 0.337·N`; наклоны 5→10→20: +0.345/+0.326/+0.342 →
**0.34 ядра на декодер**, без обрыва/суперлинейности до 20.
Итого **20 декодеров ≈ 6.7–6.8 ядра** + ~0.40 ядра parent+1 энкодер/комнату;
наблюдаемое N=20 = 7.129 ядра (0.356/сессия). Сверка с T2:
`c_device` 0.389 ядра/устройство при N=10 — здесь N=10 = 0.371 (разница ~5 %
— netem + посекундный семплинг перфлаба). Разбивка при N=10:
`vks-server` 1.459 ядра (0.146/устройство), декодеры FFmpeg 1.732 (0.173),
энкодер 0.416 (0.042). Для сравнения farm=off N=10 = 8.074 ядра (0.807/сессия)
— shared-энкодер уже даёт 2.2×.

**Отказ от пула декодеров (мотивированный).** (1) Декодирование ингерентно:
у каждого участника свой поток, объединять/переиспользовать декодеры нечего —
пул не меняет число декодеров и не экономит ядра. (2) Зависимость линейна,
обрыва/суперлинейности вплоть до 20 нет; единственный реальный предел —
память/потоки, а не CPU. (3) Стоимость сопровождения пула > выигрыша (~0).
Решение: **пул не делать**, зафиксировать «измерено, отклонено».

**Ограничения.** Замер на пустом хосте (loadavg≈3), H.264 Baseline 720p30,
36-ядерная ВМ без cgroup-квоты; при 20+ устройствах в 16-ядерном cpuset
цифры на устройство те же, но поведение шедулера не измерялось.

### 10.10 self-view через ферму: арифметика и вынос в отдельную итерацию

**Что сейчас.** `self_view` включается **только из тестов**:
`McuEngine::set_self_view` (`engine.rs:1232`) вызывают `engine.rs:2001/2070`
и `gateway_video.rs:2521`. В проде путь включения отсутствует:
`isSelfViewEnabled`/`self_view` в call-string (`vks-admin/src/api_v3/call_strings.rs:105`)
только отображается в API-ответе и в движок не пробрасывается. При включённом
self-view `gateway_video.rs:592` уводит **все** сессии в per-session энкодер
(ферма не используется).

**Почему ферма не даёт экономии в общем случае.** `frame_for_viewer`
(`engine.rs:1060-1106`) для self-view строит **уникальный для зрителя** кадр:
его ячейка в общей сетке очищается, его камера рисуется в ячейку низшего
приоритета. Кадры публикующих зрителей попарно различны → нужно N энкодеров;
ферма даст N групп, т.е. те же N энкодеров (это уже зафиксировано в §4.6
как «физика, а не наш код»).

**Где экономия всё-таки есть.** У **непубликующих** зрителей `own_slot` нет —
`frame_for_viewer` возвращает общий `base`, т.е. кадр у них одинаковый. Сейчас
каждый такой зритель получает свой per-session энкодер; в ферме они разделят
**одну** общую группу. По замеру §10.9 (энкодер 720p30 = 0.416 ядра):
«2 публикующих + 8 смотрящих» → снимаются 7 лишних энкодеров =
7×0.416/10 ≈ **0.29 ядра/устройство**; «5+5» ≈ 0.17; «10+0» (профиль T2) = 0.
Побочный плюс: персональный кадр (клон 3 МиБ + блиты, H13/§2) уезжает
из-под `rooms`-лока — это лок-риск, не CPU.

**Объём и решение.** ~3–4 ч: ключ farm-группы с `viewer`-ом (базовая группа +
персональные), сборка персонального кадра вне `rooms`-лока, снятие fallback
`gateway_video.rs:592`, переписать `self_view_room_falls_back_to_per_session_encoder`,
инварианты «групп = числу уникальных кадров» и чистый retire, замер до/после
на «2 публикующих + 8 смотрящих», отчёт. Плюс проводка
`isSelfViewEnabled` → `engine.set_self_view` в `uas.rs`/`gateways.rs` —
вне write-scope media-core (зона proto-chain/Lead). Решение Lead:
self-view — **отдельная итерация** со сценарием «2 публикующих + 8 смотрящих»;
«Итерация 8» из готового (этот документ), новый бинарь не собирается.
