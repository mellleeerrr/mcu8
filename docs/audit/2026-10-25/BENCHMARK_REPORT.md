# Отчёт по живым замерам MCU (стенд 192.168.1.93)

Дата: 2026-10-25, 17:20–17:40 MSK. Автор: Lead. Все цифры — на **замороженном**
бинаре из `measure/PASSPORT.md` (sha256 `8ab81afd…`, `-C target-cpu=native`,
rustc 1.94.0), сервис `systemd --user vks-mcu` перезапущен, `/proc/<pid>/exe`
md5 == disk md5 (`d1c0656a…`). Измерения без изоляции CPU (MCU делит все 36
ядер с ботами) — это верхняя оценка «сколько CPU сожрёт», не проверка SLA по
задержке.

## 1. Метод

- **Контур, не PID.** Первичная метрика — `cpu.stat` cgroup контура
  `/user.slice/user-1000.slice/user@1000.service/app.slice/vks-mcu.service`
  (`usage_usec`), сэмпл 1 Гц. Это ловит `vks-server` + всех детей (FFmpeg,
  Python-сайдкар). `pidstat -p MCU` занижает в разы: видео-путь живёт в детях.
- **Бот** — `sipbot`/мой пробник: SIP INVITE (PCMU + H.264 Baseline 3.1
  `42c01f`) → 200 OK → ACK → RTP 20 мс аудио 50 pps + H.264 25 fps с
  корректным RTP-marker только на последнем пакете AU → приём композита →
  BYE. Один бот = один процесс.
- **Контент** — синтетика `testsrc2` (шум), т.е. **худший случай** по
  сложности кодирования/декодирования. Реальная камера даёт в 1.5–3 раза
  меньше CPU на кодек.
- Профиль комнаты в тесте — `1280×720@30`, 2048 kbps (из ffmpeg-cmdline
  энкодера), холст композита — 1920×1080.

### 2.1 Ёмкость по классам SLA (текущий код, худший контент)

`c_device = 1.40 ядра`; `N_per_core = U_limit / c_device`, U = 70/85/95 %.

| Класс | U | Устройств на **1 физ. ядро** | На 36 ядер |
|---|---|---|---|
| A (MOS≥4.3, loss<0.1 %) | 70 % | **0.50** | 18 |
| B (MOS≥4.0, loss<0.5 %) | 85 % | **0.61** | 22 |
| C (MOS≥3.6) | 95 % | **0.68** | 24 |

Т.е. **сейчас одно 720p30-устройство требует ~1.4 физического ядра**.
Формулировка «20 устройств на ядро» на текущем коде не выполняется ни для
одного класса. Это не оценка, а измерение; расхождение с таблицей media-core
(«сейчас 1.4–2.1 устройства/ядро») объясняется тем, что их модель не включала
энкодер-на-сессию и декодер в полном объёме (они сами это признали в §4.4).

### 2.2 Прогноз после плана O1+O3+O7 (без изменения кодека/декодера)

- O3 (resize 8.0 → 2.0–2.8 мс/кадр): −0.14 ядра/устройство.
- O1 (холст = профиль выхода, identity вместо resize): −0.20 ядра/устройство,
  композит 1080p (5.23 мс/тик) → ~2.3 мс для 720p.
- O7 (один энкодер на группу выхода): энкодер 0.31 на **комнату**, не на
  устройство.

Остаётся неустранимое: декодер 0.34 + RTP/пакетизация ~0.05 на устройство.
Для комнаты на 20 участников: 20×0.39 + (энкодер 0.31 + композит 0.1 + звук
0.05) ≈ **8.3 ядра** → **2.4 устройства/ядро** (класс C), на 36 ядрах ≈ 86
устройств. На реальном контенте (декодер ~0.12, энкодер ~0.15) — **~5
устройств/ядро**, на 36 ядрах ~180.

**Вывод для ТЗ:** 20 устройств/ядро с программным H.264-декодом недостижимы
(один только декодер 720p = 0.12–0.34 ядра). Реалистичный потолок на этом
железе после O1/O3/O7 — **2.5–5 устройств/ядро** на 720p30 (90–180 устройств
на 36 ядрах), при 1080p30 — в 1.5–2 раза меньше. Для 20/ядро нужен
аппаратный декод/энкод (VAAPI/NVENC) либо отказ от транскодинга (SFU-only).

## 3. Ёмкость по портам (не зависит от CPU)

- RTP-пул шлюзов `41000–41200` = **100 пар** (чётный RTP + нечётный RTCP,
  200 портов) = **50 видеозвонков** (2 пары на вызов: аудио + видео) или
  100 аудиовызовов. Захардкожен в `rtp_bridge.rs:22`, env-ключа нет → P0-патч
  (net-resilience, §5.A).
- ICE `43000–43100` = 101 порт (конфигурируемо `VKS_WEBRTC_PORT_MIN/MAX`).
- `MAX_PEERS_PER_ROOM = 2` (`webrtc_room.rs:33`) — браузерное плечо сегодня
  не MCU; для смешанной комнаты нужен отдельный проект (proto-chain §8.2).

## 4. Дефекты, найденные живым прогоном (не теорией)

### 4.1 Раскладка молча теряет участников сверх числа окон — P0
При 20 SIP-участниках в комнате с дефолтным пресетом (`preset_default_13`,
13 окон) в лог пошло `layout has no free geometry slot; participant stays
unassigned` (`engine.rs:605`), **7–8 участников не попали в композит**.
CPU при этом *упал* (11.98 ядра против 16.9 при 10 участниках), потому что
невидимых участников движок не декодирует/не композитит — то есть «20
устройств» на дефолтной раскладке физически не тестируются.
Причина: `gateways.rs:1627–1662` при `mode != "auto"` и пустом
`payload.preset` строит геометрию через `PresetId::equal(slot_count)`, где
`slot_count = max(assignments)+1`, а `assignments` пуст → **1 окно**; либо
явный `preset_default_13` даёт 13 окон без пейджинга.
Нужно: (а) авто-расширение геометрии при `participants > windows` (equal(N)),
(б) пейджинг страниц по 25 как в эталонах, (в) `mode=auto` по умолчанию для
импортированных комнат. Это функциональный блокер сценария «20+20+20», не
оптимизация.

### 4.2 Мой пробник давал 4× декодирование — исправлено (методологическая заметка)
Первая версия ставила RTP-marker на каждый NAL (AUD/SPS/PPS), из-за чего MCU
закрывал access unit 4 раза на кадр: декодер выдавал 116.7 fps вместо 25 и
жёг 1.21 ядра. После исправления marker-а — 25.0 fps и 0.34 ядра. Все цифры
§2 — после исправления. Это же объясняет ранние «2.3 ядра/устройство»:
не используйте их.

### 4.3 FFmpeg-диагностика в логе
`Invalid buffer size, packet size 118784 < expected frame_size 1382400`,
`missing picture in access unit with size 6` — появляются на teardown (`BYE`)
и при неполном AU. Не влияют на установившийся режим, но засоряют лог и
маскируют реальные ошибки; нужен фильтр «диагностика только при смене
состояния» + запрет подавать AU без слайса (`gateway_video.rs:415`).
