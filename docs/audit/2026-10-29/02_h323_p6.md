## §1. Вердикт

**Сегодня H.323 в VKS — это не «нативный Rust-стек», а Python-сайдкар на pycrate, обёрнутый в Rust.** Входящий вызов принимается Python-листенером (`h323_listener.py`, форк на вызов), исходящий — Python-сайдкаром (`h323_sidecar.py`, JSON-IPC). Rust умеет: поднять процесс, отдать ему порты, разобрать события, посадить участника в комнату, поднять RTP-мост. Rust **не умеет** ни одного байта Q.931/H.225/H.245.

Что реально работает по сигнализации: входящий Setup → CallProceeding+Connect (H.245 на отдельном TCP) → TCS/MSD → OLC аудио/видео → connected; исходящий — зеркально, с подтверждением `CONNECT и bidirectional media` (живой лог 2026-10-28 11:20:28, `uac.rs:356`). Кодеков в TCS ровно четыре: G.711A, G.711U, G.722, G.723.1 (`h323_audio.py:10-16`); видео — один generic H.264 baseline.

Чего нет вообще: fastStart, H.245 tunneling, reverse OLC, H.239 (второй поток), H.235/шифрования, Alerting от UAS, RAS/gatekeeper, динамических audio-PT, G.726/G.728/G.729/G.722.1/G.719/Opus/AAC-LATM в H.323, H.261/H.263/H.263+/H.265, Main/High H.264. «Нативный TCP 1720 на Rust» и «удаление `ffi.rs`» не сделаны; `ffi.rs` — mock на 279 строк с нулём вызовов вне крейта.

**Главная проблема — не список пробелов, а расхождение заявленного и сделанного.** `docs/DEVELOPMENT_PLAN.md:274-300` отмечает `[x]` «h323.rs — FFI-обёртка над H323Plus/OPAL», «G.711/G.729 → Opus», «H.263/H.264 → VP8/VP9», «FFI-граница… watchdog». В коде нет ни H323Plus, ни `unsafe`-FFI, ни таких транскодингов: `codec.rs` — mock-таблица, `call.rs` — mock-FSM, `ffi.rs` — счётчик тиков. Докстринг `lib.rs:1-22` повторяет миф про «FFI-границу H323Plus».

**Отдельно про медиа.** Живой лог 2026-10-25 содержит 133 «H.323 inbound participant landed» и 616 отказов RTP, из них 393 — по H.323. Это **не доказательство поломки продукта и не доказательство его работы**: отказы порождены самим стендом `scripts/bench/h323bot.py`, у которого TX-сокет сидит на эфемерном порту, а payload type берётся из профиля, а не из согласованного OLC (детали — §4, P0-1). Стенд нельзя использовать как приёмку; продуктовый риск асимметричного RTP при этом остаётся (§4, P1-1).

**Оценка: 3,3/10** против целевого состояния из запроса (обоснование — §10).
Отдельно проверен вопрос «кодогенерация из ASN.1 vs ручной PER» — он решает судьбу S1 в §7: см. **§12** (измерено: генерация 1,04 с / 550 490 байт, компилируется в 0 ошибок, но UPER-**декодер** rasn 0.29 падает `todo!()` на `BMPString`). Если оценивать только «то, что действительно работает», — 5/10: сигнальный минимум и один аудио-кодек-набор честно живы, но это Python, и подтверждённого e2e-медиа нет.

## §3. Спецификация сайдкара (что именно нужно перенести в Rust)

### 3.1. Процессная модель

- **Входящий:** `H323Uas::spawn` (`uas.rs:99-200`) запускает `python3 -u h323_listener.py` в отдельной process group (`process_group(0)`, `kill_on_drop`), конфиг — одна JSON-строка в stdin. Листенер слушает TCP 1720, на каждый вызов `fork`, родитель ведёт allowlist/CIDR, лимиты `MAX_CALLS/MAX_PER_IP/MAX_CHILDREN` (`h323_listener.py:1180-1224`). События — JSON-строки в stdout: `listening/incoming/connected/dtmf_digit/channel_closed/video_fast_update/failed/disconnected`; команды — JSON в stdin: `accept/reject/hangup/shutdown`. Rust читает события с лимитом 64 КиБ (`uas.rs:203-230`).
- **Исходящий:** `H323UacClient::dial` (`uac.rs:376-434`) запускает `h323_sidecar.py` с `target_ip/audio_port/video_port/call_id/call_ref`; ответы — те же JSON-события; `hangup` — единственная команда.
- **Медиа через Python не идёт никогда**: RTP-порты выделяет Rust (`PortPool`), передаёт сайдкару только как числа для OLC (`h323_sidecar.py:398`, `h323_listener.py:394`), а сам RTP-мост живёт в Rust (`gateways.rs:1520-1600`, `3630-3670`, `gateway_audio.rs`).

### 3.3. Входящий поток (UAS), как он есть

1. TCP accept (1720) → allowlist/CIDR → fork; ребёнок парсит Q.931 SETUP, H.225 `destinationAddress`/Q.931 called number → `called_alias`; эмитит `incoming` с `call_id`, `from_alias`, `remote_ip`.
2. Rust: `resolve_h323_room` (`gateways.rs:3167-3195`: uuid → DEFAULT_ROOM → `dtmf/route/alias/name` → room name) → allocate RTP-пары → `handle.accept(...)`.
3. Ребёнок: `CallProceeding(0x02)` + `Connect(0x07)` (оба с `h245Address` = свой ephemeral TCP), затем `accept()` H.245 от **того же IP**, что Q.931 (`h323_listener.py:715-720`).
4. H.245: TCS+MSD → по Ack — OLC аудио (preference G.722→G.711U→G.711A→G.723), при `video_port` — OLC видео generic H.264 + H.241; Ack с локальными портами; при входящем OLC пира — adopt кодека, при отказе — следующий кандидат (канал 3, `h323_listener.py:226-248`).
5. `connected` — только когда `signal_connected && tcs_acked && master_determined && incoming_audio && remote_audio` (`h323_sidecar.py:599-611`); видео-«камера выключена» не рвёт аудио (8 с grace, `:603-611`).
6. Медиа: Rust-мост; DTMF — только UII; ReleaseComplete — reason-токен наверх.

### 3.4. Исходящий поток (UAC)

Setup (bearer `0x88 0x93 0xa5` при видео, иначе `0x88 0x90 0xa5`; called number из alias, `h323_sidecar.py:306-313`) → Alerting (эмит `ringing`) → Connect (h245Address обязателен, IP обязан совпасть с target) → H.245 TCS+MSD → OLC → `connected` (требует `incoming_audio && remote_audio`) → медиа → `hangup` → endSession + ReleaseComplete. Видео: dynamic PT 96 (H.264), H.241 maxBitRate 5120/level 71 по умолчанию; отказ видео не рвёт аудио.

### 3.5. Инварианты, которые нельзя переносить «как есть»

| Инвариант сейчас | Почему это дефект | Как надо в Rust |
|---|---|---|
| `sessionID` аудио = 1, видео = 2, иначе reject (`h323_sidecar.py:422-423`) | H.245 разрешает 0..255; Polycom в фикстуре использует 1/2, но это coincidence, не правило | брать из OLC и запоминать per-channel; не пинить |
| ожидаемый RX-адрес = `mediaChannel` из ACK | `mediaChannel` в ACK — адрес **приёма** пира (`h245.asn` `H2250LogicalChannelAckParameters`), а не источник его RTP | TX — на ACK-адрес; RX — латч по IP+SSRC (см. P1-1) |
| только статические audio-PT (`h323_audio.py:1-8`) | G.726/Opus/AAC-LATM возможны только с dynamic PT | поддержать `dynamicRTPPayloadType` 96..127 для аудио |
| цель — только IPv4-литерал (`uac.rs:269-300`) | нет DNS/SRV | резолв имени + запрет редиректа на чужой IP |
| H.245 только с IP == TCP-peer | ломает NAT/gatekeeper | разрешить advertise другого IP при явной политике |
| G.723 только 1 SDU/пакет | часть терминалов пакует 2–3 | поддержать N SDU (мост уже умеет 30 мс) |
| Alerting не отправляется | вызывающий не слышит КПВ | отправить Alerting после accept |

## §4. Дефекты (P0/P1/P2) с минимальным фиксом и тестом

### P0-1. Стенд H.323 невалиден: PT и source-port не соответствуют согласованию

**Симптом.** Живой лог 2026-10-25: 133 входящих H.323-вызова, 616 отказов RTP; из них 393 — H.323: 240 с `expected_payload=9 received_payload=0` и 153 с `expected_payload=9 received_payload=9` (лог `vks_server.log:969-970` — landing и первый отказ, `:1004` — отказ при совпадающем PT; старый бинарь, сообщение до `8116855`). Первый отказ приходит через 0,4 мс после «participant landed» — пакет уже лежал в сокете.

**Причина — стенд, а не продукт.** `scripts/bench/h323bot.py`:
- `self.pt = 9 if self.codec == "g722" else 0` (`:232`) — PT берётся из профиля, а не из `remote_audio_payload_type`, который бот получает в событии (`:322`) и пишет только в отчёт;
- RX-сокет биндится на анонсированный `rtp_port` (`:354-360`), а TX-сокет — на **эфемерный** порт (`:362-365`), поэтому источник RTP никогда не равен `mediaChannel`, который бот сам отдал в ACK;
- как следствие: профиль `h323-m1` (G.711U) шлёт PT 0 при ожидаемом 9 → 240 отказов; профиль `g722` шлёт PT 9 с чужого порта → 153 отказа. Ни один прогон не мог дать валидную картину медиа.

**Минимальный фикс.** В боте: `pt` из `event["remote_audio_payload_type"]` (и `remote_video_payload_type` для видео), один сокет на анонсированный порт (или bind TX на `rtp_port`), в отчёт — `audio_rx_packets > 0` как обязательный критерий; в `run_matrix.sh` — падать при `rejects > 0`.

**Тест.** Один прогон 20 с: `rejected_packets == 0` на шлюзе и `rx_packets > 0` у бота; негативный контроль — профиль с заведомо чужим PT должен дать ровно 1 отказ и упасть по критерию.

### P0-2. H.235/шифрование молча игнорируется (downgrade безопасности)

**Симптом.** Терминал, требующий шифрование (`h245SecurityMode`/`tokens`/`cryptoTokens` в Setup/Connect), либо получит отказ без объяснения, либо — если он не enforcing — «успешный» вызов в plaintext. В коде нет ни чтения, ни записи security-полей: `grep H235` по рабочим `*.py` = 0; Setup/Connect собираются без `tokens` (`h323_sidecar.py:303-333`, `h323_listener.py:696-711`); `h245SecurityMode` не разбирается нигде.

**Минимальный фикс (fail-closed, без реализации шифрования).** Разбирать `h245SecurityMode` и `tokens/cryptoTokens`; если запрошено что-то кроме `noSecurity` — `ReleaseComplete` с cause «security denied» (или `releaseCompleteReason=securityDenied`) + ERROR-лог с алиасом и IP. Не притворяться, что вызов защищён.

**Тест.** Golden Setup с `h245SecurityMode=...` (сгенерировать pycrate) → ожидать ReleaseComplete; Setup без security → Connect как раньше.

### P1-1. RX-источник пинится по адресу приёма пира

**Симптом.** `RtpSource::accept` отбрасывает пакет, если `source != target` (`gateway_audio.rs:622-628`); `target` для входящего H.323 — `remote_ip:remote_audio_port` из события connected (`gateways.rs:3521-3532`, `3653-3661`), а `remote_audio_port` — это `mediaChannel` из OLC ACK, т.е. порт **приёма** пира. H.323-терминал, отправляющий RTP с другого порта (или через NAT), не даёт ни одного декодированного пакета; `source_latch=false` (`gateways.rs:3661`, `1575`) — политика не менялась после диагностического фикса `8116855`.

**Минимальный фикс.** В `RtpSource` добавить `latch_ip: Option<Ipv4Addr>`: принимать пакет, если IP совпадает с запиненным и PT валиден, независимо от порта; после первого пакета зафиксировать порт+SSRC (дальше — строго). TX (egress) не трогать — он остаётся на ACK-адрес. Это же применимо к исходящему H.323 (там та же конкатенация).

**Тест.** Unit: пакет с тем же IP и другим портом — принят, `egress` не изменился; другой IP — отброшен; смена SSRC после латча — отброшена. Live: асимметричный peer (исправленный бот) — `audio_rx_packets > 0`.

### P1-2. Нет fastStart и H.245 tunneling

**Симптом.** `h245Tunneling: False` (`h323_sidecar.py:303`); `fastStart` не заполняется ни в Setup, ни в Connect; входящий `fastStart`/`h245Control` не разбирается. Часть терминалов (упрощённые / NAT-дружественные) без этого не соединяется или соединяется без медиа.

**Минимальный фикс.** Кодировать `fastStart` как `SEQUENCE OF OCTET STRING` (готовые OLC-байты уже есть — см. §7), разбирать входящий `fastStart` (декодировать OLC и принять порты), `h245Tunneling=true` с `h245Control` (TPKT внутри Q.931) для одной из сторон. Начать с fastStart (дешевле), tunneling — вторым.

**Тест.** Golden Setup с fastStart (pycrate) → Connect с fastStart; byte-parity OLC внутри; интеракция с Polycom-фикстурой (у неё fastStart нет — негативный контроль).

### P1-3. reverse OLC и sessionID

**Симптом.** Явный reject при `reverseLogicalChannelParameters` и при `sessionID != 1/2` (`h323_sidecar.py:422-423`, `h323_listener.py:411-412`). Шлюзы/MCU часто открывают reverse-канал (предложение «принимай на этот порт»), особенно для видео.

**Минимальный фикс.** Поддержать `reverseLogicalChannelParameters` (dataType+multiplexParameters; ACK содержит наш адрес); sessionID — из параметров, не константа.

**Тест.** pycrate-вектор reverse OLC → ACK с корректным `forwardLogicalChannelNumber`; фикстура Polycom (sessionID 1/2) остаётся зелёной.

### P1-4. H.245-адрес только из CONNECT + жёсткая привязка к target IP

**Симптом.** `h323_sidecar.py:355-371` читает `h245Address` только из CONNECT и требует `ip == target_ip`; CallProceeding/Alerting игнорируются. Шлюз, отдающий H.245-адрес в CallProceeding (легально), не соединится.

**Минимальный фикс.** Запоминать первый валидный `h245Address` из Alerting/CallProceeding/Connect; подключаться к нему; политику «чужой IP» оставить, но с явным логом и env-переключателем.

**Тест.** Golden CallProceeding с h245Address → sidecar подключается; чужой IP → отказ с внятным reason.

### P1-5. DTMF в сторону H.323-терминала отсутствует

**Симптом.** Для H.323 `dtmf_payload_type=None` (`gateways.rs:1436`), а в мосте `else { dtmf.clear(); }` (`gateway_audio.rs:462-463`) — цифры из комнаты/браузера молча выбрасываются. Сайдкар не умеет `dtmf` (только `hangup`, `h323_sidecar.py:649-664`), H.245 UII не отправляется.

**Минимальный фикс.** Команда `dtmf` в IPC → H.245 `UserInputIndication` (`signal`/`alphanumeric`); в Rust — не чистить очередь при отсутствии PT, а отдавать её в H.323-канал (через событие/команду). Для терминалов, присылающих RFC 4733 в RTP, — согласовать telephone-event PT (сейчас такой PT просто отбрасывается как чужой).

**Тест.** Golden UII-байты (signal digit, alphanumeric) + unit на `dtmf.clear()`-ветку.

### P1-6. 1720 без аутентификации, вход по имени комнаты

**Симптом.** bind `0.0.0.0:1720` (`main.rs:428-430`), allowlist только по CIDR (live: `127.0.0.1/32,192.168.1.0/24`), комната выбирается по `called_alias`/`DEFAULT_ROOM`/имени (`gateways.rs:3167-3195`). Любой хост в разрешённой сети, знающий имя комнаты, входит в неё; пароля/сертификата нет.

**Тест.** `resolve_h323_room` с именем комнаты при выключенном матчинге → None; allowlist-тест уже есть (`test_h323_listener.py:289`).

### P1-7. Статус H.323 врёт про active calls

## §5. Оценка примера H.235/Q.931 заказчика

> В дереве кода примера нет (`grep derive_h235|x25519|HMAC` = 0), поэтому оценка — по описанию из задания: `derive_h235_srtp_key` на X25519 + HMAC-SHA256, ключ кладётся «как есть» в Q.931 Connect.

### 5.1. Что говорит H.235

- Ключ передаётся **ASN.1-структурами**: `ClearToken` (tokenOID, `dhkey DHset`, `eckasdhkey ECKASDH`, challenge, certificate, `h235Key`, profileInfo, `dhkeyext`) и `CryptoToken` (зашифровано/подписано/хеш); `H235Key ::= CHOICE { secureChannel KeyMaterial(BIT STRING 1..2048), sharedSecret ENCRYPTED{...}, certProtectedKey SIGNED{...}, secureSharedSecret V3KeySyncMaterial, secureChannelExt KeyMaterialExt }` (`python/schemas/h235.asn:244-252`).
- Для SRTP критично: `V3KeySyncMaterial` содержит **отдельные** `algorithmOID`, `paramS` (IV), `encryptedSessionKey`, `encryptedSaltingKey`, `clearSaltingKey`, `keyDerivationOID`, `genericKeyMaterial` (`h235.asn:290-306`). То есть мастер-ключ и **соль** — разные поля с явными OID; «один HMAC-выход = SRTP-ключ» в модели H.235 не выражается.
- H.245 несёт ключ в `EncryptionSync` (поле `h235Key` + `synchFlag`, привязанный к dynamic PT) внутри OLC/OLC-Ack (`h245.asn:1736`, `2274`), а обновление — `EncryptionUpdateCommand`/`encryptionUpdate` (`h245.asn:3645+`). `MediaEncryptionAlgorithm` — это OID/nonStandard (`h245.asn:1450-1457`), а не «X25519».
- Аутентификация: DH сам по себе не аутентифицирован; H.235 использует подписанные/сертификатные токены (`AuthenticationMechanism`, `certProtectedKey`, `H235CertificateSignature`). X25519+HMAC без подписи — MITM.

### 5.2. Что не так с примером (по пунктам)

| Утверждение примера | Реальность |
|---|---|
| «X25519-ключ — это H.235» | В H235 ASN.1 нет X25519: есть `DHset` (finite-field modulus/base/public) и `ECKASDH` с EC-точками (`h235.asn:41-80`); 32-байтовый X25519-ключ нельзя закодировать ни в один вариант `H235Key` без изобретения нового OID |
| «HMAC-SHA256 даёт SRTP-ключ» | RFC 3711 требует master key + salt под конкретный crypto-suite; H.235.8 задаёт KDF с label/итерациями; в V3KeySyncMaterial соль — отдельное поле (`encryptedSaltingKey`/`clearSaltingKey`), плюс `keyDerivationOID`. Один HMAC этого не покрывает |
| «Кладём в Q.931 Connect как есть» | В `Connect-UUIE` нет произвольного поля: есть типизированные `tokens`/`cryptoTokens` (`h225.asn`, Connect-UUIE) и `fastStart` (Sequence of OLC-PDU). Сырые байты либо сломают PER-декодирование, либо будут проигнорированы. Плюс TCP 1720 — открытый текст: ключ виден в сети |
| «Это SRTP» | SRTP требует шифрования медиа согласованным ключом; без H.245 `EncryptionSync`/`h245SecurityMode` пир не узнает, что медиа зашифровано, и не сможет расшифровать |
| «Совместимо с терминалами» | Ни один H.323-терминал не реализует X25519-HMAC-схему; интероп 0 % с Polycom/Cisco/TrueConf, если у них нет ровно этого proprietary-профиля |

### 5.3. Вердикт по примеру

**Пример непригоден как H.235 и небезопасен как «SRTP-схема».** Это не «почти H.235», а другой протокол: нет ASN.1-носителя, нет OID, нет KDF/соли, нет аутентификации, нет привязки к H.245-каналу, ключ в открытом Q.931. Использовать его в продукте нельзя; если заказчик настаивает — это отдельный proprietary-профиль для двух концов, которые его реализуют, и его нельзя называть H.235/SRTP.

**Что делать вместо:** (а) если целевые терминалы умеют **H.235.11/DTLS-SRTP** — `DTLSSecurityCapability` (`h245.asn:362-369`, fingerprint в setup/connectionInformation) и переиспользование DTLS из `vks-media-sfu` (str0m) — самый дешёвый честный путь; (б) иначе **H.235.8**: ClearToken/DHset или ECKASDH + сертификат, `EncryptionSync` в OLC с `synchFlag` = dynamic PT и `h235Key`; (в) до этого — fail-closed (P0-2), а не тихий plaintext.

## §11. Спорные тезисы (для дискуссии с Lead)

**ТЕЗИС 1. «H.323-стек нативный на Rust» — неверно.**
ДОКАЗАТЕЛЬСТВО: единственный исполняемый стек — Python (`ps`: `h323_listener.py`; `uas.rs:99-200`, `uac.rs:376-434`); Rust-крейт — spawn + JSON + mock (`ffi.rs` 279 строк, 0 вызовов; `call.rs` mock-FSM). `lib.rs:1-22` называет это «FFI-границей H323Plus», но H323Plus не линкуется (`grep bindgen/cxx` пуст).
ЧТО ПЕРЕУБЕДИТ: `ldd target/release/vks-server | grep h323`, вызовы `H323PlusBridge::call` вне тестов, или PR, удаляющий `python/`.

**ТЕЗИС 2. «ffi.rs — это FFI-граница, её нельзя просто удалить».**
ДОКАЗАТЕЛЬСТВО: `ffi.rs` не содержит `unsafe`, `extern`, `#[link]`; `H323PlusBridge` — обычная структура, `Watchdog` считает тики; публичные символы крейта никем не используются (кроме тестов крейта).
ЧТО ПЕРЕУБЕДИТ: любой внешний потребитель `vks_gateway_h323::ffi::*` (такого нет) или появление реальной линковки.

**ТЕЗИС 3. «H.323 работает, медиа идёт — вот лог».**
ДОКАЗАТЕЛЬСТВО: 133 входящих и 616 отказов RTP (393 H.323: 240 PT-несовпадение, 153 при совпадающем PT) — но стенд `h323bot.py` шлёт PT из профиля (`:232`), а не из согласования, и TX с эфемерного порта (`:362-365`). Значит лог измеряет дефекты стенда; e2e-медиа не подтверждён ни в плюс, ни в минус.
ЧТО ПЕРЕУБЕДИТ: прогон исправленного стенда с `rejects == 0 && rx > 0` или живой терминал с слышимым звуком.

**ТЕЗИС 4. «Пиннить RX по `mediaChannel` из OLC ACK — правильно».**
ДОКАЗАТЕЛЬСТВО: `mediaChannel` в `H2250LogicalChannelAckParameters` — адрес **приёма** пира; TX туда корректен, RX оттуда — нет. Код латчит только при `latch=true` и до первого SSRC (`gateway_audio.rs:622-628`), а для H.323 `source_latch=false` (`gateways.rs:3661`). Асимметричный RTP (NAT, шлюзы) даёт нулевое аудио.
ЧТО ПЕРЕУБЕДИТ: спецификация H.245 (ACK = receive address) + терминал, отправляющий с другого порта; или исправленный стенд, где источник совпадает.

**ТЕЗИС 5. «Пример H.235 заказчика почти готов, надо только вставить в Connect».**
ДОКАЗАТЕЛЬСТВО: H.235 — ASN.1 (`ClearToken`/`H235Key`/`EncryptionSync`, `h235.asn:244-306`), с отдельными `algorithmOID`/`keyDerivationOID`/`clearSaltingKey`; X25519 там нет, произвольного поля в Connect-UUIE нет, ключ в Q.931 — открытым текстом, аутентификации нет.
ЧТО ПЕРЕУБЕДИТ: OID/структура H.235 с X25519 (в стандарте отсутствует) или успешный интероп с терминалом, реализующим ровно эту схему.

**ТЕЗИС 6. «G.729 A/B двунаправленно достижим».**
ДОКАЗАТЕЛЬСТВО: `oxideav-g729` — register-only каркас; FFmpeg 8.x декодирует G.729, но не кодирует (`ffmpeg -encoders`; `transcoder_runtime.rs:85` — `encoder=false`); свободного энкодера без GPL/лицензии нет.
ЧТО ПЕРЕУБЕДИТ: рабочий энкодер в дереве (bcg729 с лицензией или покупной) + bit-exact тест.

**ТЕЗИС 7. «Python можно удалить за неделю».**
ДОКАЗАТЕЛЬСТВО: паритет требует PER-рантайма (1,1–1,3 тыс. LOC), H.225 (0,8–1 тыс.), H.245 (1,5–1,8 тыс.), FSM/транспорта (1,4–1,7 тыс.), интеграции (0,4–0,6 тыс.) — 5,2–6,4 тыс. LOC и 18–24 дня, плюс golden-паритет. Удаление без паритета = потеря единственного работающего стека.
ЧТО ПЕРЕУБЕДИТ: готовый Rust-крейт H.225/H.245 (его нет на crates.io: `q=h323` → 0, `q=h225` → 0) или генерация из ASN.1 без ручного PER.

**ТЕЗИС 8. «FastStart опционален, можно жить без него».**
ДОКАЗАТЕЛЬСТВО: целевые терминалы (Polycom/Cisco/TrueConf) в большинстве умеют и медленный путь, но часть настроек/шлюзов требует fastStart; без tunneling+fastStart теряется совместимость с «упрощёнными» endpoint’ами. Приоритет ниже H.235 fail-closed, но в целевой матрице он есть.
ЧТО ПЕРЕУБЕДИТ: матрица терминалов заказчика с указанием «fastStart обязателен/нет»; интероп-тест без fastStart на всех целевых моделях.

### 12.2. Откуда 98 ошибок (диагноз «импорты не сгенерированы» — неточен)

`rasn-compiler` 0.16 **дедуплицирует одноимённые top-level типы между модулями** и эмитит
определение только в первом модуле. В связке H.225/H.235/H.245 таких имён ровно три:

| Тип | Где определён | Совпадают ли | Последствие |
|---|---|---|---|
| `NonStandardParameter` | `h225.asn:685`, `h235.asn:14`, `h245.asn:165` | структура идентична | безопасно; 98 ошибок снимаются одним wildcard |
| `Password` | `h235.asn:9` (**BMPString** 1..128) vs `h245.asn:3259` (**OCTET STRING** 1..32) | **нет** | wildcard даёт неверный тип в редких H.245 PDU |
| `Params` | `h235.asn:205` vs `h245.asn:4086` | **нет** | то же |

Шаги проверки (каждый — отдельный `cargo check`): 98 → 8 → 3 → **0** ошибок.
`Config { default_wildcard_imports: true }` (`rasn-compiler-0.16.0/src/generator/rasn/mod.rs:50-53,178-183`)
даёт ровно то, что эмулировано пост-обработкой (`use super::<module>::*`). **Но CLI 0.16 не
имеет флага для этой опции** (`rasn_compiler_cli --help`: только `-d/-m/-o/--stdout/--no-output/-b`),
т.е. нужен `build.rs` с библиотечным API rasn-compiler, а не вызов CLI.
