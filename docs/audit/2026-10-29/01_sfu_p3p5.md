## §1. Вердикт

1. **SFU существует в двух несовместимых плоскостях.** «Легаси»-плоскость (`E` + `F` + `U`,
   plaintext RTP, порт `0.0.0.0:40000`) — учебная модель с **нулём** продакшн-потребителей у
   аналитики (BWE/simulcast/congestion). «Реальная» плоскость (`W` + `R`, str0m 0.24.1) — настоящий
   ICE/DTLS/SRTP, но **≤2 пира на комнату**, только Opus+VP8, frame-level re-payload и **без
   keyframe-gate**.
2. **Из 11 пунктов целевого состояния реально есть 3** (str0m-транспорт; TWCC/REMB+BWE+Pacing на
   браузерном плече; NACK/RTX на нём же), **2 — частично/фиктивно** (RTCP, PT-rewrite),
   **6 — отсутствуют** (3-слойный simulcast, SVC, XOR-FEC, адаптивный JB, CSS/Taffy, P5-мост).
3. **Заявка «`ServerHello.room_mode` — единственный источник истины» ложна.** Значение в
   `ServerHello` — статический i32, посчитанный **один раз на старте** из глобального режима;
   per-room override и рантайм-переключения до него не доходят (`H:285`, `M:249-263,343-370`,
   `A:129`, `L:1212-1222`).
4. **P5 не «недоделан», а явно запрещён** девятью guard'ами (`L:862-877`, `G:763,836,1208,1300,1548,2692,3582`)
   плюс принудительный `evict` браузеров при переключении в MCU (`AM:150-158`, `AR:135-137`).
   Это добросовестная инженерия для отсутствующей возможности — и именно она подлежит замене.
5. **Оценка зоны: 3.5/10.** Транспорт и композитор — взрослые; SFU-часть целевого состояния —
   каркас с двумя рабочими узлами (str0m, MCU-композитор) и отсутствующей связкой.

## §3. Дефекты по severity

Формат: симптом → причина → file:line → минимальный фикс → тест.

### P0

#### P0-1. «SFU-комната» — это вызов 1:1; третий браузер отвергается
- **Симптом.** В комнате максимум 2 WebRTC-пира (`R:33`), третий получает `WebRtcError::RoomFull`
  (`R:167,222`), в метрике `webrtc_offers{result="room_full"}`. Звонок «3 участника» невозможен.
- **Причина (архитектурная, признана в самом коде).** Egress-состояние — **один mid на kind**
  (`R:30-32`: «More publishers would interleave unrelated RTP clock domains into the same egress
  mid»), а кадры паблишера B пишутся в тот же `mid_for_kind(audio/video)` (`R:513-519`,
  `W:235-249`). Два истока в один `StreamTx` = склейка двух clock domains и seq-пространств.
  Ограничение не «бюрократическое», а следствие отсутствия mid-per-source.
- **Минимальный фикс.** Индекс `(publisher, kind) → egress Mid` + SDP-реоффер при появлении нового
  паблишера (`Rtc::sdp_api().add_media(MediaKind, Direction::SendOnly)`) и подписка на него.
  Инкрементальный вариант без реоффера: N предсозданных «пустых» video-mid в answer
  (заголовок `a=inactive`), включаемых по мере появления паблишеров — до 7–8 участников без
  реоффера. Это же снимает `MAX_PEERS_PER_ROOM` полностью.
- **Тест (детерминированный).** 3 «фейковых» пира через `mpsc` (как `R:749-757`), публикатор A
  шлёт 5 VP8-кадров → каждый из B и C получает 5 `Write` в **свой** mid; seq в каждом mid
  монотонен и не перемешивается; `peer_count == 3`.

#### P0-2. Нет keyframe-gate: новый подписчик получает P-кадры
- **Симптом.** При входе в комнату браузер до первого IDR получает дельта-кадры → чёрный экран,
  «артефакты», ошибки декодера; при переполнении очереди (`R:434-439`) — то же самое, но
  «навсегда», пока паблишер не пришлёт IDR.
- **Причина.** `forward()` копирует **любой** `MediaData` всем подписчикам (`R:416-448`); PLI
  запрашивается «на всякий случай» при accept (`R:241-257`), но состояние «ждём IDR» нигде не
  хранится и не проверяется. `MediaData.codec_extra` (флаг keyframe) не используется.
  В MCU-пути такой гейт **есть** и работает (`G:776-782`: `seen_keyframe`), т.е. паттерн в
  проекте уже принят — в SFU он просто не перенесён.
- **Минимальный фикс.** На `PeerHandle` — `waiting_idr: HashSet<Mid>`; при подписке/replace/дропе
  очереди ставить флаг; в `forward` для видео пропускать кадры `!is_keyframe` при установленном
  флаге; снимать флаг на первом keyframe; PLI — адресно `(publisher, mid)`, с коалесингом ≥300 мс.
- **Тест.** Паблишер шлёт `P,P,P,IDR,P`; подписчик, подключённый после первого P, получает ровно
  `IDR,P` (2 Write), а не 5; счётчик `frames_dropped{reason="waiting_idr"}` = 3.

#### P0-3. `ServerHello.room_mode` не является источником истины
- **Симптом.** Клиент после per-room переключения в MCU видит в `ServerHello` `SFU` и рисует
  N треков вместо композита (или наоборот). Переключение «на лету» доезжает только отдельным
  `RoomModeChanged`, а `ServerHello` остаётся враньём на весь сеанс.
- **Причина.** Доккомментарий `A:125-127` прямо декларирует: «Единственный источник истины для
  `RoomServerEvent` и `ServerHello.room_mode`» — но `ServerHello` собирается из `HandlerConfig`
  (`H:285`), который этот источник не читает. Итого 6 мест, из них `ServerHello` — самое инертное:
  1. `H:282-290`: `room_mode: self.config.room_mode` — i32 из `HandlerConfig`;
  2. `M:249-263`: `initial_mode` из `config.default_room_mode`, применённый к `state.mode` **на старте**;
  3. `M:343-370`: `proto_room_mode` из `effective_mode` **на старте** → `.with_room_mode(...)` (навсегда);
  4. `A:120-130`: `ModeState::effective_mode` — живой, per-room, используется для **решений**
     (`L:840-846`), но не для `ServerHello`;
  5. `E:364-366`: `SfuEngine::mode()` — константа `RoomMode::Sfu` (и `switch_room_mode` не вызывается
     никогда: `grep -rn switch_room_mode crates/` → 2 теста);
  6. `L:1129-1137`: `create_room` в оба движка с **захардкоженными** `Sfu` и `Mcu` для одной комнаты.
- **Минимальный фикс (обратный ходу, но единственно верный).** Сделать режим **производным**:
  `room_mode = if room_has_gateway_participant { Mcu } else { Sfu }` (+ явный per-room override как
  исключение), вычислять его в одном месте (`ModeState::effective_mode`, уже есть) и передавать в
  `HandlerConfig` **на соединение**, а не на процесс: `handler_config.room_mode = state.mode...`
  в `ws_handler` (`L:610-611`). Плюс убрать `switch_room_mode`/`mode()` из `MediaEngine`-контракта
  (см. §5) — движок не должен «знать» режим, он должен уметь оба выхода.
- **Тест.** `ModeState` с override `Mcu` для комнаты R; `ClientHello` в R → `ServerHello.room_mode == MCU`;
  после `POST /rooms/R mode=SFU` — новое соединение получает `SFU`, старое получает
  `RoomModeChanged{epoch+1}`; `switch_epoch` монотонен. Тест на 3 источника сразу (не по одному).

#### P0-4. Гибридная комната запрещена (P5 недостижим)
- **Симптом.** Браузер в комнате с SIP/H.323 получает `Error{code:"webrtc_gateway_room_unsupported"}`
  (`L:866-874`); обратный порядок — SIP INVITE получает `486 Busy Here` (`G:2692-2700`),
  H.323 — `hangup` (`G:3582`), исходящий дозвон — ошибку (`G:1300`, `G:1548`); при переключении
  комнаты в MCU браузеры **принудительно выкидываются** (`AM:150-158`, `AR:135-137`).
- **Причина.** Нет моста «SRTP-кадры ↔ пиксели композитора», поэтому половинчатая комната
  (браузер видит терминал, терминал браузера — нет) была бы хуже отказа. Guard'ы сделаны
  аккуратно: под `admission()`-локом, с двойной проверкой и защитой от гонки — это лучшая часть
  дизайна, и её надо **заменить**, а не «убрать».
- **Минимальный фикс.** Не удалять guard'ы, а инвертировать: разрешать, если мост доступен
  (`bridge_available()` — есть VP8/H.264 decode+encode worker), иначе оставить отказ.
  Порядок: сначала §6 P5-шаги 1–4, потом снятие guard'ов (шаг 5).
- **Тест.** Детерминированный: str0m-клиент (как в `W:456-620`) публикует синтетический AU →
  в `McuEngine` появляется кадр участника (`set_participant_frame` вернул true) → композит
  кодируется → str0m-клиент получает ≥1 `MediaData` видео; SIP-заглушка (`land_gateway_participant_in_room`)
  при этом не отклоняется.

### P1

#### P1-1. Вся «умная» аналитика SFU не вызывается из продакшна
- **Симптом.** BWE/выбор слоя/лестница деградации не влияют ни на один пакет. Комната на 500 кбит/с
  получает все пакеты всех слоёв.
- **Причина.** `E:131-157 on_feedback` — 0 вызовов (`grep -rn on_feedback crates/ | grep -v vks-media-sfu/` → пусто);
  `E:170-186 route` — только тесты; `E:229-340 route_udp_packet` не смотрит ни на `subscribers`,
  ни на `congestion`, ни на `simulcast` — только PT-rewrite. `sim.changed` (`E:139-149`) отбрасывается.
- **Минимальный фикс.** Удалить (см. §5), а на реальном пути использовать `WebRtcAction::Bitrate`
  (`W:343-350`) → `set_desired_bitrate` (уже есть) и `Writer::set_max_bitrate` для cap'а оператора.
- **Тест.** Записать последовательность `Bitrate(2M), Bitrate(300k)` в `run_peer` → в `rtc` cap
  изменился (проверяется через `Rtc` stats/`writer`-очередь), и ни один кадр не потерян.

#### P1-2. Ошибка записи кадра убивает транспорт подписчика
- **Симптом.** Если у подписчика нет PT, соответствующего `params` паблишера (или mid не найден),
  `write_media_matched` → `Err(UnknownMid)`; в `run_peer` это `break` (`R:513-520`) → peer
  закрывается, WebSocket-сессия остаётся, медиа умирает до следующего реоффера.
- **Причина.** `R:516-519`: `actions = match ... { Err(_) => break }` — ошибка уровня «один кадр»,
  обработанная как ошибка уровня «сессия».
- **Минимальный фикс.** `continue` + инкремент `WEBRTC_FRAMES_DROPPED{reason="pt_mismatch"}`;
  `break` оставить только для `WebRtcError::Rtc`/`Io`.
- **Тест.** Подписчик с answer, где нет VP8 (искусственно) → peer остаётся живым,
  `peer_count` не меняется, метрика растёт.

#### P1-3. PLI веером по всем паблишерам, а не по треку
- **Симптом.** PLI от одного подписчика уходит **всем** видео-паблишерам комнаты
  (`R:397-414`), каждый браузер генерирует IDR; при 4+ участниках — PLI-шторм и просадка битрейта.
  Плюс `request_keyframe` шлётся в mid, который у пира может быть `recvonly` (`R:601-604`,
  ошибка только логируется).
- **Причина.** Нет индекса `(publisher, mid) → подписчики`; `targets_for` фильтрует только по kind.
- **Минимальный фикс.** PLI адресно: `forward` знает `from` и `data.mid` → `request_keyframe_from(room, from, mid)`;
  коалесинг по `(room, publisher, mid)` — не чаще 1/300 мс.
- **Тест.** 3 пира, PLI от C → ровно один `RequestKeyframe` у A (видео), у B — ноль.

#### P1-4. Легаси-STUN не аутентифицирован и несовместим с браузером
- **Симптом.** Ответ на Binding Request строится без `MESSAGE-INTEGRITY` и `FINGERPRINT`
  (`U:295-339`), а запрос принимается при **любом** непустом `USERNAME` (`U:173-184`).
  `is_stun_request_authenticated` (правильная проверка ufrag) вызывается только в тестах (`U:844-845`).
- **Причина.** Проверка аутентичности написана, но не подключена к циклу; ответ собирается вручную.
- **Минимальный фикс.** Вызывать `is_stun_request_authenticated(req, expected_ufrag)` перед ответом;
  либо (предпочтительно) удалить легаси-STUN вместе с легаси-путём (§5), т.к. ICE на реальном пути
  делает str0m.
- **Тест.** Запрос с чужим ufrag → `packets_dropped += 1`, ответа нет; с правильным → ответ есть,
  и в нём есть `MESSAGE-INTEGRITY` (если фикс с интеграцией).

#### P1-5. `bwe.rs`: контракт физически не позволяет измерить congestion
- **Симптом.** Оценка = «прибыло байт / прошло времени» (`B:150-166`), т.е. throughput, а не
  доступная полоса. Потери **понижают** оценку (что «безопасно»), но задержка/очередь не видны
  вообще; дубликаты и переупорядоченные отчёты её завышают.
- **Причина.** `TwccReportedPacket` содержит только `(sent_seq, arrival)` (`B:18-25`); **времени
  отправки нет** → queueing delay вычислить нельзя; `sent_seq` не используется → потери не
  детектируются; размер пакета — константа `bytes_per_packet` (`B:158`).
- **Минимальный фикс.** Не чинить: удалить модуль (§5), оставить str0m BWE. Если нужен свой
  (для SIP/H.323-плеча): хранить `(seq, sent_at, size)` и считать `delay = arrival - sent_at`,
  тренд по окну, + loss-based controller — это уже 300–400 строк, т.е. дубль str0m.
- **Тест (для удаления):** `grep -rn "BweEstimator" crates/ | grep -v vks-media-sfu/` → 0
  (доказательство, что удаление безопасно); для «своего» варианта — golden-трейс с 2 % потерь
  + 30 мс джиттера, где оценка не должна падать ниже фактического bottleneck.

#### P1-6. Реальный ICE — только host-кандидат, без STUN/TURN
- **Симптом.** Браузер за NAT не подключится: в answer один `a=candidate` с `advertise_ip`
  (`W:147-148`). Конфиг `ice_servers` до str0m-плеча не доходит — он кладётся только в
  `ServerHello.ice` для клиента (`H:275-280`).
- **Причина.** `WebRtcConfig` не имеет поля relay/STUN; `WebRtcPeer::accept_offer` добавляет
  `Candidate::host` и ничего больше.
- **Минимальный фикс.** Либо явно задокументировать «LAN/публичный IP only» и валидировать в
  `WR::preflight`, либо добавить srflx через `Candidate::server_reflexive` + STUN-обмен (str0m
  предоставляет `Candidate` и `Input::Receive`; ~120–150 строк + таймаут), relay — вне scope.
- **Тест.** Юнит: при `ice_servers` непустом в answer ≥2 кандидата (host + srflx); иначе
  fail-closed на старте, а не молчаливое «не подключается» у клиента.

#### P1-7. Нет SDP-реоффера: любое изменение = новый DTLS-хендшейк
- **Симптом.** Браузер добавляет экран/трек → новый offer → `accept_offer` создаёт **новый**
  `WebRtcPeer` и **новый сокет** и заменяет handle (`R:152-260`, `R:227-231`) → старый `Rtc`
  выбрасывается, ICE/DTLS переустанавливаются, медиа прерывается на 1–3 с; плюс `validate_offer`
  вообще запрещает вторую video-m-line (`W:399-401`), поэтому screen-share отклоняется целиком.
- **Причина.** `accept_offer` не различает initial offer и re-offer; нет `SdpApi::accept_answer`/
  `create_offer` пути; `validate_offer` — «не более одной m-line на kind».
- **Минимальный фикс.** Различать `existing`: если пир уже есть — применять offer к **существующему**
  `Rtc` (`rtc.sdp_api().accept_offer`), сохраняя сокет; снять ограничение `video > 1`, а лишние
  video-mid индексировать.
- **Тест.** Один пир, два последовательных offer (audio+video, затем +второй video) → тот же
  `local_addr`, `generation` инкрементится, `peer_count == 1`, DTLS не перезапускался
  (проверяется по неизменности `connected_at`/fingerprint пира).

#### P1-8. Два движка на одну комнату → расходящееся состояние
- **Симптом.** `create_room` вызывается в `SfuEngine` **и** `McuEngine` для каждой комнаты с
  захардкоженными режимами (`L:1129-1137`); участник добавляется подписчиком в оба
  (`L:1139-1147`); `remove_subscriber` — в оба (`L:1093-1094`), но `destroy_room` — по-разному;
  `E:532-544` не чистит `subscriber_payload_types` (утечка + stale PT).
- **Причина.** Нет одного владельца комнаты; «реестр участников» и «медиа-путь» смешаны в `SfuEngine`.
- **Минимальный фикс.** Один `RoomRegistry` (участники/треки/подписки) + два выхода
  (`SfuEgress`, `McuEgress`), создаваемых лениво по факту первого участника соответствующего
  транспорта. `MediaEngine`-трейт оставить только для управления.
- **Тест.** Комната только с браузерами → `McuEngine` не создаёт комнату; с SIP → создаёт;
  после ухода последнего SIP — освобождает.

#### P1-9. Заявляемые caps не соответствуют возможностям
- **Симптом.** `ServerHello.caps = {simulcast: true, dtls_srtp: true}` (`M:348-353`, `H:70-75`)
  при том, что simulcast не реализован, а при выключенном транспорте DTLS-SRTP фиктивен
  (fingerprint `sha-256 FF:00:11`, `M:356-370`).
- **Причина.** caps — статическая константа; не зависят ни от `webrtc_runtime::enabled()`, ни от
  факта наличия rid в answer.
- **Минимальный фикс.** Строить caps из фактического answer: `simulcast = answer.contains("a=simulcast")`,
  `dtls_srtp = webrtc_runtime::enabled()`.
- **Тест.** `VKS_WEBRTC_TRANSPORT=0` → `caps.dtls_srtp == false`; комната без rid → `caps.simulcast == false`.

#### P1-10. Легаси-путь: произвольный адрес доставки медиа (reflection)
- **Симптом.** `IceCandidate` от клиента парсится без валидации (`L:463-473`) и регистрируется как
  endpoint подписчика (`L:1059` → `E:174-186 register_endpoint`); сервер начинает слать RTP на
  произвольный `IP:port`, который указал клиент. Плюс endpoint паблишера «изучается» по первому
  пакету с известным SSRC без аутентификации (`E:229-300`).
- **Причина.** Легаси-путь доверяет SSRC/кандидату как идентичности.
- **Минимальный фикс.** Валидировать кандидата (совпадение с observed source IP, приватные/
  loopback-адреса — только при явном флаге) или отключить легаси-путь по умолчанию
  (`WR:19-24` уже требует явного включения, но текущий дефолт — «выключен», т.е. легаси включён).
- **Тест.** Кандидат `10.0.0.99:9` от клиента, чей observed IP другой → endpoint не регистрируется,
  `403/forbidden` в ответе.

## §4. Оценка примеров кода заказчика

Ещё раз: текстов в репозитории нет; ниже — оценка **алгоритмов**, названных в заявке, и их
фактических аналогов в нашем коде. Формулировки «корректно/некорректно» относятся к идее, а не к
конкретным строкам, которых я не видел.

### 4.1. `RtpTranslator` (переключение слоёв, seq/ts) — **идея верная, реализация почти наверняка неполная; писать не нужно**

Что обязано быть в корректном трансляторе (проверено по RFC 3550 §5.1 и по тому, что делает
str0m `src/streams/send.rs:100-130`):

1. **Свой SSRC на каждого подписчика** (иначе два паблишера с одинаковым SSRC у одного
   подписчика склеятся — у нас это ровно P2-2).
2. **Непрерывность `seq` при смене слоя**: `out = in + delta`, где `delta` пересчитывается на
   каждом переключении; 16-битная арифметика только через `wrapping_*`, сравнение возраста —
   `(a.wrapping_sub(b) as i16) > 0` (RFC 3550 A.1).
3. **Непрерывность `ts`**: у Chrome все rid одного трека используют общий 90 кГц-таймбаз, поэтому
   чаще достаточно сохранить `ts` как есть; но при смене **источника** (другой паблишер) нужен
   offset по wallclock, иначе `ts` уйдёт назад.
4. **Переписывание `TWCC`-расширения** (`transport-wide-cc-02`): транспортный seq **принадлежит
   отправителю**, т.е. на каждый egress-лег он свой. Это самый частый пропуск в самописных
   трансляторах: подписчик возвращает TWCC по **чужим** seq → BWE на паблишере ломается.
   str0m делает это внутри (`DirectApi`/`StreamTx`), руками — почти гарантированная ошибка.
5. **RTX**: PT репарных пакетов + `OSN` (original sequence number) в 2 байтах payload'а; при
   переписывании seq нужно править и OSN.
6. **PT per-subscriber** — у нас сделано (`E:325-332`), и это единственная часть, которая есть.

**Вердикт.** Пункты 1–5 уже реализованы в str0m для frame-API (`W:235-249` + `StreamTx`
`seq_no`/`seq_no_rtx` + `rtx_cache`). Свой `RtpTranslator` = дубль 300–400 строк с шансом
сломать TWCC/RTX. Правильный ход — не писать его, а использовать `Writer`/`DirectApi` (см. §5).

### 4.2. `ResilienceBuffer` (NACK/RTX-кэш) — **корректно как идея, избыточно как код**

Минимум корректности: ключ `(ssrc, seq)`, окно по времени (200–500 мс) **и** по числу пакетов
(≤512), защита от wrap, ограничение частоты ретрансмиссий (RFC 4588 §4: не чаще 1 раз на пакет,
RTX-ratio cap ~15 % — ровно `DEFAULT_RTX_RATIO_CAP` в str0m `src/streams/send.rs:40`).
У нас этого нет и не нужно: str0m держит `rtx_cache` с duration/ratio-cap
(`src/change/sdp.rs:1041`) на каждый `StreamTx`. Для SIP/H.323-плеча (где str0m нет) кэш нужен —
но это зона `gateway_video.rs`, а не SFU.

### 4.3. `TwccBweState` — **некорректно в описанном виде**

Если состояние хранит только `seq → arrival` (а наш аналог `B:18-25` хранит ровно это), то
**delay-based** оценка невозможна в принципе: нужен `sent_at` (или пара «время отправки/размер»),
иначе нельзя посчитать `delay_i = arrival_i − sent_i` и его тренд. Останется throughput-оценка,
которая:
- не отличает «канал узкий» от «канал забит своей же очередью»;
- завышается на дублях/переупорядоченных отчётах;
- не видит потерь (нет `sent_seq` → нет «дыр»).
Корректный минимум (GCC-подобный): окно 500 мс, тренд задержки (линейная регрессия или
`delay_gradient`), loss-controller по «дырам» seq, состояние `Increase/Hold/Decrease`, + пауза
между decreases. Это 300–500 строк и повторная отладка — при том, что str0m уже содержит
`bwe/{acked_bitrate_estimator,delay,loss_controller,probe,pacer,alr_detector}`.

**Вердикт.** Некорректно/недостаточно; не писать. Единственное, что нужно от BWE на нашей стороне —
применить `Event::EgressBitrateEstimate` к пейсеру (уже сделано, `R:593-596`).

### 4.4. XOR-FEC 10:1 — **математически возможно только при выравнивании длин; на браузерном плече неприменимо**

- XOR восстанавливает **ровно одну** потерю в блоке. При 10:1 и 2 % потерь вероятность «двух
  потерь в блоке» ≈ `C(10,2)·0.02² ≈ 0.0036` — терпимо, но при bursty-потерях (реальный Wi-Fi)
  блок теряет 3–5 пакетов и FEC бесполезен.
- Пакеты разной длины: XOR определён только для равных длин → нужен padding до `max(len)` **и**
  передача длин (иначе восстановленный пакет нельзя обрезать). Это +2–4 байта на пакет в блоке
  (или length-vector в repair-пакете) — то есть «10 % overhead» превращается в 10 % + 2–4 %.
- На браузерном плече repair-пакеты надо объявлять отдельным PT (`ulpfec`, RFC 5109) и **браузер
  должен его поддерживать**: Chrome — да (исторически), Firefox — нет; при этом str0m FEC не
  умеет вообще (`str0m/src/lib.rs:560-578`: FEC в матрице отсутствует; `grep -rin fec` → только
  `useinband_fec` Opus). Значит, XOR-FEC = обход str0m-пакетизатора = возврат к ручному RTP.
- Для аудио правильный ответ уже есть и он дешевле: **Opus RED** (`RtcConfig::enable_opus(true, true)`
  + `set_red_send`), 100 % совместим с браузерами и не требует своего кодека.

**Вердикт.** Требование «FEC 10:1 (XOR)» надо снять для браузерного плеча. Оставить NACK/RTX +
Opus RED. Если устойчивость критична для SIP/H.323 — делать XOR/RED **на шлюзовом плече**, где мы
владеем обоими концами и можем включать/выключать без согласования с браузером.

### 4.5. `HybridRoomBridge` — **заглушка; в описанном виде (пустой цикл) не делает ничего и опасна**

- Пустой `loop {}` без `await` **блокирует tokio-воркер навсегда** (не «ничего не делает», а
  «вешает 1/36 рантайма»); с `sleep(1ms)` — busy-poll, который жжёт ядро.
- Мост не может быть «циклом»: у него обязаны быть **два разных контракта**:
  1. **Ingress** (браузер → композитор): `str0m::MediaData` (encoded AU, VP8/H.264) →
     **decode** → `Frame{width,height,YUV420p}` → `McuEngine::set_participant_frame`.
     Граница кодеков проходит **здесь**; без декодера моста нет.
  2. **Egress** (композитор → браузер): `farm::AccessUnit` (encoded AU + `is_idr` + `parameter_sets`,
     `vks-media-mcu/src/farm.rs:227-257`) → `Writer::write` для каждого браузера (str0m сам
     пакуетизирует, ставит seq/ts/RTX/TWCC).
- Аудио-контракт дешёвый: Opus ↔ `f32` 48 кГц моно, 960 сэмплов/20 мс — кодек уже есть
  (`vks-gateway-sip/src/opus.rs:36-90`, `FRAME_SAMPLES=960`), MCU-миксер тоже 48 кГц
  (`vks-media-mcu/src/audio_mixer.rs:18`). Нужен только re-framer (браузер может слать 10/20/60 мс).

нормально для str0m (payload-params), но требует аккуратного `match_params` при форварде между
браузерами (там остаётся VP8↔VP8 или H.264↔H.264, транскодинга нет).

## §7. Открытые вопросы / что нельзя утверждать без живого прогона

1. **Живой сервис крутит другой код.** `/proc/1814143/exe -> .../target/release/vks-server (deleted)`;
   процесс стартовал `Ср окт 28 18:00:39 2026`, а текущий `target/release/vks-server` пересобран
   `2026-10-28 23:53:20` (HEAD `d82ce4d`, `2026-10-29 00:04`). Значит, **любые** наблюдения на

   нельзя, можно только зафиксировать. Живой env: `VKS_WEBRTC_TRANSPORT=1`,
   `VKS_WEBRTC_PORT_MIN/MAX=43000/43100`, `VKS_CANDIDATE_ADDR=192.168.1.93`.
2. **Совместимость с настоящим браузером не доказана.** Тест в `W:456-620` использует **str0m как
   клиента**, а не Chrome/Firefox. Не проверено: примет ли Chrome answer с одним host-кандидатом
   (за NAT — нет, §3 P1-6), примет ли `a=simulcast` приёма, как отреагирует на `a=inactive`
   предсозданные mid (P3-1).
3. **Поведение `ts` при переключении rid не проверено.** str0m документирует `wallclock` как

4. **CPU-стоимость P5 не измерена.** Оценка «+1 decode на браузера, +0 encode» — из архитектуры

## §9. Спорные тезисы

Формат: **ТЕЗИС** / ДОКАЗАТЕЛЬСТВО (file:line, команда) / ЧТО МЕНЯ ПЕРЕУБЕДИТ.

### Т1. «XOR-FEC 10:1 на браузерном плече нереализуем и вреден — требование надо снять»
- **Доказательство.** str0m 0.24.1 не имеет FEC вообще (`str0m/src/lib.rs:560-578` — в матрице фич
  строки FEC нет; `grep -rin "fec" str0m-0.24.1/src` → только `useinband_fec` Opus-параметр).
  Наш код: `grep -rin "fec" crates/vks-media-sfu/src` → одно упоминание в комментарии `R:10`, реализации нет; RED выключен
  (`W:133`: `enable_opus(true, false)`). XOR восстанавливает одну потерю на блок и требует
  выравнивания длин (§4.4).
- **Что меня переубедит.** Живой тест Chrome↔наш сервер: repair-PT принят, при `netem loss 3%`
  доля восстановленных AU ≥ 50 %, overhead ≤ 12 %, задержка не выросла. Или требование заказчика
  «FEC обязателен на шлюзовом плече» — там он осмыслен, и я сам его предложу.

### Т2. «Адаптивный джиттер-буфер для SFU не нужен; он нужен шлюзовым плечам»
- **Доказательство.** SFU не рендерит: `R:416-448` только перекладывает кадры; reorder-окно str0m
  фиксированное (`W:135-136`, 200 мс/30 пакетов), а адаптивность — свойство **получателя**
  (у браузера свой JB). При этом на шлюзовом плече JB действительно нет: входящий пакет
  принимается только если он новее последнего (прошлый аудит `04_network_stack.md:§0 п.4`).
- **Что меня переубедит.** Замер: при `netem delay 20ms 20ms` (reorder 40 мс) str0m-плечо теряет
  >2 % кадров из-за фиксированного окна, и эти потери не восстанавливаются NACK'ом (т.е. поздно).
  Тогда окно надо делать адаптивным (по jitter из RR) — но это ~80 строк в `webrtc.rs`, не 800.

### Т3. «SVC (VP9/AV1) — не приоритет: simulcast из 3 rid закрывает сценарий»
- **Доказательство.** В коде SVC нет и не планировался (`caps.svc=false`, `M:352`); features
  `vp9/av1` есть, но кодеки вычищены (`W:132-134`); SVC требует согласования кодека и поддержки
  браузера (VP9 SVC в Chrome — да, в Firefox — нет), а H.264-терминалы SVC не понимают вовсе.
- **Что меня переубедит.** Требование «экономия полосы ≥1.5× на 1 подписчика при 4+ участниках» с
  замером, или матрица браузеров заказчика, где VP9 доступен всем. Тогда SVC = +1 задача
  (VP9-rid-иерархия), но не раньше P3-4.

### Т4. «`ServerHello.room_mode` не может быть единственным источником истины; истина должна быть производной»
- **Доказательство.** 6 мест (§3 P0-3): `H:285` (статический i32), `M:249-263` (старт),
  `M:343-370` (старт), `A:129` (живой), `E:364` (константа), `L:1129-1137` (захардкожено в
  `create_room`). `switch_room_mode` не вызывается из продакшна (grep → только тесты).
- **Что меня переубедит.** Механизм, при котором per-room override гарантированно попадает в
  `HandlerConfig` **до** `ClientHello` (например, `ws_handler` создаёт handler на соединение) — но
  это и есть моё предложение; либо доказательство, что режим обязан быть статическим на процесс
  (тогда заявка о «единственном источнике» просто неверна).

### Т5. «В смешанной комнате браузер должен получать **композит** (1 трек), а не N треков — и это дешевле, чем per-track»
- **Доказательство.** Композит уже кодируется один раз на комнату и раздаётся веером
  (`vks-media-mcu/src/farm.rs` `GroupViewer`, `G:740-760`), т.е. egress-цена для браузера ≈ 0
  (только re-packetize в str0m). Per-track потребовал бы N энкодеров (по одному на терминал) —
  на 20 терминалах это +20 энкодеров. Требование заказчика («видят общий композит») совпадает.
- **Что меня переубедит.** Замер, где композит 1080p на 20 участников даёт неприемлемое качество
  (тайл < 320×180) при 1:1-сценарии, и заказчик готов платить N энкодеров. Тогда — гибрид:
  композит для >4 участников, per-track для 1:1/2:1.

### Т6. «~1000 строк аналитики (bwe/simulcast/congestion) — вредный дубль; их надо удалить, а не дорабатывать»
- **Доказательство.** 0 продакшн-вызовов (`grep -rn "BweEstimator\|CongestionLadder\|SimulcastSelector\|on_feedback" crates/ | grep -v vks-media-sfu/` → 0);
  контракт `TwccReportedPacket` не содержит времени отправки (`B:18-25`) → delay-оценка невозможна;
  str0m содержит полноценный `bwe/{delay,loss_controller,probe,pacer}`.
- **Что меня переубедит.** Записанный трейс (pcap с TWCC), на котором наш `bwe.rs` даёт меньшую
  ошибку оценки, чем str0m, **и** требование использовать его на не-WebRTC плече. Иначе — удалить.

### Т7. «Два движка на комнату — источник расхождений; нужен один реестр + два выхода»
- **Доказательство.** `L:1129-1137` создаёт комнату в обоих движках с разными захардкоженными
  режимами; `E:364-366` `mode()` врёт; `E:532-544` не чистит PT-мапу; `remove_subscriber` в оба
  (`L:1093-1094`), а `destroy_room` — по разным правилам; `apply_layout` в SFU — no-op (`E:546-554`),
  но `JoinRoomResult.layout` всё равно отдаёт MCU-снимок (`L:1110-1128`).
- **Что меня переубедит.** Место, где двойная регистрация **необходима** (например, одновременный
  per-participant выбор выхода). Я такого не нашёл; но если оно есть — это аргумент за «реестр +
  два выхода», а не за два независимых движка.

### Т8. «Живой прогон ничего не доказывает про HEAD: сервис крутит удалённый бинарь»
- **Доказательство.** `/proc/1814143/exe -> /home/pro/.../target/release/vks-server (deleted)`;
  старт `Ср окт 28 18:00:39 2026`; файл на диске `2026-10-28 23:53:20`; HEAD-коммит
  `2026-10-29 00:04:10`. Т.е. live-бинарь старше текущего на ~6 часов сборки и удалён с диска.
- **Что меня переубедит.** Разрешение Lead на `rebuild + restart` (я его не прошу и не делаю) и
  повторный замер ключевых сценариев на новом бинаре. До этого все «живые» наблюдения (§7 п.1) —
  про другой код, и я не имею права переносить их на HEAD.
