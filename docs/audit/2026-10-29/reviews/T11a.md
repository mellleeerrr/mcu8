## Verdict

**Changes required — not mergeable as-is.** Score: **7.0 / 10** (0 P0, 4 P1, 11 P2).

The core of the change is right and was verified against real code, not against the pitfalls report:

- `MediaData::is_keyframe()` genuinely reflects depayloaded VP8 frames (str0m
  `media/event.rs:289-299` + `packet/vp8.rs:751-757`; independently reproduced end-to-end through a real
  str0m RTP/VP8 packetizer→depacketizer in `/tmp/vp8probe`: `P=0 → is_keyframe=true`, `P=1 → false`).
  The gate therefore classifies frames correctly, is video-only, is re-armed on queue overflow and on
  `SetSubscription(video=true)` (with a re-arm race, P2-2), coalesces PLI to 500 ms, and addresses the PLI to the **publisher**
  (`from`), not to all publishers. The bogus `codec.rs` payload parser from the WIP was not committed.
- The answer is really Opus+VP8 only (`clear_codecs().enable_opus(true,false).enable_vp8(true)`,
  `webrtc.rs:127-135`), `RoomCaps.simulcast` is now `false`, `dtls_srtp` is derived from
  `webrtc_runtime::enabled()`, and the real-DTLS test asserts the absence of VP9/AV1/H264/H265.
- Same-session re-offer is the correct architecture: `PeerCommand::Reoffer` → `WebRtcPeer::accept_reoffer`
  on the same `Rtc`; str0m does **not** re-init DTLS (`change/sdp.rs:763-781` is a no-op once inited),
  does **not** overwrite the remote fingerprint (`:86-92`), and treats changed ICE credentials as an ICE
  restart on the same DTLS association (`:716-761`). Stale tasks cannot delete a newer generation
  (`webrtc_room.rs:371-387`, test `:885-898`).

What blocks merge: a re-offer the SFU *rejects* now kills the live call (P1-1), the documented
cross-plane admission invariant is no longer held while a peer is registered (P1-2), one integration test
is order-dependent and fails in isolation (P1-3), and the root README still advertises the old default
(P1-4). The test story is also materially weaker than the acceptance demands: there is **no** test for
preflight, for `enabled()` semantics, for caps, or for `forward`-level gate behaviour (P2-6).

## P1 findings

### P1-1 — A re-offer the SFU cannot accept tears down the live call (screen-share, data channel)

Evidence: `crates/vks-media-sfu/src/webrtc.rs:181-182` (`accept_reoffer` → `validate_offer`),
`webrtc.rs:428-430` (`audio > 1 || video > 1` → `InvalidOffer`; any non-audio/video m-line → error at
`:423-425`); `crates/vks-media-sfu/src/webrtc_room.rs:665-669` (`Err` → `reply.send(Err)` **then
`break`**), `:732` (`remove_generation` deregisters the peer), `:211-215` (registry returns `Err` while
logging *"keeping old session"* — false); `crates/vks-server/src/lib.rs:934,960` (mapped to
`webrtc_offer_rejected` + `rollback_offer`, the `SdpAnswer` reply is dropped).

Sequence: browser `pc.addTrack(screenTrack)` (or `createDataChannel()`) → new offer with a second video
(or `m=application`) m-line → `registry.accept_offer` finds the existing peer → `Reoffer` command →
`validate_offer` returns `InvalidOffer` **before touching the `Rtc`** → the peer task breaks, the `Rtc` is
dropped (DTLS close) and the registration is deleted → the client gets `webrtc_offer_rejected`. Before
T11a the same offer at least produced a replacement peer (1–3 s media gap); now the call is permanently
dead and the only recovery is a full re-join. This is the exact screen-share scenario T11b is supposed to
enable, and the e2e re-offer step the pitfalls asked for (`pitfalls/T11a.md:439`) was not added, so no
test covers it.

**Fix:** distinguish "our own pre-check rejected the SDP" from "str0m failed". For
`WebRtcError::InvalidOffer` the `Rtc` is untouched, so reply `Err` and `continue` (keep the session; the
signalling layer already rolls the FSM back). Only break/tear down when `accept_offer` failed *inside*
str0m (it can be partially applied — `change/sdp.rs:68-150` mutates ICE/SDP before `apply_offer` returns).
Concrete:

```rust
Err(error) => {
    let _ = reply.send(Err(error.to_string()));
    if matches!(error, WebRtcError::InvalidOffer(_)) {
        continue; // session untouched, keep it alive
    }
    break; // str0m may have mutated the session partially
}
```

and either keep `validate_offer` as-is (documented "multi-video is T11b") or record in
`docs/implementation/WEBRTC_TRANSPORT_2026-10-22.md` that a screen-share re-offer is rejected without
killing the session.

### P1-2 — Admission lock is released *before* peer registration: the half-bridged-room invariant is broken

Evidence: `crates/vks-server/src/lib.rs:830` takes `admission()` and re-checks room shape (`:833-844`);
`:885` `drop(_admission)`; `:887-893` `accept_offer(...).await`; `crates/vks-server/src/webrtc_room.rs:228-350`
(`accept_fresh_offer` binds a socket and **inserts the peer**, no admission lock); the invariant is
documented at `crates/vks-server/src/webrtc_runtime.rs:113-119` ("check and registration must be one atomic
decision") and relied on by `crates/vks-server/src/gateways.rs:1221-1227` and `:1577-1584`; `evict_rooms`
(`webrtc_runtime.rs:121-127`) also depends on it.

Before the commit `accept_offer` was synchronous inside the lock (verified at `c7b8724:lib.rs:830-889`), so
the check→register decision was atomic. Now registration happens after the lock is gone. Two real
interleavings:

1. **Gateway landing:** browser offer passes `gateway_room == false`, drops the lock, is about to register
   (or is in the 2 s re-offer wait); a SIP/H.323 participant joins under the admission lock
   (`gateways.rs:1223`) and sees `room_has_peer() == false`; then the browser registers → the room is
   half-bridged with no SRTP↔plaintext bridge (garbled media for both).
2. **Mode switch:** `evict_rooms` runs under the lock, evicts the room; the browser's pending
   `accept_fresh_offer` (up to 2 s after a re-offer timeout) then registers a real peer in an
   **MCU-mode** room that was checked as SFU.

**Fix:** split the reoffer attempt from the fresh registration. `registry.accept_offer` should return
"no existing peer" (or expose `try_reoffer` / `accept_fresh_offer` separately) and `lib.rs` should
re-acquire `admission()` and re-run the mode/gateway checks **after** the await, then call the synchronous
fresh-registration path while holding the lock (a `std::sync::MutexGuard` may be held across a *sync* call;
only `.await` must be avoided). The reoffer path itself needs no lock (no room-shape change).

### P1-3 — `test_package_d_mcu_pipeline_handover_and_pnm_control_events` fails when run alone

Evidence: `crates/vks-server/tests/network_integration.rs:116-123` adds `force_legacy_webrtc_transport()`
(process-global `Once` + `set_var`), and it is called from `spawn_live_server` (`:126`),
`spawn_live_server_with_auth` (`:596`) and `spawn_live_server_with_sfu_udp` (`:870`) — but **not** from
`spawn_live_server_with_mcu_sfu` (`:1105-1107`). That helper's test sends ICE-less offers and asserts
`Payload::SdpAnswer` (`:1189-1190`). Reproduced:

```
$ env -u VKS_WEBRTC_TRANSPORT cargo test -p vks-server --test network_integration \
    test_package_d_mcu_pipeline_handover_and_pnm_control_events -- --exact
test test_package_d_mcu_pipeline_handover_and_pnm_control_events ... FAILED
panicked at crates/vks-server/tests/network_integration.rs:1190:
```

It only passes in the full suite because *some other test* sets the env first. That is exactly the
"H1 `enabled()` reads process env ⇒ race/non-determinism" trap the pitfalls warned about, and it means the
acceptance claim "tests are deterministic" is not met (`cargo test --test network_integration <name>` is a
normal developer/bisect workflow).

**Fix:** call `force_legacy_webrtc_transport()` in `spawn_live_server_with_mcu_sfu` too (minimum), and
better: stop depending on process env — inject the transport flag into the registry/handler config
(pitfalls step 0: `WebRtcRuntimeSettings` parsed once in `main`), or mark the whole binary
`#[serial]`-equivalent. Also add the missing positive test: with transport enabled, an ICE-less offer must
return `webrtc_offer_unsupported` and **not** an `SdpAnswer` (pitfalls `:430` lists two tests; neither
exists — see P2-6).

## P2 findings

### P2-1 — Re-offer through a full command queue silently falls back to a new DTLS session

`webrtc_room.rs:192-194`: `PeerCommand::Reoffer` is submitted with `try_send`; if the peer's 64-slot queue
is full (a slow/bursty subscriber), the command is dropped and the code falls through to
`accept_fresh_offer` (`:225`) — a **new** socket + new DTLS, which is what the commit message says happens
"only on timeout". No log, no metric on that branch.
**Fix:** log + `WEBRTC_OFFERS{result="reoffer_queue_full"}` and retry once after a short yield; or reserve a
dedicated oneshot control path that does not compete with media writes.

### P2-2 — `SetSubscription(video=true)` re-arm can be overtaken by a queued `Write`

`webrtc_room.rs:396-412`: `set_subscription` stores `video` (`:410`) and *then* `try_send`s
`SetSubscription` (`:411`); the gate is armed only when the peer task dequeues that command (`:685-690`).
A frame forwarded after the atomic store but enqueued before the command (`forward` is called from the
publisher's task, `:504-541`) is processed first and bypasses the gate → the re-subscribing viewer gets
deltas before an IDR, which is the defect the gate exists to prevent.
**Fix:** `handle.waiting_keyframe.store(true, Ordering::Relaxed)` in `set_subscription` **before**
`try_send` (the `Arc<AtomicBool>` is already on `PeerHandle`); keep the task-side store as a belt-and-braces
copy.

### P2-3 — A successful re-offer does not re-arm the gate (or refresh subscription atomics)

`webrtc_room.rs:196-209` only updates `publishes_video`; `webrtc.rs:181-204` rebuilds `mids`/`mid_audio` but
leaves `waiting_keyframe` alone. If the re-negotiation changes the video mid/PT (or the client starts
receiving video), the decoder state restarts while the gate is open → delta frames are forwarded.
**Fix:** arm the gate on every successful `Reoffer` when the video mid set/PTs changed (or unconditionally —
one redundant IDR wait is cheaper than a corrupt decoder), and refresh `audio`/`video` atomics from the
subscription map.

### P2-4 — A re-offer with a *new* remote DTLS fingerprint is accepted and silently breaks DTLS

`webrtc.rs:181-184` applies the offer to the same `Rtc`; str0m only records the fingerprint when none is set
(`change/sdp.rs:86-92`) and `init_dtls` is a no-op once inited (`:763-781`). A client that closes and
recreates its `RTCPeerConnection` (new self-signed cert, new ICE credentials) on the **same** WS session is
therefore answered as if the re-offer succeeded, while the server keeps the old DTLS state → handshake
never completes, the existing peer stays registered until the 30 s idle timeout (`webrtc_room.rs:35,581-585`).
Before T11a every offer created a new `Rtc`, so this path worked.
**Fix:** remember the first offer's `a=fingerprint` per peer (or expose `WebRtcPeer::remote_fingerprint()` and
compare in `accept_reoffer`); on mismatch return a dedicated error and let the registry replace the peer
(`accept_fresh_offer`) instead of renegotiating.

### P2-5 — Reoffer `Ok` path replies before its own timer flush; a timer error then leaves a "successful" answer with a dead peer

`webrtc_room.rs:646-661`: `reply.send(Ok(...))` happens **before** `peer.handle_timeout(now)`; if that call
errors the task breaks (`:660`) and `remove_generation` (`:732`) deregisters the peer — but the registry has
already received `Ok` and returns the answer to the browser (`:196-209`). The client starts ICE against a
peer task that is gone.
**Fix:** run `handle_timeout` first, then reply; on error reply `Err` instead of `Ok` (and break).

### P2-6 — Test coverage is materially below the acceptance table

Added by the commit: `keyframe_gate_blocks_deltas_until_the_first_idr` (pure function only),
`reoffer_is_answered_by_the_existing_peer_task` (registry plumbing, fake reply),
`accept_reoffer_reuses_the_same_session_and_socket` (never connected — see below),
`candidate_validation_is_fail_closed` (pure formatting). Missing relative to
`pitfalls/T11a.md:424-439` and the acceptance ("tests"):

| Missing test | Why it matters |
|---|---|
| `transport_defaults_on_and_zero_is_the_only_opt_out` | `enabled()` has no test at all; the whole acceptance hinges on it |
| `preflight_rejects_*` / assignability / port-range / exit-78 | `preflight` (`webrtc_runtime.rs:75-111`) is **untested**; only `validate_candidate` (format checks) is. `tests/config_failclosed.rs` exits 78 earlier, in `Config::validate`, so it never reaches preflight |
| `keyframe_gate_drops_deltas_until_idr` at `forward` level | `P,P,P,IDR,P → 2 Writes` and 3 × `frames_dropped{reason=...}` is not tested; only the 15-line `gate_video` helper is |
| queue-full re-arm / audio-not-gated / SetSubscription re-arm | all three are only asserted indirectly or not at all |
| `caps_do_not_advertise_unimplemented_features` | no test anywhere asserts `simulcast == false`, `dtls_srtp == enabled()`, `video_codecs == [Vp8]` (`grep -rn "simulcast" tests/` → 0) |
| enabled-transport rejects an ICE-less offer (both polarities) | the only integration coverage is the *legacy* side (P1-3) |

The "same session" test (`webrtc.rs:488-507`) cannot distinguish a reused `Rtc` from a fresh one: the peer
is never connected, `local_addr` is a constructor field, and no `Connected` action exists either way.
**Fix:** build it on a connected session (reuse the `real_dtls_srtp_handshake_and_media` harness at
`:510-577`), then `accept_reoffer` with an added video m-line and assert `peer.is_connected()` stays `true`,
no `WebRtcAction::Connected`, `local_addr` unchanged, and a subsequent `write_media_matched` still reaches
the client.

### P2-7 — Tests mutate process-global env from parallel test threads

`webrtc_runtime.rs:208` (`std::env::remove_var("VKS_ALLOW_LOOPBACK_MEDIA")`) and
`network_integration.rs:121` (`std::env::set_var`) are process-global mutations in test binaries that run
tests in parallel threads; `set_var` concurrent with reads is documented as unsound, and P1-3 is the
practical symptom. Edition is 2021, so this compiles without `unsafe` — it will stop compiling under
edition 2024.
**Fix:** inject settings (pitfalls step 0), or gate the env-touching tests behind a process-isolated test
(`assert_cmd` on the real binary) instead of in-process mutation.

### P2-8 — `MEDIA_BYTES` label and `TrackInfo.codec` are still hardcoded, not derived

`webrtc_room.rs:536-538` labels every video byte as `"vp8"`, `lib.rs:1030-1032` reports
`CodecId::Vp8` for every non-audio track, and `lib.rs:1045` hardcodes `clock_rate: 90000`. This is
**accurate today** because the answer is VP8-only (and the real-DTLS test pins that), so it is not a lie
now — but it is the same class of defect the task removed from the caps, and there is no test pinning the
label to `data.params.spec().codec`. **Fix:** derive the label from `params.spec().codec` (the pitfalls'
`codec_label_follows_payload_params` test) and assert VP8-only in a caps test.

### P2-9 — `preflight` validates a *derived* candidate and still runs after storage init

`main.rs:294-306` substitutes `127.0.0.1` (or the media-loop IP) when `config.candidate_addr` is empty, and
`handler_config` is built from that (`:359-375`); `preflight(&handler_config, …)` (`:410`) therefore never
sees an empty candidate. In prod (`allow_insecure_defaults = false`) the operator who left
`candidate_addr = ""` gets *"candidate_addr 127.0.0.1 is loopback/unspecified"* instead of "candidate_addr is
empty" — fail-closed but misleading. Also, preflight still runs after SQLite/Postgres init
(`main.rs:96-150`), so a config typo creates/opens the DB (and the `DbLock`) before `exit 78`
(pitfalls H12, not fixed).
**Fix:** validate `config.candidate_addr` directly (keep the derived fallback only for the legacy answer) and
move the WebRTC preflight above storage init; it only needs `Config`.

- `MediaData::is_keyframe()` semantics for VP8 — read (`event.rs:289-299`, `vp8.rs:751-757`) **and**
  reproduced with a real str0m handshake + VP8 packetizer/depacketizer (`/tmp/vp8probe`).
- Audio frames have `CodecExtra::None`/`Tele` ⇒ `is_keyframe() == false`, so the gate's `!audio` guard is
  required and present (`webrtc_room.rs:626`).
- str0m re-offer semantics: no DTLS restart (`change/sdp.rs:763-781` + `:86-92`), ICE restart on changed
  credentials (`:716-761`), monotonic-time guard (`lib.rs:2037-2044`), PLI requires negotiated feedback
  (`media/writer.rs:294-326`, `session.rs:1452-1461`; video payloads always get `fb_pli`,
  `format/codec_config.rs:129-147`).
- `enabled()` semantics by reading (`webrtc_runtime.rs:24-29`): unset/empty/anything except
  `0|false|off|no` (trimmed, case-insensitive) ⇒ `true`.
- No code path silently serves the fake SDP while enabled: all five branches in `lib.rs:827-950` either
  produce a real answer or `Payload::Error` (verified by reading; no test exists).
- The bogus WIP keyframe detector is not in the tree (`grep is_keyframe_payload` → 0).
- Stale task cannot remove a newer generation (`webrtc_room.rs:371-387` + existing test).
- The live DB was not opened/modified (mtime unchanged; only in-memory SQLite in tests).

**Assumed / not verified:**

- Browser behaviour (Chrome/Firefox re-offer shape, `getDisplayMedia` producing a second video m-line,
  `restartIce()` reusing the DTLS cert) — not exercised here; P1-1/P2-4 are reasoned from SDP/RFC 3264
  semantics and str0m code, not from a live browser.
- That a PLI is actually delivered to a real browser publisher (the probe proves frame classification, not
  the RTCP path); `request_keyframe` errors are swallowed at `webrtc_room.rs:677-682`, so a client that
  offers no `nack pli` would leave the gate armed forever — no such client is known, but the failure mode is
  silent (warn-level hardening would be cheap).
- The admission-lock interleavings (P1-2) are reasoned from code; no concurrency test reproduces them.
- The g723 lib-test failure is a pre-existing flake, inferred from four green isolated reruns and from
  `gateways.rs` being untouched by this commit (not bisected against `c7b8724`).
- `cargo test --workspace --locked` (the pitfalls' 1425/0 baseline) was not run; only the three required
  crates.
