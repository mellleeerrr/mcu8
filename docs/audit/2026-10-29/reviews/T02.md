## Verdict

**Changes required — not mergeable as-is.** Score: **6.0 / 10**.

The Argon2id core + PBKDF2 migration is genuinely good (correct parameters, PHC storage,
real legacy vector, lazy rehash invariant). But the headline "429 backpressure" is not
delivered by the production wiring (Busy degrades to 401 + account lockout), the hash gate
is both cancellable-unsafe and bypassable, the "global" token bucket does not cover the
login endpoint, and the lazy rehash can rewrite a local password using a password that was
verified by a *different* provider. Docs overclaim several of these facts.

## P1 — must fix before merge

### P1-1. The 429 backpressure path is unreachable in the real binary; Busy becomes 401 + lockout
`crates/vks-server/src/main.rs:236` unconditionally sets `admin_state.auth_provider = Some(auth_provider)`
— including `provider_type="local"` (`main.rs:223-236`). Therefore `login` always takes the
provider branch (`crates/vks-admin/src/api_v3/auth.rs:285-288`) and maps **every** provider
error to `LoginError::Invalid`; `crates/vks-auth/src/core_adapter.rs:35` turns
`LocalDbError::Busy` into `CoreAuthError::Other(...)`. Consequence: saturation of the hash
queue returns **401 "Login rejected"**, and `auth.rs:322-333` records it as a failed login.
Five such replies put the account/IP into the 15-minute lockout — a load spike (or an
attacker) converts backpressure into a lockout DoS. The `Busy → too_busy_response()`
mapping in the `else if let Some(db)` branch (`auth.rs:290-294,317-321`) is dead code in
production: the tests reach it only because `test_state()` never sets `auth_provider`
(`crates/vks-admin/src/api_v3/tests.rs:533-546`).

Also violates the "no 500 under saturation" requirement: `change_password` maps Busy (and
any other `LocalDbError`) to `error_json(500, "Internal error")` at `auth.rs:373-379`, and
to 401 for the old-password verify at `auth.rs:351-357`.

**Fix:** add a dedicated busy variant (e.g. `CoreAuthError::Busy`) and map it in `login` to
429 + `Retry-After` *without* `record_failure`; add the same mapping to
`change_password` / `profile_credentials` / admin credential handlers; add a test with
`auth_provider = Some(LocalAuth::with_db(db))` that saturates the gate and asserts 429.

### P1-2. Waiter counter leak on cancellation — permanent "busy" auth outage until restart
`crates/vks-auth/src/local_db.rs:54-64`:

```rust
if WAITING.fetch_add(1, Ordering::SeqCst) >= AUTH_QUEUE_CAPACITY { … }
let permit = hash_gate().acquire().await.map_err(|_| LocalDbError::Busy);
WAITING.fetch_sub(1, Ordering::SeqCst);
```

The `fetch_add` at `:57` happens before the `acquire().await` at `:61`; the matching
`fetch_sub` at `:62` is only reached if the future completes. If the request future is
dropped while waiting — axum drops handler futures when the client disconnects; also task
abort, `select!`, server shutdown — the counter is never decremented. `WAITING` is a
process-lifetime `static` (`:55`), so after 128 such drops (plus 4 in flight) **every**
hash (login, register, change-password) returns `Busy` forever until a restart. This is
borderline P0 for availability; a single client that opens and aborts 130+ concurrent
logins while the gate is contended is enough.

**Fix:** make the waiter slot RAII (a guard struct with `Drop` that decrements), or use
`Semaphore::try_acquire` + a bounded waiter semaphore/mpsc channel; add a cancellation
test (spawn N waiters, abort them, assert capacity is restored). Also note the counter
includes permit holders, so real waiters are ≤124 — the "≤128 waiters" doc is off by the
permit count anyway (`local_db.rs:35-41`, ADR-0033:28, BACKEND_RULES:28-29).

### P1-3. Sync `LocalDb::register` bypasses the 4-permit gate (criterion 4 is false)
`crates/vks-auth/src/local_db.rs:112-117` (and sync `set_password` `:238-242`) call
`hash_password` directly — no semaphore, no queue, on the calling thread (i.e. a tokio
worker), because `crates/vks-admin/src/api_v3/directory/accounts.rs:139` calls the sync
`db.register(...)` from the async handler `create_user_credentials`
(`POST /api/v3/users/{id}/credentials`). With the 200-token burst budget this allows up to
200 concurrent Argon2id hashes → ~200 × 19 MiB ≈ 3.8 GiB of transient memory (OOM) and
executor stalls of ~33 ms per hash (release). This directly contradicts "At most 4
concurrent Argon2 hashes" and the ADR claim.

**Fix:** route every credential write through `register_async`/`set_password_async`
(accounts.rs:139 is the only offender) or make the sync API private/`#[cfg(test)]`; add a
test that the gate bounds memory/concurrency (the audit plan in `04_infra_l5l7.md` even
specified `argon2_memory_bounded_by_semaphore` — it was not written).

### P1-4. Lazy rehash rewrites local credentials using a password verified by another provider
`crates/vks-admin/src/api_v3/auth.rs:304-314` runs the rehash block after *any* successful
authentication, including `state.auth_provider = Some(LdapProvider)` (mock LDAP accepts any
password; factory-gated but a documented lab mode, `main.rs:221-236`). It re-fetches the
row by login (`db_user_by_name`, `:463-472`) and, if the local row is legacy PBKDF2, calls
`rehash_async(&user.id, &body.password)` with the **LDAP-supplied** password, then
`persist_lazy_rehash` (`:477-490`) upserts that hash into `user_credentials` for that local
user id. A local account (e.g. the bootstrap operator `admin`) that shares the login name is
silently given an unverified password in persistent storage, with `generation` /
`password_changed_at` preserved. The same block writes nothing to state.users, so the
attack is silent.

Related latent issue at `:479`: `UserId::parse(&user.id).unwrap_or_else(|_| UserId::bootstrap_operator())`
— an unparseable local id writes that user's hash under the **operator's** user id. No
production id is non-UUID today (bootstrap UUID + `UserId::new()`), but a silent fallback on
a credential write is not acceptable.

**Fix:** only run rehash when the local provider performed the verification (e.g. keep a
`source` in the login result, or do the rehash inside `LocalAuth::verify`'s success path and
return the flag), and require the stored hash to equal the hash that was verified; on parse
failure skip persistence and log instead of falling back to the operator id.

### P1-5. The "global" token bucket covers only protected `/api/v3` routes
`crates/vks-admin/src/api_v3/mod.rs:471-472` applies `token_middleware` (bucket check at
`auth.rs:190-196`) only to the `protected` router. `/api/v3/login`, `/api/v3/login/status`,
`/api/v3/ws`, `/static/*` and the catch-all 501 (`mod.rs:474-491`) are exempt — so the
expensive, unauthenticated login endpoint is never rate-limited by this bucket, and a
flood of unknown paths is not either. The commit message ("on all /api/v3"),
`ApiV3State::global_ratelimit` doc (`mod.rs:87-90`), ADR-0033:30 and BACKEND_RULES §1.4:37-38
all claim (near-)global scope.

Additionally, the bucket is charged **before** token validation (`auth.rs:190-196`), so
unauthenticated clients consume the shared budget: 200 requests from anyone make legit
requests — including legit unauthenticated ones that should get 401 — receive 429 until
refill (up to 4 s at 50/s), repeatably. Criterion 5's "401 not 429 under normal load" only
holds when nobody floods.

**Fix:** move the global bucket to the outer `/api/v3` router (or explicitly document and
test the exemption list), and decide the semantics: charge after token verification, or
key by IP, so unauthenticated clients cannot drain the global budget.

## P2 — should fix

1. **Lazy-rehash TOCTOU / password-change revert** (`api_v3/auth.rs:307-313`,
   `local_db.rs:321-332`): `rehash_async` overwrites whatever hash is currently stored. A
   login that passed the `needs_rehash` check just before a concurrent `change_password`
   can re-hash the *old* password after the change, silently reverting the new password
   (and, in `persist_lazy_rehash`, mixing the new generation/mark with the old hash —
   `auth.rs:484-485`). Same class of race across HA nodes with a stale legacy row. Fix:
   compare-and-swap against the verified hash under the users lock, and skip persist if
   the stored hash changed.
2. **Wrong status codes for the 128-byte cap on credential routes**:
   `crates/vks-admin/src/api_v3/directory/accounts.rs:139-141` maps *any* register error
   (including `PasswordTooLong`) to 409 "Login already exists";
   `accounts.rs:257-261` and `:418-420` map `set_password_async` failures (including Busy
   and `PasswordTooLong`) to 500 "Internal error"; `profile_credentials` rejects an
   oversized old password with 404. Pre-check the length in the handler and return
   400/422; reserve 409 for duplicates and 429/503 for busy.
3. **Flaky rate-limit test**: `crates/vks-admin/src/api_v3/tests.rs:350-366` fails
   intermittently. Reproduced 1 failure in 7 runs: at `:361`
   `left: [200,200,…,200]`, `right: [429,…,429]` after ~1.6–1.9 s of 210 in-process
   requests, because the bucket refills 50 tokens/s on 1 s ticks
   (`RateLimiter::new(200, 50.0)`, `auth.rs:449`). Drive the limiter with a frozen clock or
   test `RateLimiter`/`global_rate_limit_allows` directly.
4. **Missing tests for the stated criteria**: no test references
   `AUTH_HASH_PERMITS`/`AUTH_QUEUE_CAPACITY`/`Busy` (the 4+128 gate and its 429 are
   untested); no HTTP-level legacy-rehash test (only `LocalDb` unit tests) and no persist
   assertion; no change-password 128-byte test; `test_state`/integration tests never set
   `auth_provider`, which is exactly why P1-1 slipped through. Add tests that exercise the
   production wiring (`auth_provider = Some(LocalAuth)`) and the gate.
5. **Timing side channel / username enumeration** (`local_db.rs:155-160,300-304` vs
   `:403-411`): unknown users still run a PBKDF2-100k dummy while real users run Argon2id.
   Measured on this host (release, throwaway project in `/tmp`, not repo source):
   PBKDF2-100k ≈ 95 ms, Argon2id m=19456,t=2,p=1 ≈ 33 ms → a ~3× difference. Use Argon2id
   for the dummy (cost-matched) or document the accepted risk.
6. **Docs/code mismatches**: "global … all /api/v3" (`api_v3/mod.rs:87-90`, ADR-0033:30,
   BACKEND_RULES:37-38) vs protected-only (P1-5); "≤128 waiters" (ADR-0033:28,
   BACKEND_RULES:28-29) vs 128 total in-flight (124 waiters); "Min 12 символов, top-10k
   check (проверка сложности — в API-валидации)" (BACKEND_RULES:30) — no such validation
   exists (`password_min_length` is only a settings field, `settings_admin.rs:100`); task
   list says "429 … готовы" (`docs/progress/MASTER_TASK_LIST_2026-10-29.md:12`) though 429
   is unreachable in production; `handlers.rs:549` says "without a configured LDAP provider"
   but no code path ever sets `ldap_sync_enabled = true` (`state.rs:322`); stale in-code
   docs still describe PBKDF2/salt (`local_db.rs:72-75,236-237,257,280,334`);
   `api_v3/auth.rs:441-444` attaches the "401 + Retry-After" doc to `global_rate_limit_allows`
   and leaves `locked_response` undocumented; `docs/DEVELOPMENT_PLAN.md:242` still claims
   `m=64MiB, t=3, p=4`.
7. **`needs_rehash` is only a prefix check** (`local_db.rs:313-315`): future parameter
   upgrades (e.g. m bump) would never rehash existing PHC rows; a corrupt `$argon2…` row is
   never repaired and always fails auth (`:405-407` returns false). Compare
   algorithm+params against policy and log/fail explicitly on unparsable PHC.
8. **Panic/robustness on the credential path**: `hash_password` uses
   `.expect("Argon2id hashing cannot fail")` (`local_db.rs:395-399`); `rehash_async`
   (`:321-332`) is `pub` and lacks the empty/128-byte guards the other entry points have.
9. **`sync-ldap` gate is dead code**: `ldap_sync_enabled` is never set to `true`
   (`state.rs:216,322`), so the 501 branch is the only reachable one and
   `Users::sync_ldap(&state, MockLdapProvider::fetch())` (`handlers.rs:564-566`) is
   unreachable. Criterion 6 is functionally met (no fake success), but the field and the
   doc comment promise a "real LDAP client" configuration that does not exist; either wire
   it when a client lands or remove it and adjust the comment. (`VKS_ALLOW_MOCK_LDAP=1` +
   `auth_provider=ldap` still means "any password accepted" — inherited from audit §8.1,
   gated and now honestly documented in `vks.env.example:46-49`; out of T02 scope but the
   §8.1 P0 remains open.)
10. **Legacy >128-byte passwords become a lockout with no rotation path**: `login` returns
    422 (`auth.rs:274-278`) and `change_password` returns 401 for an oversized old password
    (`auth.rs:348-350`), so such a user can neither log in nor change the password. Accept
    the policy if intended, but document it (and note the live DB rows are PBKDF2 — I
    cannot tell their plaintext length).
11. **Commit hygiene**: `eb514e2` mixes T02 with T04a tracker edits and five large audit
    documents (26 files, +5544/−36). Not a correctness issue, but it makes the T02 diff
    harder to isolate/roll back.

## Required fixes (ordered)

1. Make Busy observable end-to-end: dedicated error variant, 429 + `Retry-After` in
   `login` (no lockout) and in `change_password`/credential handlers (no 500); test the
   production provider wiring.
2. Fix `hash_permit` accounting with an RAII waiter guard and add a cancellation test.
3. Gate every Argon2 call (replace the sync `register` call in `accounts.rs:139`, remove or
   privatise sync `register`/`set_password`).
4. Restrict lazy rehash to local-provider verification and make it a compare-and-swap;
   stop the `bootstrap_operator()` id fallback on the credential write path.
5. Apply the global bucket to all `/api/v3` (or document/test the exemptions) and stop
   charging it before authentication; fix the flaky test with an injected clock.
6. Correct status codes for length errors on credential routes; add change-password cap
   and legacy-rehash HTTP tests.
7. Correct the docs listed in P2-6 (scope of the bucket, queue semantics, removed
   complexity claim, 429 "ready", stale PBKDF2 comments, DEVELOPMENT_PLAN params).
8. Optional hardening: Argon2-based dummy hash, param-aware `needs_rehash`, remove the
   dead `ldap_sync_enabled` field, replace `expect` in `hash_password`.
