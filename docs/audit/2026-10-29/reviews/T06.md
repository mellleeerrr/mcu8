## 1. `normalize_loaded` и отравление legacy-записей — **FAIL (P1)**

### 1.1 Что делает код

- `normalize_loaded` (`crates/vks-admin/src/api_v3/resources.rs:1113`) после фильтрации слотов
  вызывает `recalc_layout_size(layout)` (`:1128-1132`).
- `recalc_layout_size` (`:1378-1384`) берёт `derived_layout_size` (`:385-395`).
- Порядок резолвера после `d055fb5`: **preset capacity → `payload.size` → `slots.len()`**. Именно
  смена порядка (было `size → preset → len`) и создаёт P1: ёмкость пресета побеждает даже тогда,
  когда слотов/позиций больше, чем эта ёмкость.
- `validate_layout_assignments` (`:1429-1452`) затем сравнивает `position` с этой ёмкостью и
  отдаёт 409; `attach_layout_abonent` (`:960`) берёт ту же ёмкость как лимит.

### 1.2 Пробы на admin-роутах (pristine-копия, `MemoryStorage`, никакой live-БД)

Запись: `{"preset":"preset_equal_5","size":13,"slots":[position 1..9]}` (аналогично
`vks_grid_5`), загружена через `AppState::sync_from_storage()` в `/dev/shm`-копии.

| Шаг | Фактический результат |
|---|---|
| `normalize_loaded` (memory) | `size = 5`, слотов осталось **9** (позиции 1..9) |
| Документ в storage сразу после load | `size = 13` — **normalize не персистится** |
| `PATCH {"display_name":"Renamed"}` → `edit_linked` | **409**: `slot position 6 is outside layout of 5 windows` |
| `attach_abonent` #1..#5 | 200 (окна 1..5) |
| `attach_abonent` #6 | **409**: `Layout is full` (при том, что пустые окна 6..9 остались в записи) |
| Слоты после attach | по-прежнему `[1,2,3,4,5,6,7,8,9]`, заняты 1..5 |
| Любой чужой commit (создан audiochannel) | в storage уже `size = 5` — **отравленный size утёк в БД** |

Тот же результат для `vks_grid_5` + 9 слотов: `recalc → 5`, PATCH rename → тот же 409.
Тест `recalc_layout_size_распознаёт_конструктор` (`resource_tests.rs:2352-2390`) **закрепляет**
`size=5` при 9 слотах и не проверяет, что запись остаётся PATCH-able; новый
`t06_normalize_loaded_recalculates_stale_payload_size` (`:2765-2782`) использует пустые слоты,
поэтому P1 не ловит.

### 1.3 Что видит MCU (gateway)

Проба в `vks-server` через `GatewayManager::apply_layout` + `McuEngine` (scratch-тест в копии),
9 занятых слотов, после normalize `size=5`:

| Preset | `descriptor.geometry` | `descriptor.assignments` | Механизм |
|---|---|---|---|
| `preset_equal_5` | **9** | 9 | `preset_size=5`, `slot_count=max(position)+1=9`, `PresetId::parse(...).filter(size>=slot_count)` не проходит → `equal(9)` (`gateways.rs:1855-1863`, `:1893-1898`) |
| `vks_grid_5` | **9** | 9 | `grids::geometry` даёт 5 ячеек, 4 участника без окна → `regrid_for_video` расширяет до 9 (`engine.rs:1677-1682`) |

То есть при 6–9 занятых слотах админка говорит «5 окон», а MCU рисует 6–9. Если занято ≤5 слотов,
обе стороны дают 5 (для `preset_equal_5` `slot_count` считается по занятым, не по `slots.len()`).
Формулировка из pitfalls «gateway `equal(9)`» верна только для manual-пресетов; для
`vks_grid_5` итог тот же, но через regrid, а не через `equal(9)`.

### 1.4 Severity и рекомендация

**P1** (не P0: данные не удаляются, запись восстановима ручным удалением «лишних» слотов; но это
регрессия апгрейда: PATCH/rename ломается, attach вводит в заблуждение, админка и MCU
расходятся, а normalize-значение может молча попасть в БД на следующем commit).

Рекомендация — вариант A из pitfalls §5.3: `derived_layout_size` должен учитывать
`max(position)` (и `slots.len()` как fallback) и **не сжимать** ёмкость ниже фактических окон:
`size = max(id_capacity, max_position, len)`; при `max_position > id_capacity` — WARN. Тогда
`vks_grid_25 + size:7` по-прежнему даёт 25 (тест сохраняется), а `vks_grid_5 + 9 позиций` даёт 9 и
остаётся PATCH-able. Нужен тест: после `normalize_loaded` PATCH `display_name` проходит, attach
лимит = 9, повторный normalize идемпотентен. Альтернатива C (удалять только пустые слоты вне
ёмкости, занятые сохранять) — если Lead требует «пресет всегда побеждает»; это дороже и требует
тестов на идемпотентность.

## 3. `preset_size`: кламп/схема; `calculate`; §13 — **PASS по клампу, P3 по схеме/доку**

### 3.1 Пробы `preset_size` (выполнены в копии)

| id | Результат |
|---|---|
| `preset_evil_999` | `None` (999 > 100) |
| `preset_evil_18446744073709551615` | `None` (== `usize::MAX`, отброшен) |
| `preset_evil_18446744073709551616` | `None` (parse overflow) |
| `preset_equal_500` / `preset_default_256` / `preset_equal_0` | `None` |
| `preset_equal_4` | `Some(4)` |
| `preset_default_13` | `Some(13)` |
| `preset_equal_25_(2)` | `Some(25)` |
| `preset_evil_4` / `preset_unknown_4` | **`Some(4)`** — схема не проверяется |
| `vks_grid_18446744073709551615` | `None` |
| `vks_grid_100` | `Some(100)` |

Паники/переполнения нет, ёмкость ограничена 1..=100 (`lib.rs:59-72`). Это закрывает
«no panic/overflow, capacity sane». Побочный эффект клампа: вендорские id с N в 101..255
(`preset_equal_255`) теперь дают `None` и падают в `payload.size` — для PNM-конструктора (макс. 100)
приемлемо, но это изменение поведения, которое стоит зафиксировать.

**Схема не валидируется** (P3-1): `preset_size` смотрит только на `preset_*` + числовой хвост;
`preset_evil_4`/`preset_unknown_4` дают capacity 4, хотя `calculate` отвечает на них 400. Для
attach/validate это означает «окна, которых нет в статической геометрии». Ёмкость при этом
безопасная (4), поэтому P3, а не P2. Если Lead хочет строгий контракт — вызывать
`PresetId::parse`/`has_explicit_size` и валидировать схему (manual ∪ codian), как в pitfalls §4.1.

### 3.2 `calculate` и `preset_default_13`

`POST /api/v3/ui/video_layouts/calculate {"preset":"preset_default_13"}` → **400**, тело
`{"error":{"code":400,...,"details":[{"reason":"invalid.preset","position":"preset"}]}}` (выполнено).
`is_known_preset` = manual ∪ codian, `Default` туда не входит (`shell.rs:719-744`,
`preset.rs:681-683`). Серверную валидацию не трогали — правильно.

### 3.3 §13 `LAYOUT_ENGINE.md` — в основном верно, одна фактическая неточность (P3-7)

Правильно: 400 ожидаем; `Default` не manual/Codian; `preset_size = 13`, но число в id не делает
пресет manual; оракул не должен требовать ровно один `reportError`; ослаблять сервер нельзя.

Неточно: «его геометрия строится движком по числу участников, поэтому у `calculate` нет таблицы
координат, которую можно вернуть» (`LAYOUT_ENGINE.md:252-266`). Таблица есть:
`preset::geometry(PresetId::parse("preset_default_13"))` идёт в `PresetScheme::Default =>
equal_slots(count)` (`preset.rs:632-654`, `:647`) и в manual-режиме шлюз реально применяет
13 фиксированных ячеек. 400 — это **политика реестра** (`calculate` отдаёт только статические
manual/Codian/конструктор-схемы, а Default — auto-композит), а не отсутствие координат.
Формулировку стоит поправить: «геометрия Default в auto зависит от числа участников; в manual
она вырождается в equal(N), но это не тот контракт, который обещает `calculate`».

Дополнительно: `BACKEND_RULES.md` §4.6 (единый порядок capacity / 400 для auto/base id) так и не
добавлен — файл заканчивается на §4.5 (`BACKEND_RULES.md:174`), хотя pitfalls §3.4 и мастер-план
его перечисляли. P3-7.

## 6. E2E-оракул — **PARTIAL, вживую не проверялся**

Статически `tests/e2e/layout_constructor_ui.js:315`:

```js
pageErrors.length === 0 && reported.unexpected === 0
  && reported.expected === vendor400Count && vendor400Count >= 1
```

- Хрупкого `=== 1` больше нет: ожидания `reportError` сверяются с фактическим числом 400
  (`reported.expected === vendor400Count`), неожиданные ошибки = 0, `pageErrors` = 0. Обёртка
  `reportError` неизменяема, `__vksReport` живёт в Node, provenance проверяется по axios-полям
  (`config.url`, `config.data` содержит `preset_default_13`, `status===400`, `request`).
  Это соответствует требованию «`unexpected===0`, expected соответствует факту».
- **Сценарий не доказан стабильным.** Комментарий перед проверкой сам говорит, что вендорских
  400 может быть 0/1/2, но ассерт требует `vendor400Count >= 1`: если вендор в этом прогоне не
  перерисует auto-превью и не сходит в `calculate`, тест красный без регрессии. Остались
  фиксированные `waitForTimeout` (`:166`, `:170`, `:207`, `:293`) вместо ожидания ответа/селектора.
- `calculate.length >= 7` (`:317`) — слабый счётчик (pitfalls P2-12), конкретные пресеты не
  проверяются.
- `BASE` по умолчанию — `http://127.0.0.1:8080` (`:21`), т.е. запуск «по умолчанию» бьёт в живой
  сервер/`vks_data.db`. Для ревью я его не запускал; это операционный риск, а не серверный дефект.
- **Не проверено:** реальный браузерный прогон (Playwright/Chromium не запускались), ephemeral
  инстанс с БД в `/dev/shm` не поднимался, фактическое число вендорских перерисовок не измерено.
  Поэтому «оракул стабилен» — только статический вывод: `===1` убран, но `>=1` + таймауты
  оставляют P2-5. В CI e2e нет, так что зелёный CI это не доказывает.
