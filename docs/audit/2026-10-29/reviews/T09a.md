## §2. P1 (функциональные дефекты эффективного change-set)

### P1-1. `start_recording` не «persists immediately»: fire-and-forget и проглоченные ошибки

`RecorderManager::start_recording` кладёт запись в RAM и запускает запись в storage в фоне, не ожидая и не логируя результат:

- `crates/vks-server/src/recorder.rs:174-179` — `state.records.insert(...)`; `tokio::spawn(async move { let _ = storage.upsert_record(&entry).await; })`.
- Комментарий рядом (`:160-161`) утверждает «Persist the new record immediately», что неверно: это отложенная задача.

**Почему это видно снаружи.** `collect_records` предпочитает storage и при успешном (даже пустом) ответе **не** смотрит в RAM (`crates/vks-admin/src/api_v3/observability.rs:671-677`). Значит сразу после `POST .../videorecords` возможен `GET /api/v3/videorecords` → `count:0`, пока фоновый upsert не выполнился. Это гонка чтения после записи, а не только «теоретическая задержка».

**Ошибки не наблюдаемы.** `let _ =` в `start` (`:177`), в sync-stop (`:272-274`) и в `stop_recording_async` (`:315-317`) — ни `warn!`, ни метрики, ни возврата ошибки. При недоступном/залоченном storage API отдаст успешный старт, но запись не сохранится; обещание «background persistence errors are observable» не выполнено.

**Мой harness** (временный, удалён): старт через реальный `RecorderManager` + `SqliteStorage`; строка появляется в БД только после ожидания (до 1 с), т.е. синхронной гарантии «сразу» нет. Код `tokio::spawn` — детерминированное доказательство.

### P1-2. RBAC старта/остановки — Operator-only, а матрица требует Moderator+

`videorecords_start` и `videorecords_stop` проверяют `forbid(&auth)` (`observability.rs:753,804`), а `forbid` пропускает только `Role::Operator` (`observability.rs:40-45`).

Спека:

- `vks-core/src/participant.rs:253-274` — `ManageRecording` разрешён **Moderator + Operator**; тесты `:355,370,385` это фиксируют;
- `docs/audit/2026-10-29/04_infra_l5l7.md:349` — «POST … (start, Moderator+)».

Итог: Moderator получает `403 Forbidden: Operator role required`, хотя по матрице должен управлять записью. Теста на роль Moderator/Viewer для новых роутов нет (в тестах только admin-токен). Формально это согласуется с тем, что все мутации `/api/v3` сейчас Operator-only, но приёмочная матрица T09a — Moderator+, поэтому это расхождение продукта и тестов, а не косметика.

### P1-3. Активная запись отдаётся с `stopped_at == started_at`

`record_json` вычисляет `stopped_at = started_at + duration_sec` (`observability.rs:647-652`). Запись, созданная на старте, имеет `duration_sec = 0` (`recorder.rs:164-173`), поэтому вендорский список сразу видит **завершённую** запись длительностью 0 секунд, пока запись ещё идёт. После stop та же строка обновляется — но до stop UI показывает ложный `stoppedAt`.

Для активной записи корректно `stopped_at: null` (или отдельный признак активности). Приёмочный пункт «JSON fields … stopped_at correctness» не выполнен. Существующий тест `videorecords_report_the_stored_profile...` проверяет только завершённую запись (`duration_sec: 61`, `observability_tests.rs:637-660`), активный случай не покрыт.

### P1-4. Рестарт: активная строка остаётся «вечной», повторный старт плодит дубликат

Проверено harness'ом (реальный `RecorderManager` + `SqliteStorage`, временный файл в `/dev/shm`):

```text
PERSISTED IMMEDIATELY (within 1s): true
HYDRATED AFTER RESTART: RecordEntry { ..., duration_sec: 0, size_bytes: 0, ... }
STOP AFTER RESTART: Err(NotStarted)
ROWS AFTER RESTART+RESTART: 2
```

Что это значит:

- после рестарта `state.records` гидратируется (это работает), но `RecorderManager.sessions` пуст; остановить «запись», начатую до рестарта, нельзя — `stop_recording_async` → `NotStarted`, а `RecorderControl::stop` сначала видит `is_recording == false` и возвращает `Ok(())` (`recorder.rs:50-56`), т.е. API отвечает 200, но строка остаётся с `duration_sec = 0`;
- повторный `start` после рестарта создаёт новую сессию и новую строку на ту же комнату (idempotency-проверка живёт только в RAM, `recorder.rs:120-124`), в БД появляются 2 записи.

«Запись переживает рестарт» верно только для метаданных; активная запись после рестарта не финализируется и не помечается остановленной. Для приёмки T09a это нужно либо явно объявить (и тогда закрывать строки на cold start), либо реализовать восстановление/финализацию.

## §3. P2 (замечания)

1. **`profile` может стать строкой `"null"`.** При `width == 0 || height == 0` `record_json` делает `Value::Null.to_string()` → JSON `"profile": "null"` (строка), а `resolution` → `[0,0]` (`observability.rs:658-665`). Для легаси/нулевых строк UI покажет мусор. Ожидаемо: `null` (JSON null) и fallback на дефолтный профиль либо `null` resolution.
2. **Клампы размеров не те, что в плане.** `RecorderProfile::new` ограничивает W/H `2..3840` / `2..2160` (`profile.rs:33-38`), а pitfalls/зона требовали W 160–1920, H 120–1080 (`pitfalls/T09a.md:203`). Сейчас можно объявить 4K-профиль, хотя «vendor-visible range» в doc-комментарии обещает иное. Приёмочные клампы (64–8192 kbps, 15–60 fps, even) при этом соблюдены.
3. **Профиль не берётся из комнаты/запроса.** `RecorderControl::start(room_id)` не принимает профиль (`state.rs:136-143`), `start_recording` всегда использует `RecorderProfile::default()` (`recorder.rs:163,255`), тело `settings`/`profile` только эхо-возвращается (`observability.rs:756,784-788`). Для 640×360-комнаты API всё равно отдаст 1280×720/2350. Это declared-профиль, а не измеренный, но и не фактический таргет комнаты. В миграции 0006 нет `fps`/`profile` (только `bitrate_kbps/width/height`, `0006_video_records.sql:2-12`) — отклонение от схемы, предложенной в `04_infra_l5l7.md:333`; `profile` синтезируется как `"WxH"`.
4. **Одна повреждённая строка ломает весь список.** `record_from_row` возвращает `Err` на невалидный `room_id` (`core_adapter.rs:18-49`), `list_records` — `collect::<Result<...>>`, т.е. падает целиком. Проверено harness'ом: `get_record("bad")` → `Err(... invalid video_records.room_id ...)`, `list_records` → `is_err=true`. Паники нет (требование «не паниковать» выполнено), но API молча падает в RAM-fallback (`observability.rs:673-676`), а гидратация — в пустой список (`state.rs:632`, `unwrap_or_default`), без `warn!`.
5. **Stop-роут: нет 404 и connectionId игнорируется.** `videorecords_stop` не проверяет существование комнаты/записи (в отличие от start, `:757-762`), для валидного-но-неизвестного UUID вернёт 200 (`observability.rs:807-819`); `connection_id` не сверяется с активной записью, а в ответе возвращается именно он, не record id (`:814`). Для вендора это терпимо, для контракта «404s / stop route» — неточно.
6. **Soak — только арифметика.** `farm_soak_budget` и константы (`farm.rs:277-288`) нигде не используются, кроме собственного unit-теста (`:1478-1489`); release-soak harness'а `tests/farm_group_soak.rs` в коммите нет, измерение RSS/`malloc_trim` не добавлено. Приёмка «soak budgets arithmetic» формально закрыта, но гейта, который бы это проверял на живой ферме, нет.
7. **`estimated_time` по-прежнему блокирует async-рантайм.** `df -Pk /` через `std::process::Command` в async-хендлере (`observability.rs:841-850`); параметр `quality` игнорируется. Это pre-existing, но T09a менял именно эту функцию. Sanity проверена расчётом: на этом хосте `df` даёт 51 362 492 416 байт → `51362492416 / (2350*1000/8) = 174 851 с`, а не 3600.
8. **Probe не фильтрует `canvas_version`/`cancel`.** `active_h264_groups` смотрит только `room + H264 + viewers > 0` (`recorder.rs:58-68`); `GroupStat` не отдаёт `cancel` (`farm.rs:290-305`). Сейчас `retire()` удаляет группу из map синхронно (`farm.rs:622-624`), поэтому риск низкий, но семантика «активная группа» слабее, чем в pitfalls T5.
9. **Scope/history noise.** В `650a55f` попал посторонний `docs/audit/2026-10-29/pitfalls/T04b.md` (+409 строк). Сам T09a размазан по трём коммитам: гидратация — в `5d46507` (T02), контракт — в `8af77db` (T11a), остальное — в `650a55f`. Ревью «одного коммита» невозможно; это же и причина P0-1.
