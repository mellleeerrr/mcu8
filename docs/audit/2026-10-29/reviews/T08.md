## §3. Сервер: per-room effective mode, а не только boot config

**Код.**
- `SignalingHandler::on_join_room` (единственный литерал `JoinRoomResult`) кладёт `room_mode: self.config.room_mode` (`crates/vks-signaling/src/handler.rs:332-340`, поле — `:339`). `HandlerConfig::default_test()` = `1` (SFU), `with_room_mode` синхронно правит `caps.room_mode` (`handler.rs:70-72, 96-101`). Это дефолт/глобальный режим, не per-room.
- `vks-server` после `register_participant` обогащает ответ и **перезаписывает** `res.room_mode` из `ModeState::effective_mode(&rid)` (`crates/vks-server/src/lib.rs:1299-1311`). Fallback — `SFU`, не паника (`lock().ok()`, `unwrap_or`).
- Late-joiner push `RoomModeChanged` добавляется в тот же `replies` после ответа, при `effective != SFU || switch_epoch > 0` (`lib.rs:1317-1339`).

**Исполняемое доказательство.**
1. `test_signaling_ws_handshake` (дефолтная комната) ассертит `res.room_mode == Sfu` (`network_integration.rs:238-241`) — **passed**.
2. `test_package_d_mcu_pipeline_handover_and_pnm_control_events`: комната `room-pkg-d` переключается per-room в MCU (`network_integration.rs:1305-1318`), HandlerConfig при этом — `default_test()` = SFU (`:1141-1148`). Поздний **Carol** получает `JoinRoomResult.room_mode == Mcu` (`:1483-1489`) — **passed**. Это и есть доказательство, что boot-конфиг не «протекает»: без overwrite он был бы SFU.
3. **Revert-эксперимент:** в `/dev/shm/t08review-exp` заменил блок `lib.rs:1299-1310` на принудительный `res.room_mode = Sfu`; Carol-тест упал ровно на этом ассерте:

 right: 2   // MCU из per-room override

Значит overwrite-путь реален и именно он делает ответ авторитетным.

**Остаточное (P2):** `ServerHello` по-прежнему отдаёт `self.config.room_mode` (`handler.rs:282-289`) и для per-room MCU-комнаты может говорить SFU; `JoinRoomResult.caps` всегда `None` (`handler.rs:338`). ## §6. Порядок join/push и «двойное переключение»

Сервер кладёт в `replies` сначала `JoinRoomResult`, затем `RoomModeChanged` (`lib.rs:1328-1339`), оба уходят по сокету по порядку. SDK:
1. применяет снимок `room_mode` в `start_async` (`conference.rs:249`), затем ставит `Active` (`:259`);
2. только после возврата join регистрирует push-хендлер (`:266`).

Следствия:
- push, прочитанный транспортом **до** регистрации, отбрасывается; снимок уже применён — режим не теряется (ровно та же гонка, что S9 закрыл для layout);
- push, доставленный **после** регистрации, кладёт `ModeChanged` в очередь; `drain_events` вызывает `switch_mode` с тем же значением (`:122-125`). `MediaEngine::switch_mode` — просто присваивание поля (`media_engine/mod.rs:77-79`), без renegotiation/unsubscribe, поэтому **функционального двойного переключения нет**;
- но UI получает лишнее событие `ModeChanged` для уже применённого режима. Probe `room_mode_push_after_join_is_reemitted_as_event` подтверждает: `events.len()==1` при уже `Mcu`.

**Оценка:** для T08 это acceptable (режим идемпотентен, ренегоциация §8 всё равно вне T08). Полноценный фикс — дедуп по текущему `media.mode()` или `switch_epoch` в SDK-событии; это P3, не блокер.

### P1-1. Rejoin-refresh не покрыт тестом; negative control не падает

- **Где:** `client/vks-client-sdk/src/conference.rs:368-379` (строка `:375`); upstream `PushTransport` жёстко отдаёт `Unspecified` (`conference.rs:596`), поэтому ни один rejoin-тест не может сменить режим.
- **Факт:** после удаления `:375` все **52** SDK-теста зелёные; после удаления `:249` — падает.
- **Почему P1:** это ровно та P1-ловушка №1 из pitfalls, которую T08 обязана была закрыть; коммит `018badd` заявляет rejoin-refresh, но не защищает его. Регрессия в этой строке пройдёт незамеченной.
- **Фикс:** добавить в `PushTransport` поле `join_mode` (или отдельный транспорт) и тест: `start(Sfu) → set(Mcu) → reconnect → Mcu`; плюс `Mcu → Unspecified → reconnect → Mcu`. Мой probe — готовый образец, но он вне репозитория.

### P2-1. `Unspecified` fallback не покрыт upstream-тестом

`apply_room_mode` ветка `_ => {}` (`conference.rs:98-104`) не проверяется: `join_auto_selects...` тестирует только SFU/MCU (`:482-496`), а `MockSignaling::ok()` с `room_mode: 0` (`signaling_client.rs:220`) нигде не ассертит «режим остался прежним». Мой probe (`rejoin_unspecified_keeps_current_mode`) проходит, но upstream-защиты нет.

### P2-2. Приоритет двух носителей режима не зафиксирован

`RoomCaps.room_mode = 1` (`crates/vks-proto/proto/media.proto:47-54`) и `JoinRoomResult.room_mode = 7` (`signaling.proto:91`) — два носителя. В `JoinRoomResult` `caps` всегда `None` (`handler.rs:338`), SDK `caps` вообще не хранит (`signaling_client.rs:26-41`), а в `ServerHello` `caps.room_mode` отражает **глобальный** режим (`handler.rs:288-289`). Для per-room MCU-комнаты `ServerHello.caps.room_mode` может говорить SFU, пока `JoinRoomResult.room_mode` говорит MCU. Ни proto-комментарий, ни `SIGNALING_PROTOCOL §3.2`, ни тест приоритет не фиксируют.

### P2-3. `HandlerConfig.room_mode` — глобальный; per-room знает только `vks-server`

`HandlerConfig` (`handler.rs:36`), дефолт `1` (`:70-72`) и `on_client_hello` (`:288`), `on_join_room` (`:339`) используют одно поле. Авторитетная per-room подстановка живёт только в `vks-server` (`lib.rs:1299-1311`). Любой другой хост `vks-signaling` (WT — T13, тестовые хосты) получит глобальный режим; `ServerHello` уже сейчас расходится с `JoinRoomResult` для per-room override. T12/T13 должны либо резолвить режим на `ClientHello`, либо централизовать overwrite в handler-обёртке.

### P2-4. В SDK нет proto-декодера/реального транспорта — поле заполняют только моки

`JoinRoomResult.room_mode` — домен-поле (`signaling_client.rs:40`), но ни одного `prost::Message::decode` в SDK нет; `MockSignaling` — единственный источник (`:207-266`). Acceptance «SDK выбирает конвейер» проверен на уровне доменной структуры, не на байтах. Это осознанный долг фазы 8 (реальный WS/WT транспорт), но при его появлении нужна явная конверсия `i32 → RoomMode` с обработкой unknown, иначе `try_from`/match разъедется.

### P2-5. Resume не узнаёт смену режима за время обрыва

Resume-ветка (`conference.rs:338-355`) не несёт `JoinRoomResult` и не читает `ServerHello.room_mode`; SDK-структура `ServerHello` (`signaling_client.rs:15-24`) поля режима не имеет. Если комната переключилась, пока клиент был отключён, до следующего admin-push он останется в старом конвейере. Acceptance прямо разрешает «resume keeping current», поэтому это P2-долг, а не P1; канонический фикс — `room_mode` в `ServerHello` (поле 6 уже на проводе) для resume.

### P3-1. Дублирующийся `ModeChanged` после join

См. §6. `RoomModeChanged`, пришедший сразу после `JoinRoomResult`, порождает лишнее UI-событие для уже применённого режима. `switch_mode` идемпотентен, функционального двойного переключения нет. Дедуп по `media.mode()` или `switch_epoch` — задел T12.

### P3-2. Доки: пример в `ARCHITECTURE.md` всё ещё выбирает по `server_hello.room_mode`

Текст §2.1 (`ARCHITECTURE.md:81-84`) правильно говорит «SDK выбирает по `JoinRoomResult` при входе и rejoin», но code sample ниже (`:93-95`) — `match server_hello.room_mode`. `SIGNALING_PROTOCOL §3.2` (`:111`) содержит только поле 7 без семантики «снимок на момент join / авторитет effective_mode / rejoin». Doc-дрейф не влияет на код, но ревьюер/клиент может выбрать неверный источник.

### P3-3. wasm-гейт узкий: `--all-targets` падает

CI проверяет только lib (`ci.yml:90`), `cargo check -p vks-client-sdk --target wasm32-unknown-unknown --all-targets` — **101** (`mio` wasm unsupported, `E0432`), потому что dev-dependency `tokio` не загейтена по таргету (`client/vks-client-sdk/Cargo.toml:62-63`). Это известно из pitfalls №7 и не входит в acceptance T08 («wasm32 check» = lib), но остаётся P3.

### P3-4. Proto-тест не пинит тег и не проверяет «старого клиента»

`vks-proto/src/lib.rs:43-72` roundtrip-ит через ту же структуру; «old client ignores tag 7» не проверен отдельной legacy-структурой, байтовый пин тега 7 отсутствует. Поле/тип фактически верны (generated `tag = "7"`, `enumeration = RoomMode`), но регрессия номера тегом не ловится.

### P3-5. Fallback на SFU при poisoned `mode`-mutex

`lib.rs:1301-1306` при `lock().ok() == None` молча отдаёт SFU. Паники нет (хорошо), но для MCU-комнаты это неверный ответ; poisoning означает панику в другом месте, поэтому риск низкий.
