### 1.3. Следствия для T11b (до реализации)

1. **Вендорского патча для mids не существует.** Нет якоря «до», который можно заменить на «1 sendrecv + 7 recvonly»: в бандле нет ни одной строки, создающей m-line. Любая реализация `patch-pnm-webrtc-mids.py` будет либо (а) вечно красной, либо (б) вставлять мёртвую строку/комментарий, чтобы «гейт» стал зелёным. Вариант (б) — **фальсификация гейта**, он не проверяет поведение и нарушает принятую в репозитории семантику fail-closed (`pnm_patch_lib.py:6-13`).
2. **«Вендор рендерит только 2 удалённых пира» — тоже неверно**: UI вообще не рендерит удалённых пиров через WebRTC (нет ни SDP, ни `srcObject` на удалённые треки; `srcObject` встречается только в локальном `grabFrame`/image-capture, `index.bundle` байты 802989/803490/808703). Утверждение из задания описывает не этот код.
3. **Реальный клиент — `tests/e2e/webrtc.js`** (537 строк): он строит оффер через `pc.addTrack(...)` (`:233`) + `pc.createOffer()` (`:234`) — то есть ровно 1 audio + 1 video. Здесь и живёт клиентская половина T11b; здесь же оракул «третий = `room_full`» (`:402-425`).
4. **8 mids в answer — не «нельзя по RFC 3264», а обязательно.** RFC 3264 §6: answer обязан содержать столько же m-line, сколько offer, в том же порядке; менять число/порядок нельзя. План (`:63`) сформулирован наоборот и может подтолкнуть реализатора к «сервер сам добавит mids» — это невозможно; mids создаёт **клиент** в оффере, сервер лишь отвечает `sendonly` на `recvonly`-секции (и `inactive`, если не хочет принимать).

**Вердикт:** T11b — **серверная** задача + правка единственного клиента-теста. Вендорский патч из плана надо снять или заменить на честный drift-check (см. §5.1). Это решение требуется от Lead (§10, D1).

## §3. Политика это или рендеринг: ответ

- **Только серверная политика** (слои A–D выше) + **тест-клиент**. Вендорский UI не участвует: у него нет ни SDP, ни лимита участников (§1.2). Конфиг-доки и `BACKEND_RULES` описывают ёмкость как серверную: `deploy/README.md:81-88`, `WEBRTC_TRANSPORT_2026-10-22.md:48-50,84`, `BACKEND_RULES.md:231` (env — единственный канал секретов/лимитов, но лимиты ёмкости — не секреты).
- **`MEDIA_PIPELINE.md:26-31`** рисует SFU как «A publish → forwarder → B subscribe» — то есть модель «один паблишер на подписчика», из которой и вырос `mid_for_kind`. `:156` («SFU: N unmixed (client Web Audio mix)») уже предполагает **N аудиопотоков у клиента**, что противоречит «1 audio mid» из плана T11b — см. П0-3.
- **Вывод:** cap=2 — это следствие дизайна egress (один mid на kind), а не «забытая константа». Политика «сколько пиров» должна быть конфигурируемой, но снимать её можно только вместе с per-source mid.

## §4. Минимальный корректный дизайн

### 4.1. SDP-контракт (что именно предлагает клиент)

Для комнаты до N пиров каждый клиент предлагает:

```
1 × audio sendrecv   (свой микрофон)
(N−1) × audio recvonly  ← обязательно, если нет серверного микшера
1 × video sendrecv   (своя камера)
(N−1) × video recvonly  (до 7 при N=8)
```

- Порядок m-line фиксирован: сначала все audio, затем все video (иначе `accept_reoffer` `keeps_prefix` и `mids_of`-порядок ломаются, `webrtc.rs:199-235`).
- Сервер отвечает тем же числом m-line в том же порядке: на `sendrecv` → `sendrecv`, на `recvonly` → `sendonly`. Для 7 пустых video-секций писать в них можно начинать позже — направление уже согласовано, реоффер не нужен (это и есть смысл pre-offer).
- `validate_offer` (`webrtc.rs:464-500`) расширить: `audio <= MAX_AUDIO_MIDS`, `video <= MAX_VIDEO_MIDS` (8/8 по умолчанию, конфигурируемо), `audio+video >= 1`, остальные проверки (ICE, fingerprint, Opus/VP8) сохранить. Верхний предел обязателен: иначе оффер с 500 m-line = дешёвый DoS (SDP ≤ 64 KiB уже проверяется, `:465-467`, но 500 m-line в 64 KiB влезают).
- `offer_publishes_video` (`webrtc_room.rs:838-860`) сейчас классифицирует **только первую** video-секцию и делает `break` на второй (`:847-850`). При 1 sendrecv + 7 recvonly это случайно верно, но при обратном порядке (recvonly первой) даст `false` → PLI не запросится, гейт не взведётся. Переписать: `any(video section is sendonly|sendrecv)`.
- Направление каждой секции брать из `Event::MediaAdded.direction` (`str0m-0.24.1/src/media/event.rs:47-63`), а не угадывать по порядку строк: сейчас `webrtc.rs:414-418` обновляет только `mid_audio`, направление теряется.

### 4.2. Модель `(publisher, kind) → mid` (минимальная, без новых зависимостей)

`WebRtcPeer` уже владеет сессией и mids; `PeerCommand::Write` уже несёт `from` (`webrtc_room.rs:543-552`, добавлено в T11a) — значит маппинг можно держать **внутри** `WebRtcPeer` и выделять mid лениво в `run_peer`, без `Arc<Mutex<…>>` в горячем пути:

```rust
struct PeerMids {
    video_tx: VecDeque<Mid>,     // из answer: sendonly/sendrecv video, кроме своего publish-mid
    audio_tx: VecDeque<Mid>,
    src_video: HashMap<ParticipantId, Mid>,
    src_audio: HashMap<ParticipantId, Mid>,
    retired: HashSet<Mid>,       // mid, уже отдававший другого паблишера
}

impl WebRtcPeer {
    fn mid_for_source(&mut self, from: ParticipantId, audio: bool) -> Option<Mid> {
        let map = if audio { &mut self.src_audio } else { &mut self.src_video };
        if let Some(mid) = map.get(&from) { return Some(*mid); }
        let pool = if audio { &mut self.audio_pool } else { &mut self.video_pool };
        let mid = pool.pop_front()?;            // пул исчерпан → None, не паника
        map.insert(from, mid);
        Some(mid)
    }
}
```

Правила:

1. **Пул исчерпан → дроп кадра + метрика**, не отказ пиру и не второй источник в тот же mid. Новый лейбл: `webrtc_frames_dropped_total{reason="no_egress_mid"}` (`metrics.rs:84-86` — `IntCounterVec`, лейбл добавляется без миграции).
2. **Никогда не писать два паблишера в один mid** — это и есть исходный инвариант (`webrtc_room.rs:34-37`).
3. **Легаси-клиент 1+1** в комнате на 3: пул = 1 → первый паблишер получает mid, остальные дропаются с метрикой. Политика «кого первого» должна быть детерминированной: порядок регистрации пиров / `SubscribeRequest.sources` (сейчас `targets_for` источник не фильтрует, `webrtc_room.rs:479-500`). Явно задокументировать + метрика; **не** делать вид, что клиент «увидит всех».
4. **Освобождение mid при уходе паблишера:** `registry.remove()` не может дотянуться до `WebRtcPeer` другого пира. Варианты: (а) `PeerCommand::DropSource{from}` рассылкой по комнате (≈25 строк) и **retire** mid (не возвращать в пул: SSRC/часы нового источника прыгнут); (б) не освобождать вовсе — пул на сессию, при исчерпании новый паблишер не виден до реоффера. Рекомендация: (а) + retire + метрика `retired`; возврат в пул — только с новым поколением `generation` и обязательным IDR-гейтом, и это отдельное решение.
5. **Ключ гейта — `(from, mid)`**, но `forward` видит только `from` (mid выбирается в задаче подписчика). Поэтому на `PeerHandle`: `waiting: Arc<Mutex<HashSet<ParticipantId>>>` (+ `waiting_all: AtomicBool` на «всё, что придёт после подписки»). `forward` (`webrtc_room.rs:533-560`): если `!audio && target.is_waiting(from) && !is_keyframe` → дроп + `request_keyframe_from`; на keyframe — `remove(from)`. Переарм: insert при join, при `video:false→true` (`set_subscription`, `:430-441`), при `queue_full` (`:559`). T11a прямо предупреждал (`T11a.md:149-150`).
6. **PLI-коалесинг** — на `(publisher, audio)` в `request_keyframe_from`/`request_keyframe` (`:502-531`), а не один `last_keyframe_request` на пира (`:657-663`), иначе 7 источников дают 7×PLI/с.
7. **`request_keyframe` и `Connected`-PLI** (`webrtc_room.rs:713,797`, `webrtc.rs:329-333`) должны брать mid **своего publish-направления**, а не `mid_for_kind(false)` (первый video). Иначе PLI уйдёт в `recvonly`-секцию, где writer есть, а источника нет.

### 4.3. Снятие cap

- Заменить `pub const MAX_PEERS_PER_ROOM: usize = 2` на `VKS_WEBRTC_MAX_PEERS_PER_ROOM` (default 8), читать один раз в `WebRtcRoomRegistry::new` (рядом с `max_peers`, `webrtc_room.rs:153-159`).

Для нового ключа — как порты: ошибка парсинга/`0` = отказ старта (`webrtc_runtime.rs:97-115` — образец fail-closed с exit 78). Иначе опечатка `VKS_WEBRTC_MAX_PEERS_PER_ROOM=8x` даст дефолт, и «почему 2?» будет неотлаживаемо.

### 4.4. Аудио — главный пропущенный пункт плана

`vks-media-sfu/Cargo.toml:18-37` не содержит Opus-декодера; в crate нет микшера; `MEDIA_PIPELINE.md:156` честно говорит «SFU: N unmixed (client Web Audio mix)». Значит:

- При N≥3 и **одном** audio-mid два паблишера пишутся в один Opus-поток: разные `MediaTime`/seq/SSRC-контекст → второй голос не декодируется (или «квакает»). Это не гипотеза: `webrtc_room.rs:533-560` форвардит любой `MediaData` в `mid_for_kind(true)`, `write_media` пишет в один `Writer` (`webrtc.rs:377-388`; маппинг PT — `:313-327`).
- Корректных вариантов три: (а) **N−1 recvonly audio-mid** (без транскодинга, клиент играет несколько `<audio>`/WebAudio — соответствует `MEDIA_PIPELINE.md:156`); (б) серверный микс Opus (декод+микс+энкод; в проекте есть `vks-gateway-sip/src/opus.rs`, но это новый CPU-контур и отдельная задача); (в) «слышен только один» (active speaker в `vks-media-sfu` не реализован — отдельная задача/T12).
- **Рекомендация:** (а), и формулу плана изменить на «1 + (N−1) audio-mid, 1 + (N−1) video-mid». Если Lead выбирает (в) — это осознанная деградация, её надо записать в приёмку T11b, иначе «3+ пира» будут без звука.

### 4.5. Запись/ферма (почему не входит в T11b)

Браузерные кадры не попадают в MCU-композит: `gateway_video.rs:684,890` — единственный путь `set_participant_frame`/`publish_video_frame`, и он от FFmpeg-декодера шлюза. Рекордер — участник `RoomHub` (`recorder.rs:183-196`), не пир (подтверждено `T09b.md:386,395`). Поэтому «recording farm view на >2 источников» для браузеров = T12 (P5-3) после ingress VP8/H264. **T11b не должен обещать запись 3 браузеров**; в e2e — только SFU-комната без записи.
