### 1.7 Память фермы и «66 групп → 579 MB»

- 579 MB — это `[heap]` **RSS родителя** после 12 ч 56 мин, за которые произошло **66 start/stop** групп, при **0 живых ffmpeg** на момент снимка (`08_live_runtime.md:139,146`). Пик cgroup за прогон — 669.5 MB (`:146`).
- Корреляция: 66 · ~9 MB ≈ 594 MB; 17 групп → 235 MB; явно названа **гипотезой** «~9–10 MB удерживается на каждую **завершённую** группу (буферы/Arc/аллокатор)», а не измеренным per-group бюджетом (`08_live_runtime.md:148`, тезис 3 — `:313-314`, контр-тезис 8 — `:334`).
- В коде **нет** ни одного измерения памяти: `grep -rn "VmRSS\|VmHWM\|malloc_trim\|jemalloc\|MALLOC_ARENA" crates/` → пусто; аллокатор — системный glibc (в `Cargo.toml`/`.cargo/config.toml` нет ни jemalloc, ни mimalloc; `.cargo/config.toml:22-23` — `target-cpu=native`).
- Замер на этом хосте (команда в §2-T7): один **живой** 720p30-энкодер фермы (ffmpeg 8.0.1, ровно аргументы `spawn_ffmpeg`, `farm.rs:926-984`) даёт **VmHWM ≈ 52 MB**; 360p30 — 52.9 MB (фиксированные буферы ffmpeg/x264). 66 одновременных детей ≈ 3.4 GB — этого не было (пик cgroup 669.5 MB), т.е. «66 групп» — **последовательные** старт/стопы, а не 66 живых групп.
- Лимит 128 групп (`farm.rs:1085-1094`) не выведен из памяти: 128 · 52 MB детей ≈ 6.6 GB, 128 · ~9 MB удержанного heap ≈ 1.15 GB. Бюджета в коде нет.

### T2. Миграция: новая 0006, portable SQL, `reset()` и живая БД

**Тезис.** Таблица нужна новая (`0006_video_records.sql`); править 0001–0005 нельзя — `sqlx::migrate!()` хранит checksum применённых миграций, и любая правка уже применённого файла ломает старт на существующей БД («migration was previously applied but has been modified»). Плюс `Storage::reset` обязан чистить новую таблицу, иначе семантика reset разъедется между Memory и SQL.

**Доказательство.** Миграции вкомпилированы: `sqlx::migrate!().run(...)` — `crates/vks-storage/src/sqlite.rs:99-102`, `postgres.rs:107-110`. ### T3. Гидратация: порядок, hot-reload и «RAM всё равно игнорируется»

**Тезис.** Наивное «добавить `list_records` в `sync_from_storage_inner`» даёт три дефекта: (а) hot-reload (`POST /system/restart_services`) начнёт перечитывать записи и воскрешать/дублировать их; (б) гидратация может затереть только что добавленную запись, если выполняется после старта записи; (в) API всё равно читает storage напрямую, поэтому тест «после рестарта count>0» пройдёт и без гидратации — нужен тест, который смотрит **и** на `state.records`.

**Доказательство.** Одна функция на cold start и hot reload — `state.rs:548-559`; внутри — `entry().or_insert_with` для rooms/users (`:575`, `:590`) и безусловная перезапись settings (`:648-655`). `collect_records` предпочитает storage (`observability.rs:667-674`) и глотает ошибку (`if let Ok`). Единственный вызов — `main.rs:161`.

**Проверка.**
```bash
cargo test -p vks-admin --locked api_v3::observability_tests::videorecords_survive_sqlite_restart
cargo test -p vks-admin --locked api_v3::observability_tests::hot_reload_does_not_duplicate_records
```
Тест рестарта — по образцу `sessions.rs:2228-2270` (два `AppState::with_storage` на одном хранилище), но с `SqliteStorage::init("sqlite:///tmp/…/t.db?mode=rwc")` (dev-dep `vks-storage` уже есть — `crates/vks-admin/Cargo.toml:35`): state1 → POST/stop → state2 + `sync_from_storage()` → `GET /api/v3/videorecords` = 1 **и** `state2.records.len() == 1`.

**Решение.** Гидратировать только при `mark_stopped == true` (cold start), вставкой `entry().or_insert` (не перезапись); при ошибке storage — `warn!`, не молчать; `collect_records` оставить storage-first, но ошибку логировать.

### T4. Форма API и ожидания вендорского UI: id, `/static/…`, POST-путь, resolution

**Тезис.** Четыре несовместимости, которые ломают UI или контракт:
1. `POST` старта, который зовёт UI, — `/api/v3/sessions/{id}/videorecords` с произвольным телом `settings`; у нас на этом пути только `GET` → 405. Добавлять POST надо **на тот же** `route` (или merge-роутером), а не вторым `route` с `get` — axum паникует только при дубле **того же** метода (`method_routing.rs:1055-1060`), разные методы merge'атся.
2. `payload.src`/`payload.preview` UI **безусловно** клеит к `/static/videorecords/` (`"/static/videorecords/".concat(t)`), поэтому `null` превращается в `/static/videorecords/null`: `src` оставить `record.id` (это же имя будущего файла T09b), `preview:null` — известная косметика до T09b, не «чинить» в T09a.
3. `payload.resolution` уходит в шаблон как есть (`li` в бандле — это `toValue`, а не форматтер) — сохранить текущую форму `[w,h]`, не `"1280x720"`.
4. `POST` возвращает **room uuid**, а не id записи: `start_recording` отдаёт `*room_id.as_uuid()` (`recorder.rs:133`; идемпотентная ветка — `:70-72`), тогда как `RecordEntry.id = meta.id` — свежий UUID (`recording.rs:225`, `recorder.rs:184`). Тест это закрепляет: `assert_eq!(rec_id, *room_id.as_uuid())` (`network_integration.rs:1573`).

**Доказательство (вендор).** Бандл однострочный, поэтому offset'ы: `index.bundle-2.2.1.66.js` — `startSessionRecord` (offset 1026446): `POST /api/v3/sessions/{id}/videorecords`, тело = `settings`; `stopSessionRecord` — `DELETE /api/v3/sessions/{id}/videorecords/{connectionId}` (offset 1026635); `estimated_time?quality=` (offset 896644); `isRecording:"videorecord"` в маппере сессии (offset 980357). ### T5. 409 `no_active_h264_encoder_group`: порядок проверок, доступ к ферме, SFU→501

**Тезис.** 409 нельзя ставить «на глаз» в `RecorderManager`: у admin-крейта нет ни фермы, ни рекордера (зависимостей нет — `vks-admin/Cargo.toml:24-35`); проверка должна быть портом в `AppState` (по образцу `OutboundDialer`, `state.rs:134`), реализованным в `vks-server`, где есть и `McuEngine`, и `RecorderManager` (`lib.rs:129-136`). Порядок проверок критичен: **сначала** режим комнаты (SFU → 501), **потом** 409, иначе SFU-комната с H.264-группой получит 409 вместо 501.

**Доказательство.** `FarmError` не содержит «no group» (`farm.rs:258-276`: только `Overloaded`/`Spawn`/`Closed`); `GroupStat` даёт `key.spec.codec`, `viewers`, но **не** `cancel` (`farm.rs:279-305`), поэтому «мёртвую» группу в гонке не отличить — приемлемо, но надо фильтровать `canvas_version` (старые версии закрыты, `farm.rs:398-400`). Режим комнаты: `ModeState::effective_mode` (`state.rs:128-130`) + `RoomRecord.mode` (`state.rs:37`). SFU-запись: `RecordingMode::SFu` существует (`recording.rs:74-80`), но не выбирается; требование «SFU → 501» — `00_MASTER_PLAN.md:99`.

**Проверка.**
```bash
cargo test -p vks-admin --locked api_v3::observability_tests::start_recording_without_h264_group_returns_409
cargo test -p vks-admin --locked api_v3::observability_tests::start_recording_in_sfu_room_returns_501
cargo test -p vks-admin --locked api_v3::observability_tests::start_recording_is_idempotent
```
409-тест: `state.recording` = фейковый порт, возвращающий `NoActiveH264Group`; проверять `status==409`, `body["error"]["code"]==409`, `body["error"]["reason"]=="no_active_h264_encoder_group"` **и** `state.records` пуст. 501-тест: комната с `mode=Sfu` → 501, порт не вызван. Отдельный unit-тест probe на фейковой ферме (`farm_with_test_spawner`, `farm.rs:1138`): пустая ферма → `false`, `acquire` H.264 → `true`, H.265 → `false`, после `invalidate_room` → `false`.

**Решение.** `pub trait RecordingControl: Send + Sync { async fn start(&self, room: RoomId, profile: RecorderProfile) -> Result<Uuid, RecordingControlError>; async fn stop(&self, room: RoomId) -> Result<Uuid, RecordingControlError>; }` + `recording: RwLock<Option<Arc<dyn RecordingControl>>>` в `state.rs` (аналог `outbound_dialer`, `:224, :357-367`), `set_recording`/`recording()`; impl в `vks-server` (в нём — probe `engine.video_farm_stats()` по `room + FarmCodec::H264 + canvas_version + viewers>0`, и вызов `recorder.start_recording`). Ошибка `NoActiveH264Group` → 409 с `reason`; `error_json` расширить третьим полем (аддитивно для UI) или отдельный `error_json_reason(409, "no_active_h264_encoder_group", "<human>")`. SFU/501 проверять в хендлере **до** порта. `VKS_VIDEO_FARM=0` и self-view (`engine.self_view`, `engine.rs:1126-1130`) дают тот же 409 — задокументировать в `deploy/vks.env.example` и тексте ошибки.

### T6. RecorderProfile: две несовместимые модели битрейта и клампы из двух документов

**Тезис.** В репозитории уже есть «модель битрейта» — фиксированные 2048 kbps с клампами 64–8192 (`gateway_video.rs:68,127`), а спека требует `W·H·fps·bpp` с bpp 0.085 (`docs/architecture/ARCHITECTURE_MASTER_PLAN.md:100-101`), что для дефолта 1280×720@30 даёт **2350** kbps. Если не решить, какая модель — «правда», UI («Медиафайлы»), `estimated_time` и реальный энкодер фермы будут показывать три разных числа. Второй конфликт: клампы kbps `[64…8192]`, fps `[15…60]` (спека, `:100-101`) против `[64…20000]`, fps `[1…60]` (план зоны 04, `04_infra_l5l7.md:337-338`).

**Доказательство.** `ContainerConfig` битрейта не имеет вообще (`crates/vks-recorder/src/container.rs:24-51`), у `RecordingMeta`/`RecordEntry` полей профиля нет (`recording.rs:119-138`, `storage.rs:117-130`). `estimated_time` — константа 3600 (`observability.rs:745`), `bitrate: 0` и `resolution: [1280,720]` — хардкод (`observability.rs:656-661`). Реальный групповой битрейт фермы = `group_bitrate_kbps(VideoProfile.bitrate, visible_windows)` с потолком 125 % (`engine.rs:617-626`, `gateway_video.rs:513-516`) — то есть даже «2048» никогда не равно фактическому `-b:v` группы при N>1.

**Проверка.**
```bash

#            fps_and_bitrate_clamps_match_master_plan, estimated_bytes_matches_bitrate
cargo test -p vks-admin --locked api_v3::observability_tests::estimated_time_uses_bitrate_not_constant
```

**Решение.** `crates/vks-recorder/src/profile.rs` (новый, `pub use` в `lib.rs:39-47` рядом с `container`): `RecorderProfile { width: u32, height: u32, fps: u32, bpp: f32 }` + `Default` 1280×720@30/0.085/видео 2350 kbps; `clamped()` — **чётные** W/H, W 160–1920, H 120–1080, fps 15–60, kbps 64–8192 (взять клампы спеки, а не 20000, и зафиксировать это в doc-комментарии + тесте); `video_kbps()`, `audio_kbps()` (64 kbps Opus/PCMU-эквивалент, константа), `total_kbps()`, `estimated_bytes(secs)`; считать в `u64`/`f64` с `round`, тест на точное 2350. `estimated_time` = `free_bytes(dir) * 8 / (total_kbps*1000)` через `libc::statvfs` (libc уже в workspace, `Cargo.toml:39`) с инъекцией `free_bytes` в `cfg(test)`; `profile` в `RecordEntry` — **declared**, не измеренный, и это явно в doc-комментарии поля. ### T7. Soak «66 групп ≤ 579 MB»: число измеряет не то, что кажется, и недетерминировано

**Тезис.** 579 MB — это RSS `[heap]` после 66 **последовательных** старт/стопов при нуле живых энкодеров (`08_live_runtime.md:139,146`), а не 66 одновременных групп и не «стоимость группы». Живая группа стоит ~52 MB **в ребёнке** (замер ниже); 66 живых = ~3.4 GB. Кроме того, число зависит от аллокатора: glibc-арены (38 потоков в живом прогоне, `08_live_runtime.md:128`), `target-cpu=native`, отсутствие `MALLOC_ARENA_MAX`/`malloc_trim` в проекте. Гейт «RSS ≤ 579 MB» будет и ложно-зелёным, и ложно-красным; измерять надо **дельту на завершённую группу после `malloc_trim`** (живые объекты) и отдельно — удержание без trim (бюджет эксплуатации).

**Доказательство.** Ни одного измерения памяти в коде нет (`grep -rn "VmRSS\|malloc_trim\|jemalloc" crates/` → пусто); единственный timing-гейт проекта — release-only ignored (`crates/vks-media-mcu/tests/mcu_tick_soak.rs:339-346`), его структуру и надо повторить (артефакт `VKS_SOAK_OUT`, `:360`). Замер живого энкодера на этом хосте:
```bash
head -c $((1280*720*3/2*90)) /dev/zero | /usr/bin/time -v ffmpeg -hide_banner -loglevel error -nostdin \
  -threads 1 -filter_threads 1 -f rawvideo -pixel_format yuv420p -video_size 1280x720 -framerate 30 \
  -i pipe:0 -an -c:v libx264 -threads 1 -preset ultrafast -tune zerolatency -pix_fmt yuv420p \
  -profile:v baseline -level:v 3.1 -b:v 2350k -maxrate 2350k -bufsize 4700k -g 30 -keyint_min 30 \
  -x264-params repeat-headers=1:aud=1:scenecut=0 -flush_packets 1 -f h264 /dev/null
# → Maximum resident set size (kbytes): 52052   (360p30: 52932 — почти то же)
```
**Проверка.**
```bash
MALLOC_ARENA_MAX=2 VKS_SOAK_GROUPS=66 VKS_SOAK_OUT=target/t09a-farm-soak.json \
  cargo test --release -p vks-media-mcu --locked --test farm_group_soak -- --ignored --nocapture
```
Гейт: `#[ignore = "release-only memory gate"]` + `if cfg!(debug_assertions) { eprintln!("…skipped"); return; }`; цикл `N` раз: `acquire(H264 720p)` → `publish` 30 кадров → `drop(viewer)` → дождаться `group_count()==0` и отсутствия детей (`/proc/self/task/*/children`, как `children_with`, `farm.rs:1156`) → `libc::malloc_trim(0)` (только `#[cfg(target_env="gnu")]`) → `VmRSS` из `/proc/self/status`. Ассерты: (1) **живая утечка**: `ΔRSS_after_trim / N ≤ 1 MB`; (2) **удержание**: `ΔRSS_before_trim / N ≤ 12 MB` (бюджет 579 MB / 66 ≈ 8.8 MB + запас) и в артефакт — медиана по 3 прогонам; (3) `group_count()==0`, детей 0, потоков не растёт (детерминированные проверки). Если (1) не выполняется — это **реальная** утечка, и её чинят (drop broadcast-буфера/`parameter_sets`, `malloc_trim` на retire), а не ослабляют порог.

**Решение.** Константы `FARM_MEMORY_BUDGET_BYTES = 579 * 1024 * 1024` и `FARM_GROUP_RETAIN_BUDGET_BYTES = 9 * 1024 * 1024` в `farm.rs` рядом с `group_limit_from_env` (`:1085-1094`) с doc-комментарием «эмпирика 2026-10-29, не гарантия»; `group_capacity_for_budget()` — чистая функция + unit-тест (арифметика бюджета); метрики `encoder_group_active`/`encoder_group_refcount` уже есть (`crates/vks-server/src/farm_metrics.rs:30,32`), добавить gauge `encoder_group_budget`. Дефолт `VKS_VIDEO_FARM_MAX_GROUPS=128` **не менять** в T09a (это поведение продакшена, не «данные/API») — только задокументировать риск в отчёте таска.

### T8. Рестарт, SQLite↔PG, два писателя, идемпотентность

**Тезис.** «Записи переживают рестарт» (критерий `MASTER_TASK_LIST:47`) проверяемо только если (а) бэкенд — SQL, (б) запись действительно закоммичена до чтения. Три обхода: fallback на `MemoryStorage` при ошибке инициализации SQL (`main.rs:113-154`) делает вид, что «переживает»; sync-стоп пишет в фоне (`tokio::spawn`, `recorder.rs:192-199`) — GET сразу после stop может не увидеть запись; в SQLite нет `busy_timeout`/`journal_mode` (URL только `mode=rwc`, `configs/default.toml:36`), поэтому параллельные писатели (рекордер + settings/audit) могут получить `SQLITE_BUSY`.

**Доказательство.** `stop_recording` (sync) → `tokio::spawn(upsert_record)` и `let _ =` (`recorder.rs:192-200`); `stop_recording_async` ждёт (`:233-243`) и тоже глотает ошибку (`:240`). `SqliteStorage::init_options` — только `SqliteConnectOptions::from_str` (`sqlite.rs:86-96`); `journal_mode`/`busy_timeout` не выставляются. `reset()` PG/SQLite перечисляет таблицы явно (`core_adapter.rs:683-701`, `:1143-1161`) — новая таблица туда не попадёт сама. PG-тест покрывает только users/rooms (`postgres.rs:374-395`), CI-джоба — `test-postgres` (`ci.yml:131-163`).

**Проверка.**
```bash
# SQLite: два «процесса» на одном файле (два SqliteStorage::init)
cargo test -p vks-admin --locked api_v3::observability_tests::videorecords_survive_sqlite_restart
# PG-паритет:
VKS_STORAGE_PG_URL=postgres://postgres:postgres@localhost:5432/vks \
  cargo test -p vks-storage --locked postgres::tests::records_roundtrip_live_db
# гонка двух писателей (порт-уровень):
cargo test -p vks-storage --locked core_adapter::tests::concurrent_record_upserts_are_idempotent
```
Тест рестарта обязан проверять **не** `count>0` вообще, а что второй `AppState` поднят на `SqliteStorage` (не Memory) и что запись видна после `sync_from_storage`; тест гонки — 2×`upsert_record` одного id + `list_records` = 1 (PK/`ON CONFLICT`), и `tokio::join!` 32 upsert'ов разных id → 32 строки без ошибок.

**Решение.** `upsert_record` — `INSERT … ON CONFLICT (id) DO UPDATE` (как room/settings, `core_adapter.rs:267-277`), ошибки **не** глотать: sync-обёртку `stop_recording` либо удалить, либо оставить с `tracing::error!`; API-путь — только `stop_recording_async`. В `SqliteStorage::init_options` добавить `.busy_timeout(Duration::from_secs(5))` (одна строка, влияет на все таблицы — согласовать в отчёте) либо `?busy_timeout=5000` в `configs/default.toml`; решение зафиксировать тестом гонки. `storage_allow_fallback` не трогать, но в тесте рестарта явно проверять тип хранилища (например, `storage.get_record` через **новый** экземпляр, а не через `AppState`).

## §5 Резюме (10 строк)

1. Записи сегодня — 5 полей метаданных в RAM (`storage.rs:117-130`, `state.rs:234`); в SQLite/PG таблицы нет (`migrations/` 0001–0005), файлов нет (`06_hygiene_arch.md:72`).
2. Четыре record-метода `Storage` — no-op дефолты (`storage.rs:291-311`), переопределены только в `MemoryStorage` (`core_adapter.rs:205-223`); `grep` подтверждает отсутствие в SQLite/PG.
3. Гидратации `records` нет (`state.rs:561+`, `main.rs:161`), а API читает storage напрямую (`observability.rs:667-674`) — поэтому «зелёный» тест API не докажет гидратацию.
4. API отдаёт хардкод (`bitrate:0`, `resolution:[1280,720]`, `src=id`) и не имеет POST/DELETE-stop, которые зовёт вендор (`index.bundle` offsets 1026446/1026635).
5. Ферма: группы создаются только зрителем (`farm.rs:394-435`), publish — только существующим (`:508-538`), лимит 128 (`:1085-1094`), битрейт группы = base·(1+2 %·(N−1)) с потолком 125 % (`engine.rs:617-626`).
6. 409 `no_active_h264_encoder_group` в коде отсутствует; из admin-крейта ферма недоступна (нет зависимостей, `vks-admin/Cargo.toml:24-35`) → нужен порт в `AppState` по образцу `OutboundDialer`.
7. Два конфликта модели битрейта: 2048 kbps (`gateway_video.rs:68`) против 2350 по `W·H·fps·0.085` (`ARCHITECTURE_MASTER_PLAN.md:100-101`); клампы 8192 против 20000 (`04_infra_l5l7.md:338`) — брать спеку.
8. «66 групп → 579 MB» — это heap после 66 **последовательных** старт/стопов при 0 ffmpeg (`08_live_runtime.md:139,146`); живой энкодер стоит ~52 MB RSS (замер), 66 живых ≈ 3.4 GB.
9. Soak должен мерить ΔRSS/группу после `malloc_trim` под `MALLOC_ARENA_MAX=2` (утечка ≤1 MB, удержание ≤12 MB), а не абсолютные 579 MB; иначе гейт недетерминирован (аллокатор, 38 потоков, native).
10. Рестарт проверять только на SQL-бэкенде с новым экземпляром хранилища; sync-стоп пишет в фоне (`recorder.rs:192-199`), в SQLite нет `busy_timeout`, PG-тест записей надо добавить в джобу `test-postgres` (`ci.yml:131-163`).
