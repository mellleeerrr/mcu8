## §2 S6: тест n=5@1280×720 — что именно должно быть и что делает его красным

### 2.1 Требование

Из `00_MASTER_PLAN.md:129`: S6 растягивать сетку до 100% **нельзя** (разные окна/аспекты, рассинхрон с вендорским `preset_equal_3`); центрирование оставить; добавить «тест движка n=5@1280×720 (fill 83,28%) + строку в `LAYOUT_ENGINE.md`». S6 уже реализован коммитом `e6ab3c8`; T06 добавляет контрактный тест и docs, **не меняя алгоритм**.

### 2.2 Точные числа (проверено пробой на текущем `grid.rs`)

`GridLayout::compute(Canvas::new(1280,720), 5)` → `(rows, cols) = (2,3)`, `base_w = 1280/3 = 426`, `base_h = 720/2 = 360`:

| # | x | y | w | h | Примечание |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 426 | 360 | полный ряд |
| 1 | 426 | 0 | 426 | 360 | |
| 2 | 852 | 0 | **428** | 360 | последний в полном ряду добирает остаток `1280−852` |
| 3 | **214** | 360 | 426 | 360 | неполный ряд центрирован: `(1280−2·426)/2` |
| 4 | **640** | 360 | 426 | 360 | правый край 1066, правый зазор 214 |

- Площадь: `767 520`; canvas `921 600`; **fill = 767520/921600 = 0.8328125 (83.28125%)**; чёрные поля `154 080` = **16.71875%**.
- Проверять надо **exact** `767_520`/`0.8328125`, а не `≈0.83`: допуск `±0.0001` пропустит ошибку в 92 px².
- На 1920×1080 те же 5 тайлов дают `640×540`, нижний ряд `x=320,640`, fill `5·345600/2073600 = 0.833333… (83.33%)`. **Число 83.28% имеет смысл только на 1280×720**; тест на 1920×1080 с ожиданием 83.28% красный.

### 2.3 Почему наивный тест красный (даже при корректном коде)

1. **«Полный ряд занимает всю ширину» для всех рядов** — неверно: последний ряд центрирован, правый/левый зазоры по 214. `total_area == canvas.area` только при `n % cols == 0` (здесь `5 % 3 = 2`).
2. **«Все ширины равны 426»** — неверно: `rect[2].w = 428` (остаток полного ряда отдан последнему тайлу).
3. **«Превью и движок совпадают»** — на 1280×720 **не совпадают**:

   | # | `grid.rs` (движок) | `grids::geometry("vks_grid_5")` (превью) |
   |---|---|---|
   | 0 | (0,0,426,360) | (0,0,**427**,360) |
   | 1 | (426,0,426,360) | (**427**,0,426,360) |
   | 2 | (852,0,428,360) | (**853**,0,**427**,360) |
   | 3 | (214,360,426,360) | (**213**,360,**427**,360) |
   | 4 | (640,360,426,360) | (640,360,**427**,360) |

   Площади: `767 520` против `768 240` (+720 px², +0.078%); причина — `grid.rs` целочисленный (`w/cols`, остаток последнему), `grids::gallery` float + `.round()` краёв. Тест, сравнивающий два движка через `assert_eq!`, красный **сегодня**; это не регрессия T06.
4. **`get_grid_edges`/`.round()`** в `grids.rs` даёт другой remainder; не «чинить» это в T06 — S6-план прямо запрещает менять `grids.rs` на 1280×720 (golden 1..100).

### 3.2 Почему 400 — правильный ответ, а не баг

1. `preset_default_13` — это **id авто-композита** «Общей», а не ручная схема: его геометрия зависит от числа участников (`regrid`/`total_slots`). Вернуть из `calculate` фиксированные 13 ячеек — значит пообещать превью, которого не будет в composite при 20 участниках (и наоборот).
2. У базовых id (`preset_equal`, `preset_default`, `preset_unknown_4`) **нет явного числа**; `preset_size` для них `None` (кроме `preset_default_13`, где 13 — это **ёмкость**, а не геометрия). `calculate` — API геометрии, а не ёмкости.
3. 400 уже закреплён тестами и объяснён в doc-комментарии; «починка» сервера (добавить default13 в `is_known_preset` или вернуть `equal_slots`) сломает различие auto/manual, тесты `:852-859` и семантику `explicit_preset`, а также создаст второй источник геометрии для auto.

**Следствие:** `preset_size("preset_default_13") == Some(13)` и 400 в `calculate` — **не противоречие**: первое — ёмкость для attach/валидации, второе — отсутствие статической геометрии. Так и надо задокументировать.

## §4 «Один резолвер»: минимальное определение и оставшиеся расхождения

### 4.1 Определение

Один **серверный** резолвер ёмкости раскладки, вызываемый из attach, validate, PATCH/create, mode, normalize:

```text
capacity(payload) =
  id_capacity(payload.preset)          // только известная схема + явное число
  ?? payload.size (если > 0)
  ?? max(position) слотов (или slots.len — см. D2)
  ?? None
```

где `id_capacity` — **чистая** функция в `vks-layout`:

```rust
// vks-layout/src/lib.rs
pub fn preset_capacity(id: &str) -> Option<usize> {
    grids::slot_count(id)
        .or_else(|| codian::slot_count(id))
        .or_else(|| {
            if !preset::has_explicit_size(id) { return None; }
            let p = preset::PresetId::parse(id)?;       // валидирует схему и u8
            Some(usize::from(p.size))
        })
        .filter(|n| (1..=grids::MAX_WINDOWS).contains(n)) // 1..=100, см. D3
}
```

Ключевое: **`preset_size` в нынешнем виде для этой роли не годится** — он смотрит только на форму `preset_<...>_<tail>` и парсит хвост как `usize`, не проверяя схему и не ограничивая размер. Пробой подтверждено:

```text
preset_unknown_4                  -> Some(4)     // calculate: 400
preset_evil_999                   -> Some(999)
preset_evil_18446744073709551615  -> Some(18446744073709551615)  // usize::MAX!
preset_default_256                -> Some(256)
preset_equal_500                  -> Some(500)   // PresetId::parse: None (u8)
```

`attach`/`validate`/`mode` доверяют этому значению → лимит 999/2^64, `payload.size` = 999/2^64, фронтенд получает число с потерей точности (`18446744073709552000`), а шлюз (`u8::try_from`) отбрасывает его и уходит в `equal(slot_count)`. Это не «редкий кейс»: `preset_unknown_4` уже используется в тесте 400.

**Вариант без изменения `preset_size`:** оставить `preset_size` для обратной совместимости (шлюз/тесты), добавить `preset_capacity` и использовать только её; `preset_size` пометить как wire-хелпер, не использовать в admin. Но тогда два похожих имени — риск снова разойтись. Лучше один `preset_capacity`, а `preset_size` сделать его alias'ом **после** проверки, что шлюз не полагается на неизвестные схемы (см. D3).

### 4.2 Что должен использовать каждый путь

| Путь | Сейчас | Должно быть |
|---|---|---|
| `attach` (`resources.rs:958`) | `layout_size(...).unwrap_or(64)` | `layout_size(...).unwrap_or(13)` (или 409, если слотов нет); без 64 |
| `validate` (`:1427-1436`) | `preset_size` → `layout_size` | только `layout_size(payload)`; `position==0` → `Invalid` 422 (P2-9) |
| `PATCH`/`create` (`:1484`, `:447`) | `recalc` → `validate` | тот же `layout_size`; порядок уже верный |
| `mode` (`shell.rs:984-1007`) | inline-порядок + `unwrap_or(13)`, **без recalc** | собрать draft из patch → `recalc_layout_size(&mut draft)` → `validate`; не доверять request `size` |
| `normalize_loaded` (`:1126-1129`) | `recalc` | `recalc`, но с защитой от сжатия (см. §5.3) |
| `gateway` (`gateways.rs:1855`) | `preset_size` + u8 | `preset_capacity` (u64→u8) + `payload.size`; геометрию не менять |
| фронтенд (`codian-layouts.js`) | `currentCount` | **не трогать**: display-only; серверный size авторитетен |

### 4.3 Конкретный баг mode (P1)

`switch_video_layout_mode` (`shell.rs:984-1007`) ставит request `size` **раньше** ёмкости пресета, хотя комментарий `:993-995` утверждает обратное. Пример: запись `{preset:"preset_default_13", size:13, slots:[13 AUTO]}`, UI выбирает `preset_equal_4` и присылает `{"preset":"preset_equal_4","size":13,"slots":[4 слота]}` → `inferred_size = 13`, patch `size=13`; `validate` видит 4 слота (ок) и сохраняет `size=13` с `preset_equal_4`. Шлюз: `preset_size=4`, `slot_count=4` → geometry equal(4) — ок, но админ-ёмкость 13, attach разрешит 5-й слот, и следующий PATCH с 13 слотами пройдёт, а шлюз `equal(13)`. Если UI пришлёт 13 слотов (старые AUTO), `validate` пройдёт (size 13), шлюз снова `equal(13)` — пресет `equal_4` не применён, но запись выглядит валидной. **Лечение:** не использовать request `size` при наличии id-ёмкости; после merge всегда `recalc_layout_size` (preset → size → len), затем validate.

### 4.4 `slots.len` vs `max(position)` (D2)

`derived_layout_size` берёт `slots.len()`. Для sparse-модели это неверно: `slots:[{"position":4}]` без preset/size даёт capacity 1, тогда как позиция 4 — четвёртое окно. `attach` возьмёт пресет (если он есть) и не заметит; для custom-раскладки без preset — лимит 1 и PATCH 409 на позицию 4. В текущих тестах sparse всегда с preset (`vks_grid_4`), поэтому баг скрыт. Рекомендация: `max(position)` (с `len` как fallback) + тест `{"slots":[{"position":4}]} → 4`; это не ломает contiguous-кейсы и `t00_attach_into_sparse_layout_uses_free_position` (позиции 1..4). Если решено сохранить `len` — задокументировать ограничение в §4.4 BACKEND_RULES.

## §5 `normalize_loaded`: ловушки, которые не видны в зелёном тесте

### 5.1 Главная: нормализация не персистится

`state.rs:708-712` вызывает `normalize_loaded(&mut loaded)` и сразу `*resources = loaded`; `persist` **не вызывается**. Следствия:

- GET после старта показывает новый size (память), а `SELECT document_json` — старый; рестарт без коммита снова нормализует, но БД «врёт» для внешних читателей/бэкапов.
- Нормализация «залипает» только когда кто-то сделает любой `commit` (например, переименует аудиоканал) — тогда весь документ, включая нормализованные size, уйдёт в БД. Это неявно и недокументировано.
- Тест, который вызывает `normalize_loaded` и проверяет `resources`, **пройдёт**, даже если персиста нет; тест «перезапустить state из storage и проверить документ» — **провалится**. Не выдавать первый за доказательство второго.
- **Не добавлять `persist` внутрь `normalize_loaded`**: функция синхронная, не держит lock, а `persist` асинхронный и берёт `video_settings`/`conference_settings`. Вызов из `state.rs` после присваивания потребует lock и создаст окно lost update (между load и persist другой хендлер может записать). Если durability нужна — отдельный one-shot на старте, под тем же lock, с проверкой, что документ не изменился (version/hash), и только для `mark_stopped=true` (не hot-reload). В минимальный T06 это не входит; приёмка «пересчитывает size» проверяется на состоянии, а не на БД.

### 5.2 Идемпотентность

`normalize_loaded` вызывается на каждом `sync_from_storage_inner` (старт и hot-reload), тесты вызывают дважды. `recalc` идемпотентен (size → тот же size), `ensure_slot_roles` — тоже (валидные роли не перезаписываются). Любая новая «починка» слотов (dedupe/trim) обязана быть идемпотентной и не менять `slots` при повторном вызове; иначе hot-reload будет «пилить» данные.

### 5.3 Пересчёт может «отравить» запись (самая опасная)

`recalc_layout_size` ставит size из пресета, **не глядя на позиции слотов**. Легаси-запись:

```json
{"preset":"vks_grid_5", "size":13, "slots":[{"position":1},...,{"position":9}]}
```

после `normalize_loaded` → `size=5`, но 9 слотов остаются. Далее:

- `PATCH {"display_name":"rename"}` → `update_resource` → `recalc` (5) → `validate`: позиции 6..9 > 5 → **409**, переименовать нельзя;
- `attach` limit 5 → шестой участник «Layout is full», хотя в данных 9 окон;
- шлюз: `preset_size=5`, `slot_count = max(position)+1 = 9`, `PresetId::parse(vks_grid_5).size=5 >= 9` ложно → `equal(9)` → MCU рисует **9** окон, админка говорит **5**. Рассинхрон ровно того класса, который T06 должен убрать.

Этот же fixture уже есть в тесте `recalc_layout_size_распознаёт_конструктор` (`resource_tests.rs:2357-2368`: `vks_grid_g8_m16_5` + 9 слотов → size 5) — тест закрепляет size 5 и **не проверяет**, что запись остаётся валидной. `normalize_loaded` теперь применяет это к legacy-данным.

**Минимальные варианты (выбрать и записать, D1):**

- **(A) size = max(id_capacity, max(position))** для normalize/attach: сохраняет все окна, запись остаётся PATCH-able; но `preset_equal_4` + 13 слотов даст size 13 (не 4), т.е. «пресет — источник истины» нарушается только для уже противоречивых данных. Тест `{"vks_grid_25","size":7}` с позициями ≤7 всё равно даёт 25.
- **(B) size = id_capacity; лишние слоты не трогать, но `normalize_loaded` логирует WARN и** `validate` при загрузке не вызывается; запись остаётся отравленной до ручного ремонта. Не годится для приёмки «attach работает».
- **(C) size = id_capacity; удалить слоты с position > capacity, но только пустые (AUTO/EMPTY, без abonent_id); занятые — сохранить и поднять size до max(position).** Компромисс без потери людей; сложнее и требует тестов на идемпотентность.

Рекомендация: **(A)** как минимальная и безопасная (не теряет данные, не создаёт 409), плюс WARN, если `max(position) > id_capacity`; в docs зафиксировать, что для противоречивой legacy-записи ёмкость расширяется до фактических окон. Если Lead требует строго «пресет всегда побеждает» — тогда (C) с явным правилом и тестами, но это уже не «минимальная правка».

### 5.4 Дубли/ноль/отсутствие позиции не ремонтируются

`normalize_loaded` фильтрует только не-объекты (`:1125-1126`), но не проверяет `position`:

- `position:0` → `validate` 409 (`Conflict`, P2-9), запись нельзя PATCH-ить; в шлюзе `checked_sub` даёт None → слот пропускается с WARN. Исправление P2-9 (409→422) не ремонтирует данные, но перестаёт врать клиенту.
- `position` отсутствует/строка → `validate` 422; шлюз пропускает; attach не считает занятым. Такие слоты — мусор; можно удалять при загрузке с WARN (не occupant), но это отдельное решение.
- **Дубли `position`** — худший случай: `[{pos:1, abonent:"A"}, {pos:1, role:"AUTO"}]`. `attach` ищет свободный слот по `position in 1..=limit`, не проверяя, что эта позиция уже занята другим слотом → посадит B в свободный pos1 → два участника на одном окне. Далее:
  - `validate` → 409 duplicate, PATCH невозможен;
  - шлюз `assignments.insert(pid, position)` для двух pid с position 1 → в `slot_to_pid` (BTreeMap<u32,pid>) останется **один**, второй участник молча без окна (`engine.rs:230-234, 688-696`).
  Минимальный фикс в attach: при выборе `free` пропускать позицию, если **любой другой** слот с той же позицией занят (`abonent_id`/`contact_id` непусты); либо в normalize дедуплицировать по position, оставляя занятый (и логируя потерю пустого). Тест: два pos1 (один занят) + attach → не создаёт дубль, 409/минимальная свободная.
- `position > capacity` (легаси) — attach уже пропускает (`:966-970`), validate 409; normalize не трогает; см. §5.3.

### 5.5 Прочие ловушки

1. **`payload` не объект** → заменяется на canonical default (`:1117-1119`): теряются preset/slots, size становится 13. Это уже необратимая потеря; не «улучшать» и не пытаться восстановить.
2. **`slots` не массив** → `[]` (`:1124`), затем recalc по preset; если preset нет, size остаётся прежним. Пустые слоты — легальное состояние (sparse), не заполнять их «до size»: иначе появятся фантомные AUTO-окна и UI покажет больше окон, чем есть.
3. **`payload.size` строкой** (`"13"`): `as_u64` → None → fallback на slots/preset; recalc запишет число 13. Это тихое приведение типа; ок, но тест на строку полезен.
4. **Огромный/переполненный size**: `preset_evil_18446744073709551615` → `json!(usize::MAX)`; в JS `Number` теряет точность; `attach` лимит 2^64; `u8` в шлюзе отбрасывает. Клампить `preset_capacity` до 100 (или 255) **до** записи в payload; не клампить молча в `attach` (иначе админка и шлюз разойдутся ещё сильнее).
5. **`normalize_loaded` обнуляет `abonents`** (`:1131`): это производное поле, GET пересчитывает (`with_layout_abonents`); не персистить документ сразу после normalize, иначе в БД на мгновение окажется `abonents.count=0` (для не-attached раскладок это может быть видно).
6. **`type` ремонтируется в `default`** (`:1121-1123`): legacy individual без type станет default; это меняет группировку UI и право удаления. Уже существующее поведение; не менять в T06.
7. **`repair_scope_defaults`** может добавить default и изменить links (`:1145+`); normalize не должен затем пересчитывать capacity по «слотам» добавленной default — у неё canonical size 13.
8. **`version:1`** документа — единственная версия; нет per-layout `schema_version`. Не вводить новое поле в payload без ADR; recalc должен терпеть неизвестные поля (Value) и не сериализовать типизированную структуру.
9. **`ResourceState` serde**: `layouts` — `Value`, отсутствующие поля карты `#[serde(default)]`; битый документ целиком (`serde_json::from_str` error) не нормализуется — старт падает, это отдельный риск (не T06).
10. **Тест на БД**: если добавлять интеграционный тест «после рестарта size пересчитан», нужно поднимать `AppState` из `MemoryStorage`/SQLite-копии в `/dev/shm`, а не из живой `vks_data.db`; и помнить, что без persist он проверит память, а не документ.

### 5.6 Минимальные тесты для normalize

```rust
#[test]
fn normalize_loaded_recalculates_stale_size() {
    let mut resources = ResourceState::default();

#[test]
fn normalize_loaded_does_not_poison_out_of_range_slots() {
    let mut resources = ResourceState::default();
    let slots: Vec<serde_json::Value> =

    assert!(payload["size"].as_u64().unwrap() >= 9);
    // и запись остаётся PATCH-able:
    let mut record = resources.layouts["b"].clone();
    assert!(super::update_resource(&mut record, &json!({"display_name":"x"})).is_ok());
}
```
