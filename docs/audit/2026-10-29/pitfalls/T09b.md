## §2 Ловушки

### P0-1. Приёмочный `ffprobe -show_streams` — ложноположительный: текущий файл играет без `avcC`

**Факт (измерено на pristine HEAD, реальный x264 Annex-B, 60 AU):**

| Файл | `is_avc` | `nal_length_size` | `time_base` | `nb_frames` | `duration` | `ffmpeg -frames:v 1` |
|---|---|---|---|---|---|---|
| текущий writer (Annex-B в `mdat`, без `avcC`) | `false` | `0` | `1/1000` | 60 | 1.966 | exit 0 |
| эталонный прототип (`avcC` + 4-byte length prefix, 90000) | `true` | `4` | `1/90000` | 60 | 2.000 | exit 0 |

`ffprobe -count_frames` на текущем файле даёт `nb_read_frames=60` — потому что mov demuxer при `is_avc=false` отдаёт пакеты как есть, а H.264-декодер понимает Annex-B. `extradata_size` при этом ненулевой (`36`/`72`), его ffmpeg синтезирует/находит эвристикой, поэтому проверка «extradata_size > 0» тоже **не** доказывает наличие `avcC`. `profile=Constrained Baseline` тоже берётся из SPS в битстриме, а не из `avcC`.

**Почему это P0.** Если T09b напишет tap и оставит writer как есть (или добавит только length-prefix без `avcC`), заявленный гейт «MP4 играется ffprobe/ffmpeg» пройдёт, хотя файл не соответствует 14496-15: браузер/hardware/строгий парсер не смогут его открыть. Приёмка должна проверять **структуру**, а не только факт декодирования.

**Минимальные обязательные assert'ы:**
- `ffprobe -show_streams`: `codec_name=h264`, `codec_tag_string=avc1`, `is_avc=true`, `nal_length_size=4`, `profile`/`level` соответствуют SPS, `time_base=1/90000`, `nb_frames==N`, `duration≈N/fps`.
- Свой box-parser: `avcC` существует как child `avc1`, `lengthSizeMinusOne==3`, SPS/PPS в `avcC` побайтово равны SPS/PPS из потока (без start code), первый сэмпл в `mdat` начинается с 4-байтовой длины, а не с `00 00 01`.
- `ffmpeg -v error -i file -map 0:v:0 -f null -` (полный декод, не один кадр) и `-count_frames` = числу записанных AU.
- Для аудио — `ffprobe` `codec_name=aac`, `profile=LC`, `time_base=1/48000`, `nb_frames` и реальный decode, а не только `mp4a`-тег.

**Не делать:** гейт «ffprobe exit 0» / «есть `moov`/`mdat`» / «`nb_frames>0`» — все три проходят на текущем невалидном файле.

### P0-2. Tap не должен спавнить скрытую группу: `acquire` — единственный публичный путь, и он создаёт FFmpeg

**Факты:**
- `EncoderFarm::acquire` (`farm.rs:407-502`): если группы с ключом нет — вставляет группу в `groups`, делает `tokio::spawn(run_group(...))`, логирует `encoder group started` (`:493-501`). Если группа есть — увеличивает `refcount` и возвращает `GroupViewer` (`:505-515`).
- `GroupViewer` — владеющий: `refcount` стартует с 2 («зритель + энкодер», `farm.rs:462`), `Drop`/`release_inner` уменьшает и при `previous<=2` делает `retire` (`:705-716`, `:735-739`). Публичного `subscribe` без refcount нет.
- `gateway_video` — единственный потребитель: `acquire_video_viewer` на каждую видео-сессию (`gateway_video.rs:586-615`), затем `broadcast::Receiver<Arc<AccessUnit>>` (`:706-780`).
- `RecorderControl::start` (`recorder.rs:42-67`) не подписывается ни на что; `active_h264_groups` только считает (`:96-106`).

**Что произойдёт, если tap реализовать через `acquire_video_viewer`/`acquire`:**
1. Нет ни одной H.264-группы → `acquire` **создаст** новую группу и FFmpeg-процесс, хотя зрителей нет. Это и есть «скрытая группа»: она занимает слот из 128 (`VKS_VIDEO_FARM_MAX_GROUPS`, `farm.rs:1098-1104`), потребляет CPU/RSS, пишет `frames=0`; при последующем `start` `active_h264_groups` станет `>0`, и 409-гейт начнёт пропускать запись без реального зрителя.
2. Есть существующая группа, но с другим ключом (например, `RecorderProfile::default()` 1280×720@30 vs gateway 640×360@15) → `acquire` создаст **второй** энкодер рядом с реальным; битстримы разные, запись может быть пустой/несовместимой.
3. Есть группа с тем же ключом → `acquire` подключит tap как ещё одного зрителя: `refcount+1`, `GroupStat.viewers=2` при одном человеке; после ухода человека группа останется жить из-за tap, а метрики/409 будут считать её «активной». Это уже не скрытая группа, но скрытый зритель; для приёмки «tap не спавнит скрытую группу» лучше избегать и этого.

**План зоны противоречит мастер-плану.** `04_infra_l5l7.md:351` предлагает «рекордер как скрытый viewer: `VideoFarm::viewer(key)` с `GroupSpec` из `RecorderProfile`», а `04:352` — тест `record_without_viewers_writes_bytes` (soak 3 с, `size_bytes > 0`). Это прямо противоречит мастер-плану: `00_MASTER_PLAN.md:99` — «**tap = subscribe к существующей группе фермы** (нет зрителя → 409)», `:127` — «Компромисс: `EncoderFarm::subscribe` к существующей группе, 409 при её отсутствии». Для T09b выполнять мастер-план; тест «запись без зрителей пишет байты» **не** добавлять — он закрепляет скрытую группу/скрытого зрителя.

**Рекомендуемый минимальный контракт (не спавнит и не меняет refcount):**
```rust
pub struct FarmTap {
    pub key: EncoderKey,
    pub rx: broadcast::Receiver<Arc<AccessUnit>>,
    pub parameter_sets: Vec<Arc<[u8]>>, // snapshot, может быть пустым
}

impl EncoderFarm {
    /// Только существующая группа: room + codec + текущий canvas_version,
    /// !cancel, viewers > 0. Никакого spawner/insert/refcount.
    pub fn subscribe(&self, room: RoomId, codec: FarmCodec) -> Option<FarmTap>;
}
```
- Выбор при нескольких группах: сначала `viewers > 0`, затем максимум `viewers`, затем детерминированно по `EncoderKey` (BTreeMap уже упорядочен); фильтровать `key.canvas_version == self.canvas_version(room)` и `!group.cancel`.
- `FarmTap` не реализует `Drop` с refcount; если группа ретируется, `rx.recv()` вернёт `Closed`. Это значит, что запись закончится, когда уйдёт последний реальный зритель, — честная семантика «нет зрителя → нет записи». Если продукт требует продолжать запись без зрителей, нужен **отдельный** счётчик `taps` (не `viewers`), чтобы не ломать 409/метрики; это уже P1-решение, а не минимальный T09b.
- `subscribe` не должен вызывать `ensure_composite_size`, `acquire`, `viewer` или `publish`.

**Как ловить скрытую группу тестами:**
- Unit `farm.rs` с fake-spawner: счётчик вызовов spawner'а; `subscribe` при пустой ферме → `None`, `group_count()==0`, `spawn_calls==0`; после `acquire` → `subscribe` возвращает `Some`, `group_count()==1`, `spawn_calls==1`, `refcount` не изменился.
- Integration `RecorderControl::start` на `McuEngine::new()` (пустая ферма): `engine.video_farm().group_count()==0`, `active_h264_groups==0`, нет нового `ffmpeg`-child; в `RoomHub` только `recorder-<room>` (не WebRTC-peer).
- Integration с реальной группой: `snapshot().len()` до/после tap одинаков, `GroupStat.key` тот же, `viewers` не вырос (для non-owning), `frames` растут; `farm_metrics::update_from_stats` не добавляет вторую серию `encoder_group_active`.
- Лог-assert (если есть тестовая tracing-подписка): ровно один `encoder group started` на комнату, ни одного второго.

### P0-3. `avcC` и length-prefix: порядок преобразования, SPS/PPS и профиль/level

**Текущий код:** `write_video_frame` (`container.rs:84-102`) сначала берёт `offset = media_data.len()` и `size = data.len()`, потом копирует `data`. Если добавить преобразование **после** этого, `stsz`/`stco` будут описывать сырые байты, а `mdat` — length-prefixed; файл станет нечитаемым. Если преобразование **до**, то `size`/`offset`/`check_capacity` должны считаться от результата.

**Алгоритм преобразования (H.264):**
1. Определить формат: если `len>=4` и `u32::from_be_bytes(first4) == len-4`, считать уже length-prefixed (идемпотентность) и копировать; иначе — Annex-B.
2. Сканировать `00 00 01`/`00 00 00 01` (как `find_start_code` в `farm.rs:1082-1096`; 3- и 4-байтовые start code). NAL = от start code до следующего start code/конца.
3. Отбросить start code, обрезать хвостовые нули (`trailing_zero_8bits`), пустые NAL пропустить/ошибка.
4. Для каждого NAL: `u32 BE len(nal)` + `nal`. Сумма — размер сэмпла; кап `u32` на NAL.
5. `mdat` хранит результат; `SampleEntry.size` = результат; `stsz` — результат; `stco` offset — после записи результата.
6. AUD (type 9) можно оставить в сэмпле — это валидный NAL с length prefix; ffmpeg его переварит. Если хочется уменьшить файл — выкинуть AUD, но не обязательно.
7. SPS/PPS (type 7/8) из `AccessUnit` должны попасть в `avcC`, но **не** быть обязательными в каждом сэмпле; `repeat-headers=1` у x264 дублирует их на IDR — это нормально.

**`avcC` (AVCDecoderConfigurationRecord):**
```
configurationVersion          = 1
AVCProfileIndication          = SPS[1]   (profile_idc)
profile_compatibility         = SPS[2]   (constraint flags)
AVCLevelIndication            = SPS[3]   (level_idc)
0xFF                          (reserved 6 bits + lengthSizeMinusOne=3 → 4-byte lengths)
0xE1 | (num_sps & 0x1F)       (reserved 3 bits + count)
u16 be sps_len, sps_bytes     (без start code, с emulation-prevention bytes)
u8 num_pps
u16 be pps_len, pps_bytes
```
- SPS/PPS из `GroupViewer.parameter_sets` и `AccessUnit.parameter_sets` **включают start code** (farm режет Annex-B и хранит NAL целиком, `farm.rs:895-909`, `:1037-1060`). Перед `avcC` start code снять; **не** делать unescape emulation-prevention (`00 00 03`) — в `avcC` SPS хранится как в битстриме. В измеренном SPS x264 (`67 42 c0 1f ... 00 00 03 00 04 ...`) байты профиля/level находятся до первой эмуляции, но парсить дальше без unescape нельзя.
- Для High profile (`profile_idc` 100/110/122/144) ffmpeg обычно пишет 4 дополнительных байта extension (`chroma_format`, `bit_depth_luma_minus8`, `bit_depth_chroma_minus8`, `numOfSequenceParameterSetExt`). Если их не писать, многие парсеры всё равно принимают, но строгие — нет; лучше писать для High.
- Если SPS/PPS нет — `finalize` должен вернуть `MissingParameterSets`, а не писать `avcC` с нулями. Tap должен ждать первый IDR + sets.
- `avcC` — child `avc1`; `stsd` entry size и `moov` size меняются; см. P0-5.
- Проверка «SPS/PPS match»: сравнить bytes в `avcC` с SPS/PPS из первого IDR, а `profile`/`level` — с `ffprobe`.

**Измеренный эталон (не коммит, только проверка):** SPS 25 байт / PPS 4 байта → `avcC` 40 байт; ffprobe: `is_avc=true`, `nal_length_size=4`, `extradata_size=40`, `profile=Constrained Baseline`, `time_base=1/90000`, `duration=2.000`, `avg_frame_rate=30/1`. Это ровно то, что должно получиться на фикстуре x264.

**H.264 vs H.265:** не пытаться записать H.265 в `avc1`. H.265 NAL header — 2 байта, type=`(b0>>1)&0x3f`; VPS/SPS/PPS = 32/33/34, AUD=35, IRAP=16..23; sample entry `hvc1`/`hev1` + `hvcC`, массивы VPS/SPS/PPS. Текущий writer всегда `avc1`; при подаче H.265 ffprobe показывает `h264/avc1`, `profile=unknown`, декодер сыпет `sps_id 7 out of range` — это подтверждено пробой. Для T09b минимум: `FarmCodec::H265` не выбирать в tap и возвращать `UnsupportedCodec` из writer (fail-closed), `hvcC` — отдельная задача/ P2.

### P0-4. Timescale и `stts`: 90000/48000, сумма дельт, последний сэмпл, VFR

| Трек | Сейчас | Нужно | Следствие |
|---|---|---|---|
| movie `mvhd` | timescale 1000, duration = video `dur` (`:224-225`) | 1000, duration = max по трекам (ms) | Аудио длиннее видео → обрезанный `mvhd` |
| video `mdhd` | 1000 (`:279`), `stts` в мс (`:337-347`) | **90000**, `stts` = `pts_us*90/1000` | `time_base=1/1000`, джиттер 33/34 мс, `avg_frame_rate` 30.3 |
| audio `mdhd` | 1000 (`:415`), default 20 мс (`:471-473`) | **sample_rate (48000)**, `stts` = 1024 на AAC-кадр | Невозможно корректно описать AAC; `time_base=1/1000` |
| `tkhd` | duration `dur` в ms (`:258`, `:395`) | ms (movie timescale) | Нельзя переиспользовать `dur` как `mdhd` duration после смены timescale |
| `stts` последний | копия предыдущей дельты (`:342-343`, `:468-469`) | реальная/дефолтная длительность последнего сэмпла, delta≥1 | `mdhd duration` ≠ sum(`stts`) |

**Измерено на текущем файле:** `mdhd duration=1966`, сумма `stts`=1999 (60 кадров, 33/34 мс) — расхождение 33 мс; `ffprobe duration=1.966`, `avg_frame_rate=60000/1999` (30.015), `r_frame_rate=1000/33` (30.303). На эталонном прототипе `mdhd=180000`, sum `stts`=180000, `duration=2.000`, `avg=30/1`.

**Правила:**
- `duration_ticks = sum(deltas)`, а не `last_pts`; `effective_duration` (`:210-213`) для этого не годится.
- Каждая дельта ≥1 тик. При дубле/немонотонном timestamp: `ContainerError::InvalidTimestamp` (вариант уже есть, `:18-20`, но не используется) или clamp до 1 с логированием; `saturating_sub` (`:341`) молча превращает назад-идущее время в 0 → default, это скрывает сброс `pts_us` после смены группы.
- VFR/дропы: `stts` c большими дельтами — нормально (пауза/пропуск); не заменять все дельты на `1000/fps`. Для последнего сэмпла брать медиану/дефолт кадра, но `mdhd` = sum.
- `tkhd` duration = `round(duration_ticks * 1000 / timescale)`; `mvhd` = max по трекам. `mdhd` version 0 (u32) при 90000 хватает ~13.2 ч; для длинных записей — version 1/u64 или guard.
- Не конвертировать `au.pts_us()` → ms → ticks: это два округления. Tap должен передавать `pts_us` (или сразу 90k ticks), writer — хранить `pts_us`/ticks.
- Audio: AAC-LC 1024 samples/frame при 48000; `stts` delta 1024, `mdhd duration = samples`; для 44.1k — 1024 при 44100. Если аудио нет — не писать audio trak (см. P0-6).

### P0-5. `stco`, двухпроходный `moov`, faststart и 32-bit/co64

**Что сейчас правильно:** текущий layout — `ftyp` → `moov` → `mdat`, т.е. уже «faststart» (moov до mdat). Измерено: `ftyp` 28 байт, `moov` 1744, `mdat` payload начинается с 1780, первый `stco`=1780 — совпадает. Пока состав `moov` не меняется, pass 1/pass 2 дают одинаковый размер, и `stco` корректен.

**Где ломается:**
1. **Размер `moov` между pass 1 и pass 2.** `build_moov` (`:215-246`) включает `avcC`, `esds`, аудиотрек, `stss`, `stts` RLE. Если `avcC`/`esds` появляются/меняются после dummy-прохода, или аудиотрек добавляется условно, `moov_len` в `:163` не равен реальному, и **все** `stco` смещаются на дельту. Нужен assert `real_moov.len() == dummy_moov.len()` (payload) до записи; если нет — пересчитать с фиксированной точкой или вернуть ошибку, а не писать битый файл.
2. **`co64` condition.** Если выбирать `stco`/`co64` по `dummy_offsets` (нули), pass 1 выберет `stco`, pass 2 при offset >4 GiB — `co64`, размеры разные → смещения врут. Решение о `co64`/64-bit `mdat` принимать по `media_data.len()`/оценке файла **до** pass 1.
3. **Усечение.** `build_stco` (`:564`) и `write_box` (`:570`) кастуют в `u32`; при >4 GiB offset/размер молча станут мусором. Для T09b с `max_size_bytes` по умолчанию 50 MB это не достигается, но `ContainerConfig.max_size_bytes` публичный. Либо `co64` + `mdat` с `size==1`+largesize (16-байтовый заголовок, offsets учитывают его), либо `ContainerError::TooLarge` при `media_data.len()+overhead > u32::MAX`; тест на чистой функции без 4 GiB аллокации.
4. **Faststart.** Текущий moov-first — это уже faststart; не надо двигать mdat. Если в будущем перейти на mdat-first (streaming), то после переноса `moov` в начало `stco` надо пересчитать (ffmpeg `-movflags +faststart` делает это сам; ручной `memmove` без пересчёта — битый файл). В T09b не менять layout без необходимости.
5. **`check_capacity`.** `+2048` (`:191`) не покрывает `stbl` при длинной записи: 1 ч @30 fps = 108k сэмплов → `stco` 432 KB + `stsz` 432 KB + `stts`/`stss` ~1 MB. Нужен финальный `if output.len() > max_size_bytes` → `StorageFull`, либо оценка `moov` по числу сэмплов. Иначе квота «50 MB» может быть превышена.
6. **mdat size patching.** Сейчас размер пишется сразу (`:182`), патчинга нет. Если делать streaming, нужно резервировать 8 (или 16) байт и патчить в конце; `stco` зависит от размера заголовка `mdat`, поэтому выбирать его до первого сэмпла.

### P0-6. Аудио: `esds` требуется планом, но AAC-источника в записи нет

**Факты:**
- Текущий writer **всегда** пишет audio trak (`:242-243`) и `mp4a` (`:450-458`), даже если аудиосэмплов 0. На реальном видео-файле ffprobe показывает второй поток `codec_name=aac`, `sample_rate=48000`, `channels=2`, `duration=1.966`, `nb_frames=N/A`, хотя в `mdat` нет ни одного аудиобайта и `esds` отсутствует. Это фиктивный поток.
- `enable_container` не вызывается, audio tap отсутствует; `gateway_aac` — это SIP MP4A-LATM мост, не запись микса. Микс MCU — PCMU/PCMA/G722/Opus (`gateway_audio.rs:59-92`), не AAC. Чтобы получить `esds`/AAC-дорожку, нужен AAC-энкодер (FFmpeg child) и audio tap — это **не** «+avcC», это отдельный кусок работы.
- Пустой контейнер: `finalize()` без сэмплов даёт 968 байт; ffprobe показывает два потока, а `ffmpeg -i empty.mp4 -f null -` падает `Cannot determine format of input 0:0 after EOF`. То есть «пустой файл» тоже нельзя считать успехом.

**Решение (рекомендуется для T09b):**
- По умолчанию — **video-only** MP4: audio trak не писать, если `audio_samples.is_empty()`. `ContainerConfig` получает `audio: Option<AudioConfig>` (default `None`); `write_audio_frame` без конфига → `UnsupportedAudio`.
- `esds` реализовать и протестировать как отдельный путь: `AudioConfig { codec: Aac, sample_rate, channels, asc: Vec<u8> }`; при наличии AAC-сэмплов писать `mp4a`+`esds`, `stts` 1024, `mdhd` 48000. Тест — синтетические AAC-кадры из ADTS (FFmpeg генерирует `aac.aac`, тест срезает 7/9-байтовые ADTS-заголовки), ffprobe `profile=LC`, `time_base=1/48000`, decode. Это доказывает `esds`, не притворяясь, что в проде есть аудио.
- Если продукт требует аудио в записи — отдельная задача: AAC-энкодер + audio tap; не втискивать в T09b.
- **Конфликт формулировки приёмки:** `MASTER_TASK_LIST:48` буквально требует «avcC/**esds**/timescale/stco корректны». Если понимать это как «esds присутствует в каждом записанном файле», то video-only недостаточно: нужен AAC-путь (энкодер + audio tap) или явное решение parent, что `esds` проверяется синтетическим тестом, а прод-запись видео-only. Не подменять это пустым `mp4a`/фиктивным `esds`. Этот выбор должен быть зафиксирован до реализации, иначе приёмка и scope разойдутся.

**Формат `esds` (проверен прототипом):**
```
version/flags 0
ES_Descriptor tag 0x03, len
  ES_ID u16=1, flags 0
  DecoderConfigDescriptor tag 0x04, len
    objectTypeIndication 0x40 (MPEG-4 Audio / AAC)
    streamType 0x05 (audio)<<2 | ...
    bufferSizeDB u24, maxBitrate u32, avgBitrate u32
    DecoderSpecificInfo tag 0x05, len=2, ASC 0x11 0x90 (AAC-LC, 48 kHz, stereo)
  SLConfigDescriptor tag 0x06, len=1, 0x02
```
Для 48k stereo LC `ASC=11 90`; для других частот/каналов — вычислять/конфигурировать. `mp4a` sample entry: 6 reserved + dref=1 + 8 reserved + channels u16 + sample_size 16 + pre_defined 0 + sample_rate 16.16 (`48000<<16`), затем `esds`. Нельзя класть ADTS/LOAS-заголовки в `mdat` как AAC access unit.

**Что не делать:** писать `mp4a`/`esds` с нулевыми/пустыми сэмплами «для галочки»; кормить PCMU/Opus в `mp4a`; ставить `esds` без ASC; оставлять пустой audio trak, который ffprobe показывает как живой.

### P1-1. `ContainerConfig` должен быть из фактического `EncoderSpec`, а не из `RecorderProfile::default()`

`RecorderManager::start_recording` (`recorder.rs:203-213`) и `stop_recording_internal` (`:288`) пишут в `RecordEntry` `RecorderProfile::default()` = 1280×720@30, 2350 kbps. Фактическая группа фермы — из `farm_spec_for(&profile, visible_windows)` (`gateway_video.rs:536-560`): может быть 640×360@15, другой bitrate, profile main/high. Если tap возьмёт `ContainerConfig::default()`/`RecorderProfile`, `avc1` width/height и `tkhd` будут 1280×720, а SPS — 640×360 (ffprobe обычно верит SPS, но строгие плееры/UI — нет; `RecordEntry` врёт).

**Правило:** `ContainerConfig { width, height, fps }` — из `GroupStat.key.spec` выбранной группы (или `FarmTap.key.spec`); `profile`/`level` — из SPS в `avcC`; `RecordEntry.width/height/bitrate_kbps` обновить после выбора группы (T09a разрешал declared profile, но T09b уже знает фактический). `RecorderProfile` оставить для `estimated_time`/клампов, не для MP4.

### P1-2. Выбор группы, re-key, `Closed`, сброс `pts_us`, несколько групп на комнату

- На комнату может быть **несколько** H.264-групп (разные caps/profile/visible windows), а `visible_windows` меняет bitrate → gateway пересоздаёт группу с новым `EncoderKey` (`gateway_video.rs:736-746`, `farm.rs:569-591`). Tap должен:
  - выбирать группу с `viewers>0`, текущим `canvas_version`, `!cancel`;
  - при `RecvError::Closed` **не** вызывать `acquire` (иначе скрытая группа), а завершать запись/ждать появления новой группы снаружи; при смене ключа/разрешения — финализировать текущий файл, не писать новый SPS в старый `avcC`;
  - `AccessUnit.pts_us` — время от старта **группы** (`farm.rs:227-258`, `AccessUnit::pts_us`), при переподключении сбрасывается в 0. Если писать его напрямую, `stts` получит назад-идущее время (сейчас `saturating_sub` → 0 → default, т.е. скрытая порча). Нужен монотонный таймлайн записи: `session_start + au.pts_us` или накопленный offset; при разрыве — пауза/новая сессия, не отрицательная дельта.
  - `active_h264_groups` (`recorder.rs:96-106`) не фильтрует `canvas_version`/`cancel` — это уже отмечено в T09a rereview; `subscribe`/`has_active_h264_group` должны фильтровать, иначе 409 пропустит мёртвую группу.
- `Lagged(n)` в broadcast (`gateway_video.rs:762-768`) — это дропы; для записи считать и продолжать, но если потерян IDR, `stss`/первый кадр могут быть некорректны; лучше при `Lagged` не начинать с середины GOP.

### P1-3. SPS/PPS: кэш, `parameter_sets` со start code, смена SPS

- `GroupViewer.parameter_sets` — snapshot на момент `subscribe` (`farm.rs:505-515`), может быть пустым, если группа только стартовала: первый IDR ещё не закодирован. `AccessUnit.parameter_sets` — только sets, встреченные в этом AU (`farm.rs:227-258`, `:895-909`); у P-кадров пусто.
- Tap должен копить sets из snapshot + каждого AU; ждать первый `au.is_idr() && !sets.is_empty()` (x264 `repeat-headers=1:aud=1` даёт SPS/PPS в IDR). Если sets не появились — `MissingParameterSets`, не писать файл.
- Sets включают start code; в `avcC` — без start code, с emulation-prevention. Дедуп по байтам, SPS type 7, PPS type 8; если новый SPS отличается — это смена конфигурации: финализировать/новый файл, не менять `avcC` на лету.
- Профиль/level брать из SPS (`SPS[1..4]` после NAL header), не из `EncoderSpec.profile`/`level` (они могут быть «baseline»/«3.1», а SPS — «Constrained Baseline»/31).

### P1-4. `stss`: не подставлять кадр 1; первый сэмпл должен быть IDR

`container.rs:352-363`: если keyframes пуст, а сэмплы есть, пишется `stss=[1]`. Это объявляет первый delta-кадр sync; декодер начнёт с мусора/артефактов, а `ffprobe -show_packets` покажет `K__` у не-keyframe. Для записи, начавшейся в середине GOP, это типичный сценарий.

**Правило:** `write_video_frame` для первого сэмпла требует `is_keyframe=true` (`ContainerError::FirstSampleNotKeyframe`); tap дропает AU до первого IDR. Если за всю запись не было IDR — `finalize` ошибка `NoKeyframe`, не файл с фейковым `stss`. Для H.265 `is_idr` — IRAP (BLA/IDR/CRA), но это только при реализации `hvcC`.

### P1-5. `finalize` на ошибке/остановке/рестарте: сейчас ошибка глотается, а `stop_recording_internal` может оставить recorder-участника

- `recording.rs:309-313`: `if let Ok(bytes) = writer.finalize() { ... }` — при ошибке `finalized_container=None`, `stop()` возвращает `Ok(meta)`, `size_bytes` может быть 0, API отвечает 200. Это скрытый отказ: файла нет, но запись «успешна».
- `recorder.rs:263`: `let meta = session.stop()?;` — сессия уже удалена из `sessions` (`:249-261`). Если `stop()` начнёт возвращать ошибку finalize, early-return **до** `unregister_participant`/`storage.save`/`state.records` оставит `recorder-<room>` в RoomHub и «активную» строку. Нужно: финализировать, сохранить meta/строку (duration>0, size=0, error в лог), затем unregister/уведомить; либо guard/компенсация.
- `RecordingError` (`recording.rs:48-62`) не имеет варианта `Container`; добавить `Container(String)` или хранить `finalize_error` в сессии. API должен либо вернуть 500, либо честно отдать запись с `size_bytes=0` и логом; не 200 с несуществующим файлом.
- Рестарт процесса: контейнер живёт только в RAM (`RecorderManager.containers`, `recorder.rs:116`); T09a сохраняет только метаданные. После рестарта файла нет; `src=record.id` и `/static/videorecords/...` — фикция (роута нет). T09b не должен обещать «playable after restart», если не добавляет файловое хранилище; это отдельный scope.

### P2-1. H.265: `avc1` — не «просто ещё один кодек»

Текущий writer не имеет ни `VideoCodec`, ни `hvcC`; при подаче H.265 он пишет `avc1` с width/height из конфига. Измерено: ffprobe показывает `codec_name=h264`, `codec_tag_string=avc1`, `profile=unknown`, `nb_frames=1`, декодер — `sps_id 7 out of range`, `missing picture`. Это не «H.265 не поддерживается», это **неверная идентификация**.

**Минимум T09b:** `ContainerError::UnsupportedCodec` для H.265; tap выбирает только `FarmCodec::H264` (`active_h264_groups` уже фильтрует H264); тест «H.265-группа не выбирается / writer отклоняет». **Если** H.265 в scope — `hvc1`/`hev1`, `hvcC` (VPS/SPS/PPS arrays), `stss` по IRAP, отдельная фикстура x265; это +100–150 LOC и отдельный риск. Не делать H.265 «заодно» в T09b.

### P2-2. B-кадры/DTS-PTS и `ctts`

В WebRTC H.264 обычно baseline/constrained baseline без B; x264 `-tune zerolatency` и x265 `zerolatency` отключают B. Но `EncoderSpec.profile`/`extra_params` приходят из gateway и могут быть main/high; `AccessUnit.pts_us` — это `started.elapsed()` в момент эмиссии (`farm.rs:895-909`), а не PTS из энкодера. Если B-кадры есть, порядок вывода ≠ порядок показа, а `ctts` в writer нет: `stts` опишет output order, декодер покажет неверный порядок/дёрганье. T09b: зафиксировать допущение «B-кадров нет» в docs/тесте (`ffprobe has_b_frames=0` на фикстуре), не добавлять `ctts` без источника DTS/PTS. Если нужно — отдельная задача с парсингом SPS VUI/slice header.

### P2-3. Аудио/видео interleaving и порядок сэмплов

Сейчас video-only; `stsc` = 1 сэмпл/chunk, `stco` — на каждый сэмпл. Это валидно. Если добавить аудио, два независимых потока могут писать в `mdat` блоками (все видео, потом аудио) — `stco` всё равно корректен, но seek/буферизация хуже; для T09b не требуется. Не пытаться «interleave» без пересборки offset'ов; если делать — писать по DTS и обновлять `stsc` (chunks с несколькими сэмплами) осторожно.

### P2-4. Пустой/короткий файл, gap-сегменты, zero-duration last sample

- Пустой `finalize` (0 сэмплов) → 968 байт, ffprobe показывает фиктивные потоки, `ffmpeg` decode падает. `stop` без единого AU должен вернуть `ContainerError::Empty`/не сохранять файл, а не «успех».
- Запись, начавшаяся до первого IDR: см. P1-4.
- Gap/дропы: `stts` большая дельта; `mdhd` sum; не вставлять фиктивные сэмплы.
- Zero-duration last sample: delta 0 запрещена; использовать дефолт/медиану, `mdhd` sum; `stts` не должен содержать 0.
- `StorageFull` в середине: writer вернул ошибку, tap должен остановить запись и финализировать то, что есть (или пометить failed), не оставлять «вечный Running».

### P2-5. Rotation matrix/tkhd, language/udta

- `tkhd`/`mvhd` matrix identity (`0x00010000,0,0, 0,0x00010000,0, 0,0,0x40000000`) — корректно для некрученого композита; `tkhd` width/height 16.16. Если появится rotation, нужна матрица с translation и пересчёт `moov`; T09b не требует.
- `mdhd` language `0x55c4` = `und` (`:281`, `:417`) — корректно; `hdlr` names — корректно. `udta`/`meta`/creation_time нет — для playback не нужно; если добавлять, это меняет размер `moov` (P0-5), не делать в T09b.
- `ftyp` compatible brands стоит дополнить `avc1` (и `hvc1` при H.265); не критично, но дешево.

### P3-1. Память/квоты: `media_data` + output + `containers`

`finalize` держит `media_data` и собирает `output` (double), `RecorderManager.containers` — безлимитный `HashMap<String, Vec<u8>>` (`recorder.rs:116`), `save_container` копирует `bytes.to_vec()` (`:265`). При 50 MB cap это ~150 MB на запись; при нескольких комнатах — заметно. T09b может оставить (cap 50 MB), но не увеличивать cap и не добавлять третий буфер без нужды. `check_capacity` см. P0-5.

### P3-2. Рестарт/файлы/UI

Метаданные переживают рестарт (T09a), контейнер — нет; `get_container` после рестарта `None`, `src` в API — id, а `/static/videorecords/<id>` роута нет. Если приёмка T09b проверяет файл после рестарта — нужен файловый store (новая задача), не «починить» это в writer. В отчёте T09b явно указать: playable file — in-process artifact, не durable.

## §3 Tap semantics: что это в этом коде, почему нельзя скрытую группу

### 3.1 Термины и текущие сущности

| Понятие | Где | Что означает |
|---|---|---|
| `tap` | в коде отсутствует | В T09b — подписка рекордера на **уже кодируемый** `AccessUnit`-поток группы фермы |
| `EncoderFarm` | `farm.rs:360-370` | Одна на `McuEngine`; `BTreeMap<EncoderKey, Arc<Group>>` |
| `Group` | `farm.rs:320-355` | child FFmpeg + `broadcast::Sender<Arc<AccessUnit>>` + `parameter_sets` + refcount |
| `GroupViewer` | `farm.rs:671-722` | Владеющий зритель: `acquire` → refcount+1, `Drop` → refcount-1/retire |
| `AccessUnit` | `farm.rs:227-258` | Annex-B AU + `is_idr` + `pts_us` + sets; broadcast capacity 8 |
| `RecorderManager` | `recorder.rs:109-120` | Сессии/контейнеры в RAM; recorder-участник в RoomHub |
| `RecordingControl` | `admin/state.rs:136-143` | `start/stop/active_h264_groups`; 409 в admin-handler |
| `MAX_PEERS_PER_ROOM` | `webrtc_room.rs:38` | Лимит **WebRTC** пиров SFU (2), не групп фермы |
| `VKS_VIDEO_FARM_MAX_GROUPS` | `farm.rs:1098-1104` | Лимит групп фермы (128), каждая = FFmpeg-процесс |

### 3.2 Как считаются группы и зрители

- `Group.refcount` инициализируется 2: «зритель + сам энкодер» (`farm.rs:462`). `viewers = refcount.saturating_sub(1)` (`:606`). `GroupViewer::release_inner`: `previous<=2` → `retire` (`:705-716`). То есть группа живёт, пока есть хотя бы один владеющий зритель.
- `FarmInner.groups.len() >= max_groups` → `FarmError::Overloaded` (`farm.rs:426-434`, `:258-276`); default 128.
- `active_h264_groups` = room + H264 + `viewers>0` (`recorder.rs:96-106`); admin 409 при 0 (`observability.rs:780-790`).
- `farm_metrics` — `encoder_group_active`, `encoder_group_refcount`, `encoder_group_viewers` и др. (`farm_metrics.rs:30-53`), обновляются из `video_farm_stats`; скрытая группа = лишняя серия с `frames=0`, `viewers=1` (если tap владеющий) или `viewers=0` (если non-owning, но группа жива).
- `MAX_PEERS_PER_ROOM=2` — только `WebRtcRoomRegistry` (`webrtc_room.rs:267,324`); recorder в RoomHub (`recorder.rs:183-196`) не является WebRTC-пиром и не должен им становиться. Если тап реализовать как скрытого WebRTC-участника/peer, в SFU-комнате на 2 человека он займёт слот и получит `RoomFull`; T09b должен оставаться в MCU/RoomHub.

### 3.3 Почему «скрытая группа» — это дефект, а не оптимизация

- Лишний FFmpeg: ~52 MB RSS на живой энкодер (замер T09a), плюс CPU; при 128 группах — риск OOM/`Overloaded` для реальных зрителей.
- Лишний `groups.len()`: может вытеснить реальную группу по лимиту; при `max_groups=1` скрытая группа займёт единственный слот.
- Лишний `active_h264_groups`: 409-гейт начнёт пропускать запись без зрителя; после рестарта/ретира — «активная» группа-призрак.
- Лишний файл: запись без кадров (frames=0) даст пустой/битый MP4, но API вернёт успех.
- Лишняя метрика/лог: `encoder group started` без зрителя; алерты/дашборды врут.

### 3.4 Рекомендуемая семантика (non-owning subscribe)

1. `RecorderControl::start` после создания сессии вызывает `mcu_engine.video_farm().subscribe(room, H264)`.
2. `None` → запись стартует, но tap не запускается; в лог `warn`; для пользовательского пути admin уже вернул 409 до `start`. Если хочется закрыть гонку — вернуть типизированную ошибку/409, но это ломает `network_integration.rs:2234` (обновить тест).
3. `Some(tap)` → `ContainerConfig` из `tap.key.spec`; `session.enable_container(config)`; `tokio::spawn` tap-таск, хранить `AbortHandle`/`JoinHandle` в `RecorderManager`; на `stop` — abort + join.
4. Tap: `select!` на `rx.recv()`/cancel; `Lagged` — счётчик/продолжить; `Closed` — завершить; до первого IDR+sets — дропать; `write_video_sample(au.data(), au.pts_us(), au.is_idr())`; на `ContainerError` — лог + cancel/stop, не паника.
5. `FarmTap` не увеличивает refcount; `viewers`/409/метрики не меняются. Если нужен keep-alive — отдельный `taps` счётчик и явное решение, что 409 значит; не маскировать под viewer.

| `farm_metrics_no_hidden_group_series` | unit `farm_metrics` | после start без группы нет `encoder_group_active` серии/сумма 0 |

### 4.3 Фикстуры/golden

- **Не коммитить MP4-golden** — он зависит от версии x264/ffmpeg и быстро протухает. Генерировать фикстуры в тесте через `ffmpeg` (skip, если нет), как PG-тест.
- Если нужен checked-in бинарник — только **крошечный** Annex-B H.264 (0.3–0.5 с, 160×90, ~10–30 KB) и/или ADTS AAC (~8 KB); путь `crates/vks-recorder/tests/fixtures/t09b/`; не класть в `crates/vks-server`.
- Для `avcC`/`esds` лучше golden **байты полей** (SPS/PPS, ASC, descriptor tags) в тесте, а не весь файл.
- Временные файлы: `std::env::temp_dir()`/`CARGO_TARGET_TMPDIR`, уникальное имя с PID, удалять; не писать в repo, `/home/pro/Рабочий стол/mcu/backups`, live DB.

### 5.1 Шаг 1 детально

- `ContainerConfig`: `VideoCodec` (H264 default, H265 reject), `audio: Option<AudioConfig>` (default `None`), `max_size_bytes`; `width/height/fps` из spec; `sample_rate/channels` — для audio config.
- `PlayableContainerWriter`: `parameter_sets: Option<ParameterSets>`, `video_samples` с `pts_us`/`size`/`offset`/`keyframe`, `audio_samples`.
- `write_video_frame_pts(pts_us, keyframe, data)` — канонический; `write_video_frame(ms, ...)` — wrapper для старых тестов (или удалить и обновить).
- `finalize`: проверить `samples`/`sets`, pass 1/pass 2 assert, `Empty`/`MissingParameterSets`/`FirstSampleNotKeyframe`, `TooLarge`.
- `build_avcc` (H264), `build_esds` (AAC), `build_stts` (ticks), `build_stss` (1-based), `build_stco` (u32) / `build_co64` (u64) при необходимости.
- `duration_ticks(track)`, `tkhd_duration_ms`, `mvhd_duration`; `next_track_ID` = 2/3 по числу треков.
- `ftyp` brands + `avc1`; audio trak только при `audio.is_some() && !audio_samples.is_empty()`.
- Не менять `ftyp`/`moov` порядок; `mdat` после `moov` (faststart).

### 5.2 Шаг 3/4 детально

- `FarmTap` (non-owning): `key`, `rx`, `parameter_sets`; `subscribe` под `groups.lock()`, фильтры, максимум viewers, BTreeMap tie-break; никакого `viewer`/`acquire`/`spawn`.
- `RecorderManager`: `taps: Arc<Mutex<HashMap<RoomId, TapHandle>>>`; `start_tap(room, record_id, tap, config)`, `abort_tap(room)`, `push_video(record_id, ...)`; `get_container` после stop.
- `RecorderControl::start`: `start_recording` → `subscribe` → `enable_container`/spawn; `None` — warn/best-effort (или typed error, см. P1-6); `stop` — abort tap до `stop_recording_async`.
- `RecorderControl::active_h264_groups`: `video_farm().has_active_h264_group(room)` (room+codec+current canvas+!cancel+viewers>0).
- Tap: `tokio::select!` на `rx.recv`, `cancel` (watch/AtomicBool/AbortHandle); `Closed`/`Lagged`; `IDR+sets` gate; `pts_us`; `write`; on error log+stop; no panic.
- `ContainerConfig` из `tap.key.spec`; `RecordEntry` width/height/bitrate обновить; `size_bytes` после stop.

### 5.3 Как запускать ffprobe/ffmpeg-приёмку

```bash
# 1) unit/writer
cargo test -p vks-recorder --offline

# 2) ffprobe (host 8.0.1; в CI — skip, если нет)
cargo test -p vks-recorder --test ffprobe_acceptance --offline -- --nocapture

# 3) серверный tap/no-hidden-group
cargo test -p vks-server --test recorder_tap --offline -- --nocapture
```

Ожидаемые значения на реальном x264 60 AU 640×360@30 (эталонный прототип):
```
codec_name=h264
codec_tag_string=avc1
profile=Constrained Baseline
width=640 height=360
is_avc=true
nal_length_size=4
time_base=1/90000
avg_frame_rate=30/1
nb_frames=60
duration=2.000000
extradata_size=40
```
`ffmpeg -v error -i out.mp4 -map 0:v:0 -f null -` — exit 0. Для AAC: `codec_name=aac`, `profile=LC`, `time_base=1/48000`, `nb_frames=48`, `duration=1.024`.

### 5.4 Что НЕ делать

- **Не** вызывать `acquire`/`acquire_video_viewer`/`viewer` из recorder/tap; **не** спавнить hidden group; нет группы → 409/None, не «создать для записи».
- **Не** переписывать `vks-recorder` и не добавлять `tokio`, `mp4`, `ffmpeg-next`, `openh264`, `hound` и т.п.; writer остаётся dep-light, tap — в `vks-server`.
- **Не** менять DB-схему/миграции, `vks_data.db`, `backups/`, порты `:8080/:18082`; T09b — контейнер/tap, не storage.
- **Не** ослаблять тесты: не удалять проверки `ftyp/moov/mdat/stbl`, не заменять ffprobe-гейт на «exit 0», не делать `stss=[1]`/пустой audio trak/фейковый `esds`.
- **Не** писать H.265 как `avc1`; **не** добавлять B-frame `ctts` без DTS/PTS; **не** делать streaming mdat-first без пересчёта `stco`/faststart/co64.
- **Не** конвертировать `pts_us`→ms→ticks; **не** использовать `duration_ms` как `mdhd` duration после смены timescale.
- **Не** коммитить большие MP4-фикстуры/golden; генерировать ffmpeg в тесте, иначе skip.
- **Не** обещать durable MP4 после рестарта: контейнер в RAM; это отдельная задача файлового storage.
