## §2 Ловушки

### P0 — ломают приёмку или данные

#### P0-1. Строки + JSON + маркер обязаны быть в одной транзакции

**Что.** Существующий `put_configuration_document` — одиночный UPSERT (`core_adapter.rs:269-281`, `:799-811`). Если миграция делать так:

```text
BEGIN; вставить directory_*; COMMIT;      // 1
BEGIN; UPDATE configuration_documents; COMMIT;  // 2
BEGIN; INSERT schema_state; COMMIT;        // 3
```

— то краш/ошибка между шагами даёт: строки без маркера (повторный импорт), JSON без строк (данные потеряны), маркер без строк (миграция «применена», справочник пуст). Приёмка «идемпотентная миграция с маркером» требует **ровно одной** транзакции на все три эффекта.

**Как не наступить.** Новый метод порта (не `put_configuration_document`):

```rust
async fn migrate_directory_document(
    &self,
    key: &str,
    expected_document: Option<&str>,
    new_document: Option<&str>,
    snapshot: &DirectorySnapshot,
) -> Result<DirectoryMigrationOutcome, StorageError>;
```

SQLite/PG реализуют его через `pool.begin()`: marker → чтение/CAS документа → `replace_snapshot` → CAS `UPDATE configuration_documents` → `commit`. Memory — под `RwLock`, заменяя карты и документ атомарно. `Outcome = Applied | AlreadyMigrated | DocumentChanged`.

#### P0-2. Маркер и `ON CONFLICT DO NOTHING` не защищают от воскрешения

**Что.** План прямо предупреждает: «`ON CONFLICT DO NOTHING` недостаточно» (`00_MASTER_PLAN.md:131`). Сценарии:

1. Миграция применилась, контакт удалён через API, маркер потерян (restore старого `schema_state`/`reset`/ручная правка) → повторная миграция читает **старый JSON**, где контакт ещё есть, и `INSERT … ON CONFLICT DO NOTHING` вставляет его обратно.
2. Маркер записан, но JSON не очищен (старый бинарь/частичный сбой) → следующий старт «уже мигрирован», ключи остаются; любой старый writer может их перезаписать.
3. Маркер записан **до** вставки строк (если порядок неверный) → строки не импортированы, JSON очищен → данные потеряны без права повторного импорта.

**Как не наступить.**

- Маркер, строки и удаление `resources.directory`/`resources.addresses` — **в одной транзакции**.
- При отсутствии маркера, но **непустых** таблицах: не импортировать JSON, а принять существующие строки за истину, очистить legacy-ключи и поставить маркер. Это защищает от «потеряли маркер → воскресили удалённое».
- При маркере `version >= 1`: ничего не импортировать и не очищать (чужой/старый writer мог добавить данные, которых нет в SQL; молчаливая потеря недопустима). Ключи просто игнорируются новым кодом.
- Тест: `lost_marker_does_not_resurrect_deleted_contact` — миграция, удаление строки, `DELETE FROM schema_state`, повторный запуск → строки нет.
- Ограничение, которое надо записать в отчёт: если маркер потерян **и все таблицы пусты**, а в старом JSON остался удалённый контакт, отличить «свежую БД» от «потерянный маркер» невозможно; это документированный предел, а не баг.

#### P0-3. Одна таблица `directory_addresses(id PK, owner_id)` конфликтует с личными копиями

**Что.** Сейчас `attach_user_call_string` **копирует** глобальный `AddressRecord` в личную книгу под тем же `id` (`directory/addresses.rs:54-88`). `GET /users/{u}/call_strings` отдаёт копию; `update_user_call_string` меняет только копию (`:221-276`); удаление глобального адреса (`call_strings.rs:1276-1312`) **не удаляет** личные копии. Это осознанная семантика.

Если сделать `directory_addresses(id TEXT PRIMARY KEY, owner_id TEXT)`:

- `INSERT` личной копии с тем же `id` либо падает по PK, либо (при `ON CONFLICT DO UPDATE`) **переносит** глобальную строку в owner — глобальная книга теряет адрес;
- `DELETE` глобальной строки по `id` удалит и личную копию (если не различать owner), ломая текущее поведение;
- `primary_address` профиля ссылается на личный `id`; при merge/удалении ссылка может стать висячей.

**Как не наступить.** PK `(owner_id, id)`, где `owner_id = ''` — глобальная книга, иначе `user_id`. Либо отдельная таблица `directory_user_addresses(user_id, address_id, …)`. Глобальный partial unique — `WHERE owner_id = ''`. Личные копии не должны иметь FK на глобальную строку (иначе удаление глобальной каскадно удалит копию — смена поведения).

#### P0-4. Убрать поле из JSON, но оставить чтение/запись через RAM-кэш — значит потерять данные после рестарта

**Что.** Сейчас **все** чтения идут из `ResourceState`:

- глобальная книга: `call_strings.rs:844-850` (`address_book_records`), `:1140-1160` (`address_target`);
- личная: `directory/addresses.rs:28-52`, `:329-349`;
- профили/группы/роли: `directory.rs:510,658-670,739,801-864,929-930,965`; `directory/{groups,roles}.rs`;
- косвенные читатели: `history.rs:277-289` (`contact_json`), `history/export.rs:41-44`, `shell.rs:61-62`.

Если просто удалить `directory/addresses` из `ResourceState` (или поставить `skip`), не загрузив SQL в кэш и не переключив записи:

- после рестарта `sync_from_storage` создаст пустой `ResourceState` → `/api/v3/call_strings` вернёт 0, `/users` без профилей;
- `POST /call_strings` запишет в RAM, `persist` больше не сериализует адрес → после рестарта запись исчезнет;
- `POST /system/restart_services` вызывает `hot_reload_from_storage` (`crates/vks-admin/src/api_v3/settings_admin.rs:748-758`), который **целиком заменяет** `*api_v3.resources` (`state.rs:701-713`) → RAM-кэш справочника обнулится на живом сервере.

**Как не наступить.** После загрузки документа (layouts/history) отдельно загрузить `DirectorySnapshot` из SQL и заполнить кэш; `hot_reload_from_storage` обязан делать то же. Все мутации directory/addresses должны писать SQL (snapshot), а не только RAM. Тест `hot_reload_preserves_directory_and_addresses` обязателен.

#### P0-5. Миграция через `serde_json::from_value::<ResourceState>` / `to_value` теряет неизвестные поля

**Что.** `ResourceState` (`resources.rs:22-55`) не имеет `#[serde(deny_unknown_fields)]`, но и не сохраняет неизвестные поля: любой round-trip через структуру их выбрасывает. Требование плана — «удалить ключи, сохранив неизвестные поля» (`00_MASTER_PLAN.md:100`). Кроме того, после удаления полей из `ResourceState` старый парсер просто перестанет их видеть, и миграция не сможет прочитать данные.

**Как не наступить.** Миграция работает с `serde_json::Value`:

```rust
let mut doc: Value = serde_json::from_str(&raw)?;
let resources = doc.get_mut("resources").and_then(Value::as_object_mut)...
let legacy: LegacyResources = serde_json::from_value(Value::Object(resources.clone()))?; // отдельный DTO
resources.remove("directory");
resources.remove("addresses");
let new_raw = serde_json::to_string(&doc)?;
```

`LegacyResources` — отдельный `#[derive(Deserialize)]` с `addresses` и `directory` (можно переиспользовать `AddressRecord`/`DirectoryState`/`deserialize_addresses`). Не парсить весь `ResourceState`. Заметить: `persist` и так теряет неизвестные поля при **любой** мутации (`resources.rs:257-262`) — T10 не обязан чинить это навсегда, но миграция не должна терять их **сама**.

#### P0-6. Built-in роли не лежат в `directory.roles`

**Что.** `default_roles()` возвращает Administrator/Operator, но в `DirectoryState.roles` хранятся только кастомные/override-роли (`directory.rs:61-74`, `:207-208`). При этом `DirectoryUser.roles` содержит и built-in id (например, `770fada3-71d8-4176-a969-e12ec2059e64`) — это проверяется тестами (`directory_tests.rs:359-360`). Если `directory_user_roles.role_id` имеет FK на `directory_roles(id)`, миграция живой БД упадёт на первой же built-in роли. Если «сидировать» built-in роли в таблицу, появится второй источник истины с `default_role_permissions()`.

**Как не наступить.** В v1 — **никакого FK** на `role_id`; join-таблица хранит любые строковые id. Аналогично для `groups` — исторические dangling id лучше сохранить/залогировать, а не падать. Если FK нужен, сначала сидировать built-in роли и синхронизировать `default_role_permissions` с БД, что выходит за рамки T10.

### P1 — высокий риск, но локально исправимо

#### P1-1. `vks-admin` не имеет runtime-зависимости от `vks-storage`

`crates/vks-admin/Cargo.toml:33-36`: `vks-storage` только в `[dev-dependencies]`. План зоны предлагает `crates/vks-admin/src/api_v3/directory_migrate.rs` (`04_infra_l5l7.md:374`), но если этот модуль вызывает `SqliteStorage`/`PostgresStorage`/`sqlx`, он не соберётся в обычной сборке. Варианты:

- **рекомендуется:** нейтральные типы `DirectorySnapshot`/`StoredDirectory*` + trait-методы в `vks-core`/`vks-storage`; admin только парсит legacy JSON и вызывает порт;
- альтернатива: добавить `vks-storage` в `[dependencies]` admin — проще, но тянет sqlx в admin и ломает «admin не знает бэкенд».

#### P1-2. SQLite FK OFF vs PostgreSQL FK ON

`SqliteStorage::init_options` (`sqlite.rs:86-93`) не включает `PRAGMA foreign_keys=ON`; sqlx сам его не включает. PG всегда enforce. Если добавить FK:

- на SQLite тесты пройдут, на PG — упадут (порядок delete/insert, dangling id, built-in roles);
- включение pragma глобально может сломать существующие тесты/данные (миграции `0001` содержат FK `rooms/layouts/api_keys`, live `foreign_key_check=[]`, но тестовые вставки могут быть неполными).

Рекомендация для T10: **не добавлять FK в 0007** (кроме, возможно, чистых child-таблиц, и только вместе с pragma + тестом). Логическую уборку делать в коде. Если Lead требует FK — включить `foreign_keys(true)` в `SqliteConnectOptions`, прогнать весь `vks-storage`, `vks-admin`, `vks-server` и parity-тест.

#### P1-3. Unique по canonical URI для личных адресов может отвергнуть легальные данные

Глобальный `POST /call_strings` идемпотентен по canonical URI (`call_strings.rs:1091-1108`), но личный `create_user_call_string` (`directory/addresses.rs:279-327`) **не** проверяет дубли и сохраняет `uri` как есть. В старом JSON у одного пользователя могут быть две записи с одинаковым canonical URI. Если создать `UNIQUE(owner_id, uri_canonical)` для personal (owner != ''), миграция/API упадут (или `ON CONFLICT DO NOTHING` молча потеряет одну).

Рекомендация: в v1 — unique **только** для глобальной книги: `CREATE UNIQUE INDEX … ON directory_addresses(uri_canonical) WHERE owner_id = ''`. Личные — либо дедуп в миграции с merge payload (как `dedup_addresses`), либо без индекса. Не менять API-семантику личной книги без отдельного решения.

#### P1-4. `reset()` — тестовый, но его забудут

`reset()` вручную перечисляет таблицы: Memory `core_adapter.rs:251-263`, PG `:778-794`, SQLite `:1308-1324`. Нужно добавить удаление 6 таблиц + `schema_state` **во все три**. Иначе:

- тест сделал `reset`, маркер остался → следующий `init` считает миграцию применённой, строки пустые;
- или строки остались, а документ очищен → «фантомный» справочник.

`MockStorage` в `crates/vks-admin/src/rooms.rs:393-506` реализует трейт вручную; при добавлении **обязательного** метода его тоже надо обновить (иначе компиляция тестов).

#### P1-5. `storage_allow_fallback=true` превращает ошибку миграции в пустой MemoryStorage

`main.rs:131-169`: ошибка `SqliteStorage::init`/`PostgresStorage::init` при `storage_allow_fallback=true` логируется и заменяется на `MemoryStorage`. Если миграция живёт внутри `init`, любая ошибка (битый JSON, конфликт индекса, нехватка диска) → сервер стартует с пустым справочником и принимает записи в RAM. В default/prod `false`, но dev-конфиги могут включить.

Рекомендация: миграцию вызывать **после** init в `main.rs` (под уже взятым `DbLock`) и при ошибке делать `config_exit`/`return Err`, независимо от `storage_allow_fallback`. Fallback оставить только для сетевых/инициализационных ошибок. Либо ввести отдельный `Error::Migration` и не fallback'ить его.

#### P1-6. PG CI не увидит миграционные тесты в `vks-admin`

`ci.yml:131-163` (`test-postgres`) запускает только `cargo test -p vks-storage`. Если новый тест «sqlite==pg» живёт в `vks-admin` (где типы `DirectoryState`/`AddressRecord`), PostgreSQL-джоба его не выполнит. Варианты:

- держать backend-parity тест в `vks-storage` на нейтральном `DirectorySnapshot` (рекомендуется);
- расширить `test-postgres`: `cargo test -p vks-admin --lib --locked directory` с тем же `VKS_STORAGE_PG_URL` (потребует, чтобы admin-dev-dep storage собирался в CI — он уже есть);
- вынести legacy-парсер в `vks-storage` (но тогда дублируются типы admin).

#### P1-7. `vks-db-dedup` перестаёт быть dedup'ом справочника

`dedup_document` обрабатывает `resources.addresses` и `resources.contacts`, но **не** `directory.user_addresses` (`dedup.rs:130-253`). После T10 в документе не будет ни `addresses`, ни `directory`:

- `vks-db-dedup` на новой БД станет no-op (это нормально, но оператор может решить, что «дедуп прошёл»);
- старый бинарь на новой БД тоже no-op, но если он запустится **до** миграции — сделает только глобальные адреса, личные дубли останутся;
- `validate` проверяет только `resources.addresses` (`vks-db-dedup.rs:57-63`), SQL-дубли не видит.

Рекомендация: обновить doc/`--help` и, если возможно, при наличии `schema_state.version>=1` печатать предупреждение «directory already in SQL; tool covers only legacy JSON». Дедуп личных адресов делать в миграции (факторизовать `dedup_addresses`), а не в CLI.

#### P1-8. Id/типы/время: не биндить `Uuid`, не путать секунды и миллисекунды

- directory user id — строковый UUID из `UserId` (`directory.rs:160-175`); address id — `cs-<uuid>` или произвольный (`call_strings.rs:1111`, `directory/addresses.rs:306`); group/role id — строки/константы.
- `created_at` у `AddressRecord`/`DirectoryUser` — **секунды** (`now_secs`, `now_unix_sec`), а `video_records.created_ms` — миллисекунды (`0006`). Не умножать на 1000 «для единообразия» и не менять API-значения.
- SQLite `UUID PRIMARY KEY` в `0001` — BLOB; новые таблицы только `TEXT`. `Uuid` в `WHERE id=$1` не найдёт TEXT-строку.
- `u64` → `i64` для BIGINT: `created_at as i64` с разумным clamp; `sqlx` SQLite не умеет `u64` напрямую.

#### P1-9. `delete_user` идёт в порядке credentials → core_users → directory

`directory.rs:902-939`:

1. LocalDb/`user_credentials` (`:905-917`);
2. `Users::delete_async` → `core_users` (`:919-925`);
3. `commit_directory` → профиль + личные адреса (`:927-933`).

Если добавить FK `directory_profiles.user_id → core_users(id)`/`users(id)`:

- `ON DELETE CASCADE` при `Users::delete_async` удалит профиль **до** шага 3 (и личные адреса, если каскад), а `commit_directory` потом вернёт 404/ошибку;
- `users` — UUID/BLOB, `core_users` — TEXT; FK на неверную таблицу не сработает/не найдёт.

Рекомендация: **без FK на пользователя**; `commit_directory` удаляет профиль/адреса в одной транзакции, порядок шагов не менять. Тест `delete_user_cascades_directory_rows_but_keeps_global_addresses`.

#### P1-10. `POST /call_strings` — read-then-insert гонка на PG

`create_call_string` (`call_strings.rs:1091-1118`) ищет existing по canonical URI в RAM, затем вставляет. В одном процессе `resources.lock()` сериализует; в PG-кластере два узла могут одновременно не найти адрес и вставить два. Unique-индекс спасёт от дубля, но второй запрос получит `unique violation` → 500, если не обработать.

Рекомендация: SQL-upsert по `uri_canonical` (глобальный owner) с `RETURNING`, либо поймать conflict и перечитать. Для T10 достаточно single-node, но тест на unique violation полезен; не выдавать «sqlite==pg» за доказательство кластерной гонки.

#### P1-11. `groups`/`roles` — векторы в профиле, а join-таблицы — производные

`DirectoryUser.groups`/`.roles` — `Vec<String>` (`directory.rs:170-171`), а не отдельные map. Удаление группы чистит векторы (`groups.rs:225-233`), удаление роли — тоже (`roles.rs:295-312`). Если миграция разложит их в `directory_group_members`/`directory_user_roles`, а API продолжит менять только векторы, join-таблицы разъедутся.

Рекомендация: либо snapshot-persist (каждая мутация переписывает и векторы, и join-таблицы из одного состояния), либо per-entity repo, который в одной транзакции обновляет и профиль, и join. Не делать join-таблицы «вторым источником», который никто не обновляет.

#### P1-12. Битые legacy-записи: tolerant-парсер только у `addresses`

`deserialize_addresses` (`resources.rs:60-98`) отбрасывает записи без `uri` и не-объектные протоколы. Но `directory.user_addresses` парсится как обычный `BTreeMap<String, AddressRecord>` без этого фильтра: запись без `uri` станет `uri=""`, а не будет отброшена. `DirectoryUser`/`Group`/`Role` с неверными типами полей могут уронить весь `from_value`.

Рекомендация: миграция разбирает каждую запись отдельно (`serde_json::from_value::<DirectoryUser>`), битую — логирует и пропускает/чинит, а не роняет весь документ. Для `user_addresses` применять ту же `address_record_from_value`, что и для глобальных. Тест `broken_legacy_entries_do_not_abort_migration`.

#### P1-13. Пустой документ / отсутствие документа

`sync_from_storage_inner` загружает ресурсы только если `get_configuration_document` вернул `Some` (`state.rs:701-713`). Если после `reset`/ручной очистки документа нет, а строки directory есть, справочник не должен исчезать: `load_directory_snapshot` надо вызывать **вне** `if let Some(document)`. Миграция при отсутствии документа должна всё равно поставить маркер (иначе каждый старт будет пытаться).

## §3 Что значит «поле убрано из JSON» и что делать со старыми БД

### 3.1 Три возможные трактовки

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. `#[serde(skip)]` на двух полях `ResourceState` + SQL-snapshot (рекомендуется)** | поля остаются в структуре как RAM-кэш, но **не** читаются и **не** пишутся serde; миграция читает raw `Value` | 0 правок в 60+ read-сайтах; старый JSON физически не читается; `persist` не воскрешает; минимум риска | формально поле не удалено из `ResourceState` (расхождение с `00_MASTER_PLAN.md:100`); надо не забыть загрузить snapshot в `sync`/hot reload |
| **B. Literal removal: перенести `DirectoryState`/`addresses` в `ApiV3State`** | `ApiV3State.directory: Mutex<DirectorySnapshot>`; обновить ~63 non-test + тестовые сайты | буквально соответствует плану | +150-250 LOC механических правок, два лока (resources/directory) → риск дедлока, больше конфликтов с параллельными задачами |
| **C. `skip_serializing` only** | старый ключ ещё **читается** при загрузке | проще всего | старый JSON может воскресить данные в RAM; не соответствует «старый ключ больше не читается»; отвергнуть |

Рекомендация: **A** в одном коммите T10, с комментарием в коде и в docs, что literal removal — отдельный follow-up. Если Lead настаивает на B — budget +200 LOC и отдельный тест на lock ordering.

### 3.2 Старые БД и read-compat

- Новый бинарь на старой БД: **единственное** чтение старого `directory`/`addresses` — миграция, raw `Value`. После неё ключи удалены; `ResourceState` их не десериализует.
- Если миграция не может выполниться (read-only БД, битый JSON, ошибка SQL) — **fail-fast** (`config_exit`/`Err`), не отдавать частичный справочник. Исключение — явный Memory-fallback для dev, но он тоже не должен притворяться, что данные на месте.
- Старый бинарь на новой БД не поддерживается: он увидит пустой `directory`, создаст записи в JSON, новый бинарь их проигнорирует. Это надо записать в `deploy/README.md` и в отчёт T10.
- Бэкап старого JSON (если оператор его сохранил) остаётся читаемым для миграции только пока `resources.directory`/`addresses` не удалены; после миграции это исторический артефакт.

### 3.3 `normalize_*`-функции

| Функция | Что делать |
|---|---|
| `normalize_loaded` (`resources.rs:1163-1226`) | **убрать** вызов `dedup_addresses` (`:1225`); оставить ремонт layouts/audiochannels/links/active_layouts. Иначе она будет «чинить» пустые/устаревшие карты и создавать иллюзию миграции |
| `dedup_addresses` (`:1233-1275`) | **факторизовать** в `pub(crate) fn dedup_address_book(addresses: &mut BTreeMap<String, AddressRecord>, user_addresses: &mut BTreeMap<String, BTreeMap<String, AddressRecord>>)`; вызывать из миграции и (опционально) из загрузки SQL-snapshot. Тест `normalize_loaded_collapses…` переписать на неё |
| `deserialize_addresses` / `address_record_from_value` (`:60-98`) | сохранить как legacy-парсер для миграции (сделать `pub(crate)`), но не вешать на `ResourceState` после `skip` |
| `normalize_resource` (`:475`) | не трогать — это layouts |
| `normalize_address_payload` / `address_payload` / `default_contact_payload` (`call_strings.rs:44-129`, `:1017-1045`) | сохранить: SQL хранит `payload` как JSON, при update парсить → merge → сериализовать; не двойное кодирование |

### 3.4 Обратная совместимость API

Проверено: **ни один** endpoint не принимает `directory`/`addresses` как часть тела (granular CRUD). Поэтому «клиент ещё шлёт поле» — это только старый **документ**/старый бинарь, не API-клиент. Тем не менее:

- формы `GET/POST/PATCH/DELETE /call_strings`, `/users`, `/groups`, `/roles`, `/users/{u}/call_strings` не менять;
- `address_book_record` (`call_strings.rs:832-842`) оставить тем же (id/uri/display_name/created_at/busy/payload/contact);
- `created_at` не пересчитывать;
- `primary_address` при загрузке SQL: если ссылка битая — `null` в ответе, не 500;
- `AddressLookup::Ambiguous` (`call_strings.rs:1127-1160`) — глобальный id vs комнатный contact id; SQL-таблица глобальная не должна менять эту логику.

### 3.5 `dedup.rs` / `vks-db-dedup`

- Оставить `dedup_document` для **pre-migration** БД: он безопасен и идемпотентен (`dedup.rs:130`, тест `second_run_is_byte_identical`).
- Он **не** покрывает `directory.user_addresses`; миграция должна дедупить личные адреса сама.
- `CONFIGURATION_KEY` — одна константа (`dedup.rs:28`), не дублировать в миграции.
- `vks-db-dedup` не должен запускаться на живой БД: `--apply` берёт lock (`:77-85`), dry-run — нет; после T10 он видит только layouts/links/contacts.
- Тесты `dedup.rs:568-690` и `tests/dedup_lock.rs` не удалять: они проверяют pre-migration инструмент.

### 4.3 SQLite/PG-инфраструктура

В CI — сервис `postgres:16` и `VKS_STORAGE_PG_URL=postgres://postgres:postgres@localhost:5432/vks` (`ci.yml:131-163`). Локально можно поднять одноразовый `postgres:16` в docker на **неживом** порту, но это не обязательно для T10; главное — parity-тест должен быть в джобе, которая реально получает env.

### 5.2 SQL-скелет `0007` (portable SQLite/PostgreSQL)

```sql
-- 0007_directory_normalized.sql — T10b: directory/addresses out of JSON.
-- Portable: no UUID/BLOB, no JSON1, no dialect-specific time functions.
-- 6 data tables + schema_state; addresses: owner_id='' -> global book.

CREATE TABLE IF NOT EXISTS schema_state (
    state_key  TEXT PRIMARY KEY,
    version    BIGINT NOT NULL,
    updated_at BIGINT NOT NULL
);

CREATE TABLE IF NOT EXISTS directory_profiles (
    user_id       TEXT PRIMARY KEY,
    profile_json  TEXT NOT NULL,   -- full DirectoryUser (forward-compatible)
    updated_at    BIGINT NOT NULL
);

CREATE TABLE IF NOT EXISTS directory_groups (
    id           TEXT PRIMARY KEY,
    group_json   TEXT NOT NULL,
    updated_at   BIGINT NOT NULL
);

CREATE TABLE IF NOT EXISTS directory_roles (
    id           TEXT PRIMARY KEY,
    role_json    TEXT NOT NULL,    -- custom/override roles only; built-in ids are NOT rows
    updated_at   BIGINT NOT NULL
);

CREATE TABLE IF NOT EXISTS directory_group_members (
    group_id TEXT NOT NULL,
    user_id  TEXT NOT NULL,
    PRIMARY KEY (group_id, user_id)
);

CREATE TABLE IF NOT EXISTS directory_user_roles (
    user_id TEXT NOT NULL,
    role_id TEXT NOT NULL,         -- may be a built-in id -> no FK
    PRIMARY KEY (user_id, role_id)
);

CREATE TABLE IF NOT EXISTS directory_addresses (
    owner_id       TEXT NOT NULL DEFAULT '',  -- '' = global; otherwise user_id
    id             TEXT NOT NULL,
    uri            TEXT NOT NULL,
    uri_canonical  TEXT NOT NULL,
    display_name   TEXT NOT NULL,
    payload_json   TEXT NOT NULL,
    address_json   TEXT NOT NULL,             -- unknown/future fields
    created_at     BIGINT NOT NULL,
    PRIMARY KEY (owner_id, id)
);

CREATE INDEX IF NOT EXISTS idx_dir_group_members_user ON directory_group_members(user_id);
CREATE INDEX IF NOT EXISTS idx_dir_user_roles_user    ON directory_user_roles(user_id);
CREATE INDEX IF NOT EXISTS idx_dir_addresses_owner    ON directory_addresses(owner_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_dir_addresses_global_canonical
    ON directory_addresses(uri_canonical) WHERE owner_id = '';
-- No personal unique index in v1: old personal books may contain duplicate canonical URIs.
-- No FK to core_users/users/roles in v1: built-in role ids are not rows; SQLite FK is OFF by default.
```

Почему так, а не «6 таблиц с owner_id в одной addresses»: `(owner_id,id)` — минимальная правка плана, сохраняющая личные копии; built-in роли — не строки; partial unique — только глобальная книга. Если Lead хочет per-field колонки вместо `*_json`, это ок, но тогда `directory_user_addresses` станет 7-й таблицей — лучше честно, чем ломать PK.

### 5.3 Транзакция миграции (SQLite/PG)

```rust
// core_adapter.rs, одинаковый скелет для SqliteStorage и PostgresStorage.
let mut tx = self.pool().begin().await.map_err(to_storage_err)?;

// 1) Резервируем маркер. rows_affected == 1 -> мы владеем миграцией.
let owned = sqlx::query(
    "INSERT INTO schema_state(state_key, version, updated_at) VALUES ('directory', 1, $1)
     ON CONFLICT(state_key) DO UPDATE SET version = excluded.version, updated_at = excluded.updated_at
     WHERE schema_state.version < excluded.version")
    .bind(now_secs() as i64)
    .execute(&mut *tx).await.map_err(to_storage_err)?.rows_affected() == 1;
if !owned {
    tx.rollback().await.map_err(to_storage_err)?;
    return Ok(DirectoryMigrationOutcome::AlreadyMigrated);
}

// 2) Считаем существующие строки (маркер потерян, но данные есть -> adopt, не import).
let existing = count_directory_rows(&mut tx).await?;
if existing == 0 {
    replace_directory_snapshot_tx(&mut tx, snapshot).await?; // DELETE children -> INSERT parents
}

// 3) CAS документа: не перезаписываем чужую правку.
if let Some(new_doc) = new_document {
    let changed = sqlx::query(
        "UPDATE configuration_documents SET document_json = $1
         WHERE document_key = $2 AND document_json = $3")
        .bind(new_doc).bind(key).bind(expected_document.unwrap_or_default())
        .execute(&mut *tx).await.map_err(to_storage_err)?.rows_affected();
    if changed == 0 {
        tx.rollback().await.map_err(to_storage_err)?;
        return Ok(DirectoryMigrationOutcome::DocumentChanged); // caller retries
    }
}

tx.commit().await.map_err(to_storage_err)?;
```

Важно: маркер вставляется **первым** — на SQLite это сразу берёт write-lock и сериализует с другими писателями; на PG — блокировка строки/уникального индекса. `COUNT` и `replace` — в той же tx. Для `expected_document = None` (документа нет) CAS не выполняется.

### 5.4 Admin-runner

```rust
// directory_migrate.rs
pub async fn run(state: &AppState) -> Result<Report, String> {
    let Some(storage) = state.storage.as_ref() else { return Ok(Report::no_storage()) };
    for attempt in 0..3 {
        let old = storage.get_configuration_document(CONFIGURATION_KEY).await?;
        let (snapshot, new_doc, counts) = parse_legacy(old.as_deref())?;
        match storage.migrate_directory_document(CONFIGURATION_KEY, old.as_deref(), new_doc.as_deref(), &snapshot).await? {
            Applied | AlreadyMigrated => return Ok(Report { ...counts, attempt }),
            DocumentChanged => continue,
        }
    }
    Err("directory migration: document kept changing".into())
}
```

`parse_legacy`:

1. `serde_json::from_str::<Value>`; ошибка → Err (не очищать документ).
2. `resources` object; `legacy = serde_json::from_value::<LegacyResources>(resources.clone())` (только `addresses`/`directory`, `#[serde(default)]`).
3. `dedup_address_book(&mut legacy.addresses, &mut legacy.directory.user_addresses)`.
4. Собрать `DirectorySnapshot` (profile/group/role JSON, join-векторы, addresses с `owner_id`).
5. `resources.remove("directory"); resources.remove("addresses");` сериализовать.
6. Если ключей не было — `new_doc = None` (не переписывать документ зря), но маркер поставить.

### 5.5 Что НЕ делать

1. **Не менять `0001`–`0006`** — checksum'ы `_sqlx_migrations`; только новый `0007`.
2. **Не делать `INSERT … SELECT json_extract(...)`** — JSON1/`::jsonb` разъезжаются, битые записи не переживаются (`04_infra_l5l7.md:277`).
3. **Не использовать `ON CONFLICT DO NOTHING` как единственную идемпотентность** — нужен маркер + очистка JSON + правило «строки побеждают».
4. **Не переписывать документ через `ResourceState`** — потеря неизвестных полей.
5. **Не делать `directory_addresses(id PK)` с `owner_id`** — личные копии конфликтуют с глобальными.
6. **Не добавлять FK на built-in роли, `users` или `core_users`** в v1; SQLite FK OFF, PG ON — разъедется.
7. **Не удалять `contacts`, `layouts`, `links`, `history`, `admin_settings`** — они остаются в JSON.
8. **Не трогать `user_credentials`/PBKDF2** — 2 строки на живой БД; T02 перехеширует при логине, миграция к ним не относится.
9. **Не вызывать миграцию в `hot_reload_from_storage`** — только один раз на старте, до `sync_from_storage`, под `DbLock`.
10. **Не запускать миграцию/`vks-db-dedup --apply` на живой БД**; не удалять `vks_data.db.lock`; не трогать `backups/`.
11. **Не менять API-формы и `created_at`**; не «нормализовать» секунды в миллисекунды.
12. **Не делать personal unique index** без дедупа: старые книги могут иметь дубли.
13. **Не делать `vks-db-dedup` единственным путём миграции** — он SQLite-only и не видит личные адреса.
14. **Не добавлять `directory_accounts` с паролями** — пароли/логины уже в `user_credentials`+`LocalDb`; `DirectoryUser.login` — только отображаемое поле.
15. **Не считать `--all-features` доказательством PG** — это разные джобы; PG без `VKS_STORAGE_PG_URL` skip.

### 6.2 Оговорки

- **`--all-features`:** CI гоняет его отдельно (`ci.yml:114-129`), baseline после T03a зелёный. Он **не** подменяет PG: `VKS_STORAGE_PG_URL` не появляется, PG-тесты skip. Если включать `--all-features` локально, время сборки растёт; сначала `cargo check -p vks-admin -p vks-storage`.
- **`--workspace`:** полный baseline в плане — 1425 passed/8 ignored; в этом probe не гонялся. Перед приёмкой сравнить с текущим HEAD (после T09a/T06 число другое), падения не «списывать» на T10.
- **Clippy:** CI использует `--all-features --all-targets`; именно этот вариант обязателен, а не только `-p`.
- **PG локально:** без сервера `postgres::tests::init_roundtrip_live_db` печатает skip и **passed**; это не доказательство. Для реального parity нужен `VKS_STORAGE_PG_URL`; в CI — `test-postgres` (только `vks-storage`). Если parity-тест в admin — расширить джобу.
- **Живой стенд:** после мержа — остановить сервис, скопировать `vks_data.db` (WAL нет, `journal_mode=delete`), запустить новый бинарь, проверить `_sqlx_migrations` (7), `schema_state('directory',1)`, counts, `integrity_check`, `foreign_key_check`; только потом открывать UI. Не проверять на живой БД без бэкапа (`08_live_runtime.md:252`).
- **Формат/линии:** `rustfmt` на 1.94.0; проект в путях с пробелами — всегда кавычки.

### 6.3 Что считать доказательством «sqlite==pg»

1. Один и тот же legacy-JSON fixture (включая битую запись, дубль canonical, built-in роль, личную копию).
2. Миграция на SQLite-файле и на PG.
3. `load_directory_snapshot` с обоих; сравнить `Value` (не строки) по профилям/группам/ролям/адресам; порядок — `ORDER BY`.
4. Проверить `schema_state` версию и отсутствие `resources.directory`/`addresses` в JSON на обоих.
5. Повторить миграцию: counts не меняются.
6. Удалить контакт, повторить миграцию: не воскрес.
7. Для PG — `foreign_key_check`/`\d` (если FK), для SQLite — `PRAGMA foreign_key_check`.
