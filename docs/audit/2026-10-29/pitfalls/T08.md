## §2 Совместимость на проводе

1. **Аддитивность.** `vks.media.RoomMode room_mode = 7` — новый тег в конце; старые поля 1–6 не двигаются. prost по умолчанию **пропускает неизвестные поля**, поэтому старый клиент декодирует новый кадр и просто не увидит тег 7. Проверено тестом в копии (см. код ниже): старый клиент видит `participant_id`/`join_nonce`, а новый клиент на старом кадре получает `room_mode = 0`.
2. **proto3-дефолт.** Отсутствующее поле → `0 = ROOM_MODE_UNSPECIFIED`. Это **не** «SFU по умолчанию» на проводе: значение 0 обязано означать «сервер не сообщил» и включать fallback. Текущий SDK-fallback — «оставить дефолт движка (Sfu) и ждать push» (`conference.rs:243-245`); это допустимо, но должно быть покрыто тестом (`Unspecified → Sfu`), иначе регрессия в `Mcu` пройдёт незамеченной.
3. **Генерация кода.** Checked-in сгенерированного кода нет (`crates/vks-proto/src/lib.rs:22-33` — `include!(concat!(env!("OUT_DIR"), …))`); регенерация не нужна, `build.rs` пересоберёт по `rerun-if-changed=proto` (`build.rs:31-33`). `Cargo.lock` не меняется.
4. **protoc герметичен** (`protoc-bin-vendored`, ADR-0031), но CI отдельно гоняет сборку/тесты **в пути с пробелом** (`ci.yml:185-208`, job `path-with-spaces`, `working-directory: vks build with spaces`). Проверено: `cargo test -p vks-proto --locked` в каталоге `/dev/shm/t08 space` — 7 passed. Живой путь репозитория тоже содержит пробел (`Рабочий стол`) — не переносите проверку proto в безпробельный путь как единственную.
5. **Линта proto нет.** В CI нет `buf`/`protolint`; поля проверяются только компиляцией prost и код-ревью. Значит тег 7 может быть случайно переиспользован/перенумерован — пиньте его тестом (как `layout_metadata_wire_tags_are_stable`, `vks-proto/src/lib.rs:118-136`).
6. **Прочие гейты, которые реагируют на proto:** `cargo check --workspace --all-features --all-targets` (`ci.yml:53`), `clippy --workspace --all-features --all-targets -D warnings` (`ci.yml:71`), `cargo test --workspace` (`ci.yml:110`), rustdoc `-D warnings` (`ci.yml:220-222`). Джобы `--all-features` **не** ловят proto-семантику, но ловят рассинхрон литералов (`..Default::default()` не используется — поле добавлено во все 1 литерал proto-структуры).

Проверенный аддитивный тест (в копии `/dev/shm/t08live3`, зелёный; рекомендуется внести в `crates/vks-proto/src/lib.rs`):


### 3.2 Порядок относительно join (почему поле вообще нужно)

Сервер в одном `replies` возвращает `[JoinRoomResult, RoomModeChanged]` (`lib.rs:1313-1338`), и оба уходят в сокет по порядку. Но SDK регистрирует push-хендлер **после** того, как future join завершилась (`conference.rs:261`). На реальном WS-транспорте кадр-push может быть прочитан и отброшен до регистрации хендлера — классическая гонка «push раньше/позже ответа», из-за которой S9 уже переносил layout в `JoinRoomResult` (ADR-0030). `room_mode` в ответе закрывает ту же гонку для режима. **Не удаляйте** late-joiner push: он нужен клиентам, которые не читают тег 7 (старые SDK), и это чужой код (T12) — T08 его не трогает.

Обратная сторона: клиент, который читает и снимок, и push, получит `ModeChanged` для режима, который уже применён. В SDK нет дедупа по `switch_epoch` (`ConferenceEvent::ModeChanged` его не несёт — `types.rs:17`), поэтому UI увидит «смену режима» сразу после join в MCU-комнате. Минимальный фикс в рамках T08 — в `drain_events` не эмитить/не применять `ModeChanged`, если `RoomMode::parse(mode) == Some(self.media.mode())`; полноценный — добавить `switch_epoch` в SDK-состояние (задел T12/ADR-0026).

### 3.3 Смена режима на живом звонке: что реально произойдёт

| Сценарий | Поведение сейчас | Риск |
|---|---|---|
| SFU→MCU (push) | SDK меняет рендерер на композит; сервер **выселяет** WebRTC-пиров комнаты (`rooms.rs:126-137`) и отклоняет новые WebRTC-офферы кодом `webrtc_mcu_room_unsupported` (`lib.rs:872-878`) | «Смена конвейера» без renegotiation: композитный трек в WebRTC-плоскость не приходит; SDK отрисует заглушку. Это ожидаемо до T12 (audio/composite egress), но тест не должен требовать медиа |
| MCU→SFU | рендерер переключается, раскладка остаётся прежней (MCU-композит её игнорировал) | ок; `LayoutChanged`-эпоха (T10c guard) не сбрасывается — это by design |
| Push при активном медиа | SDK не делает unsubscribe/re-offer, хотя `SIGNALING_PROTOCOL.md:235-243` §8 это предписывает | **вне T08**: реального §8-renegotiation нет; не выдавайте «RoomModeChanged handling» за его реализацию |
| Rejoin после обрыва в MCU-комнату | режим **не** обновляется (§1.3 E) | P1: клиент остаётся в SFU и рисует N треков вместо композита |
| Resume (`join_nonce`, TTL<60 c) | `JoinRoomResult` нет, push late-joiner'а нет; режим остаётся прежним | P1: то же + нет способа узнать режим до следующего admin-переключения |

Рекомендация: вынести `apply_room_mode(mode)` и вызывать в трёх местах — `start_async`, rejoin, resume; для resume — либо принудительный rejoin при неизвестном режиме, либо добавить `room_mode` в SDK-`ServerHello` (proto-поле 6 уже на проводе, wire-изменений не требует; это же советует F-05 в `05_frontend_sdk.md:201-214`).

## §4 wasm32: что реально проверяется и что ломается

**CI-гейт ровно один** (`ci.yml:74-90`, job `wasm-sdk`):

```bash
rustup target add wasm32-unknown-unknown
cargo check -p vks-client-sdk --target wasm32-unknown-unknown --locked
```

Локально (проверено): `~/.cargo/bin/rustup target add wasm32-unknown-unknown` (сеть нужна один раз; `rust-toolchain.toml:4-8` уже декларирует target, но rustup ставит его по требованию), затем команда выше — **OK, 40 с** на чистом `target/`.

Зависимости, из-за которых это работает, и их ограничения:

| Крейт/фича | Как гейтится | Файл |
|---|---|---|
| `tokio` | **только** `cfg(not(target_arch="wasm32"))`; в wasm — `setTimeout`/`JsFuture` | `client/vks-client-sdk/Cargo.toml:27-28`, `conference.rs:430-445` |
| `sync_helper::block_on` | в wasm — `panic!("…use async methods")` (компилируется, но не вызывать) | `sync_helper.rs:14-22` |
| `getrandom 0.3` | фича `wasm_js` — обязательна, иначе линковка/рантайм | `Cargo.toml:31-32` |
| `uuid` | workspace-фича `js` (иначе `getrandom` на wasm) | корневой `Cargo.toml:55` |
| `web-sys`/`js-sys`/`wasm-bindgen-futures` | только wasm-таргет | `Cargo.toml:30-53` |
| `ulid`, `vks-proto` (prost) | wasm-совместимы, ничего не тянут из tokio | `Cargo.toml:15-26` |

**Типовые поломки (проверены):**

1. `cargo check -p vks-client-sdk --target wasm32-unknown-unknown --all-targets` → **101**, `error: This wasm target is unsupported by mio. If using Tokio, disable the net feature` + `E0432 unresolved import crate::sys::{IoSourceState,tcp}`: dev-dependency `tokio` (`Cargo.toml:62-63`) не загейчена и компилируется для тестов. Не добавляйте `--all-targets` в wasm-гейт и не тащите tokio в wasm-путь.
2. Любой новый код с `tokio::time::sleep`/`tokio::sync::*` в SDK без `cfg` — сломает wasm-джоб; образец правильного гейта — `backoff_sleep` (`conference.rs:430-445`).
3. `#[tokio::test]` в SDK (`conference.rs:732, 882`) для wasm не компилируется — тесты SDK гоняются только на native (CI `test`, `ci.yml:110`); не пытайтесь запускать SDK-тесты под wasm32.
4. `getrandom` без `wasm_js` проявляется не на `cargo check`, а в рантайме браузера — не «почините» это, убрав фичу.
5. `block_on` в wasm — паника; публичный API для wasm должен быть async (сейчас публичного `#[wasm_bindgen]` нет вообще — F-06/C8; **вне T08**).

## §6 Границы, риски, пошаговый план

### 6.1 Границы (что T08 **не** делает)

- **T11b** (per-source 8 mids, patch вендора, >2 пиров) — не трогать SFU mids/`webrtc_runtime`; T08 не меняет SDP/ICE.
- **T07** (frontend, deep link, gzip, PNM) — ни строки JS/CSS; `#[wasm_bindgen]`-обёртка (`VksClientSession`, F-06/C8) — **не** T08, несмотря на слово «wasm» в названии: acceptance = «wasm32 check».

- **ADR**: новый ADR не обязателен (прецедент ADR-0032 — «аддитивное поле + тест»), но §3.2 `SIGNALING_PROTOCOL.md` и §2.1 `ARCHITECTURE.md` обновить нужно: ревьюер сверит доку с прото.
