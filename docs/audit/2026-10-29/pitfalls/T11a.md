## 2. Keyframe-gate

### 2.1. Где добавляются подписчики и что происходит

- Вход пира: `webrtc_room.rs:152-262`. Подписка `(audio, video)` берётся из
  `subscriptions`-мапы на момент оффера (`:190-198`, дефолт `(true,true)`), кладётся в
  `PeerHandle.audio/video: Arc<AtomicBool>` (`:38-54`, `:209-217`).
- Кадры в комнату: `webrtc_room::run_peer` → `dispatch` → `WebRtcAction::Media` →
  `forward(room, from, data)` (`:416-446`) → `targets_for(room, from, audio)` (`:362-374`) →
  `PeerCommand::Write` (`:64-69`) → `run_peer` (`:513-518`) → `peer.write_media_matched(mid_for_kind(audio), …)`.
- **Гейта нет.** `forward` копирует любой `MediaData` всем подписчикам; `MediaData::is_keyframe()`
  (`str0m-0.24.1/src/media/event.rs:289-299`) не вызывается ни разу: `grep -rn "is_keyframe"
  crates/vks-media-sfu/src` → только `codec.rs:116-228` (мёртвый H.264-парсер) и ничего в webrtc-пути.
- PLI «на всякий случай» есть в двух местах: при приёме оффера — **веером по всем уже
  подключённым видео-паблишерам** (`:240-257`, комментарий `:240-241`), и на `Event::Connected`
  (`dispatch`, `:598-605`). Состояние «ждём IDR» нигде не хранится.
- Очередь **bounded**: `PEER_COMMAND_QUEUE = 64` (`:28`), переполнение — `try_send` → дроп
  (`:424-439`). Неограниченной очереди нет, но есть два других дефекта: (а) на **каждый**
  дропнутый кадр вызывается `request_keyframe_from` (`:439`) без коалесинга ⇒ при 30 fps и полной
  очереди это до 30 PLI/с одному паблишеру при 2 пирах и N× при большем числе (усиливает P1-3);
  (б) после дропа подписчик получает дельты и остаётся с «чёрным/битым» видео **навсегда**, пока
  паблишер не пришлёт IDR сам.

**Риски, которые обязана закрыть реализация:**
1. **Чёрное видео:** новый подписчик получает `P,P,P…` без IDR.
2. **PLI-шторм:** гейт без коалесинга (`≥300 мс` на `(publisher, mid)`) + существующий дроп-путь.
3. **Аудио:** `MediaData::is_keyframe()` для аудио **всегда false** (`CodecExtra::None|Tele => false`,
   `event.rs:291-292`) ⇒ гейт только для `!audio`, иначе звук встанет.
4. **Ре-арм:** `set_subscription(audio, video)` (`:308-324`) при переходе `video:false→true` и
   re-offer обязаны снова ставить «ждём IDR», иначе зритель, включивший видео позже, получает дельты.
5. **Флаг должен жить на `PeerHandle`, а не в задаче:** решение принимается в `forward` (сторона
   паблишера), а `PeerCommand::Write` не несёт `is_keyframe` — добавить поле в команду можно, но
   тогда кадр уже лежит в очереди (дроп не экономит память). Минимальный вариант —
   `waiting_idr: Arc<AtomicBool>` в `PeerHandle` (`:38-48`), arm при insert/queue_full/subscription-on,
   disarm в `forward` на первом keyframe.
6. **Ключ гейта:** сейчас один video-mid на подписчика (`mid_for_kind`, `webrtc.rs:225-227`), поэтому
   `AtomicBool` честен. В T11b (per-source mids) обязателен `Mutex<HashSet<(ParticipantId, Mid)>>` —
   зафиксировать это комментарием+тестом, иначе T11b тихо сломает гейт (дельты второго паблишера
   пройдут без IDR).
7. **`MAX_PEERS_PER_ROOM = 2`** (`:33`) значит «второй пир = и паблишер, и подписчик»; тест на
   «подключился после первого P» обязан использовать 2 пира (паблишер+новичок), а не 3.

### 2.3. ⚠️ Уже начатая реализация (в дереве с 08:32) построена на ложной предпосылке

В рабочем дереве появился `crates/vks-media-sfu/src/codec.rs` +122 строки: `is_keyframe_payload(codec,
payload)` + самописные `vp9_is_keyframe`/`h265_is_keyframe`/`av1_is_keyframe`. Докстринг утверждает:
«The SFU forwards opaque RTP, so the keyframe gate cannot rely on `MediaData::is_keyframe` (str0m 0.24.1
has no such field)». **Оба утверждения неверны:**

1. **Поле есть.** `str0m-0.24.1/src/media/event.rs:289-299` — `pub fn is_keyframe(&self) -> bool`,
   матчит `CodecExtra::{Vp8,Vp9,Av1,H264,H265,H266}`; `CodecExtra` — `pub` enum
   (`src/packet/mod.rs:146-161`). Это ровно тот API, который нужен.
2. **SFU форвардит не «opaque RTP», а депакетизированные кадры.** `WebRtcAction::Media(Box<MediaData>)`
   (`webrtc.rs:341`) несёт `MediaData.data` = «This data is a full depayloaded Frame»
   (`event.rs:262-266`) и `codec_extra` из депайлоадера (`media/mod.rs:379`). RTP-заголовок и
   payload-descriptor сюда уже **не доходят**.
3. **Поэтому `parse_vp8_rtp(data.data)` — семантически неверный вызов.** `parse_vp8_rtp`
   (`codec.rs:293-337`) читает **RTP payload descriptor** (X/S/PID-биты байта 0, RFC 7741), а байт 0
   депакетизированного VP8-кадра — это frame tag (bit0 = frame type, bits1-3 = version, bit4 =
   show_frame, bits5-7 = размер первой партиции). Итог: `x_bit` = старший бит размера партиции,
   `s_bit` = show_frame ⇒ классификация keyframe практически случайна. То же для H.264/H.265/AV1-веток.
   Валидного места вызова у функции в forward-пути **нет вовсе** (сырых RTP-пакетов SFU не видит).
4. **Fail-open по умолчанию:** `_ => true` («never block traffic we cannot classify») — для гейта это
   значит «неизвестный кодек никогда не гейтится», т.е. тихий возврат чёрного видео; при этом
   собственный парсер AV1 без sequence-header-состояния keyframe вообще не отличает (комментарий это
   признаёт).

**Что делать:** удалить весь блок +122 строки (до коммита) и реализовать гейт как
`if !audio && !data.is_keyframe() { drop }` в `forward`. Тогда «определение keyframe» — 0 строк кода,
и оно покрыто тестами str0m. Если когда-нибудь понадобится классификация без str0m (gateway-плечо) —
это отдельная задача с реальными RTP-дампами, а не 122 строки «на глазок»; и тогда имя обязано быть
`is_keyframe_rtp_payload`, с явным «вход — RTP payload, не кадр».

Дополнительно: этот блок — `pub`, поэтому `dead_code` его не поймает; он останется мёртвым грузом в
крейте, который T11c и так чистит (цель «−1230 строк»), и его докстринг закрепит в коде ложь про
str0m — прямое нарушение `docs ≡ код` (T03b сделал доки блокирующим гейтом).

### 2.4. ⚠️ WIP-гейт в `webrtc_room.rs` (08:38) не откроется никогда — P0

В дереве появился `gate_video(&waiting_keyframe, params.spec().codec, &data)` в `run_peer`
(`PeerCommand::Write` → дроп + PLI раз в 500 мс). Он получает **депакетизированный кадр** и снова
зовёт `codec::is_keyframe_payload`, который ждёт **RTP payload descriptor**. Для VP8 это доказуемо
ломается:

- `str0m`'s `Vp8Depacketizer::depacketize` (`packet/vp8.rs:615-700`) сдвигает `payload_index` за
  descriptor и кладёт в `out` только сам VP8-кадр (RFC 7741 §4.3) ⇒ `MediaData.data` = `[ft0, ft1,
  ft2, 0x9d, 0x01, 0x2a, …]` (frame tag из 3 байт + start code), **без** descriptor.
- `parse_vp8_rtp` (`codec.rs:293-357`) на этих данных: `x_bit = ft0 & 0x80 = 0`,
  `s_bit = ft0 & 0x10` = show_frame (у видимого кадра 1), `pid = ft0 & 0x07` = 0 (совпадение) ⇒
  `offset = 1`; `frame_header = payload[1]` — **это второй байт frame tag (размер первой партиции), а
  не тип кадра**; затем синк-код проверяется по `payload[4..6]`, тогда как настоящий sync code лежит
  в `payload[3..5]` ⇒ `payload[4]=0x01, payload[5]=0x2a` ≠ `9d 01 2a` ⇒ `is_keyframe = false`
  (**кроме** кадров короче 7 байт, где ветка `else { true }`).
- Итог: `waiting_keyframe = true` (ставится при insert, `video=true`) **не снимется никогда** ⇒
  **всё видео дропается навсегда**, каждые 500 мс уходит PLI паблишеру, метрика
  `WEBRTC_FRAMES_DROPPED{reason="awaiting_keyframe"}` растёт на каждом кадре, у всех участников
  чёрный экран. Это регрессия хуже исходной (сейчас видео хотя бы идёт).

**Правильно (и дешевле):** `let is_keyframe = data.is_keyframe();` в `forward` (там есть `&MediaData`,
`str0m/src/media/event.rs:289-299`), передать `is_keyframe: bool` в `PeerCommand::Write`, а
`gate_video(&waiting, is_keyframe)` оставить как есть — тогда парсер не нужен вообще.
Дополнительно в WIP **пропущен** путь переполнения очереди: `forward` на `try_send`-ошибке

первого overflow подписчик снова получает дельты без IDR. Это надо добавить (там же, где счётчик
`queue_full`).

### 2.2. Как тестировать детерминированно, без RTP и без браузера

`MediaData` — не `#[non_exhaustive]`, все поля `pub` (`event.rs:217-276`); `Vp8CodecExtra` (`pub`,
`str0m/src/packet/vp8.rs:376-393`) переэкспортирован (`packet/mod.rs:53`);
`PayloadParams::new(pt, resend, CodecSpec)` публичный (`format/payload_params.rs:158`), `CodecSpec`
собирается из pub-полей (`format/codec.rs:11-24`), `Frequency::NINETY_KHZ/FORTY_EIGHT_KHZ`
(`rtp/mtime.rs:46,49`), `FormatParams::default()` (`format/format_params.rs:8`), `Pt::from(u8)`/`SeqNo`
— `num_id!`-макрос (`rtp/id.rs:78-116`). Значит кадр конструируется прямо в тесте:

```rust
let params = PayloadParams::new(
    Pt::from(96u8), None,
    CodecSpec { codec: Codec::Vp8, clock_rate: Frequency::NINETY_KHZ, channels: None, format: FormatParams::default() },
);
let frame = |key: bool| MediaData {
    mid: Mid::from("0"), pt: Pt::from(96u8), rid: None, params,
    time: MediaTime::from_millis(0), network_time: Instant::now(),
    seq_range: SeqNo::from(1u16)..=SeqNo::from(1u16), contiguous: true,
    data: vec![0u8; 32].into(), ext_vals: ExtensionValues::default(),
    codec_extra: CodecExtra::Vp8(Vp8CodecExtra { discardable: false, sync: false, layer_index: 0,
        picture_id: None, tl0_picture_id: None, is_keyframe: key }),
    last_sender_info: None, audio_start_of_talk_spurt: false,
};
```

`forward` — приватный метод в том же модуле, тестовый модуль уже собирает `PeerHandle` с
`mpsc::channel(8)` (`:671-685`) ⇒ пишем `registry.forward(room, publisher, frame(false)).await` и
читаем `rx.try_recv()`: **P,P,P,IDR,P** → до IDR `rx` пуст, после IDR ровно 2 `Write` (IDR,P).
Никаких сокетов/str0m-сессий. Для e2e-уровня — расширить существующий harness
`webrtc.rs:456-620` (реальный str0m-клиент, `client.writer(video_mid).write(...)`), но VP8-кадр там
надо собрать руками как валидный VP8 payload-descriptor+header, чтобы depayloader выставил
`is_keyframe` — это дороже; базовый тест должен быть на `forward`.

## 3. Re-offer: где создаётся SDP/DTLS и что происходит сейчас

- **Оффер принимается один раз на каждый `Payload::SdpOffer`**: `lib.rs:827-1052` (ветка `SdpOffer`, включая реестр треков `:966-1051`); внутри
  `crate::webrtc_runtime::accept_offer(&handler_config, room, pid, &offer.sdp)` (`:883`) →
  `webrtc_runtime.rs:156-170` → `WebRtcRoomRegistry::accept_offer` (`webrtc_room.rs:152-262`).
- **`registry.accept_offer` всегда создаёт нового пира**: `bind_socket()` (новый UDP-порт,
  `:173-176`) → `WebRtcPeer::accept_offer` (`webrtc.rs:125-175`), а внутри — **новый `Rtc`**
  (`RtcConfig…build`, `:145`), `add_local_candidate` (`:147-148`), `rtc.sdp_api().accept_offer(offer)`
  (`:151`). Затем `generation = next_generation++` (`:188`) и `peers.insert(...)` заменяет хендл
  (`:232`), старый таск выходит по закрытию канала (`:230-231`, `remove_generation` → no-op,
  `:283-299`).
- ⇒ **Ре-оффер = вторая DTLS-ассоциация**: новый `Rtc` (новый DTLS-ключ/роль), новый ICE-агент,
  **новый UDP-порт**, старый `Rtc` бросается (DTLS close), медиа рвётся на 1–3 с, `WEBRTC_PEERS`
  на мгновение считается по замене, метрика `webrtc_offers{result="accepted"}` инкрементится
  повторно. Комментарий `webrtc_runtime.rs:166-168` («Re-offer: `accept_offer` installs a newer
  generation atomically») — это описание **текущего** поведения, а не требуемого; его придётся
  переписать.
- Дополнительно `validate_offer` (`webrtc.rs:376-406`) **запрещает** `audio>1 || video>1` (`:399-401`)
  и любую m-line не audio/video (`:394-396`) ⇒ screen-share/второй video-трек от браузера получает
  `InvalidOffer` целиком; DataChannel — тоже.
- FSM: `on_sdp_offer` допускает оффер только в `InRoom|MediaActive` (`handler.rs:345-352`) — ре-оффер
  во время `Negotiating` отвергается `bad_state`; `pre_offer_state` (`:359`) корректно откатывается
  при отказе транспорта (`:954-957`).

**str0m 0.24.1 — что действительно позволяет (проверено по исходникам крейта):**
- `SdpApi::accept_offer` (`change/sdp.rs:68-150`) вызывается **на существующем `Rtc`** и
  «переигрывает» сессию: `apply_offer` → `sync_medias` + `add_new_lines` (`:946-959`). Pending-оффер
  инвалидируется (`next_change_id()`, `:72`).
- **DTLS не перезапускается:** `rtc.init_dtls` — no-op при уже инициализированном DTLS
  (`lib.rs:1487-1490`); `remote_fingerprint` при повторном оффере **не перезаписывается**
  (`sdp.rs:85-92`) ⇒ смена fingerprint молча игнорируется.
- **ICE:** `add_ice_details(..., None)` берёт ufrag/pwd из оффера ⇒ смена креденшелов = ICE restart
  (та же DTLS-ассоциация); одинаковые креды — ICE не трогается.
- **Порядок/index m-lines обязателен:** `sync_medias` требует `idx == media.index()`
  (`sdp.rs:1112-1116`), иначе `RemoteSdp`-ошибка. Браузер порядок сохраняет, наш тест — тоже обязан.
- **Ответ не может добавлять m-lines (RFC 3264 §6):** `as_sdp(&session, …)` строит ответ строго по
  m-lines оффера. Поэтому серверные «предсозданные 8 video-mid в answer» из `01_sfu_p3p5.md:499`
  **невозможны**; нужен серверный *offer*: `SdpApi::add_media(MediaKind, Direction::SendOnly, …)`
  (`sdp.rs:274`) + `apply()` (`:502`) → оффер браузеру → `accept_answer(pending, answer)`
  (`:158`). Это T11b, но T11a обязана не заложить архитектуру, которая на это не оставляет места.

**Уже сделано в WIP (в целом верно):** `WebRtcPeer::accept_reoffer` (`webrtc.rs:182-209`) вызывает
`sdp_api().accept_offer` на том же `Rtc`, пересобирает `mids`/`mid_audio` из нового ответа, снимает
`a=ice-options:trickle`, делает `drain()` — DTLS/сокет сохраняются. Осталось: (1) `validate_offer`
(`:399-401`) по-прежнему запрещает >1 video-mid ⇒ добавление screen-share в ре-оффере падает; (2)
`registry.accept_offer` ещё создаёт нового пира (§3 выше), т.е. `accept_reoffer` пока **не вызывается**;
(3) нужен тест «нет второго `Connected`/`local_addr` не изменился».

**Минимальное корректное изменение (T11a):**
1. `WebRtcPeer::reoffer(&mut self, offer_sdp: &str) -> Result<(), WebRtcError>` — `validate_offer`

### 4.2. Что ломается при «включить VP9/AV1/H264/H265 в caps»

- `tests/e2e/webrtc.js:380-381` **явно** утверждает `!answer.includes('H264') && !answer.includes('H265')
  && !answer.includes('VP9')` — зелёный браузерный тест покраснеет. Правка теста обязательна в том же
  коммите, иначе «фича» выглядит как регрессия.
- Chrome в оффере предлагает H264/VP9/AV1; `enable_h264(true)` добавит их в **answer** (str0m
  отвечает по пересечению оффера и своего config). Тогда:
  - `answer_payload_types` (`lib.rs:578-588`) знает `vp8|h264` и **не знает** vp9/av1 ⇒ при
    vp9-первом PT `TrackInfo.codec` соврёт (`Vp8`);
  - `MEDIA_BYTES` будет писать `vp8`;
  - браузерный клиент PNM (`client/`) не проверялся на приём VP9/AV1 — риск «connected, но чёрное».
- **H265 включать нельзя** (нет браузерной поддержки) — только убрать из `ARCHITECTURE.md:14`.
- Минимально честный T11a-набор: **Opus+VP8 в answer** (как сейчас), **caps.video_codecs = [VP8]**,
  `dtls_srtp` из факта, `simulcast=false`, и **явная таблица** «VP9/AV1/H264 — не реализованы,
  причина» в `ARCHITECTURE.md`. Включение VP9/H264 — отдельный коммит с e2e-доказательством
  (иначе это ровно тот дефект, который T11a должен убрать).

### 4.3. ⚠️ В дереве уже включены ВСЕ кодеки — это ровно то, что T11a должен убрать

`git diff crates/vks-media-sfu/src/webrtc.rs` (08:36): к `clear_codecs()` добавлены
`.enable_vp9(true).enable_av1(true).enable_h264(true).enable_h265(true)` с комментарием «every video
codec with a keyframe classifier is safe to negotiate». Последствия по пунктам приёмки:

1. **Caps и answer теперь расходятся сильнее, чем до правки.** `RoomCaps.video_codecs` = `[Vp8]`
   (`main.rs:349`, `handler.rs:73,128`), `TrackInfo.codec` = `Vp8` для любого видео
   (`lib.rs:1024-1026`), `MEDIA_BYTES` label = `"vp8"` (`webrtc_room.rs:441-443`), а SDP-ответ
   Chrome теперь содержит `VP9/90000`, `AV1/90000`, `H264/90000`. Приёмка «caps advertise only what is
   truly implemented» **нарушена в противоположную сторону**: транспорт обещает больше, чем говорит
   caps и метрики.
2. **`tests/e2e/webrtc.js:380-381` покраснеет** (`!answer.includes('H264') && !includes('H265') &&
   !includes('VP9')`) — оракул приёмки WebRTC.
3. **H265 не поддерживается браузерами в WebRTC** (нет стандартного rtpmap в Chrome/Firefox/Safari):
   `enable_h265(true)` ничего не даст в answer, но закрепит в коде ложное «safe to negotiate» и
   создаст иллюзию поддержки; в `ARCHITECTURE.md:14` H.265 уже обещан — этого делать нельзя.
4. **`match_params` кодек-агностичен** (`webrtc.rs:240-253` → `writer.match_params`), т.е. форвард
   VP9/AV1/H264 «заработает» — но потребители не готовы: запись (`vks-recorder`), MCU-мост (T12,
   H.264-only), PNM-клиент (`client/`), `TrackInfo`/метрики. Ни одного теста на приём VP9/AV1 нет;
   `webrtc.js` проверяет только VP8.
5. **Решение «включать кодек, потому что для него есть классификатор keyframe» — неверная связь.**
   Классификатор вообще не нужен (см. §2.3), а честность кодека определяется сквозным путём
   (SDP ↔ forward ↔ caps ↔ метрики ↔ запись/мост/клиент), а не наличием парсера.

**Вывод для T11a:** эти 5 строк (`enable_vp9/av1/h264/h265`) откатить. Честный минимум T11a —
`opus + vp8` в answer **и** в caps, `simulcast=false`, `dtls_srtp` из факта. Включение VP9/H264 —
отдельная задача с e2e-доказательством (декодированные кадры в браузере), правкой `TrackInfo`/
`MEDIA_BYTES`, `webrtc.js` и записи. H265 — только убрать из обещаний.

### 5.3. Жёсткие ловушки

- **H0. Свой keyframe-детектор уже написан и он неверен** — §2.3. Удалить `codec.rs` +122 до коммита,
  использовать `MediaData::is_keyframe()`; иначе «гейт» будет резать IDR и пропускать дельты случайно.
- **H1. `enabled()` читает env процесса ⇒ гонка в тестах.** `std::env::set_var` в параллельных
  тестах — недетерминированно; `#[tokio::test]`/edition 2021 спасает от `unsafe`, но не от гонки.
  Лечение — шаг 0 (settings-параметр). Без него `network_integration.rs:927,1170` придётся
  «лечить» установкой env внутри теста — не делать.
- **H2. `tests/e2e/webrtc.js:380`** утверждает «Opus+VP8 only». Включение любых кодеков = красный
  браузерный тест (запускается вручную, но это оракул приёмки).
- **H3. `MAX_PEERS_PER_ROOM = 2`** (`webrtc_room.rs:33`) + `webrtc.js:409-420` (`room_full` для
  третьего) — **не трогать в T11a**, это T11b; снятие в T11a сломает e2e и не имеет per-source mid.
- **H4. Живой стенд.** `VKS_WEBRTC_TRANSPORT=1`, `candidate=192.168.1.93`, диапазон 43000–43100.
  После смены дефолта: (а) второй процесс PID 3253281 (`/tmp/smoke.toml`, без явного
  `VKS_WEBRTC_TRANSPORT`) при рестарте станет реальным WebRTC-сервером и будет конкурировать за
  43000–43100 с боевым — preflight это **не** поймает (bind+drop транзиентный); (б) smoke-процедура
  T01 (`:18082` + копия БД) обязана явно выставлять `VKS_WEBRTC_TRANSPORT=0` **и** свободный
  `VKS_WEBRTC_PORT_MIN/MAX`, иначе она полезет в боевой диапазон; (в) `RestartPreventExitStatus=78`
  в юните есть — при опечатке в candidate сервис не зациклится, но и не поднимется.
- **H5. Порт-проба preflight (`:71-73`) не резервирует порт** — «OK» в логе не значит «диапазон мой».
- **H6. `UdpMediaLoop` на `0.0.0.0:40000`** (`main.rs:283`) не связан с WebRTC-диапазоном; не путать
  при проверках «кто занял порт».
- **H7. `shared_dtls_cert`** (`webrtc.rs:366-369`) — **один** сертификат на процесс ⇒ тест «новый
  ре-оффер = новый fingerprint» бессмысленен; проверять надо `local_addr` + отсутствие `Connected`.
- **H8. `WebRtcPeer::accept_offer` вырезает `a=ice-options:trickle`** (`:154`) — при ре-оффере это
  надо повторить, иначе клиент включит trickle, которого мы не обслуживаем.
- **H9. Порядок m-lines** в ре-офферe обязателен (str0m `sdp.rs:1112-1116`); наш собственный
  тест-оффер должен добавлять новый video-mid **в конец**.
- **H10. `webrtc_runtime.rs:166-168`** — комментарий, который прямо противоречит приёмке
  («installs a newer generation atomically»); его правка входит в шаг 3, иначе ревьюер справедливо
  назовёт доки ложью.
- **H11. `prod.example.toml:18-19`** «Keep `VKS_WEBRTC_TRANSPORT=0` until a canary» после смены
  дефолта = инструкция «ничего не делай», которая включает транспорт. Переписать.
- **H12. Смоук `vks_data.db`**: preflight вызывается после storage (`main.rs:407`) — при ошибке
  конфига БД уже создана/залочена; перенос preflight выше storage меняет порядок инициализации
  (проверить, что `config_exit` и логирование доступны до `init_storage`).
