# Проектные правила (Project Rules)

> **Данный документ — обязательный к прочтению для любого ИИ-агента, начинающего работу над проектом VKS (видеоконференцсвязь на Rust).**
>
> Порядок чтения перед началом любой работы:
> 1. `docs/PROJECT_RULES.md` (этот файл)
> 2. `docs/architecture/ARCHITECTURE.md`
> 3. `docs/decisions/DECISIONS.md` (актуальные ADR)
> 4. `docs/progress/MASTER_TASK_LIST.md` (единственный живой трекер: что сделано, что в работе)
> 5. Документация к используемым библиотекам (см. правило 2.1)

---

## Часть I. Общие правила

### 1. Язык и приоритеты

1.1. **Язык проекта — Rust. Приоритет всегда на Rust.** Любой новый компонент по умолчанию пишется на Rust. С#/JS/Python/C++ — только когда нет разумной альтернативы на Rust (например, H.323 через FFI-обёртку над H323Plus/OPAL), и такое решение фиксируется в ADR.

1.2. **Синхронность запрещена в медийных и сетевых путях.** Медиа, сигнализация, кластерная шина — только асинхронный код (`tokio`). Блокирующие вызовы разрешаются лишь в утилитах за пределами hot path, и их нужно явно помечать.

1.3. **Версии фиксируются:** `rust-toolchain.toml` (MSRV), `Cargo.lock` под версионным контролем, `deny.toml` (cargo-deny) для лицензий и CVE. Обновление крейта — отдельный коммит, отдельно от функциональности.

### 2. Документация — главный актив проекта

2.1. **Правило «документация первой»:** перед написанием кода ИИ-агент ОБЯЗАН изучить:
   - официальную документацию языка (rust-lang.org) по используемым концепциям;
   - документацию каждой библиотеки, которую он собирается использовать или изменить (docs.rs, README в репозитории, CHANGELOG);
   - ADR проекта (`docs/decisions/`), если тема ранее обсуждалась.

   ИИ-агент **не имеет права** выдумывать API библиотек «по памяти». Если в документации API нет — агент обязан: (а) проверить последний релиз, (б) зафиксировать это в `MASTER_TASK_LIST.md` как open question, (в) запросить подтверждение у человека.

2.2. **Каждый крейт** обязан содержать `README.md` с: назначением, зависимостями, примером использования, ссылками на ADR.

2.3. **Каждая публичная функция/трейт/структура** в крейтах `vks-core`, `vks-proto`, `vks-auth`, `vks-storage` имеет rustdoc-комментарий с примером.

2.4. **Документация живёт рядом с кодом:** `docs/architecture/` — описание архитектуры и схем, `docs/decisions/` — ADR, `docs/progress/` — живой статус, `docs/rules/` — правила по областям (frontend, backend, code style).

### 3. Ведение MASTER_TASK_LIST.md (обязательно)

3.1. `docs/progress/MASTER_TASK_LIST.md` — единственный живой документ о состоянии проекта. Он обновляется **в том же коммите**, что и код, который он описывает. Исторические `PROGRESS.md`/`REWORK_PLAN.md`/`FRONTEND_PORT_PLAN.md` лежат в `docs/progress/archive/` и не обновляются.

3.2. Формат записи (каждый блок — одна итерация работы):

```markdown
## [YYYY-MM-DD] Краткое название итерации

### Выполнено
- [x] Конкретное действие (файл/крейт/коммит)

### Осталось выполнить
- [ ] Следующий шаг

### Ошибки, с которыми столкнулись
| Ошибка (кратко) | Где/когда встретилась | Почему возникла | Как исправили | Статус |
|---|---|---|---|---|
| ... | ... | ... | ... | open / fixed / accepted |

### Риск / вопрос к команде
- Вопрос, требующий решения человека.
```

3.3. **Ошибки фиксируются ВСЕГДА**, даже если исправлены в том же цикле. Это память проекта: одна и та же ошибка не должна встречаться второй раз.

3.4. Закрытые итерации переносятся в архив `docs/progress/archive/YYYY-MM.md` раз в месяц.

### 4. Ведение ADR (Architecture Decision Records)

4.1. Каждое значимое решение (выбор библиотеки, архитектурный паттерн, изменение протокола, изменение структуры) получает ADR: `docs/decisions/NNNN-название.md` по шаблону `docs/decisions/TEMPLATE_DECISION.md`.

4.2. ADR имеет статусы: `proposed → accepted → superseded (by NNNN)`. Отменённый ADR не удаляется, а помечается.

4.3. Реестр всех ADR — `docs/decisions/DECISIONS.md` (таблица: id, название, статус, дата).

4.4. **Запрещено менять решение, зафиксированное в ADR, без нового ADR**, ссылающегося на старое.

### 5. Правила для ИИ-агента (поведение)

5.1. **Малые итерации.** Один коммит = одна логическая единица (feature, fix, docs, refactor). ИИ-агент не смешивает их.

5.2. **Не додумывать требования.** Если требование не явлено в этом документе, в ADR или в PROGRESS.md — агент формулирует вопрос и фиксирует его в PROGRESS.md → «Вопрос к команде», а не принимает молчаливое решение.

5.3. **Контроль качества перед commit:**
   - `cargo fmt --all --check`
   - `cargo clippy --workspace --all-targets -- -D warnings`
   - `cargo test --workspace`
   - `cargo deny check` (лицензии + CVE)
   - Для `vks-proto`: регенерация и проверка, что код компилируется со сгенерированными типами.

5.4. **Запрещено:**
   - использовать `unsafe` без ADR и комментария `// SAFETY: ...`;
   - вводить новую зависимость, не согласованную в ADR;
   - нарушать границу крейтов (зависимости строго по дереву в ARCHITECTURE.md);
   - удалять ADR и записи трекера (только архивировать);
   - использовать `todo!()`/`unimplemented!()` в коде, идущем в production-ветку (разрешены с `#[allow]` + ADR на ограниченное время).

5.5. **Тестирование:** каждая новая публичная функция `vks-core` — unit-тест; каждый сценарий жизненного цикла комнаты — integration-тест с mock-транспортом (без сети).

5.6. **Язык общения в коде:** идентификаторы и комментарии в Rust-коде — на английском. Документация проекта (docs/) — на русском (по требованию команды), названия ADR и идентификаторы — на английском.

## Часть II. Правила бэкенда

### 6. Архитектурные инварианты

6.1. **Прозрачность MCU/SFU (главный инвариант).** Клиент никогда не знает и не узнаёт, работает ли сервер в режиме SFU или MCU. Единый API, единый сигнальный протокол, единственный источник истины — поле `room_mode` в `ServerHello`. Любое изменение сигнального протокола, нарушающее это, требует ADR.

6.2. **Гексагональная архитектура.** `vks-core` — чистая доменная логика без I/O (никаких `tokio`, `axum`, `std::net`, `std::fs`). Внешний мир — только через порты (traits): `MediaEngine`, `Storage`, `AuthProvider`, `Events`, `Clock`, `Rng`.

6.3. **Sans-I/O для медиа.** Медийное ядро (SFU/MCU) не владеет сокетами. Транспорт (UDP/TCP/QUIC) — это адаптер, который вызывает методы ядра. Ядро детерминировано и тестируется без сети.

6.4. **Одна комната — один владелец медиа-инстанса** (room ownership). При кластерном развёртывании все участники одной комнаты обязаны попасть на один медиа-инстанс (консистентное хеширование room_id → инстанс, координируется через NATS).

### 7. Структура workspace

7.1. Структура workspace зафиксирована в `docs/architecture/ARCHITECTURE.md`. Добавление нового крейта — только через ADR.

7.2. **Дерево зависимостей (строго):** см. [`docs/architecture/ARCHITECTURE.md` §3](architecture/ARCHITECTURE.md) — блок «Дерево зависимостей крейтов».

Крейт может зависеть только от крейтов, указанных над ним в дереве, и никогда — в обратную сторону. Циклы запрещены. Единственный источник истины — ARCHITECTURE.md.

7.3. **Каждый крейт — отдельная директория в `crates/`** со своей `Cargo.toml`, `README.md`, тестами.

### 8. Протокол и сообщения

8.1. Проводной протокол — **protobuf** (крейт `vks-proto`, генерация через `prost` в `build.rs`). `.proto`-файлы — источник истины, ручной JSON в hot path запрещён.

8.2. **Версионирование:** каждое сообщение содержит `proto_version`. Неизвестные поля не ломают парсинг (protobuf-семантика). Breaking changes — только через новый major-версионный номер в `ServerHello` и ADR.

8.3. Сигнализация: WebSocket/WSS (основной, совместимость с браузерами) + WebTransport (QUIC, опциональный fast-path). Оба транспорта реализуют один `SignalingTransport`-порт.

8.4. **ICE/TURN:** сервер предоставляет списки STUN/TURN-серверов в `ServerHello` (`repeated IceServer`). TURN-сервер — обязательный компонент деплоя (coturn или turn-rs), не опция.

### 9. Аутентификация и авторизация

9.1. Два независимых контура:
   - **API-контур** (админка → vks-admin): JWT (access + refresh, `jsonwebtoken`) или API-ключи для машин.
   - **Медиа-контур** (клиент → сигнализация): короткий-lived token комнаты, выданный admin-контуром (JWT с room scope).

9.2. **Провайдеры идентификации** — стратегия `AuthProvider` (порт из vks-core): встроенная БД (по умолчанию), LDAP/FreeIPA (`ldap3`), OIDC (опционально, ADR).

9.3. **Роли:** `Operator` (полный доступ), `Moderator` (комнаты), `Participant`, `Viewer`. Права проверяются в `vks-core` (домен), не в HTTP-слое.

### 10. Хранилище

10.1. Порт `Storage` (vks-core) + реализации: `memory` (тесты), `sqlite` (single-node), `postgres` (production). Выбор — через конфигурацию, без компиляционных фич.

10.2. Миграции — `sqlx` (или sea-orm — решение зафиксировано в ADR), файл миграции = один коммит, обратимые миграции обязательны.

10.3. В БД хранится: пользователи, комнаты (метаданные), раскладки (Layout), API-ключи, сессии записи, аудит-лог. Медиа-потоки в БД не хранятся.

### 11. Масштабирование и отказоустойчивость

11.1. Кластерная шина — **NATS**. Темы `vks.cluster.*` зафиксированы в `vks-proto`.

11.2. **Graceful shutdown:** при остановке медиа-инстанса клиенты получают `ServerMaintaining` с указанием нового владельца комнаты и переподключаются без потери места в комнате.

11.3. **Simulcast/SVC и bandwidth estimation (TWCC/REMB)** — обязательны для SFU. Без них simulcast некорректен.

11.4. **Мониторинг:** `tracing` (структурные логи) + `prometheus`-метрики на каждый сервис (`/metrics`), включая QoE: MOS, jitter, RTT (от клиентов).

### 12. Безопасность бэкенда

12.1. Медиа — только DTLS-SRTP (встроено в str0m). Голый RTP — только в доверенной внутренней сети.

12.2. Rate limiting + защита от DDoS на всех WS/WSS/admin-эндпоинтах.

12.3. **Аудит-лог** административных действий — обязательный компонент (кто, что, когда, из какого IP): смена режима MCU/SFU, создание/удаление комнат, управление пользователями, раскладками, ключами.

## Часть III. Правила фронтенда

### 13. Технологический стек фронтенда

13.1. **Фреймворк — Dioxus** (Rust, RSX, fine-grained signals). Обоснование — ADR. Альтернативы (Leptos, Yew) не рассматриваются без ADR.

13.2. **Стили — Tailwind CSS v4** + `dioxus-shadcn` (headless-примитивы + стилизованные компоненты). Глобальные стили — один `input.css` → `tailwind.css`.

13.3. **Два SPA + один SDK:**
   - `client/vks-client-sdk/` — Rust SDK (WASM-совместимый), единый API `Conference::join()`, рендер-сурфейс, автоопределение режима MCU/SFU;
   - `client/vks-admin-ui/` — админ-панель (Dioxus SPA): управление сервером, комнатами, пользователями, раскладками, мониторинг;
   - `client/vks-meeting-ui/` — UI участника конференции (Dioxus SPA), использует vks-client-sdk.

### 14. Структура фронтенд-крейтов

14.1. Каждый SPA-крейт имеет `Dioxus.toml`, `tailwind.css`, `src/main.rs`, `src/app.rs`.

14.2. **Обязательная структура SPA:**

```
src/
├── main.rs            # точка входа
├── app.rs             # корневой компонент + роутер
├── api/
│   └── client.rs      # СГЕНЕРИРОВАННЫЙ клиент из OpenAPI (utoipa → progenitor)
├── state/
│   ├── auth.rs        # JWT, сессия пользователя
│   └── server_state.rs# глобальное состояние сервера
├── components/
│   ├── ui/            # базовые примитивы (Button, Input, Card, Modal)
│   ├── layout/        # шаблоны страниц (AdminLayout, MeetingLayout)
│   └── video/         # VideoGrid, VideoTile, Controls
└── pages/
    ├── login.rs
    ├── dashboard.rs
    ├── rooms.rs
    ├── users.rs
    ├── layouts.rs     # редактор раскладок
    ├── settings.rs    # настройки сервера: имя, IP, БД, LDAP
    └── monitors.rs    # метрики, QoE, записи
```

14.3. **Типобезопасность API-клиента.** Вручную написанные HTTP-запросы — запрещены. Клиент генерируется из OpenAPI-спецификации `vks-admin` (utoipa) через `progenitor` (или `openapi-gen`) в build-процессе. Спецификация — в `vks-proto/openapi.json`.

### 15. Состояние и реактивность

15.1. Файн-грейн — **Signals** (Dioxus). Глобальное состояние — Context API. Для сложного cross-cutting состояния (например, состояние комнаты с частыми обновлениями) — `Fermi`, но только по ADR.

15.2. Состояние комнаты на клиенте — единственный источник для UI: список участников, треки, текущий layout, режим комнаты (из `ServerHello`). UI **не дублирует** эту информацию в локальных переменных компонентов.

### 16. Раскладки (Layout)

16.1. **Единый крейт `vks-layout`** используется и сервером (MCU compositor), и клиентом (SFU рендерер). Раскладка = абстрактное описание: слоты с нормализованными координатами, z-index, назначением (fixed/auto/pinned). Рендереры — два: пиксельный (MCU) и CSS-Grid/Taffy (клиент).

16.2. В админке — **редактор раскладок** (drag-and-drop **slots**, на базе `hadrone-core` + собственный слой): перетаскивание/ресайз/з-индекс слотов, привязка участника (Fixed), создание кастомных раскладок, сохранение в БД, назначение по умолчанию, назначение на комнату.

16.3. Оператор редактирует **один** Layout — он корректно применяется в любом режиме (MCU/SFU). Клиент не видит разницы.

16.4. Пресеты раскладок (2x2, 3x3, focus + thumbnails, спикер-режим) — встроены в `vks-layout`.

### 17. Meeting UI (UI участника)

17.1. Meeting UI использует `vks-client-sdk` и **никогда не знает** о режиме MCU/SFU. Видит только `RenderSurface`.

17.2. Обязательные компоненты: **PreJoinScreen** (предпросмотр камеры/микрофона, имя, устройства), VideoGrid (сетка видео, использует Layout + **layout switcher**), Controls (mic, cam, **screen share**, **raise hand**, settings, выйти), ParticipantList (moderator tools: mute, remove, promote, pin, **waiting room**), Chat (опционально) + **Reactions**, **InMeetingNotifications** (join/leave, recording, mode switch, auto-quality), **RecordingIndicator**, **QualityIndicator** (popup: bitrate/jitter/RTT/loss/codec/layer), **ReconnectionOverlay**, **Timer**.

17.3. **PWA** — обязательное (manifest + service worker, offline banner, auto-reconnect).

17.4. **Mobile/responsive**: portrait/landscape адаптация, touch-жесты (swipe, tap, long-press), haptic feedback, touch targets ≥ 44px.

17.5. **Hotkeys**: M (mic), C (cam), S (screen), R (raise hand), F (fullscreen), ? (help), Esc (close/exit fullscreen).

17.6. **Audio processing (v1)**: echoCancellation, noiseSuppression, autoGainControl (CTM WebRTC) — включены по умолчанию, переключатели в settings.

17.7. **Identity**: avatar (initials + color) при выключенной камере, anonymous mode («Гость N»), редактируемое имя.

17.8. **State sync**: SDK = source of truth, UI signals = mirror. Один `Conference` instance (Context/hook). UI не дублирует SDK state.

### 18. Качество UI

18.1. Доступность (a11y) — обязательна: ARIA-роли, клавиатурная навигация, контрастность, `prefers-reduced-motion`, `prefers-contrast: more`, screen reader.

18.2. Тёмная/светлая/high-contrast темы — обязательны (CSS-переменные + Tailwind). **i18n**: ru (default) + en, `locales/ru.json`, `locales/en.json`.

18.3. **E2E-тесты с реальным браузером** (headless Chrome через `chromiumoxide`) — для Meeting UI и ключевых страниц админки: вход, pre-join, создание комнаты, переключение MCU/SFU (глобальный + per-room), применение layout, screen share, raise hand, reconnection, recording.

18.4. Bundle-бюджет: Meeting UI ≤ 500 KB (gzipped), Admin UI ≤ 800 KB (gzipped), **SDK ≤ 500 KB (gzipped)**. Превышение — ADR.

18.5. **Уведомления**: toast-система (успех/ошибка/инфо) в обоих SPA. Админка — push-канал событий (WS/SSE) → badge.

18.6. **Глобальный поиск** (админка): Ctrl+K, комнаты/пользователи/записи/раскладки.

18.7. **Keyboard shortcuts (admin)**: Ctrl+K (поиск), G R/U/L (Rooms/Users/Layouts), Esc (закрыть).

## Часть IV. Правила написания кода

### 19. Стиль

19.1. `rustfmt` со стандартными настройками (`.rustfmt.toml` в корне). `clippy` в режиме `-D warnings`.

19.2. Имена: snake_case — функции/переменные, PascalCase — типы/traits/enum, SCREAMING_SNAKE — константы. Долгие имена предпочтительнее сокращений.

19.3. **Ошибки:** единый `vks_common::Error` (thiserror-enum) с вариантами на каждый слой. `?` — по умолчанию. `unwrap()`/`expect()` — только в тестах и в коде с пояснением `// SAFETY`/`// INVARIANT`.

19.4. **Логирование:** `tracing`-макро (`info!`, `warn!`, `error!`, `debug!`), structured fields (`tracing::info!(%room_id, participants, "room created")`). Глобальный лог-уровень — из конфига.

### 20. Фичи и зависимости

20.1. Feature flags в `Cargo.toml` медиа-крейтов для кодеков: `[features] vp8, vp9, h264, h265, av1, opus, g722, g711, ...`. Default — минимальный набор, полный набор — фича `all-codecs`.

20.2. Новая зависимость = ADR + запись в `deny.toml` (лицензия) + фиксация минорной версии.

### 21. Тесты

21.1. Unit-тесты — в `src/` (mod tests) крейта; integration — в `tests/`.

21.2. Тесты домена (`vks-core`) — без I/O: mock-порты. Тесты SFU — без сети: UDP-пэки в памяти (sans-IO позволяет).

21.3. **Тестовый эмулятор сети:** `tokio-test` + задержки/packet loss для проверки SFU/MCU при деградации.
